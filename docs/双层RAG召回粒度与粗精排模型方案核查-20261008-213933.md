## 核心结论

两层是“研究材料层”和“引用证据层”；每层都已有“粗排→精排”两个阶段。粗排采用BM25＋向量两路召回，再以RRF融合，精排调用qwen3-rerank。层数、阶段数和粗排路数是三个不同维度。

召回粒度由入库生成的unit_type及查询过滤控制，实际文本大小由自然段/句子/表格行边界控制，1024 token只是单chunk上限。当前不是查询时把上一层命中的段落临时再切句子：两种粒度在同一次入库时均已建立，引用层可查当前主题的全部原句/表格，避免只在首层命中文档中寻找支持证据。

## 切分与两个视图

1. 来源正文准入、规范化并冻结，生成稳定正文ID、哈希和原文编号；字符坐标指向冻结的规范化正文。
2. 识别小节标题、段落边界、表格及结构化记录。表格在普通分句之前独立处理。
3. 普通文本生成完整原句子chunk，再按同一小节、同一自然段归组生成父段落chunk。段落过长时沿完整句子分片，短段落保持原大小，不跨自然段强行拼满1024 tokens。句子记录parent_chunk_id。
4. 小表保留整表；大表沿完整数据行分片，每片重复表头和必要注释。两层复用同一table chunk，不把表格行变成失去表头的原句。表格metadata保留table_id、row_range、row_ids和source_spans。
5. 为context和citation视图各自建立前后chunk ID，避免在句子和段落重复单元之间跳转。两层默认补取前后各一个邻居，之后受输入预算约束。

| 项目 | 研究材料层context | 引用证据层citation |
|---|---|---|
| 查询 | 会话层完整任务，逐章再带章节标题与描述 | 每条原子论断的完整claim |
| 允许单元 | paragraph、table、record | sentence、table、record |
| 粒度 | 小节内的自然段或长段分片 | 完整原句 |
| 结构化材料 | 整表或带表头的小表、记录 | 同一份表格/记录chunk |
| 精排种子数 | 默认8 | 默认5 |
| 材料JSON预算 | 默认8192 tokens | 每条claim默认2000 tokens |

段落的heading_path和source_section_id提供小节归属；当前未另外生成整节聚合chunk，虽然检索过滤兼容section类型。句子父段落、前后邻居可以恢复上下文，但当前不会自动将整父段落替代原句作为最终引用。

当前单句超过1024 tokens或某一表格数据行连同表头、注释仍超预算时，程序记录分块错误、保留正文，整份正文不提交这次chunk索引；没有截断原句或猜测表格。复杂PDF尚未有可靠表格结构/OCR恢复，这是既有边界。

## 每层的两阶段检索与模型选择

两层分别执行相同骨架：BM25最多40个＋text-embedding-v4向量最多40个→按chunk ID去重、等权RRF(k=60)融合最多60个→qwen3-rerank精排→邻居补取→token预算装包。向量相似度为COSINE。40/40/60当前为代码常量；8/5、材料预算及邻居半径支持SESSION_EVIDENCE配置。

建议确定两层统一使用text-embedding-v4、1024维，以及qwen3-rerank。BM25和RRF是算法，无需额外聊天模型。保持同一embedding模型可以共用父子/表格索引；即使维度相同，不同embedding模型的向量也不能直接混用。本次没有证明该组合在项目标注数据上最优，只是据现有实现与官方纯文本RAG推荐确定基线。

官方[Embedding兼容接口](https://help.aliyun.com/zh/model-studio/embedding-interfaces-compatible-with-openai)说明text-embedding-v4支持1024维、单条8192 tokens、批量最多10条；[模型选择建议](https://help.aliyun.com/en/model-studio/embedding-rerank-model/)将1024维列为通用配置。[Rerank文档](https://help.aliyun.com/en/model-studio/rerank)列出qwen3-rerank最多500个文档、单条query/document 4000 tokens、整批120000 tokens。候选默认60个、正文chunk最多1024 tokens，仍需单独检查query和整批预算，不能用生成模型上下文窗口代替精排接口的输入限额。

官方[精排API文档](https://help.aliyun.com/zh/model-studio/text-rerank-api)说明instruct可以指定任务策略，整批token计算为query tokens×文档数＋文档tokens总和。跨批返回分数为本次请求内的相对分数，不能未经校准直接合并排序。

两层应使用不同精排指令：

- 研究材料层：寻找解答当前研究问题及章节要求的事实、解释、比较和限制条件，匹配主体、时间、地区与范围，同时保留相关反面发现。
- 引用证据层：寻找能核验当前论断的支持、否定、纠正及限定条件，关注数字、单位、主体和时间，相关反证不因与论断结论不同而降为无关材料。

这两条指令仍属于拟改造方案。当前共用“verify the claim”指令，研究层也使用了它。当前模型ID是代码默认值，尚未暴露独立的SESSION_EVIDENCE_EMBEDDING_MODEL/RERANK_MODEL环境配置。本次不更改会话摘要模型。

## 需要补充的代码与接口事项

1. chunker可以按paragraph/sentence/table分别配置最大token预算，保留自然结构优先的规则。建议基线仍各为1024，不为了数字不同把完整原句切成固定128/256 tokens；需要更短粒度时必须显式保留原句映射，不能伪装成完整句子。
2. 给retrieve/rerank传入layer，分别选择研究材料和引用核验指令。粗排两路候选数、融合数和模型配置也应显式暴露，便于复现实验。
3. 校准qwen3-rerank请求/响应协议。当前本地没有显式SUMMARY_RETRIEVAL_RERANK_URL，默认原生路径、嵌套input/parameters及output.results；官方中文说明对qwen3-rerank使用顶层query/documents/top_n/instruct和顶层results。英文文档仍有原生路径示例，因此这里记录的是协议不匹配风险，不能把某条路径直接判为已实测不可用。实际区域端点须做联调。
4. 增加精排单条与整批输入预算预检。预算溢出时明确记录原因，不能把token/API失败后的RRF结果视作已完成精排。
5. 当前精排异常会记录rrf_without_rerank并退回RRF顺序。服务可继续，但本次“两阶段实验”的统计应将其记作降级，单独报告精排成功率。

## 指标、失败样例与边界

已核查的配置指标：粗排40/40，融合60，精排8/5，neighbor_radius=1，单chunk最多1024 tokens，材料预算8192/2000，embedding维度1024。它们是配置与代码事实，不是效果指标。

建议实验分别记录：分块类型数量及token分布、超长/异常正文分块失败率、表格表头及邻居完整性；每层每次检索的query、词法/向量/融合候选ID及名次、精排分数与选中ID、各阶段延迟、请求tokens、预算剔除数和降级状态。标注数据再测粗排Recall@40、融合Recall@60、精排后研究层Recall@8/引用层Recall@5及MRR或nDCG。最终还需引用原文回读一致率和论断支持/反证核验质量；相关性分数不能当作论断真实性证明。

本次实测失败样例仅是模型目录CLI：qianwen版本1.9.0；查询text-embedding-v4和qwen3-rerank均退出码2、TOKEN_EXPIRED。它是CLI登录状态问题，没有证据说明项目API Key失效；本次改用官方文档确认规格，未进行登录变更或付费API调用。

间接推断风险：精排协议未校准、长query或整批预算超限会导致精排错误；由源码可知精排错误随后降级。尚未实测这些错误在本地账号真实API上是否发生。本次也未新增真实RAG检索失败样例，历史正文分块失败和机制验证见[既有实现报告](/Users/bxy/projects/industry_information_assistant/docs/会话临时双层RAG实现与验证结果-20261008-2057.md)。

尚未评估：本组合的语义召回率、精排质量、真实回答/引用正确率、在线成本/延迟、账号模型可用性及真实30+轮全部完成率。

结论：当前分块及检索骨架支持“研究段落/引用原句”两层各自粗排＋精排；基线模型确定为text-embedding-v4/1024维和qwen3-rerank。下一步先完成分层精排指令、显式配置及接口预算/协议联调，再用标注样本验证排序质量，最后恢复长会话实验。
