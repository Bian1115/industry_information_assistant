# 摘要生成与 Claimify 分离改造及验证

评估日期：2026-10-01。对象：智能体工作历史摘要、旧输入派生摘要、Claimify 后续核验和相关异常埋点。本次为离线机制与兼容性验证，没有调用真实模型，也没有重跑五题评测。

## 改造结论

采用“生成正文 → 检查格式与长度 → 保存正文并推进覆盖游标 → 可选 Claimify 审计”的顺序。摘要作为工作记忆保存，核验状态明确记录，避免后续把未核验内容当成已经证实的事实。Claimify 的筛选、消歧和论断拆解是核验的前置处理，本身不判定事实真伪；来源定位及 NLI 属于后续检查。

正文生成成功并不代表每个中间分块都能推进游标。只有本次完整候选摘要通过检查、确实缩短输入并成功提交，才覆盖对应的连续已完成历史；在途调用的保护规则保留。原始消息不删除，来源编号及哈希随摘要保存，模型仍可通过受控回读获取原文。

核验开启时，先提交正文再执行核验。普通核验超时、解析失败或拒绝保留已提交正文与游标，并保存失败状态；不会因审计失败重新生成同一批正文。用户取消、研究取消、权限错误及已识别的历史持久化错误仍向上传播。核验注释只更新同一摘要版本和正文哈希，不能覆盖并发产生的新摘要。

旧输入单条压缩也采用先保存派生视图、再追加审计状态的顺序。它不推进全局历史覆盖游标，原始输入及已有派生事件不被改写。

## 当前配置与适用范围

已在 `backend/.env` 设置，并同步到 `.env.example`：

```dotenv
AGENT_SUMMARY_CLAIMIFY_ENABLED=0
AGENT_SUMMARY_GENERATION_TIMEOUT_SECONDS=120
AGENT_SUMMARY_CLAIMIFY_TIMEOUT_SECONDS=120
```

关闭开关时，仍生成自然语言摘要，但不运行摘要的 Claimify 筛选、消歧、拆解、引用定位及依赖该链路的 NLI/遗漏检查。正文带有 `summary-prose-v1` 和 `unverified` 状态，元数据记录 `claimify=disabled`、`semantic_support=not_run`。策略名仍为 `claimify-v1`，表示所用正文策略；是否执行后续审计由新增开关决定。

重新启用时，将 `AGENT_SUMMARY_CLAIMIFY_ENABLED` 设为 `1`。生成与审计分别有完整的阶段计时和超时，生成阶段结束后才持久化正文，随后启动审计时钟。当前审计是在同一次调用中串行执行，不是后台异步任务。

读取当前 `.env` 后，实际选中的新运行配置为：`summary_lifecycle.version=summary-first-v1`、`claimify_enabled=false`、两个超时均为 120 秒、`semantic_verification=false`。配置哈希：`ecca0f63500756ae64a5f6d6ea0ba25f0fb1b872c5ae99b9b870f321ebcfd986`。

没有重启正在运行的服务。代码和环境配置需要在后端重新加载后用于新运行。已有运行的冻结策略不会被环境变量覆盖：历史快照没有 `summary_lifecycle` 字段时保持旧提交协议及原配置哈希。使用显式消融配置文件时，文件优先于环境变量，需在新配置中加入 `summary_lifecycle`，同时将关闭开关对应的 `semantic_verification` 设为 `false`。

## 埋点与保存内容

- `summary_error`、`input_history_error`、`summary_stage_error` 和 `summary_claimify_error` 保存 `error_type`、`error_module`、`message`；有显式异常原因时附 `cause_type` 和 `cause_message`。
- `summary_phase_start/end` 用 `phase=generation/claimify` 区分阶段，记录阶段耗时及状态。`summary_attempt_id` 关联同一次正文生成与后续审计；阶段模型调用还保留各自的 `call_id`。
- `summary_generated` 保存完整候选正文及生成状态；`summary_committed` 记录实际提交的正文哈希、摘要版本及覆盖游标；关闭审计记录 `summary_claimify_skipped`。
- 摘要阶段输出、分句结果、来源回读和语义核验事件保留在原有历史记录中，并补充阶段及尝试编号。即使 `TimeoutError` 的消息为空，也能从异常类型识别超时。模型调用被超时取消时，调用层可能记录 `CancelledError`，外层阶段记录 `TimeoutError`，二者含义不同。

## 逐类结果与失败样例

已测量：

1. 关闭开关后不发起 Claimify 请求；成功摘要推进覆盖游标，原文仍可回读，再次准备输入复用保存的摘要。
2. 真实 Claimify 代码路径中的筛选、消歧、拆解和引用定位均在提交后调用，核验结果保存至元数据，正文保持生成时的版本。此处“真实代码路径”使用模拟模型输出，并非真实模型调用。
3. 审计超时、取消时已提交摘要及游标保留；取消继续传播。生成阶段超时不提交、不推进游标，并记录 `TimeoutError`。
4. 生成和审计分别使用自己的期限：两段模拟耗时之和可超过任意一段期限而仍成功完成。
5. 保存失败时不开始审计；并发新摘要出现后，旧审计元数据不能覆盖新版本。
6. 单条旧输入视图在审计前保存，审计失败后仍可复用，且全局摘要版本和游标不变。
7. 多轮摘要保留先前原文来源编号及哈希；历史五题冻结配置反序列化后保持原哈希。

首轮完整回归的两项失败是旧测试断言仍要求 `validated_history_summary` 标签。现改为 `history_summary` 并显式展示核验状态，测试同步检查不会出现误导性的旧标签。另一项错误来自新增多轮测试重复使用同一个 `call_id`：第二次准备输入被正确的在途边界规则阻止覆盖。测试改成每次调用使用独立编号后通过，没有放松边界保护。

## 局限、判断与下一步

间接推断：关闭后续 Claimify 可减少这部分模型调用；将提交与审计拆开能消除“正文已经生成，却因后续审计超时而没有提交”的耦合。实际节省的 token、时延及整任务成功率尚未测量。

尚未评估：真实 PostgreSQL 的新元数据更新方法、真实模型输出稳定性、开启 NLI 后的完整生产审计、整任务 token 预算与最终报告质量。生成阶段自身失败或上下文仍超限时，任务仍可能失败。本次改动也没有解决设备睡眠造成的墙钟计时问题。

当前实现适合先推进通用研究轨迹采集，再由人工及独立评分者评估报告。摘要须继续作为未核验工作记忆使用，报告核验应回到原文。下一步可用同一五题创建独立的新运行，保存新配置和完整轨迹后比较提交成功率、生成/审计耗时及 token；本次未执行该付费重跑。
