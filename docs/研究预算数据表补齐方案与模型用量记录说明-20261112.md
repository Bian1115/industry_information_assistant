# 研究预算数据表补齐方案与模型用量记录说明

日期：2026-11-12，Asia/Singapore。对象：本地 DeepResearch 预算表缺失、数据库迁移状态和模型用量采集。状态：方案及只读核查已完成，数据库修复尚未执行。

建议保留现有三张预算表设计，先通过受控的新增表操作恢复研究入口，再单独校准数据库迁移记录。模型服务商统计请求用量，项目后端负责将用量与题目、研究任务、Agent 和失败重试关联保存。补表阶段保持当前累计 token 上限为 0，不重新启用总 token 限额。

## 一 当前状态和证据

核查程序使用 `backend/.env` 加载当前磁盘配置，在 PostgreSQL 只读事务中查询结构；没有读取用户消息正文，没有执行建表、数据修改、版本登记、后端重启或外部模型请求。没有读取运行中后端的完整环境，因此正式实施时仍需核对服务实际连接目标。

| 项目 | 已测量结果 | 对实施的影响 |
|---|---|---|
| 业务数据库及结构空间 | `industry_assistant`，`public` | 补表必须使用服务实际连接的库和结构空间 |
| 三张预算表 | `research_budgets`、`research_budget_attempts`、`research_budget_calls` 均不存在 | 需要一起补齐，不能只建截图中的第一张表 |
| 预算表前置依赖 | `research_runs` 存在 | 三表的外键有对应的研究运行表 |
| Alembic 登记版本 | `20260919_0008` | 数据库记录自己升级到第 8 个版本 |
| 仓库迁移头 | `20261014_0014` | 仓库已有预算建表脚本，版本链中间还有 6 项 |
| 后续版本结构 | 智能体历史表、会话证据表已经存在；历史表已有 `history_scope_id` 等后续字段 | 实际结构与版本登记不一致，不能直接重放全部迁移 |
| 时间字段 | 多张表的实际字段不带时区，当前模型要求带时区 | 历史时间如何解释需要证据，不能凭版本号推定已经转换 |
| LangGraph 检查点表 | 本次核查的 4 张表均存在 | 检查点建表命令不能代替业务预算表迁移 |
| 累计 token 上限 | `RESEARCH_MAX_LLM_TOKENS=0` | 继续记账，不按累计 token 数触发上限停止 |
| 累计时长上限 | 当前加载配置为 2400 秒 | 补表不改变时间策略；已有运行还可能使用自身冻结策略 |
| 本轮操作 | 数据库写操作 0，外部模型请求 0 | 未测量修复成功率或研究报告质量 |

`schema` 是数据库内部划分表的命名空间，可理解为同一个数据库中的不同文件夹。另一个测试命名空间中存在预算表，但业务服务默认查询 `public`，因此不能用“数据库里某处已有同名表”作为修复完成的证明，也不应把业务查询切到测试空间。

原始机器可读证据：

- [只读核查结果](../backend/eval/data/研究预算补表方案只读核查-20261112-143922/只读核查结果.json)
- [相关表结构差异](../backend/eval/data/研究预算补表方案只读核查-20261112-143922/相关表结构差异.json)

第二份文件的类型差异来自字符串比较，是排查线索。例如 `TIMESTAMP` 与 `TIMESTAMP WITHOUT TIME ZONE`、数组类型的不同打印方式不直接代表实际结构不同；带时区与不带时区的差异则需实际处理。不能将所有列差异条目直接计为数据库缺陷。

## 二 服务商会记录什么 项目需要保存什么

以 OpenAI 为例，服务商提供按时间区间汇总的 Usage API，可返回请求数、输入和输出 token，并支持若干分组维度；也有费用查询接口。[OpenAI 官方用量接口](https://developers.openai.com/api/reference/resources/admin/subresources/organization/subresources/usage)

服务商还会在模型响应的 `usage` 中返回单次请求用量。Responses API 的字段包含输入、输出和合计 token 等信息。[OpenAI 官方 Responses 文档](https://developers.openai.com/api/reference/python/resources/responses/methods/create)

服务商的计量能力不要求调用方先创建数据库表。但服务商不会替本项目自动建立“验证题目编号 → 研究运行 → Agent 阶段 → 第几次请求”的完整业务关系。这部分关系由项目后端掌握，需要由后端保存。其他服务商或中转服务是否提供同等字段及查询能力，应分别验证，不直接套用 OpenAI 的接口行为。

| 保存位置 | 适合回答的问题 | 使用边界 |
|---|---|---|
| 服务商用量记录和账单 | 这个账号或项目用了多少资源、最终被收取多少费用 | 账单对账依据；不自动提供本项目完整的题目和运行归因 |
| 项目 PostgreSQL 数据库 | 一次研究、一个 Agent、一次失败重试消耗多少；重启后还能否正确累计 | 当前预算执行逻辑直接依赖这三张表 |
| Langfuse 监控记录 | 哪一步耗时、调用了什么模型、研究轨迹如何变化 | 项目需要把调用信息和关联编号上报；本方案不把监控上传成功作为模型请求的执行前提 |

因此，并非所有模型应用都必须为用量新增一张专门的表：持久化日志、已有调用记录或其他可靠存储也可以承担统计工作。但当前项目已经按三张预算表实现了请求预留、累计检查和恢复，继续使用这套实现就必须补齐这些表。改为完全依赖 Langfuse 或日志会涉及执行逻辑重构，不属于本次补表范围。

例如，一道题先检索，再写报告，最后由 Critic 要求返工。服务商分别返回这些模型请求的用量；后端把每次返回的用量与同一个研究编号关联，才能计算这道题的总消耗，并区分首次写作和返工。只在 Python 对象的内存字段里累加，后端进程退出后该计数就会丢失。后端提交数据库事务成功后，记录才成为数据库中可供后续进程读取的持久记录；本轮未验证数据库主机断电等基础设施故障。

## 三 三张表的补齐范围

复用已有 [预算表模型](../backend/app/models/research_budget.py) 和 [0014 迁移](../backend/alembic/versions/20261014_0014_研究运行预算账本.py)，保持现有字段、外键和索引定义。

| 表 | 核心内容 | 关联关系 |
|---|---|---|
| `research_budgets` | `run_id`、预算规则 `policy`、初始累计值 `baseline`、创建时间 | 每个研究运行一条，关联 `research_runs` |
| `research_budget_attempts` | 阶段、Agent、执行者、执行次数标识、耗时、状态 | 每次阶段尝试一条，关联对应研究预算 |
| `research_budget_calls` | 请求编号、模型、预留 token、实际 token、状态 | 每次应用发起的模型请求一条，关联阶段尝试 |

建表顺序为预算主表、阶段尝试表、模型请求表。核对两项查询索引：`ix_research_budget_attempts_run`、`ix_research_budget_calls_attempt`。三层外键按现有代码采用级联删除，这意味着删除研究运行记录时可能连带删除其预算记录。30 题实验的长期用量证据需随运行导出到评估目录，不能把会话相关表当作永久账单档案。

本次不新增第四张汇总表。后端按研究编号从三张表计算累计结果即可。当前请求表只有预留量与实际总 token，不具备完整价格计算字段，因此恢复这三张表不等于已经获得准确费用报表。

## 四 具体实施顺序

### 1 确认目标和建立恢复点

执行者核对正在运行的后端实际使用的数据库、schema 和账号权限，与只读核查结果一致后，暂停新研究入口并等待现有研究结束；核对定时清理任务是否需要暂停，防止备份和修复期间发生关联数据删除。

执行者将业务数据库备份到本地受限目录，保存结构、数据和 `alembic_version`，并在隔离数据库验证备份可以恢复。备份路径、源码版本及相关迁移文件哈希写入新的中文实施记录。连接密码只供数据库客户端使用，不写入命令输出和实施报告。

### 2 在隔离副本演练预算表修复

针对当前“登记为 0008、实际已有部分后续结构”的状态，准备一次性修复脚本。它只处理指定业务库中的三张预算表，并复用 0014 的已有 `upgrade()` 建表逻辑，不执行整条历史升级链。

脚本必须先核对 `research_runs` 的主键及关联字段，确认三张目标表全部缺失；如果目标库变化、出现部分已建表或不匹配结构，脚本退出并报告差异，不能凭 `checkfirst=True` 跳过结构核对。执行者用单一迁移进程，在一个数据库事务中创建三张表及其约束、索引；完成结构校验后才提交。数据库执行失败时回滚该事务。

本步骤不自动修改 `alembic_version`。记录中应明确“0014 的预算结构已单独补齐，历史迁移登记仍待校准”。这是一次受控的部署修复，不引入程序运行时的旧表或旧接口兼容路径。

### 3 在业务库实施同一修复

隔离副本通过后，在维护窗口对已确认的业务库执行同一修复脚本。保存执行前后结构差异，要求本阶段差异仅包含三张预算表及其约束、索引，已有研究、消息、报告和时间字段保持原值。

修复后，后端现有 SQL 查询即可看到新表；是否需要重启取决于服务连接和启动检查状态，不把重启当作建表操作。旧失败运行是否可继续应由保存的状态判断；本次验收优先使用一条新研究，避免把历史失败状态误当作修复未生效。

### 4 单独校准历史迁移记录

这一步处理后续部署升级的可靠性，不与当前三张表的新增操作混在一个未经审查的 `upgrade head` 中。

| 版本 | 核查和处理 |
|---|---|
| 0009 时间统一 | 查明历史时间写入方式和原时区；只对确实需要转换的列执行转换，不能根据电脑所在地猜时区 |
| 0010 智能体历史 | 已有表包含 0011 后续字段，0010 的严格列集合检查会拒绝；校验最终字段、约束和历史记录，不直接重放旧定义 |
| 0011 历史接续 | 已有新增字段和唯一约束；验证归属及非空约束，不再次用旧运行编号覆盖已有会话历史范围 |
| 0012 会话过期 | 验证过期字段类型、默认值、索引及现有数据；只新增字段的脚本不能修正已经存在但类型不同的字段 |
| 0013 临时证据库 | 表已存在，仍需核对字段类型、约束、索引；“表存在”不足以证明迁移后状态一致 |
| 0014 研究预算 | 核对本次已补齐的三张表与迁移定义一致 |

执行者将确认的结构和数据差异形成修复清单，在备份副本演练后再修正。只有所有前置迁移要求和数据转换结果均已验证，才可让 Alembic 登记经过核对的版本。`stamp` 只改版本记录，不执行结构或数据转换，不能用它掩盖差异。无法确认的历史时区或数据转换必须保留为待解决事项，不将“预算表可用”报告成“迁移链完全正常”。

迁移命令通过 Python 启动器先加载 `backend/.env`，再导入 Alembic 环境；现有 `alembic/env.py` 本身不调用 `load_dotenv`。正式执行时使用锁定的目标版本，避免源码后续增加迁移后无意扩大执行范围。

### 5 验证运行和保存证据

先在隔离环境执行已有 [预算持久化验证脚本](../backend/eval/scripts/验证预算持久化与检查点租约隔离.py)。脚本会创建并删除自己的测试 schema，包含模拟进程崩溃，因此属于实施阶段的测试，不能当成纯只读检查。

需要覆盖的验收条件：

1. 新研究没有预算记录时，查询合法返回空结果；后端开始执行阶段后能够建立主记录。
2. 一次模型请求预留 1000 token、返回实际用量 300 后，后端按 300 计入该请求；不会把预留和实际量相加成 1300。
3. 同一请求重复结算不会重复累计；新发起的重试请求使用新编号并单独记录。
4. 请求中断且实际用量未知时保留未知状态和预留量；重启后不能自动变成零消耗。
5. 阶段失败、恢复和并发请求仍能正确读取累计值，其他研究运行的用量不混入。
6. 当前 token 上限为 0 时，仍能记录和展示消耗；不因累计 token 达到某个值而拒绝请求。
7. 业务库三张表的字段、外键、主键、索引以及服务账号读写权限通过核对。

之后执行一条小规模真实研究，检查前端能够进入后续研究阶段、数据库产生对应记录、模型返回用量与记录一致，以及配置启用时 Langfuse 的同一运行能关联相应调用。将用量未知的调用单列，不要求其数值与服务商账单强行相等。先通过此验收，再启动 30 题批量运行。

为本次实际执行创建新的中文结果目录和中文验证报告，保留修复前后结构、执行日志、逐项检查、失败记录和复测结果。当前这份只读方案不充当未来执行成功的证明。

### 6 防止再次出现启动后才缺表

后续增加启动就绪检查：后端在开放研究接口前只读检查所需表、关键字段与迁移状态，缺失时报告明确的部署错误。部署步骤显式执行迁移，普通用户请求不承担自动建表职责。现有检查点生命周期只打开连接池，检查点 `setup()` 也不会创建业务预算三表。

建表事务未提交时的失败由数据库回滚；提交后若发现问题，先停止新请求并保留已有记录，不直接运行删除三表的降级脚本。需要恢复时依据备份及新增数据情况制定恢复步骤，避免删除已经记下的真实用量。

## 五 用量采集和监控的建议

当前主 Agent 的 [BaseAgent 调用流程](../backend/app/service/deep_research_v2/agents/base.py) 已经执行以下步骤：后端先提交请求预留，随后向模型服务商发请求，收到 `usage` 后更新实际用量；失败或未知用量由预算逻辑单独处理。[预算累计实现](../backend/app/service/deep_research_v2/budget_ledger.py) 区分 `known_tokens`、`charged_tokens` 与 `unknown_usage_calls`。

- `known_tokens`：已经取得用量数据的累计值。
- `charged_tokens`：代码中用于预算控制的累计值；实际用量未知时使用预留量。这个字段名不代表服务商已收取的费用。
- `unknown_usage_calls`：实际用量尚未知的请求数。请求未到达服务商、到达但响应丢失等情况都可能产生不确定性，不能统一声称已发生实际计费。

请求前的预留是本地估算，不应当作供应商精确计量。API Key、模型输入、模型响应和用量是不同数据，预算表无需保存 API Key 或完整提示词。

现有 [Langfuse 上报代码](../backend/eval/runtime/langfuse_tracing.py) 已将调用记录中的输入、输出、合计 token 送入 `usage_details`。仍需在实施验收时确认配置启用、实际调用覆盖和上传结果；读到代码不等于证明所有请求已经进入监控平台。

后续统一统计按实际调用入口盘点：主 Agent、问题补全、摘要、论断提取、独立核验和离线裁判均需要确认。当前预算主路径主要挂在 BaseAgent，仓库还有其他独立客户端调用，补表不能自动使全部调用获得完整覆盖。GPT 裁判当前也单独保存响应 `usage`，应归类为离线评估消耗，与报告生成、在线 Critic 返工消耗分别汇总。

若后续需要准确费用分析，再增加输入、输出、缓存等用量明细，服务商请求标识、请求时间及价格版本，或从已有原始调用记录建立可追溯的汇总。不同 API 的 `prompt_tokens/completion_tokens` 和 `input_tokens/output_tokens` 需归一化，保留原始用量，避免把不同字段名称当成零值。最终费用以服务商账单对账，不能只拿总 token 乘一个统一价格。

## 六 结论和验证边界

**已测量**：当前加载配置指向的业务结构缺少三张预算表；迁移登记为 0008、源码头为 0014；部分后续结构存在；当前累计 token 上限为 0。原始查询结果已在本地仓库保存。

**间接推断**：数据库曾经局部准备后续结构而未同步完整迁移状态。当前结构可以证明两者不一致，但不能确定历史操作由哪个进程、何人在何时执行。三表缺失与截图查询错误一致，但补表不能证明之后所有研究步骤都会成功。

**尚未评估**：补表执行、备份恢复、迁移历史校准、预算故障复测、真实研究、30 题评测、全部客户端用量覆盖、Langfuse 实际上传和服务商账单对账。

下一步按上述顺序实施：先恢复三表支持的当前功能，独立校准历史迁移，再以单题真实研究作为批量评测的准入条件。保持当前不设置累计 token 上限的策略，将用量统计、时间控制、监控分析和实际费用对账分别报告。
