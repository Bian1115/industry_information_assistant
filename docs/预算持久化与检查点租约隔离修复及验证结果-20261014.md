## 修复内容

### 预算独立持久化

新增[预算模型](../backend/app/models/research_budget.py)和[迁移](../backend/alembic/versions/20261014_0014_研究运行预算账本.py)，包含三张表：

| 表 | 保存内容 |
| --- | --- |
| `research_budgets` | 一次运行的冻结预算配置及只导入一次的旧检查点已知消耗 |
| `research_budget_attempts` | 独立物理尝试 ID、节点、阶段、执行器/token、开始时间、期限、已耗时间和结束状态 |
| `research_budget_calls` | 每个供应商请求的独立 ID、所属尝试、模型、预留、真实返回 usage 和结果状态 |

[PostgresRuntimeBudget](/Users/bxy/projects/industry_information_assistant/backend/app/service/deep_research_v2/budget_ledger.py:97)在节点执行前创建持久化尝试；取消、失败和成功均独立结束记账，不依赖该节点成功返回图状态。硬崩溃后，未结束尝试在恢复时按旧租约截止时间为上界计时并标记 `abandoned/lease_upper_bound`；不能把这种上界估计当成精确活跃时长。

[模型请求接入](../backend/app/service/deep_research_v2/agents/base.py)在供应商调用前持久化“估算输入＋输出上限”预留，拿到 usage 后立即结算。预留和预算检查在同一运行行锁内完成，并发请求不能分别读到同一份剩余额度而共同超额。同一 call 的重复结算不重复累计；不同 usage 的覆盖被拒绝。

`known_tokens/llm_tokens` 表示已返回 usage，`charged_tokens` 表示预算约束采用的实际量加未知请求预留。`consumed_tokens` 在独立账本路径使用扣账量；不能把未知调用当作 0 token 或把扣账预留称作实际费用。

Writer 已保存章节继续使用原有 task 产物，不新增重复生成；原章节请求记录仍在独立预算表内，重建 Agent 后不会因模型计数器归零而漏掉。物理节点尝试次数从账本恢复，进度事件使用更新后的 attempt。

[服务接入与状态读取](../backend/app/service/deep_research_v2/service.py)为持久化执行注入预算 store。状态读取从独立账本投影最新消耗，公开 `runtime_budget`；失败节点前的旧图快照不会遮盖已落盘消耗。离线 `persist_events=False` 入口保留原有非持久化机制，不冒充真实预算恢复。

### 检查点提交的租约隔离

[LeaseFencedPostgresSaver](/Users/bxy/projects/industry_information_assistant/backend/app/service/deep_research_v2/checkpointer.py:103)为每次执行创建独立实例，共享连接池但不共享可变的租约身份。写入绑定同一 run；可靠服务入口拒绝静默退回无保护的 saver。

完整检查点和 pending writes 均使用以下事务顺序：

1. 在 saver 的写连接上锁定 `research_runs` 行。
2. 校验 session、user、owner 和 fencing token；锁等待结束后用数据库时钟判断期限。
3. 在同一事务里写 checkpoint、blob 或 pending writes。
4. 提交前再次校验租约；失效则回滚该事务。

租约获取和续租对同一运行行的更新会等待上述事务释放行锁。因此接管与检查点写入有明确提交顺序；已有事件/终态交付的校验不能替代这项保护。

检查点必须与业务租约使用同一 PostgreSQL 目标和 search_path。显式 `RESEARCH_CHECKPOINT_DATABASE_URL` 可以换账号，但 host、port、dbname 和 options 不一致时明确拒绝。原先允许独立检查点实例的部署方式不再符合本修复的原子隔离前提。

阶段保护还补上 action 完成后的租约、取消及预算检查，避免快速完成跳过轮询。单 AsyncConnection 的嵌入/测试入口共用连接锁，防止并发事务变成彼此的 savepoint；saver 实例锁与连接锁保持一致顺序。

迟到 usage 可以结算原执行器已经预留的原请求，需要匹配原 attempt、owner、token 和运行归属。这种消耗对账不授予旧执行器发起新请求或提交图状态的权限。

## 失败记录与补充复评口径

1. 首轮核心回归出现 1 项失败：旧事件落账失败测试传入占位 saver，却未适配新的可靠执行准入，未到达预期注入点。补上仅用于该假图测试的 saver 适配桩后，又发现该夹具的非 UUID 身份先触发了临时证据校验；最终为这个无数据库测试明确关闭临时证据，事件落账失败断言正常通过。没有放宽生产准入或临时证据校验。
2. 应用入口首轮 10 项中 1 项失败：旧假服务将 lease 获取模拟为 None、recorder 模拟为不持久化，但没有声明 `persist_events=False`。改为明确的离线服务代理后 10/10 通过；生产可靠执行依旧要求真实 saver 和租约。
3. 数据库场景初版 5/5；新增迁移与并发预留后 7/7；新增单连接处理后 8/8；统一锁顺序并新增等待顺序断言后，最新 8/8。前后目录及源码哈希均保留，不累加为 28 个独立故障场景，也不以重复成功推导总体成功概率。
4. 注入的搜索节点异常、供应商瞬时错误、超预算拒绝、旧租约写入拒绝和到期回滚均为预期故障；通过表示满足失败后的保护断言，不能把错误日志当作真实生产事故。

## 局限性、结论与下一步

**已测量**：真实预算数据库持久化、并发预留、幂等结算、冻结配置、独立连接的租约接管顺序、迟到 checkpoint/pending writes 拒绝、事务到期回滚、真实 SIGKILL 与新进程章节复用、迁移往返、单连接锁顺序和上述离线回归。

**间接推断**：相同 PostgreSQL 行锁与事务边界在正常请求中的隔离效果；未知 usage 预留的保守额度保护。测试只覆盖所列确定性边界，不代表所有网络或部署故障。

**尚未评估**：真实模型/搜索费用，数据库主从切换及网络分区，生产负载下的持久化开销，浏览器端到端恢复，以及独立同步模型客户端的统一预算接入。没有计算耗时节省率或费用下降率。

升级前未保存的失败消耗和旧章节产物的未知 usage 无法补造，旧运行只导入检查点已经记录的已知预算。新账本的未知请求预留可能比实际消耗高；硬崩溃时长也可能包含崩溃至租约上界之间的保守余量，均单独标记。预算账本缺失而检查点已经声明使用独立预算时明确拒绝重置，避免把消耗归零。

结论：本次两项源码缺陷已修复，并通过真实数据库故障边界验证。启用前应完成业务迁移和 LangGraph 建表步骤，保持检查点与租约同库。下一步可在实际部署完成后验证一条真实服务请求，再单独测量账本与同步检查点事务带来的正常路径开销。
