# 跨存储对账修复及故障恢复验证结果

评估日期：2026-10-16，Asia/Singapore。补充复评均在同日完成。

评估对象：DeepResearch v5 的 LangGraph 检查点、待合并节点结果、Writer 章节 task、Agent 原始工作历史、预算账本、会话证据正文、派生 chunk/向量索引、事件和终态交付之间的恢复一致性。

结论：已在代码中加入随产物提交的版本化依赖清单、检查点写事务内复核、恢复前统一对账和索引补建。正文、历史或预算依赖缺失/改写会明确阻止恢复；有完整依赖的待合并节点和章节仍可复用。最终离线回归共 144 项，其中 140 项通过、4 项既有数据库用例跳过；专用 PostgreSQL 隔离验证 17/17 通过。合计实际通过 157 项，不把重复复评累计成独立样本数。本次未升级主业务 schema、未重启现有服务。

## 缺口与修复机制

### 1. 把依赖版本与执行产物一起提交

新增 [storage_reconciliation.py](../backend/app/service/deep_research_v2/storage_reconciliation.py)，协议版本为 `research-storage-v1`。输入、节点结果、终态结果和 Writer 章节保存 `storage_manifest`，包含产物自身哈希、run/session/user 归属、节点/产物种类及依赖：

- 外置正文的定位、payload 哈希、generation、文档编号；检查正文自身哈希、正文版本和原句编号。
- Agent 原始历史的记录 ID、内容哈希、调用和 invocation ID、节点等稳定字段。
- 预算策略/基线哈希、物理 attempt、调用预留和已知 usage。已知 usage 必须保持一致；未知预留可以迟到结算，累计时长与回退计数不得倒退。
- 已保存事件的序号水位。

清单直接存入原有 checkpoint 或章节 `__return__` pending write，省去“清单单独成功、检查点提交失败”的新增窗口，不需要新增数据库表或迁移。

[graph.py](../backend/app/service/deep_research_v2/graph.py) 在节点业务结果完成、证据提交并外置之后封存清单；纯 finish 节点也封存最终结果。[Writer](../backend/app/service/deep_research_v2/agents/writer.py) 在章节 task 返回前封存章节内容及输入依赖。新协议下章节输入哈希排除清单、预算计数和索引诊断指标，索引修复不会改变章节业务输入；旧章节继续沿用原输入哈希口径。

### 2. 写入检查点时再次复核

[checkpointer.py](../backend/app/service/deep_research_v2/checkpointer.py) 在既有租约事务及 run 行锁内校验清单，然后执行原生 checkpoint/blob/pending write 写入，提交前仍复核租约。清单生成之后到 saver 写入之前，如果依赖已被删除或改写，整次提交拒绝，不留下一个声称可恢复的新检查点。

不在持有 run 锁时反向获取 chat 行锁，保持与会话清理路径的锁顺序兼容。正文有效期使用与证据 Store 相同的 idle TTL 规则：只承认到期前已经提交的新消息延长的期限，对账本身不续期。

### 3. 恢复前检查完整的持久化边界

[service.py](../backend/app/service/deep_research_v2/service.py) 在恢复的图执行和终态补交付前对账，覆盖原始 checkpoint、LangGraph 合并视图、待合并节点结果以及章节 task 返回值。仅检查 `snapshot.values` 会漏掉章节或尚未合入 checkpoint 的节点，本次将两类 pending writes 一并纳入。

核对所有事件属于当前用户/会话、序号从 1 连续到 `next_event_seq`。终态还检查 checkpoint 编号、完成事件、run 交付指针和已保存 assistant 报告一致。缺少终态交付时沿用已有的幂等业务事务补交付；存在冲突时阻止覆盖。

独立历史和预算允许在节点失败后保留，新增历史作为观察记录，不据此宣布节点成功或把进度正文替换成已提交报告。图和章节的真实提交结果继续决定复用位置。

### 4. 区分正文缺失与可重建索引

[session_evidence_store.py](../backend/app/service/session_evidence_store.py) 为新正文保存切分协议和 chunk token 参数。恢复时从验证后的原文逐文档重建完整预期 chunk 集合，补缺失项、修复内容/locator 损坏项，并移除该文档多出的 PG chunk。原始正文不变；原本未准入或无法切分的正文保留其错误标记，不伪装成已经索引。

[session_evidence_vectors.py](../backend/app/service/session_evidence_vectors.py) 核查 Milvus 中实际存在的 ID，按用户、会话、主题和 generation 过滤，并检查文档及单元类型。每批最多 256 个 ID，使用强一致读取。PG 的 `indexed` 标记不再被当作向量实际存在的证明。

[session_evidence_rag.py](../backend/app/service/session_evidence_rag.py) 对缺失向量重新标记 pending、embedding、upsert/flush 后再标记 indexed。向量基础设施不可用时记录 `lexical_only`，继续使用已验证的 PG 正文和词法检索；正文/原句编号、归属或 generation 不合法则阻止恢复。正文 hydrate 同样加入版本和哈希比对，避免把数据库中另一份正文套在旧引用上。

修复摘要落入持久化的 `storage_reconciled` 观察事件，包含补建 chunk、缺失向量、索引状态和旧切分配置数量。

### 5. 让状态与入口给出相同诊断

状态接口返回 `storage_reconciliation`，区分 `consistent`、`legacy_checked`、`blocked` 和暂时 `unavailable`。阻止恢复时关闭 `resumable` 和 `delivery_ready`，保留具体原因；HTTP 恢复入口在获取执行租约前返回 409。旧的运行失败消息不会覆盖本次查出的依赖错误。

旧 checkpoint 没有历史依赖清单，标记为 `legacy_checked`，只核对仍可验证的数据。新产物已声明协议却丢失、清空或损坏清单时必须阻止，不能自动退成旧版。升级前已经消失的历史或预算无法补造。

## 核心指标与逐类结果

| 项目 | 最终结果 | 解释 |
| --- | --- | --- |
| 离线完整回归 | 140 通过 / 144 总项，4 跳过 | 图、章节、恢复/交付、预算、事件、HTTP、临时 RAG、分页精排 |
| 新增索引机制测试 | 9/9 | SQLite chunk 重建/正文拒绝/降级 7 项，向量适配层 2 项；已包含在离线总数 |
| 专用 PostgreSQL 故障验证 | 17/17 | 不与离线模拟数据库测试混算 |
| 最终隔离 schema 清理 | 17/17，残留 0 | JSONL 生命周期记录加只读全前缀扫描 |
| 真实外部模型/搜索请求 | 0 | 响应、usage、embedding 和 rerank 为固定模拟 |

PostgreSQL 17 项逐类分析：

1. **提交与预算 4 项**：清单随检查点持久化并允许迟到结算；封存后删除历史拒绝整个 checkpoint；删除预算调用拒绝 pending write；已结算 usage 被减小会拒绝。
2. **正文生命周期与归属 4 项**：替换成另一份自带合法哈希的正文仍拒绝；过期/generation 改变拒绝；到期前新消息可延长期限、到期后消息不能复活旧空间；修改产物或跨用户引用拒绝。
3. **历史、事件与兼容性 4 项**：额外历史保留为观察；事件缺号拒绝且不补造；旧产物明确有限检查；新协议缺失/空/损坏清单不能降级绕过。
4. **可重放产物 2 项**：第三章失败后，新图继续复用已保存前两章；节点结果已入 pending writes、后继 checkpoint 写失败时，新图继续合并且 Writer 不重跑。修改任一 pending 产物内容均在恢复检查中阻止。
5. **服务和交付 3 项**：正文删除后状态不可恢复，真实 service 恢复没有调用任何 Agent；终态补交付先落对账观察、再完成交付，没有 Agent 重跑；既有完成事件与终态报告冲突时阻止。

索引测试还验证重复修复不新增 chunk、PG 内容/locator 损坏会重建、整份向量集合丢失会重新 embedding、索引不可用明确词法降级、损坏正文绝不用于重建。HTTP 用例验证 409、拒绝获取租约及错误原因展示。

## 失败样例与复评记录

- **预期故障样例**：正文被删除、替换/改写、generation 改变、历史/预算记录被删除、事件只剩 seq=2、章节正文被修改、终态完成事件写了另一份报告。这些案例以正确拒绝为通过标准，不能算作恢复数据成功。
- **首轮离线**：140 项，2 失败、1 错误、4 跳过。新 hydrate 测试实际触发“编号不存在”而断言只允许“哈希”；旧预算投影夹具使用 `AsyncPostgresSaver(object())` 没有模拟新增只读对账；旧事件持久化失败夹具在注入事件错误前遇到了未模拟的清单封存。分别放宽为正确的拒绝类别、补充只读对账模拟、补充封存模拟；未放松生产检查。[原始日志](../backend/eval/data/跨存储对账修复验证-20261016/首轮离线回归/原始测试日志.txt)。
- **首轮数据库**：11 项，1 失败、3 错误。手工构造 saver config 漏了必需的 `checkpoint_ns`；章节图夹具使用外置正文却未配置真实 RAG 回读，确定性分析把缺失 content 重新计算为空哈希，被新保护正确拒绝。补齐配置并接入使用隔离 Store 的 RAG。[原始日志](../backend/eval/data/跨存储对账修复验证-20261016/首轮真实数据库/原始测试日志.txt)。
- **同日补充复评**：先完成 140 项离线（4 跳过）和 11 项数据库通过；扩展真实服务补交付/拒绝为 14 项，增加待合并节点为 15 项，TTL 口径复核为 16 项，损坏清单拒绝为最终 17 项。中间目录保留对应代码哈希和日志。
- **最终接口诊断复评**：在最后 144 项离线回归中确认“上次网络失败”不会遮盖新查出的正文缺失原因。最终 PostgreSQL 17 项之后仅调整此 HTTP 展示分支，依赖校验、saver、证据和服务执行代码未再改变。

## 局限、部署和下一步

本次使跨存储依赖可核对、错误可定位、派生索引可补建；独立历史/证据已提交而节点尚未提交时，仍由图和章节的持久化结果决定重放。没有提供跨 PostgreSQL 与 Milvus 的分布式原子提交，也没有保证外部请求恰好一次。

旧正文没有冻结切分配置时，使用当前配置重建并明确记录 `legacy_chunk_profiles`；旧 checkpoint 不具备升级后同等依赖证明。可变 Agent 摘要没有作为不可变产物冻结，原始消息记录为本次历史核对对象。向量核对验证成员、作用域和文档类型，不重新比对所有已有向量的数值；不扫描/回收整个集合的所有游离向量。正文仍受原有会话 TTL 限制。

本次新增字段内嵌于原有检查点，无需新迁移。部署仍需满足之前预算/历史/证据表及 LangGraph 表已准备的条件，按 [后端说明](../backend/README.md) 完成现有 Alembic 和检查点建表步骤后加载新代码。本次没有替用户运行主库迁移或重启现有服务。

下一步可单独做真实 Milvus 丢集合/部分数据丢失与网络故障的端到端验证，测量清单大小和正常提交开销，再处理独立的终态后台补交付调度。上述项目不计入本次已完成和已测量范围。
