# URL排序与模型信源评分机制分析

- 分析日期：2026-10-11（Asia/Singapore）。
- 评估对象：当前 Scout 读取前 URL 排序与读取后大模型信源评分是否为同一机制。
- 数据／配置口径：当前工作区相关源码和提示词；未调用模型、未搜索或读取真实网页、未运行评测，未修改业务代码。
- 原始记录：[静态检查记录.json](../backend/eval/data/URL排序与模型信源评分机制分析-20261011/静态检查记录.json)，保留源码片段、行号及 SHA-256。
- 补充口径：此前信源分类和原始出处追溯分析之后，本次明确区分“决定先读哪些URL”和“读取后给提取事实的信源评分”；为新的静态分析。

## 结论

用户观察正确：读取前的 URL 排序没有调用大模型。模型评分发生在读取正文后的事实提取阶段。当前所检查候选排序路径没有使用模型分数重新排序 URL。

实际顺序是：搜索结果 → 域名范围过滤 → 规则排序 → 按预算读取正文 → 合格正文进入模型 → 提取事实并输出来源类别、可信度分数。

## 逐项分析

### 读取前的排序分数

`quality_pipeline.py:26` 的 `candidate_source_score` 使用以下规则，返回整数分数，不调用模型：

| 判断项 | 规则 |
| --- | --- |
| 命中低质量域名集合 | 直接返回 -100，不再叠加后面的规则 |
| 解析后的 hostname 以 .gov.cn 或 .edu.cn 结尾 | +80 |
| 网站名或标题包含“官网、官方、年报、annual report、监管、统计局”等 | +50；命中多个关键词也只加一次 |
| URL 字符串以 .pdf 结尾 | +20 |
| 网站名或标题包含“文库、论坛、自媒体、博客” | -30；命中多个关键词也只扣一次 |

域名判断针对解析后的 hostname；关键词判断针对 `site_name` 和 `title`，并非任意匹配 URL 路径。

`scout.py:936` 使用 `sorted(in_scope, key=candidate_source_score, reverse=True)` 排序，再把结果及读取上限交给 `web_read`；`scout.py:1070` 转交 `web_reader.read_many`。

### 读取后的模型评分

`scout.py:1310` 只允许正文读取合格的结果进入提取。`evidence_batches.py:33` 将标题、URL、网站名、日期、摘要和当前批次编号正文交给模型；`:178` 实际调用 LLM。`scout.py:220` 要求模型在每条提取事实中输出 `source_type` 和 0—1 的 `credibility_score`，主提示还提供截图中的评分区间。

这不是为所有搜索候选逐URL打分，也不是独立的 URL 重排调用。模型分数被保存、展示，并作为事实信息提供给 Writer 和 Critic。所检查 URL 排序路径的键始终是读取前规则分数，没有模型评分反馈重排。

## 失败样例与局限性

本次没有新增实测失败样例。以下是假设风险：标题自称“官方报告”可能获得优先级；未命中规则的原始论文可能排在靠后位置；预算有限时未读到的候选无法依靠后续模型评分纠正优先级。

本次只检查当前本地候选阅读与事实提取链路，不能据此评价外部搜索引擎自身的排序，也没有测量真实漏读比例。读取后的可信度分数不能直接解释为事实正确概率。

## 下一步建议

产品和代码说明应分别标注“候选阅读优先级”与“模型信源可信度”，避免混用。若目标是让模型决定先读哪些网页，应在读取前新增基于标题、网址和摘要的候选比较环节，再用正文核验；这属于新的实现，本次没有进行改造。是否值得增加该步骤，应通过人工标注候选集与现有规则比较后判断。
