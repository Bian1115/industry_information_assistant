# 追问契约统一更新实现与验证

评估日期：2026-09-29。对象：追问路由输出结构化修改后，将完整契约提交到共享研究状态，再进入现有 Writer、Scout、Architect 分支。按用户决定，不增加 Critic → Architect 路径。

## 1. 实现结果与配置口径

新运行的路由提示词版本为 `followup-router-v2-contract`，一次调用同时生成消解query、修改指令、契约补丁和路由决定。补丁包含 `base_revision` 和 `operations`，操作为 add、replace、remove；每项携带本轮用户原话 quote。服务端校验后合并，模型不能改写来源权限或验收策略等字段。

契约仍存储在运行级 `state['research_contract']`，没有增加进程级全局变量。`contract_revision` 是契约更新序号，与原契约的 schema `version` 分开。历史契约没有更新序号时以0为基线。每次成功接收追问生成一个新快照；再次应用同一旧版本补丁会被拒绝。

路由在继承父材料后安装完整新契约，并从契约同步 `active_constraints`。原始问题、消解query和修订指令均保留，契约自身query不混入提示词附加内容；兼容仍以state.query读取背景的下游，该字段包含本轮有效契约。字段内容无法只凭当前schema确认语义正确，程序不将格式/出处校验冒充意图识别正确性保证。

支持更新的字段：max_body_chars、required_entities、critical_questions、explicit_requirements、required_metrics、required_calculations、time_range、geography、language、output_format。数组字段通过完整替换实现增删项，保留原有稳定ID。字数上限支持明确取消；范围改变时若原契约存在指标/计算，补丁必须同时核对并更新或删除相应范围，不能保留相互冲突的旧检查条件。

新旧协议不能混用。新v2模型结果缺少constraint_patch时，不默认解释为“用户未修改要求”。空operations可以表达无结构化变更，但仍生成包含当前query与修改指令的完整快照。

兼容范围：冻结为 `followup-router-v1` 的旧运行仍可使用旧的constraint_updates协议；原有回归夹具明确使用v1，新增专项测试使用v2。没有修改智能路由启用开关，`FOLLOWUP_ROUTER_ENABLED` 仍由部署环境决定。本次未重启服务或调用在线模型；已有进程是否加载新代码需按实际部署流程确认。

## 2. 各分支和失败处理

- Writer：修订提示词明确接收完整研究契约。全局契约字段变化时修订所有章节，避免只更新局部而留下旧语言、范围或格式。
- Scout：接收更新后的共享契约与完整问题背景；显式要求发生删除/替换时，同步清理或替换继承章节中的 requirement_ids/requirement_responses。新增要求绑定到路由提供的承接章节，没有承接章节则不能继续局部路径。
- Architect：读入路由已提交契约；重新规划只刷新章节覆盖等派生关系，保留用户约束和取消结果，不让模型生成的新实体清单覆盖用户要求。修复原有父材料分支缺少 `import json` 的错误。
- 路由异常：保留父契约基线并标记 pending，进入原有 Architect 降级路径。Architect 必须返回结构化 followup_contract_update，并通过相同合并校验才能继续；已有最多两次规划重试用尽仍不合法时抛错，不能带旧约束静默继续。
- 对象、时间、指标或显式要求等结构化变更不能直接交给Writer，至少进入Scout评估补证或Architect重规划。这是保守规则，并未测量其额外成本。

本次不接入此前整份 Architect 新提示词草案，也不改全局会话消解模块。仅在现有规划提示词补充已提交契约/失败补解析的输入协议，保持首次规划主流程兼容。初次规划现有实体抽取策略未整体重构；本次保护针对已提交的追问契约。

## 5. 逐类分析和失败样例

| 案例 | 已测量行为 |
| --- | --- |
| 三分支字数5000改3000 | 契约修订号从3到4，其他要求保留，执行投影一致 |
| 取消字数上限 | 上限从契约及执行投影删除，Architect不能恢复旧限制 |
| 对象清单改为A、B | 真正替换required_entities，不只是追加自由文本 |
| 更换主题不复用 | 不复制旧对象、时间、字数限制或事实 |
| 重复/过期补丁 | 拒绝旧修订号，防止重放覆盖 |
| 伪造用户出处、非法字段、错误值类型 | 拒绝；校验阶段失败不改变输入状态 |
| add/replace/remove混淆、重复字段 | 拒绝，不以null模糊表示取消 |
| 时间变化但遗留旧指标范围 | 拒绝，要求同步更新指标/计算 |
| 直接Writer承接研究范围变化 | 拒绝并由现有异常路径重规划 |
| 取消显式排名要求 | 同步清除旧章节的要求ID与内嵌要求内容 |
| 全文改语言但路由只选一节 | Writer实际收到新契约并处理全部章节 |
| 路由异常后取消字数限制 | Architect补解析成功后使用新契约继续 |
| 路由异常且Architect始终不给合法补丁 | 3次规划调用后抛错，保留待解析基线，不继续研究 |
| 路由节点完成后暂停/恢复 | 检查点已含新契约；从目标节点继续，补丁不重复应用 |

失败样例为注入的伪造出处、旧版本、非法类型、遗漏补丁、超时与不合法规划输出，不是本次线上发生的失败。两轮测试均通过；首轮之后的修订来自代码检查发现的章节/全局作用域缺口。

## 6. 局限与后续

已测量：字段合并、取消、版本防重放、重规划保留、章节同步、内存检查点恢复与旧协议回归。语法编译及相关已跟踪文件diff空白检查通过。

间接推断：统一新契约可减少各条追问路径的约束不一致，拒绝含糊更新可避免错误交付。全局修改可能增加Writer调用范围，严格补丁协议也可能增加降级/重试次数，当前未测其线上频率。

尚未评估：真实模型补丁生成准确率、指代消解语义正确率、研究事实与新对象/时间范围的实际适用性、真实数据库检查点恢复、token/时延以及开发集端到端成功率。新约束能写入状态，不代表报告已满足所有约束；字数仍由现有长度检查验收，语言/范围等仍依赖生成与审核。

建议下一步在启用智能路由的测试环境用“改字数、取消限制、更换对象、补充年份”四类真实追问验证，再跑固定开发集比较质量和成本。Critic路由保持当前实现。
