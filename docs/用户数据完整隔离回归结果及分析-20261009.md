| 场景 | 结果与含义 |
| --- | --- |

| 附件操作 | 跨用户上传/详情/列表/删除均拒绝；拒绝后文件和数据库不变；本人上传、后台提取、列表及删除可用；用户 ID 由后端写入 |

## 失败样例及复评记录

1. **首轮（28 项，48 个 error 事件）**：真实 Token 的 `sub` 是字符串，原认证查询直接传入 UUID 列，在 SQLite UUID 绑定时出现 `'str' object has no attribute 'hex'`；测试资源清理顺序还导致关闭连接后的重复清理错误。因此 48 是错误事件数，不是 48 个独立测试。本轮未能有效验证所有隔离行为，原始日志保留。
2. **第二轮（28 项通过）**：认证查询先规范化 UUID，调整测试清理顺序后通过。随后核查发现新 FastAPI 版本延迟注册路由，直接遍历 `app.routes` 会漏掉匿名入口检查；本轮的匿名测试通过不视为入口覆盖证据。
3. **第三轮（104 项，77 通过、27 跳过）**：匿名检查改为遍历 OpenAPI 展开的路由，并要求至少检查 30 个方法/路径，实际测得 48 个；新增反向双用户测试。
4. **最终同日补充复评（105 项，78 通过、27 跳过）**：代码补充聊天检索本地文档归属白名单，并新增错误归属及孤儿索引切片测试。此轮是最终口径。

业务失败样例已转为回归用例：乙的会话/附件 ID 在甲的请求中得到 404；批量删除包含甲/乙文档时整批授权失败且甲文件未先删除；旧公开 JWT 密钥签出的伪造身份得到 401；旧账号延迟返回的列表不覆盖新账号缓存。

- **间接推断**：统一认证依赖和归属 SQL 条件在真实数据库使用相同业务代码；Redis/Milvus 用户作用域已通过源码及已有离线替身测试核查。此推断不能替代实际服务部署验证。

## 实现变化与兼容性

详细说明：[用户隔离实现说明-20261009.md](用户隔离实现说明-20261009.md)。新增共享归属查询与上传工具，所有私有业务统一认证；附件、聊天附件、文档和后台任务补充归属；用户私有知识检索禁用共享 benchmark 映射；前端账号切换清理缓存并忽略旧请求写回。

`/documents` 现在必须提供本人 `kb_id`，使用本地知识库文档 UUID，索引名由服务端派生，不再访问共享默认远端数据集。历史匿名或归属冲突数据拒绝访问，未自动迁移或删除。本地公开默认 JWT 密钥已随机替换，代码拒绝缺失/过短/已知默认密钥；实际密钥未写入报告或原始结果。需要重启后端并重新登录才能使用新配置。

## 局限性

测试使用隔离 SQLite 和服务替身，无法测量外部存储真实配置、索引清理失败、数据库级并发竞争、真实模型行为或历史数据污染。文件名哈希仍沿用已有 DocMind 切片 ID 规则，同一个知识库内同名文档的版本语义属于另一个问题；不同用户的私有集合与临时文件路径分别限定。内部可信进程及数据库管理员权限没有改变。

## 结论和下一步建议

本次识别的匿名访问、附件越权、旧共享数据集入口、后台作用域、私有集合映射、公开 JWT 默认密钥和前端旧账号缓存问题已修复，并通过上述离线回归。项目的用户隔离基础仍是共享存储中的应用层 `user_id` 归属过滤，并对关联资源、缓存、文件与检索上下文保持作用域。

启用新代码前重启后端并重新登录；其他部署环境配置独立随机 JWT 密钥。部署前在隔离的测试环境运行已跳过的真实 PostgreSQL/Redis 集成，并完成实际索引服务端到端验证。如需保留旧共享或匿名数据，先核实所有权再迁移，不应直接按当前登录用户认领。
