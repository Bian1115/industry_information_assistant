## 1. 评估目标与概念

SSE是服务器通过一条持续打开的HTTP响应，向浏览器陆续发送事件的方式。例如：用户点击“开始研究”，浏览器发起请求；后端完成规划时发送进度事件，写完第一章时发送章节事件；浏览器收到章节内容后更新报告区域，用户可以在全文完成前阅读第一章。协议依据见[WHATWG SSE规范](https://html.spec.whatwg.org/multipage/server-sent-events.html)和[MDN说明](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)。

评估回答四个核心问题：用户是否更早看到有用内容，后续内容是否及时显示，断线后是否缺失或重复，最终交付是否完整一致。答案准确性、引用可靠性和研究深度另用内容质量评测衡量。SSE可能改善等待体验，但不保证模型更快生成或答案更准确。

本项目使用自定义POST流式请求和`after_seq`恢复游标；当前`frontend/src/api/session.ts`的`resumeResearch`由Axios的fetch适配器执行请求。不能把原生`EventSource`对象的自动重连能力直接当成本项目已经具备的能力，必须验证项目实际的恢复逻辑。

## 2. 核心指标与计算口径

| 维度 | 怎么测 | 需要排除的误判 |
| --- | --- | --- |
| 首次反馈 | 浏览器记录用户提交时间，以及首个有业务意义的进度文本可见时间，二者相减 | HTTP头、心跳、空文本不能算有效反馈；进度不能当正文 |
| 正文首显 | 首段有效正文在报告区域可见的时间减用户提交时间 | 后端开始生成、浏览器收到字节、前端更新内存对象都不等于页面已显示 |
| 逐步显示 | 统计完成前出现正文的运行数；逐章核对章节接收时间与对应页面显示时间 | 不能只检查最终全文；只提前显示第一段也不代表后续章节都及时显示 |
| 连续性 | 记录相邻正文更新间隔、每章接收至显示延迟，以及超过预设等待预算的次数 | 深度研究按章输出，检索和写作空窗不一定是传输卡顿；心跳不算正文更新 |
| 事件完整性 | 固定同一运行的核对终点，比较后端已提交事件序号集合E与前端成功应用序号集合A；缺失率为`|E−A|/|E|` | 事件收到但未成功应用不能计入A；失败运行只有前缀事件时，即使缺失为0，也不能判任务完成 |
| 重复与顺序 | 统计同一运行、同一页面重建代次内同序号重复应用；另检查章节ID、版本及正文显示顺序 | 同序号去重不等于同章节去重；同一章节重跑后可能获得新序号；合法内容修订应替换对应版本 |
| 故障恢复 | 规定观测窗内完整恢复的运行数÷注入故障运行数；分别测网络恢复→首个新增事件、网络恢复→缺口补齐、网络恢复→完成 | 超时必须留在分母；刷新后手动点击继续与自动恢复分开；节点重算时间与传输补齐时间分开 |
| 最终一致性 | 核对服务端最终报告、完成事件和前端报告数据一致；检查页面实际呈现正确、报告记录数量符合预期 | Markdown源文本与渲染后的HTML不应直接逐字比较；应比较同一表示的正文及关键展示内容 |
| 并发与资源 | 在固定事件大小、频率、任务时长下增加连接数，测延迟、连接错误率、CPU、内存、发送积压及关闭后资源回收 | 本机单用户低延迟不能外推为部署环境的并发能力 |

完成前正文可见率建议同时报告两个口径：①所有计划运行中的提前可见数，并列失败/超时数；②成功且确实有提前正文事件的运行中的提前可见比例。没有提前正文事件的运行单列，防止把后端不发正文与前端不显示正文混为一谈。

延迟至少报告样本量、P50和P95。P50是中间水平，P95表示约95%的样本耗时不超过该数值；小样本P95只能描述这些样本。以“运行”为统计单位衡量任务稳定性，事件级延迟可以另报，但同一次任务中的上千个事件不是上千次独立任务。

## 3. 怎样定位慢在哪里

测试程序让浏览器和后端记录同一章节的下列时间：

1. 浏览器：用户发起操作`t0`。
2. 后端：模型输出达到可发送的章节粒度`t_generated`。
3. 后端：该事件的数据库事务提交完成`t_committed`，以及事件交给HTTP响应层`t_send`。
4. 浏览器：解析出完整章节事件`t_received`。
5. 浏览器：报告区域中该章节的文本进入可见页面结构`t_visible`。

正文首显为`t_visible−t0`；前端显示延迟为`t_visible−t_received`。后端生成耗时应从其接收请求或对应写作阶段开始计量；`t_received−t_send`包含传输、代理缓冲和浏览器解析调度，不能叫纯网络延迟。跨机器时间相减必须校准时钟并报告误差，浏览器内的阶段耗时优先使用同一页面的单调时钟。

浏览器页面结构通常叫DOM，它是浏览器内存中的页面表示，不是磁盘文件。DOM可见时间是实用测量边界，仍不等于精确的屏幕像素首次显示时间；可用浏览器截图或渲染轨迹佐证。后端事件数据、用于查询事件的程序对象、数据库中已经提交的事件记录也要分开，不能把“放入程序内存待发送”计作“事件已经提交”。

## 4. 推荐实验设计

### 固定事件对照，先隔离显示收益

测试服务使用同一组事件内容、顺序、大小及生成时间表。A组在任务结束时一次显示全文；B组每次收到章节就显示。两组使用相同浏览器、网络、代理和并发条件；若比较两个SSE实现，则同样固定这些条件，交替运行旧版和新版。不要让不同模型回答、不同检索耗时成为唯一差别。

示例仅为解释，不是实测：同一任务第3秒产出第一章，第20秒产出全文。A组第20秒才显示，B组第3秒显示第一章、随后逐章更新；B组减少的是首次可读等待时间，全文生成仍约20秒。计算首显改善率时采用`(A首显−B首显)/A首显`，同时报告完整完成时间及失败率。

可以先复用项目五题夹具，分别覆盖首次发起和恢复入口，重复执行以发现抖动。该阶段验证传输与显示机制；真实用户延迟还需要固定问题集、模型、检索配置的真实研究运行，并补测实际代理链路。五题机制样本不能建立生产稳定成功率。

### 按场景验证正确性和恢复

| 场景 | 测试程序执行的操作 | 验证重点 |
| --- | --- | --- |
| 正常首跑与继续运行 | 从两个入口发送相同章节事件 | 第一章在完成前显示，后续章节及时到达页面 |
| 弱网与慢客户端 | 限制下载带宽、增加延迟，使用大章节载荷 | 是否突发成批显示、队列持续增长、内存无法回收 |
| 同事件重复 | 重发相同`run_id/seq` | 浏览器可重复收到，但同一页面代次只产生一次业务作用 |
| 同章节新事件 | 用新seq重发相同章节，并另外提供合法修订 | 同章不叠加；新版本正确替换旧版本 |
| 中间事件缺失 | 让传输层跳过若干已提交事件 | 浏览器通过事件查询接口补齐，正文顺序正确 |
| 完成事件丢失 | 丢掉末尾完成事件且不再发送后续事件 | 没有后续序号触发缺口时，客户端仍能对账终态 |
| 断网再恢复 | 在第一章显示后切断真实连接，离线指定时间，再恢复网络 | 保留真实断线证据；验证补齐、恢复时间和最终报告 |
| 刷新与重建 | 刷新页面，再执行产品规定的恢复流程 | 区分自动恢复与用户手动继续；旧事件重放不造成正文重复 |
| 长静默与大量历史事件 | 让后端长时间没有正文，或制造超过单页上限的缺口 | 连接保活、补齐分页、失败提示和重试边界 |
| 服务进程重启 | 单独测试后端进程退出再启动 | 事件补齐与计算状态恢复分开归因；依赖检查点的收益不能全部归给SSE |

恢复示例：浏览器已成功应用到第41号事件，断线期间后端提交了42～60号事件；连接恢复后，客户端携带41查询缺失事件，后端返回42～60，客户端按顺序应用。评估程序检查42～60是否全部补回，以及41是否被重复应用。若模型计算也中断，还需另测后端保存计算状态的检查点机制；SSE本身不负责恢复模型计算。

协议层另测UTF-8字符跨网络分片、一条事件跨多次读取、多条事件合并到一次读取、多行`data:`、换行格式和注释心跳。网络返回的一个字节块不必对应一个完整SSE事件，判定依据是[WHATWG事件流解析规则](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream)。

### 保存可追溯证据

每案保留版本及配置、运行ID、后端已提交事件、发送日志、浏览器接收和应用日志、页面显示时间、故障起止时间、最终正文、失败原因及截图。预先规定超时与成功条件，失败不能从统计分母中删除。沿用中文结果目录，原始JSON/JSONL保存在`backend/eval/data/`，报告保存到`docs/`。

## 5. 本项目历史结果及逐类分析

历史来源：[跨场景指标与一致性分析.json](../backend/eval/data/SSE浏览器真实链路评测-20261008-194700/跨场景指标与一致性分析.json)；完整配置和局限见[2026-10-08浏览器评测报告](SSE浏览器首显延迟去重与断线补齐评测结果及分析-20261008-194700.md)。这些结果来自本机Chrome、历史事件回放或确定性Agent夹具，没有使用真实模型生成，不能当作真实模型速度或生产网络指标。

| 历史场景 | 已测量结果 | 对评估方法的启示 |
| --- | --- | --- |
| 首次发起5案 | 最终交付5/5；完成前正文可见0/5；正文首显P50为6234.5ms | 最终成功不代表流式展示成功，必须单独设置提前可见判定 |
| 同序号重复注入 | 主评测5案、首跑补充1案，同代次重复应用均为0 | 受控样本验证了事件序号去重，仍需测同章节不同序号 |
| 缺口注入 | 主评测5案、首跑补充1案，最终已提交事件缺失均为0 | 支持这些小缺口样本的补齐，不代表大缺口或尾部完成事件缺失已覆盖 |
| 主评测断网 | 4/5完成；题目28在30秒观测窗内超时 | 即使已提交前缀无缺失，也不能将没有完成的任务判成功 |
| 连接清理复评断网 | 5/5交付，5/5出现过程章节重复 | 恢复成功与过程中显示正确必须分别评分 |
| 连接清理复评刷新 | 5/5交付，5/5出现过程章节重复 | 最终报告覆盖可能掩盖之前重复显示，必须检查过程 |

历史机器字段`strict_success`未要求正文在完成前显示，因此首次发起5/5的该字段不能解释为“流式体验全部通过”。建议新评测分开给出“事件正确”“提前显示”“恢复完整”“终态一致”，再按明确规则判断总体通过。
