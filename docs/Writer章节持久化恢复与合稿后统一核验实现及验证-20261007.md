# Writer章节持久化恢复与合稿后统一核验实现及验证

评估日期：2026-10-07（Asia/Singapore）。补充复评日期：2026-10-07。

评估对象：当前工作区 LeadWriter 正常逐章生成路径的章节持久化与恢复；全部章节合稿后统一调用引用核验。

实施口径：用户本次明确授权修改代码。基于现有单主图、AsyncPostgresSaver、节点级阶段保护与报告核验入口，新增节点内部的 LangGraph 持久化 task；不重构整张主图。源码包含用户已有未提交修改，本次仅在 Writer 的逐章生成循环增加章节保存与重放逻辑，并新增对应测试和故障验证脚本。

## 一、结果与边界

- 已实现：每章的正文和 claims 作为可序列化 task 返回值保存；后续章节或合稿失败时，恢复重入 write 节点，读取已持久化章节产物重建 draft_sections、section_claims、章节状态与参考文献，避免再次调用这些章节的生成模型。
- 已实现：章节产物标记引用核验尚未执行；全部章节生成并合稿后才调用原有统一核验入口，沿用具体运行的核验开关和失败处理配置。
- 已测量：120 项有效离线回归全部通过；一次真实 PostgreSQL、两个独立进程、SIGKILL 故障恢复通过；独立工作历史上下文传播检查通过。
- 间接推断：应用原有 PostgreSQL saver 会同样保存生产章节 task 的结果；主图拓扑及 recursion_limit 无需因本次 task 包装增加节点。
- 尚未评估：真实模型的 token/费用收益、HTTP/SSE 断连或浏览器端到端、数据库故障与竞争租约、外部调用完成但 task 结果尚未入库的瞬间中断。

保存的是 LangGraph task 的持久化返回值，属于检查点关联的任务结果；不是每章都另建一份主图完整 StateSnapshot。根图在中断后仍可显示 next=write，续跑通过任务结果重放复用章节。不能以根图 draft_sections 尚为空推断章节任务结果未保存。

## 二、实现位置与数据口径

主要实现：[writer.py](/Users/bxy/projects/industry_information_assistant/backend/app/service/deep_research_v2/agents/writer.py:520)。

逐章循环调用 _write_checkpointed_section，随后才执行 _synthesize_report。新增 task 名称为 writer_section_draft_v1，其返回值包括：

| 字段 | 含义 |
| --- | --- |
| version | 章节产物格式版本 |
| section_id | 章节稳定 ID |
| input_hash | 研究业务输入与写作配置指纹 |
| content | 生成并清理链接后的完整正文 |
| claims | 本章论断及引用原文编号声明 |
| citation_verification | not_evaluated，仅表示尚未执行统一引用核验 |

恢复时检查产物版本、章节 ID、输入指纹、正文非空及 claims 容器，再按章节 ID 覆盖对应条目，避免重复追加。参考文献从当前整份草稿重新生成。恢复章节通过现有 section_content 事件重新投影，带 restored 标记。

输入指纹包含业务研究状态、模型、章节提示词和写作参数；排除 node_attempts、runtime_budget、messages 等会随物理尝试变化的观测字段。运行字段与事件回调不作为 task 输入序列化，运行实例保留在闭包中。某章已有持久化结果但恢复时模型/相关配置变更，会明确拒绝静默复用。

直接调用 Writer、没有 LangGraph task 调度上下文的离线入口沿用普通 _write_section；不能把这种调用描述为支持持久化恢复。主服务的图内写作使用持久化 task。任务上下文识别与本地 LangGraph 1.x 运行协议对应，升级依赖时应复跑新增测试。

本次覆盖正常 _write_report 路径，包括补搜后再次进入正常写作。用户编辑的一次性整稿生成、Critic 定向修订方法没有在本次改造中增加章节 task，仍使用其原有节点提交边界。

## 五、真实 PostgreSQL 跨进程故障样例

验证脚本：[验证Writer章节跨进程恢复.py](/Users/bxy/projects/industry_information_assistant/backend/eval/scripts/验证Writer章节跨进程恢复.py)。

脚本创建独立测试 schema，部署 saver 所需表，只运行本脚本创建的两个子进程，结束后清理 schema。没有终止用户正在运行的服务或研究。

故障流程：

1. 进程 A 生成第一、第二章，进入第三章模型调用屏障并阻塞。
2. 控制进程从 PostgreSQL 读取 pending_writes，确认第一、第二章的正文与 claims 已提交。
3. 控制进程对 A 执行 SIGKILL，退出码为 -9。
4. 进程 B 使用相同 run_id、同一测试检查点 schema，重新构建图与 Writer，并以输入 None 续跑。
5. B 复用前两章，生成第三章，合成首尾，调用统一核验，再执行审核与终态节点。

| 指标 | 已测量结果 |
| --- | --- |
| 被杀前调用次数 | 第一章 1、第二章 1、第三章开始 1 |
| 新进程调用次数 | 第三章 1、首尾合稿 1 |
| 已提交前两章重复调用 | 0 |
| 复用章节 | sec_1、sec_2 |
| 恢复前后已保存正文及 claims | 逐项相等 |
| 完成章节数 | 3 |
| 合稿后统一核验调用 | 1 |
| 图执行终态 | completed |
| 隔离 schema 清理 | 成功 |
| 真实模型/搜索请求 | 0 |

这是一次有受控屏障的跨进程机制实验，确认的是“已入库章节结果能够复用”，不是所有随机崩溃窗口的成功率，也不是 token 节省或真实引用核验准确率。

## 七、“选合适的样本/轮次”的具体含义

样本就是用于测试的研究问题。选择某个样本，是为了让目标故障位置实际出现：

- 测章节恢复：选择需要至少四章的问题，才能在第三章保存后、第四章执行中注入故障。
- 测部分搜索恢复：选择需要多个查询或多个 URL 的问题。
- 测返工恢复：选择会触发 Critic 补搜或修订的问题，或用确定性假 Agent 固定要求返工。

“轮次”原表达不够明确，应分别记录：

| 名称 | 含义 | 例子 |
| --- | --- | --- |
| 实验重复次数 | 同一问题、同一故障计划重复几次 | 每次新建 run，重复 3 次 |
| 业务返工轮次 | 一次研究内部第几次审核后的补搜/修订 | 第一次补搜时中断 |
| 对话轮次 | 同一会话中第几条用户追问 | 第二个追问要求补充章节 |

例如，“五章固定任务，每次在第三章确认入库后中断第四章，新建 run 重复三次”，就清楚说明了样本、故障点和重复次数。它不要求必须进行多轮对话。本次实际跨进程实验是三章任务，前两章入库后在第三章调用中中断，仅执行一次。

## 八、局限性、结论与下一步

本次未测量真实模型的文本差异、token、费用和延迟；没有验证网络断线、浏览器刷新、数据库故障、竞争租约或终态补交付。task 结果尚未提交的外部调用仍可能在恢复时重复，不能承诺外部 API exactly-once。新增检查点保存章节正文与 claims，不表示这些声明已被原文支持；是否核验及怎样处理失败仍由具体运行的配置决定。

章节 task 的输入包含当前完整业务快照，后续可将大型证据材料改为不可变引用，测量检查点存储开销后再优化。本次没有为节省存储裁剪原文或章内容。

结论：已实现正常逐章生成产物的持久化复用，并通过真实 PostgreSQL、SIGKILL 与新进程续跑验证；完整报告组装后统一核验的顺序保持成立。建议下一步用固定四至六章样本，在更多写入边界重复注入故障，并另测真实模型资源收益；若需要编辑/修订路径也支持章节恢复，可按其不同输入契约单独扩展。
