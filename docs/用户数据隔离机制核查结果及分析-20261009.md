## 失败样例与潜在越权路径

以下为源码推导的缺口样例，未发送真实请求、未读取或删除任何其他用户数据。

1. 用户 B 或匿名调用者持有用户 A 的有效会话 ID，调用 `POST /attachments` 或 `GET /attachments/session/{session_id}`：代码只验证会话存在及有效期，未验证属于当前用户。
2. 用户 B 或匿名调用者持有 A 的附件 ID，调用 `GET /attachments/{attachment_id}`：详情查询仅校验附件 ID 和会话有效期。调用 `DELETE /attachments/{attachment_id}` 时，删除查询仅按附件 ID，亦未验证归属。
3. 调用 `/documents/list`、`/documents/retrieve`、`/documents/delete`：路由没有用户认证及用户作用域，使用服务配置的默认数据集。实际可读取/删除内容及外部服务状态尚未验证。

UUID 难以猜测不等同于归属校验；上面的缺口也不等同于已完成真实攻击复现。

## 结论与下一步建议

**项目的核心用户数据主要通过 `user_id` 隔离，但当前代码没有做到所有接口一致隔离。** 消息、知识库文档等子资源还通过已校验的会话或知识库归属间接隔离。

建议优先为附件接口增加必须认证及资源归属检查；明确旧文档接口是否应保留，如保留则补充访问权限和数据集作用域。之后使用两个测试用户及匿名身份验证读、写、删除与研究恢复的边界。本次仅回答现状，未实施这些修复或执行测试。
