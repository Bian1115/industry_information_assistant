## 用一句话理解

让模型先给一份答案，再通过搜索、执行代码等方式检查，写出有依据的修改意见，最后据此修订答案。

可以把它理解成“写初稿—查证—写批注—修改”。CRITIC是一套推理时流程；模型参数保持不变，通常由同一个模型承担回答、检查与修改。检查能力依靠示例提示词和外部工具反馈。

## 怎样实现

以下依据[官方问答代码](https://github.com/microsoft/ProphetNet/blob/master/CRITIC/src/qa/critic.py)、[数学代码](https://github.com/microsoft/ProphetNet/blob/master/CRITIC/src/program/critic.py)、[去毒代码](https://github.com/microsoft/ProphetNet/blob/master/CRITIC/src/toxicity/critic.py)和[问答提示词](https://github.com/microsoft/ProphetNet/blob/master/CRITIC/prompts/hotpot_qa/critic.md)，读取日期为2026年10月17日，未固定提交哈希。

1. **产生初稿。** 问答先生成带推理说明的回答；数学题先生成求解程序。
2. **检查并获取反馈。** 把原问题和当前答案放进检查提示词。问答要求检查是否切题、是否有事实依据，并允许多次搜索。
3. **写具体批评。** 反馈应说明哪里有问题，以及根据什么证据判断。一次检查可包含多次“模型提出查询—程序执行搜索—返回证据—模型继续检查”。
4. **修改并再次检查。** 模型结合问题、旧答案与批评生成新版；达到停止条件或轮数上限时结束。

工具可以统一包装成文本输入、文本输出：

| 任务 | 工具输入与反馈 | 修改方向 |
| --- | --- | --- |
| 事实问答 | 搜索词 → 检索证据 | 修正事实、补全推理所需信息 |
| 数学程序 | Python代码 → 报错及计算结果 | 修复代码、检查计算与题意 |
| 文本去毒 | 续写内容 → 有害内容属性及分数 | 按反馈改写，再评分 |

问答代码使用 `> Search Query:` 等文本标记识别工具请求，并在 `> Evidence:` 前停止模型生成；程序执行搜索后插入结果，继续调用模型。提示词中给出完整示例，展示如何查询、解读证据和修订。这让模型学会流程，实际工具执行仍由外部程序完成。

数学代码把执行报告和 `answer` 值放入上下文，先调用模型生成批评，再调用模型生成新程序，随后执行新程序。正常执行只提供了一种反馈，程序是否符合题意仍要检查。

去毒代码直接把外部评分改写成反馈，依据最高分属性指导改写；当总分低于阈值时停止。该实现还会保留没有被新版改善的旧候选。三类任务的检查形式并不完全相同。

## 一个教学例子

以下为自拟例子，没有调用模型运行。

题目：20名学生中，20%选A课程，其余学生的25%选B课程，剩下的选C课程，C占全班多少？

如果初稿写 `100 - 20 - 25 = 55%`，代码可以正常执行。真正需要指出的批评是：“25%的分母是剩余的16人，B有4人，C有12人，应为60%。”

它说明反馈的两层作用：工具给出可观察结果，模型还要判断结果与题意是否一致。报错、反常数值比较容易暴露问题，合理范围内的错误更容易漏检。

## 最小工程流程

以下为表达方法的伪代码，接口尚未实现，本次未执行。

```python
answer = generate(question)
for _ in range(max_rounds):
    # 内部循环：模型提出查询，程序执行工具并返回真实结果。
    critique = verify_with_tools(question, answer)
    if critique.satisfied:
        break
    answer = revise(question, answer, critique)
return answer
```

`satisfied`在这里代表检查流程给出的停止信号，不能视为客观正确性证明。工程上可用结构化函数调用承载请求，并保存问题、每版答案、工具证据、批评和修改关系；这些是接入选择，不是作者必须使用的JSON协议。

## 作者实验结果及逐类分析

**以下均为作者已测量、本次未复现。** 表1中历史版gpt-3.5-turbo在三个问答验证集各抽取500题，最多修订3轮，每轮最多7次工具交互；下表均为答案级F1分数。

| 数据集 | CoT初稿 | CRITIC | 无真实工具反馈 | CRITIC相对初稿 |
| --- | ---: | ---: | ---: | ---: |
| AmbigNQ | 64.3 | 74.9 | 67.3 | +10.6分 |
| TriviaQA | 79.2 | 81.7 | 79.9 | +2.5分 |
| HotpotQA | 42.8 | 52.9 | 46.1 | +10.1分 |

三个任务中，真实工具反馈的成绩都高于无工具消融。这里的F1比较答案与参考答案的词项重合，不能换写为整篇报告事实准确率；无工具消融保留检查提示，但让模型生成“证据”，也不同于所有可能的纯模型反思方案。

数学表2中，gpt-3.5-turbo在GSM8k上的准确率从PoT的72.5%提高到78.2%。同表text-davinci-003在SVAMP上从84.0%降至80.7%，说明收益并非逐模型、逐数据集都为正。数学指标是数值答案匹配，与上述F1分开解读。

## 局限性与证据边界

- **已测量：** 作者在论文历史模型和数据口径上的成绩；本次核对了部分成绩与失败案例。
- **已核查：** 官方问答、数学、去毒流程以及问答示例提示词。代码核查为静态阅读，不保证当前依赖下可直接运行。
- **间接推断：** 同样的证据反馈思路可用于行业研究草稿检查，但接入效果需要实验确认。
- **尚未评估：** 本项目收益、当前模型表现、长篇中文报告准确性、延迟和费用。

工具可以带来新证据，模型仍可能误读证据或误解题目。轮数增加也会增加模型和工具调用，停止条件只能控制流程，无法保证答案正确。论文指标不能直接迁移为本项目简历指标。

## 结论和下一步建议

值得学习的是让批评与可追溯的证据、执行结果联系起来，再把反馈交给修订步骤。用于行业研究时，可以先围绕具体事实或计算组织“论断—证据—问题—修订”，保留证据不足状态，允许维持有依据的原答案。

若后续接入本项目，应固定同一批问题、模型和预算，对比初稿、纯模型检查、工具辅助检查；分别统计修对、改错、漏检、拒答及额外成本。本次仅提出该验证方案，没有执行。
