# 检查点恢复评测集设计及现有证据缺口分析

评估／分析日期：2026-10-15，Asia/Singapore。

评估对象：本项目 DeepResearch 检查点恢复评测集的设计，以及已有恢复证据能够支持的结论。当前工作区图版本为 `single-main-v5-session-evidence`。

本次只读核对已有机器结果、相关源码和官方资料，提出待实施方案；没有新增模型请求、搜索、数据库故障注入、SIGKILL 或浏览器实验。以下题量、验收条件和实验分组均为设计建议，不是已经完成的评测集或新的恢复实测结果。

## 一、结论

有效的基本样本应为：**业务任务 × 可验证的故障窗口 × 故障方式／调度 × 预期恢复行为**。只收集研究问题、只在一个节点停机，或者只检查最后有无报告，都不足以评价检查点恢复。

建议构建两层数据：

1. **确定性机制集**：固定模型／工具响应，使用真实持久化存储与新进程恢复，精确断言结果复用、状态一致、预算保留、租约隔离和交付幂等。
2. **真实任务效果集**：覆盖检索、长证据、多章写作、返工和追问，以配对对照衡量时间、费用和独立任务质量。

两层单独报告，机制用例数不能与真实任务数混成一个成功率。对于不兼容配置、权限错误和损坏存档，另报正确拒绝／受控失败，不计恢复成功。

## 四、确定性机制集：按恢复契约选场景

固定的响应应包含有 ID 的事实、来源、章节、claims 和模拟 usage，能够精确追踪哪些成果已经真正持久化。用数据库确认提交，不能用“函数返回”或一条日志代替提交证明。

| 场景族 | 具体故障窗口／方式 | 必须预先写出的预期行为 |
| --- | --- | --- |
| 节点中断 | 搜索或分析节点执行一半时异常、SIGKILL | 回到最后可靠边界；未持久化部分允许重做，已提交输入与成果不丢失 |
| 待合并结果 | `aput_writes` 提交后、完整 `aput` 提交前 SIGKILL | 合并已保存成功结果；不因 `next` 为空就拒绝，不重新生成同份结果 |
| 完整检查点 | 完整事务提交后、下一节点开始前终止 | 从后继工作继续；上一节点的模型／工具计算不重做 |
| 章节复用 | 第二章 task 已提交、第三章进行中时终止 | 前两章正文、claims、来源关系均复用；第三章依约重做；原调用消耗仍在账本 |
| 外部结果不明 | 供应商已受理或完成，客户端超时／崩溃，结果未保存 | 标记未知状态，保留预算预留；有幂等键／查询能力时核对，不能宣称外部调用恰好一次 |
| 外置证据 | 证据已提交而图尚未提交；依赖暂不可用、缺失或哈希不符 | 验证引用可解引用及内容身份；按预定规则重试、重建或明确失败，禁止静默当作空证据继续 |
| 预算恢复 | 已计费节点失败、失败后再恢复、并发预留 | 已知消耗不因图回滚归零；未知预留不被清除；剩余额度由独立账本约束 |
| 交付前中断 | 终态检查点已提交、报告事务前终止 | 只补交付；新增模型和工具请求为 0；报告、消息、完成事件一致 |
| 交付后丢响应 | 报告事务提交后，客户端收到响应前终止／断线 | 重试返回同一交付身份，不新增正式报告或完成事件；事件回放不算新写入 |
| 并发接管 | 双恢复请求；旧租约过期、新执行器接管后旧进程迟到 | 新持有者可推进，旧 token 的 checkpoint／pending writes／交付被拒绝 |
| 存储故障 | 保存中断连接、事务内到期、提交成功但客户端未获确认 | 不暴露半提交状态；重试不污染已提交成果；恢复判定依赖数据库事实 |
| 多次中断与兼容性 | 同一 run 连续中断 2～3 次；不支持配置、错误用户、存档损坏 | 累计进度与预算不回退；拒绝场景无越权读取或副作用；拒绝率独立统计 |

每个适用场景覆盖关键提交前后窗口及至少两种明确调度，例如“旧写先到／接管先完成”。先用可控屏障定位事务边界，再增加带种子的随机延时／SIGKILL。随机实验不能代替已知边界覆盖。

硬崩溃必须由独立控制进程终止专用 worker，再由新进程通过生产恢复入口续跑；正常抛异常的清理路径可能掩盖硬崩溃问题。使用隔离数据库／schema，记录实际迁移版本和启用的持久化模式，不改动正在运行的研究。

## 五、真实任务效果集：建议 6 类、每类 2 题

任务应具有明确交付约束、可核对的事实／引用清单和足够多的已完成工作。每题至少包含多次工具操作与三章写作，以便观察章节复用。下列是选题模板，不代表已经采集完成。

| 类别 | 两道题的结构示例 | 重点观察 |
| --- | --- | --- |
| 多来源研究 | 比较两个行业方案；梳理一项技术的产业链 | 任务约束、来源 ID 与已有事实能否保留 |
| 多轮检索与阅读 | 必须组合多次检索解答的问题；须从附件与网页交叉验证的问题 | 搜索预算、已读结果、工具调用重复 |
| 长证据与外置内容 | 需要大量封存网页／PDF 的综述；包含互相矛盾来源的核对 | 原文解引用、证据边界、跨存储一致性 |
| 多章写作 | 规定章节及每章引用的研报；多对象对比报告 | 章节及 claims 复用、合稿完整性 |
| 审核返工 | 提供可被发现的遗漏以触发补搜；提供冲突证据以触发修订 | 业务返工与技术重复计算的区别，轮次／修订进度 |
| 追问继承 | 沿用上轮成果增加比较对象；保持历史限制条件完成深化研究 | 同一研究 run 的恢复与新追问的边界，继承快照和隔离 |

每题保存问题、来源快照及哈希、预期必答点、关键数字与出处、禁止丢失的约束、预算配置、可达故障窗口和质量评分表。主实验冻结检索／网页／附件内容；另设少量实时联网外部有效性实验，避免把搜索结果变化误归因于恢复。

正式方案将 12 题按业务任务分为 4 题开发、8 题留出测试，覆盖各类并交叉分配长短难度。同题的不同故障窗口、重复实验及同一父会话都留在同一分组，防止在开发集修好后把同题变体当成独立新测试题。

### 六个主故障窗口及建议规模

1. 搜索节点执行中，已有部分调用消耗。
2. 一个节点的 pending writes 已提交、完整检查点提交前。
3. 完整检查点已提交、下一节点执行前。
4. Writer 前两章 task 已提交、下一章执行中。
5. 终态检查点已提交、业务交付事务前。
6. 业务交付事务已提交、响应到达客户端前。

12 题 × 6 窗口 × 2 次重复，最多 144 个故障情景；其中开发集 48 个、留出测试集 96 个，分开报告。这个数量不包含对照组和额外的并发／存储专项，也不是 144 个独立业务任务。必须实际命中窗口；未命中记为注入无效并报告，禁止算恢复成功。若任务无法到达某窗口，应先调整任务或如实报告未覆盖，不能补造结果。

低成本起步先做 4 道开发题 × 4 个窗口（搜索中、节点待合并、章节保存后、交付前）× 2 次，共 32 个故障情景。它用于发现问题与校准实验，不足以宣称生产级可靠性。机制集通过后，再扩大到留出集及随机故障；按失败率和置信区间需求追加样本，不能先定一个漂亮的成功率再挑题。

## 六、对照实验：把机制、收益和质量分别验证

| 组别 | 执行方式 | 与谁比较、回答什么 |
| --- | --- | --- |
| A | 无故障，不保存图检查点 | A/B：正常保存开销 |
| B | 无故障，启用生产持久化配置 | B/D：故障后质量是否变化 |
| C | 指定窗口发生故障，随后从头重跑 | C/D：恢复相比重跑省多少 |
| D | 同任务、同故障前缀，从检查点恢复 | 检查恢复契约及最终交付 |

C/D 优先从同一份崩溃前隔离存储快照分支，两分支保留相同故障前消耗；D 保留可恢复成果，C 按事先声明的“从头重跑”产品策略执行。不能复制一份图快照而遗漏预算、外置证据、运行身份和交付状态，也不能让两个分支共享可变缓存或租约。若尚无经过验证的分支工具，可独立复跑相同前缀并证明其可比性，降低配对强度的结论等级。

对于第六个窗口，恢复本就应只回读已交付结果；C 的用户重跑是特定对照策略，不能把这个末端特例当成所有中途恢复的平均收益。

A/B 保持同模型、同工具数据和同预算规则。当前正式交付需要检查点证据，若无法在保持其他工作相同的条件下关闭检查点，则先独立测 saver 的耗时／写入量；注明它是组件开销，不冒充纯粹的端到端开销。改变其他存储、交付或预算路径会造成混杂。

真实模型即使设置温度为 0，也不能保证逐字相同。固定响应集可要求确定性产物完全相等；真实任务只要求已保存前缀、关键状态和交付身份精确保持，后续文本用统一必答点、事实正确性、引用支持率和独立盲评比较。提前确定质量允许差值，不用流程自己的 Critic 分数代替外部质量评价。

## 七、建议指标、分母与验收口径

| 指标 | 定义／口径 |
| --- | --- |
| 有效故障恢复成功率 | 在指定观察期限内满足恢复契约且完成技术交付的次数／范围内所有有效注入次数；再次崩溃、超时和预算耗尽分别标记，不隐去失败 |
| 任务可交付率 | 在全部有效恢复情景中，技术交付并通过独立质量门槛的比例；与技术恢复成功率并列 |
| 已保存成果保留率 | 恢复入口及首次后继工作前核对已提交成果的 ID、内容哈希、来源关系；允许后续按业务规则修订，保留版本／血缘 |
| 重复计算 | 恢复后对同一逻辑工作单元、相同输入版本、已持久化输出再次发起的模型／工具计算数及 token；单列未保存工作的合法重做和业务返工 |
| 恢复时延 | 分开测故障到服务可用、请求到状态就绪、请求到首个新工作、请求到交付；列出租约等待。终态补交付没有“首个新节点”，单列补交付时延 |
| 时间／费用节省 | 故障后增量收益为 `1 - D/C`；另报包含共同故障前消耗、失败重试和持久化成本的全程总收益。失败无交付时不使用低费用冒充高效率 |
| 状态与交付一致 | 关键任务约束、事实／证据、章节／claims、迭代进度、预算及交付身份全部满足预定不变量；每 run 正式交付一份 |
| 正常持久化开销 | 可比 A/B 的耗时差、checkpoint 写耗时、数据库／存储写入量与存储增长 |

重复计算用稳定逻辑身份判断，例如节点、业务轮次、章节 ID、输入版本／哈希；不能只看函数进入次数。节点函数重放但复用 task 输出不等于模型重复调用；同一章节在 review 后修改了输入的重新生成属于返工。

未知供应商 usage 应分别记录已知实际 token、保守预留、未知请求数，报告费用可知范围；预留不是实际账单。模型、搜索、embedding／rerank、NLI 等若未全部接入计量，明确费用覆盖范围。

按故障族／窗口和业务任务逐项报告成功数与总数，不先汇成一个平均值。时延同时列出失败数与超时；小样本给逐条值、中位数和范围，不能将其包装成生产 P95。同一题的多窗口和重复运行具有相关性，置信区间应按业务任务聚类，不能把 144 个情景全当独立任务。

适合用作机制验收的硬条件：已确认持久化成果丢失 0、已保存结果的重复生成 0、额外交付 0、已知预算不漏记、接管后旧 token 成功写入 0。其保证范围以冻结的场景和版本为限；供应商结果未保存窗口不要求不可能证明的外部请求恰好一次。

## 九、失败样例与可检测性

1. **历史入口误判**：原题 26 出现 `next` 为空但成功 Writer 结果仍待合并。应由“待合并结果”样本发现；只构造普通非空 `next` 样本会漏测。
2. **历史有正文未交付**：原题 28 终态检查点有正文，正式报告／完成事件缺失。应由“终态后、交付前”样本发现；只读检查点正文会把失败判成成功。
3. **已修复的预算回退**：失败尝试消耗 100、续跑消耗 40 时只显示 40。专项已验证累计 140；应固化为常驻回归，防止图快照覆盖独立账本。
4. **已修复的旧执行器写入风险**：接管后旧进程迟到提交。最新专项已验证拒绝完整 checkpoint 与 pending writes；需要保留新旧进程调度证据。
5. **待新增的外置证据失败样本**：检查点仅存证据 ID，而对应原文被删除或不可读。它是设计中的反例，本次没有实测当前系统出现该故障；不能只校验事实 ID 存在。
6. **质量失败不等于恢复失败**：历史题 8、25 技术完成却仍需修订。须让技术恢复与独立交付质量分别出分，并与 B 组配对后才讨论质量变化原因。
