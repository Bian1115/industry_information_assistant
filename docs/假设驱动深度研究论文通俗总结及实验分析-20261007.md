## 通俗总结

HDRI 把假设当作组织研究的工具：先提出待核查判断，再收集证据，并根据缺口补查。论文的八阶段为：问题理解 → 假设生成 → 研究规划 → 搜索 → 事实抽取 → 分析推理 → 报告 → 保存；分析阶段可返回搜索。作者在 InfoMiner 中以现有模型和模块化流水线实现这一思路。[论文第 3—5 节](https://arxiv.org/html/2605.10224v1)

以下例子和实现方案是本次整理的工程建议，不是作者的具体运行记录、源码复现或效果结论。

例如，用户想知道“甲公司的利润增长来自哪里”，可以先提出几个待验证解释：卖得更多、单件成本降低、出现一次性收益。这些解释分别决定需要找销量、成本和利润构成的资料。查询不是为了让某个解释成立；证据也可以否定它。

“销量增加”和“利润增加”同时发生，只说明它们可能有关。要说销量是主要原因，还需要利润构成或其他足以排除替代解释的证据。发现这一缺口后，系统应补查相关资料；找不到时，就明确保留不确定性。

## 如何做出可用的实现

### 1. 把研究过程存成可更新的记录

最小状态可包含五类记录：

| 记录 | 建议保存的信息 | 作用 |
|---|---|---|
| 研究目标 | 用户问题、研究对象、时间范围、必须回答的要点 | 检查有没有偏离任务 |
| 假设 | 编号、待验证判断、验证条件、推翻条件、当前状态 | 确定查询为什么要做 |
| 证据 | 编号、原始网址、原文片段、主体、发布日期、数据所属期间 | 支持核查和追溯 |
| 判断 | 对应假设、支持与反对的证据编号、简短推导依据、未解决问题 | 避免证据和结论脱节 |
| 缺口 | 缺少什么、为什么重要、补查问题、优先级 | 驱动下一轮调查 |

这些信息可以先保存在 JSON 或数据库中。数据库和编排框架可以按项目需要选择；只有存储结构清楚，后面的检查才容易实现。

### 2. 模型负责语言任务，程序负责约束

用现有 LLM 分别执行“生成待核查判断”“把判断拆成查询”“从网页抽取证据”“判断证据关系”“识别缺口”和“撰写报告”。每一步返回结构化数据，程序校验必填字段、编号引用和状态枚举。

提示词需要说明：假设只是待查判断；同时寻找支持、反对和替代解释；不得用模型常识伪造证据；证据不回答问题时，标为不相关或无法判断。程序要拒绝引用不存在的证据编号。

### 3. 搜索后读取原文并做主体和时间检查

调用搜索接口找到页面，再读取正文，保留支持具体论断的片段。标题和摘要可用于定位线索，强结论应尽量绑定可读原文。

确认资料说的是同一家公司、同一个人或同一个产品。比较数字时还要确认期间、币种、单位和统计范围。网页发布日期与数字所属期间分开记录，不能因为新闻较新就认为其中所有数字都是最新数据。

转载同一公告的多篇新闻，应尽量归到同一证据来源组。五篇转载不能自动算成五份独立佐证。

### 4. 建立证据与假设的对应关系

每条证据标为“支持”“反对”“不相关”或“无法判断”，并绑定假设编号。把直接观察到的事实与根据事实作出的推断分开保存。

建议展示证据强弱与待核实原因。若使用数字置信度，必须说明是质量分还是经过校准的概率。不能仅因模型输出 0.9，就宣称判断有 90% 的正确概率。

### 5. 对重要缺口做有限补查

缺口检查应同时对照用户要求和假设；否则假设本身漏掉的方面，也可能永远不会被发现。

可以先采用“最多两轮补查、每轮最多四个新查询”的试验配置，并按任务成本调整。新增资料需要合并、去重和重新判断。没有重要缺口、达到预算或连续没有获得有效新证据时，停止补查，并记录停止原因。

概念伪代码如下；本次未将其写入业务系统或执行：

```python
def research(question, tools, llm, max_gap_rounds=2):
    state = define_scope_and_requirements(question, llm)
    state.hypotheses = propose_testable_hypotheses(state, llm)
    tasks = make_initial_queries(state, llm)

    for round_id in range(max_gap_rounds + 1):
        pages = tools.search_and_read(tasks)
        evidence = extract_and_validate_evidence(pages, state, llm)
        state = merge_and_deduplicate(state, evidence)
        state = assess_support_and_conflicts(state, llm)
        gaps = find_gaps_against_requirements_and_hypotheses(state, llm)

        if not important(gaps) or round_id == max_gap_rounds:
            break
        tasks = choose_new_queries(gaps, limit=4)
        if not tasks:
            break

    report = write_with_evidence_ids_and_uncertainties(state, llm)
    validate_citation_bindings(report, state)
    save_state_and_report(state, report)
    return report
```

函数名表示职责，不代表已存在的库接口。两轮和四个查询是一个可调整的起点，不是效果保证。

### 6. 报告必须能回答“依据是什么，还有什么不知道”

按用户问题组织报告，对每个重要判断显示证据、反证与状态。用户要求要点的覆盖情况与假设状态分别检查：假设得到验证，不代表所有要求都已回答。

每条强事实应能定位到证据片段；有争议的判断说明争议；未解决的缺口留在报告里。把报告、中间状态与检索记录一起保存，方便检查研究为何得到当前结论。

## 失败样例与一致性检查

### 已核查的报告口径问题

按表中显示值复算，FD 的相对变化是 `(10.1-8.2)/8.2 = 23.17%`，与表中标注的 22.4% 不一致。未获得更高精度的底数，不能确定具体原因。这是表格算术核查，不是效果复现。

按消融表显示值，RC 相对增加约 14.67%，绝对增加 0.11；耗时相对增加约 30.77%。论文成本分解中的 7.8% 是某阶段占总耗时的比例，与开启/关闭补查的相对耗时差不是同一分母。用它们说明成本时需要区分。

### 尚未运行的机制失败样例

- **确认偏差**：假设“增长来自降本”，只搜索降本报道，遗漏一次性收益。应要求反证与替代解释。
- **虚假多源**：多篇新闻都来自同一公告。应按来源关系去重，再评估佐证强度。
- **因果跳跃**：销量和利润同时上涨，就写成销量导致利润增长。应补查利润构成或降低结论强度。
- **补查空转**：不断换同义词搜索，却没有新增证据。应根据有效新增证据停止。

这些是构造的风险示例，不是本次测得的 InfoMiner 失败样本。

## 局限性、结论与下一步建议

本次没有作者逐题原始结果，也没有执行系统，因此只能解释方法并核查论文口径。论文主结果的模拟性质尤其限制了效果判断。

方法值得参考的地方是把研究目标、待验证判断、证据、缺口和结论明确关联。是否适合本项目，需要真实对照数据，而不能直接采用论文摘要的提升百分比。

若下一步实施，先建立证据绑定和缺口记录，再单独增加假设指导。在相同模型、搜索资源和总预算下，对比基础流程、仅加假设、仅加补查以及两者同时启用，才能区分不同机制的贡献。评估重点应包括事实正确性、用户要求覆盖、反证处理、引用支持和实际成本。本次只提出方案，没有启动这些评估。
