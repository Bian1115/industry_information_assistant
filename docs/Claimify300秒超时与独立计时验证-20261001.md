# Claimify 300 秒超时与独立计时验证

日期：2026-10-01。对象：历史摘要生成及 Claimify 审计的超时配置与阶段耗时埋点。本次为前次摘要生命周期改造的补充验证，未覆盖历史结果，也未重跑真实研究任务。

## 当前配置与改动

`backend/.env`、`.env.example`、运行时配置默认值均已将 `AGENT_SUMMARY_CLAIMIFY_TIMEOUT_SECONDS` 从 120 改为 300。摘要生成超时保持 120 秒，Claimify 开关保持关闭：

```dotenv
AGENT_SUMMARY_CLAIMIFY_ENABLED=0
AGENT_SUMMARY_GENERATION_TIMEOUT_SECONDS=120
AGENT_SUMMARY_CLAIMIFY_TIMEOUT_SECONDS=300
```

没有重启现有服务。后端重新加载后，新运行使用此配置；已经冻结的运行策略按其保存的配置继续执行，环境变量不覆盖历史快照。显式消融配置文件仍优先于环境变量。

300 秒是 Claimify 的阶段超时上限，提前完成时立即结束。它覆盖该阶段的分句抽取、引用定位及按配置启用的核验，生成阶段有独立的 120 秒限额。

## 埋点保存口径

`summary_phase_start/end` 使用 `phase=generation` 和 `phase=claimify` 分别记录阶段开始、结束及实际 `duration_seconds`，通过同一个 `summary_attempt_id` 关联。阶段结束事件记录成功、失败或取消状态；错误保留异常类型。

保存的摘要元数据中分别记录 `generation_duration_seconds` 与 `claimify_duration_seconds`。生成结束事件和元数据现使用同一个测量值，避免写入埋点所花的时间造成二者差异。Claimify 的耗时在审计结束时确定，随后保存审计元数据，仍保留已有摘要与覆盖游标。

Claimify 关闭时，记录 `summary_claimify_skipped`，其 `phase=claimify`、`status=disabled`、`duration_seconds=null`；元数据的 `claimify_duration_seconds` 也为 null，表示没有执行该阶段。两段耗时使用单调时钟，不是供应商计费时间。

## 逐类验证与失败样例

已测量：

1. 加载实际 `.env` 后选中的新运行策略为生成超时 120 秒、Claimify 超时 300 秒且开关关闭；配置类本身的 Claimify 默认值也为 300 秒。
2. 关闭审计时不发起 Claimify 请求，跳过事件和元数据均使用 null 表示没有执行，成功摘要仍提交并保留原文。
3. 模拟审计超时样例中，生成耗时约 0.00376 秒，Claimify 耗时约 0.02154 秒，分别保存到阶段事件；测试同时检查它们与元数据中的数值完全一致、尝试编号相同。审计上限在该测试中特意设为 0.02 秒，不能把样例耗时当作真实模型表现。
4. 模拟生成超时不推进游标；审计超时记录 `TimeoutError`，保留已提交正文和游标；取消继续传播；提交失败时不开始审计。
5. 历史五题冻结策略恢复后仍保持其原配置哈希，没有因新默认值被修改。

模拟超时是预期失败样例，相关测试通过；本次没有未修复的测试失败。

## 局限、结论与下一步

间接推断：更长的审计上限给串行模型请求更多完成时间，但不会降低 token 成本。

尚未评估：真实 Claimify 在 300 秒内的完成率、真实模型耗时分布、真实 PostgreSQL 的新计时数据落库及设备休眠情况下的墙钟行为。此次跳过的数据库集成测试不应计为已验证。

本次配置与埋点要求已实现。当前仍关闭 Claimify；后续开启并运行真实任务时，可按尝试编号分别统计生成与审计耗时、超时率和 token 成本，再判断 300 秒是否合适。
