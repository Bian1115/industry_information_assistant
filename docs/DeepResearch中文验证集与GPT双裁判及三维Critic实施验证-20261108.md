### 数据校验中发现的原始差异

初次装配时，严格的一致性检查拦截了官方第1题：题目和细则写的是“中国所有阶层”，官方清洗后参考报告携带的任务文本写的是“中国9阶层”。核对后确认30题的原题与细则完全一致，只有这份参考报告的任务文本存在上述差异。

程序保留官方文件原文，并将差异写入`抽样清单.json`的`reference_prompt_differences`。本轮独立评分只读取原题、细则和项目生成报告，不使用参考报告给事实背书，因此没有为消除差异而改写研究问题。这项数据准备失败及处理不代表研究Agent失败。

研究服务只应读取`验证题目.jsonl`。`评分专用材料`目录中的细则和参考报告供离线分析使用，不能注入受测Agent的输入或可检索资料库。

## 二 GPT与Claude双裁判

本轮当前入口：[评分DeepResearchBench生成报告.py](../backend/eval/scripts/评分DeepResearchBench生成报告.py)。通用实现：[报告双裁判.py](../backend/eval/报告双裁判.py)。

用户选择的GPT型号是`gpt-6-astra`，Claude继续读取现有`CLAUDE_RELAY_MODEL`等配置。GPT配置独立于研究服务的Qwen配置，不会把生成、检索、摘要或引用核验中的其他Qwen调用一并替换。

| 项目 | 本轮口径 |
| --- | --- |
| 待评对象 | 项目生成并冻结的最终报告 |
| 裁判 | GPT-6 Astra、现有Claude配置 |
| 重复次数 | 每位裁判独立评两次 |
| 离线维度 | 全面性、洞察力、指令遵循、可读性，沿用官方逐题细则 |
| 分数尺度 | 0—10分 |
| 汇总 | 维度内按细则权重归一化，再按官方维度权重加权；先平均各裁判两次，再平均两裁判 |
| 在线分数 | 单独保存在`online_critic`，不参与离线融合，不发送给独立裁判 |
| 缺失结果 | 未完整完成两位裁判各两次时，不产生双裁判融合分 |
| 续跑 | 只复用输入与参数指纹完全一致的有效评分，补未完成评分，不重跑报告生成 |

评分规则和虚构评分锚点沿用现有逐细则体系。当前入口校验细则ID完整性、分数范围、摘录是否为正文连续原文，以及服务响应是否完整结束。Claude本轮要求原生JSON，不新增格式兼容或截断响应恢复分支。裁判原始响应、请求参数、用量、失败尝试和加权结果均保存到本地。

GPT使用Responses API的严格JSON结构输出，并保留原Qwen质量评分的`xhigh`推理档位；上限为32000个输出token。没有沿用原请求中的`enable_thinking`、`seed`或`temperature`参数。接口依据：[OpenAI结构化输出说明](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)、[GPT-6迁移说明](https://developers.openai.com/api/docs/guides/latest-model/gpt-6-astra.md#migration-quickstart)、[GPT-6 Astra模型说明](https://developers.openai.com/api/docs/models/gpt-6-astra)。

密钥已保存到Git忽略的`backend/.env.eval-judges`，权限为`0600`，仅文件所有者可读写；报告和运行配置不包含密钥。新评分器通过专用`EVAL_GPT_API_KEY`读取凭证，不覆盖研究服务原有凭证。

历史Qwen评分脚本和结果保留历史身份，本轮入口在[评估README](../backend/eval/README.md)中单独列明。不能把历史Qwen与Claude的一致性指标继续当作GPT与Claude已经校准过的证据。

## 三 在线Critic改为三维

当前在线维度为可读性`readability`、全面性`comprehensiveness`、深度`depth`，每维0—100分、等权。程序按以下公式计算总分并保留两位小数：

```text
总分 = （可读性 + 全面性 + 深度）/ 3
```

评分口径标识更新为`report_review_3d_100_v1`。程序拒绝旧四维输入，不自动丢掉第四维再换算；历史记录也不自动改分。

用户要求的时间、地区、研究对象和交付内容仍由审核者检查，纳入全面性和具体问题清单；不再单独计算“指令遵循”维度。离线官方评分仍保留原四维，两者服务不同用途。

- [Critic实现](../backend/app/service/deep_research_v2/agents/critic.py)和[审核提示词](../backend/app/service/deep_research_v2/prompts/对抗式审核提示词.txt)

既有通过规则继续生效：总分至少60且没有critical或major问题才通过。严重问题不直接压低算术均分，但影响通过结论和返工路线。

## 四 失败归因与自动修复分别由谁执行

原方案中的“用实验验证归因”，指开发阶段的改进过程。开发者可以自己完成，也可以把任务交给当前编程助手：助手读取失败报告、模型和工具轨迹、来源原文，提出原因假设，修改项目源码或提示词，运行针对性测试，再用固定题目比较修改前后。

例如，网页读取器已经保存了某个数据，但Writer输入没有这段材料，编程助手可以修改证据传递模块；随后让修改前后的模块读取同一份材料，确认数据是否被传给Writer，再重新生成研究报告比较结果。分析者必须先找到证据，不能见到低分就直接增加搜索次数。

研究Agent内部的在线Critic只负责单次研究中的审核和返工：Critic提出问题，系统按规则让Scout补搜或Writer修订，然后复审。它不修改项目源码、离线评分标准或自己的部署配置。

本次没有新增“Agent自动改项目代码并自行部署”的循环。后续若由编程助手执行归因和修改，也应以验证集调优、正式测试集最后验证，不能让测试集结果反复参与选方案。

### 失败样例与处理边界

- 数据装配阶段曾因官方第1题参考报告任务文本差异而中止；已核对原题与细则一致，并保留差异记录，没有修改官方问题。
- 离线测试构造的缺项、重复细则、非有限分数、伪造摘录、响应截断和旧四维输入均被拒绝；拒绝意味着本次评分无效或需补跑，不等于报告质量为零。
- 同一报告只有GPT完整两次、Claude只有一次时，汇总程序保留已有分数但不给融合分，避免不完整双裁判被当作完成。

**已测量：** 数据文件完整性、当前接口连通与最小结构化返回、上述离线回归结果。

**间接推断：** 当前实现具备对冻结报告进行GPT与Claude逐细则评分的基础；新的裁判组合可能改变评分偏差，需要在实际报告上重新观察分歧。

**尚未评估：** 30题生成完成率、GPT与Claude长报告评分质量及一致性、当前Claude长响应真实联调、Langfuse端到端关联和分数发布、修复前后质量收益、完整评测费用。接口联调用量不代表每篇研究报告的生成或评分成本。

下一步先用3道验证题跑通真实研究、完整轨迹归档和双裁判评分，再冻结配置执行全部30题；失败原因分析只使用本验证集，正式30题测试集后续独立选取。
