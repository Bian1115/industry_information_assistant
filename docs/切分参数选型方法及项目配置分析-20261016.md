## 为什么不能直接选一个通用值

切分要在证据完整性、检索区分度和资源消耗之间取舍。小块可能更容易定位细节，也可能丢掉主体、年份、限定条件；大块可能包含完整论证，也可能混入更多无关主题。是否发生这些问题取决于实际文档和问题，本项目尚未测量。

本项目已存在句子与父段落两种视图，表格和记录另行处理。因此，`chunk_tokens` 主要约束证据单元及父段落打包，不能把候选值理解为每个句子块的固定长度，也不能假定改小预算一定提高句子层召回。

## 可执行的选型流程

### 1. 建立与切分策略无关的评测集

建议先准备 50–100 个有代表性的真实问题作为首轮筛选集；这是起步规模建议，不代表足以证明很小的效果差异。覆盖事实定位、条件解释、跨段综合、表格数值和无答案问题。

每题至少记录：问题、类型、参考答案或关键要点、来源文档、原文证据位置、必须共同出现的证据，以及是否允许拒答。来源位置使用文档版本/哈希加字符区间或稳定句子 ID。

不要只标注现有 chunk ID：改变切分后 chunk 会改变，旧标签会偏向旧切法。对于有多个合法证据来源的题目，记录等价证据组，避免把合法替代来源判成漏召回。

问题尽量来自真实需求；如辅助使用模型生成，应基于完整来源并人工复核，不要仅从某一候选配置生成的块中出题。按文档或主题对问题分组划分开发集与保留测试集，防止高度相似的问题同时进入两边；检索语料仍应包含测试问题需要的来源。

### 2. 分别建立候选索引

建议网格如下，均为待验证的实验起点：

| 链路 | 首轮候选值 | 其余切分策略 |
| --- | --- | --- |
| 现有字符文档入库 | 300、500、800、1200 字符 | 可先把 overlap 固定为大小的 10%，评估的是固定重叠比例下的块长配置；再对入围块长单独比较重叠比例 |
| 会话临时证据 | 256、512、768、1024、1536 tokens | 保持句子、父子关系、结构化证据规则和邻居策略一致 |

每个配置使用同一份解析后的原文，重新切分、生成向量并建立独立索引或隔离的存储空间。不要让不同配置共享会被相互覆盖的派生块。保持 embedding、reranker、模型、提示词、原文解析版本和排序规则一致，并记录 tokenizer 及实际长度分布。

本项目的 `session_evidence_store.py` 会保存来源的 `rag_chunk_profile`，补建时可能沿用已保存的 `chunk_tokens`。仅修改环境变量不能证明已有来源已按新参数重建；实验必须核对每组实际使用的 profile、块内容及长度分布。

构建失败必须记录失败类型和覆盖范围。当前实现遇到单句或结构化单元超预算会明确拒绝部分情况；不能静默丢掉失败文档，再把剩余更容易的语料拿来宣称候选值更好。

### 3. 控制检索预算，同时记录实际用量

主要比较使用相同的最终上下文 token 上限，例如先使用 4096 tokens。这个值是实验预算示例，不是对当前默认 8192 的修改建议。不同块长允许返回不同块数，以接近相同资源约束；对每组记录实际装入的正文及序列化上下文 tokens。

仅固定 `top_k=5` 会让不同块长带入不同数量的文本，难以区分块长效应与信息量效应。预算相同也不保证实际装入量相同，因此应同时报告实际 tokens、预算利用率及被预算排除的块。

本项目预算包含序列化行及元数据，邻居块也会占用预算，不能简单用 `top_k × chunk_size` 代替实际计数。上下文与引用层应分别核算。先在统一预算下比较，入围后再在真实生产的 top_k、上下文和引用预算下复验。

粗排候选上限、去重和精排策略必须固定并记录。小块可能在同样候选条数下覆盖更少来源，若后续调整候选池，应作为第二轮联合调参，独立记录，不能混称为只改变块长。

### 4. 先筛检索，再比较最终回答

| 指标 | 口径 | 本次结果 |
| --- | --- | --- |
| 证据覆盖率 `EvidenceRecall@Budget` | 最终预算内上下文覆盖的必要证据单元数 / 必要证据单元总数；按稳定原文证据判定 | 尚未评估 |
| 完整证据命中率 | 能同时覆盖一组足以作答的全部必要证据的问题比例；支持等价证据组 | 尚未评估 |
| 冗余与无关内容比例 | 重复来源片段和与作答无关内容的占比；应说明人工或自动判定方法 | 尚未评估 |
| 答案正确率与完整性 | 按关键要点或人工 rubric 判断；数值题检查对象、单位、时期和限定条件 | 尚未评估 |
| 引用支持率 | 被引用的原文是否支持对应结论；与答案看似正确分别计分 | 尚未评估 |
| 无答案题正确拒答率 | 语料缺少证据时是否正确拒答；不进入无定义的证据召回分母 | 尚未评估 |
| 时延与成本 | 查询 p50/p95、精排/生成 tokens、块数、索引体积、建库 embedding 用量 | 尚未评估 |

先对全部候选运行检索评测，保留 2–3 个配置运行完整生成链路。检索指标按粗排、精排、扩展和预算装配后的阶段拆开，有助于区分召回不足与最终装配丢证据。

最终根据业务目标选择：在答案正确性、引用支持性达到要求的配置里，比较成本、时延和各题型的稳定性。对同一批问题做成对比较；小样本差异很小时，增加样本或报告区间，不凭单次平均分排名认定最优。

### 5. 保留最终测试，按失败原因决定下一轮

在开发集选好配置后，用未参与调参的保留问题确认效果。若多条问题来自同一来源，分析误差时应考虑来源内的相关性。生成模型有随机性时，对入围配置使用可复现设置，并对关键差异做适量重复验证。

若大量事实定位失败，检查切分边界、标题信息、召回候选与精排；若能定位证据但解释不全，检查父段落与邻居扩展；若表格数值错误，检查表头、单位、脚注和行绑定。不要把所有失败都归因于块长。

| 类别 | 假设样例 | 要检查的问题 |

| 表格/记录 | 单元格值依赖列标题、行标题、单位及脚注 | 分块后是否保留这些关联；过小预算是否导致构建失败 |

## 已测量、间接推断与尚未评估

- 已核查：源码中的默认参数、长度计算口径、父子块与邻居关系、结构化单元预算机制、来源切分 profile 的保存与复用；机器记录保存了源码指纹。
- 间接推断：字符与 token 混用、固定块数下文本量不同、复用旧 profile、静默丢弃超预算来源，都可能使参数对比失真。这些是实现与实验设计分析，没有量化其影响。
- 尚未评估：当前语料的实际长度分布、各候选的构建成功率、检索质量、最终答案质量、成本与时延、生产环境配置，以及最佳块长。

## 结论与下一步

目前只能确认两条链路采用不同计量口径，不能确认 500 字符或 1024 tokens 最适合本项目。推荐保留现有默认值作为基线，分别使用上述候选网格，在同一真实问题集、同一原文快照和同一上下文预算下比较证据覆盖，再用最终回答质量与成本选择。

下一步是构建带稳定原文证据标签的开发集与保留测试集，然后执行独立索引对比。后续实际运行须新建中文运行目录、保存逐题机器结果并新增中文分析报告，不覆盖本次静态核查文件。
