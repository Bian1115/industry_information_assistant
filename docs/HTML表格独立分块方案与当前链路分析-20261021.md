# HTML表格独立分块方案与当前链路分析

分析日期：2026-10-21，Asia/Singapore。

建议将表格作为结构化对象独立保存，短表作为一个 chunk，长表按完整数据行或行组切分。每片附带标题、适用范围、完整表头、单位和相关注释。切分依据是最终送入模型的内容 token 数和语义完整性，而不是原 HTML 字符数或固定行数。

## 对象与证据口径

本次分析当前工作区网页读取、证据单元切分与会话检索源码，未执行运行评测、模型调用或阈值消融。静态发现与代码哈希见 [代码核查记录.json](../backend/eval/data/HTML表格分块静态核查-20261021/代码核查记录.json)。无原始性能结果，JSON 是静态分析证据。

- 已测量：无；本文数值为源码默认值或建议起点。
- 静态已核实：读取器会补回 HTML 表格；当前表格分块分支识别 Markdown 管道表；会话分块默认 1024 tokens。
- 间接推断：HTML 表格与 Markdown 分块分支之间存在衔接缺口，可能进入普通文本或字段记录路径；实际影响尚未测量。
- 尚未评估：HTML 表格端到端分块成功率、不同 chunk 大小的检索/回答准确率、延迟与成本。

## 当前代码

1. [web_content_selection.py](../backend/app/service/web_content_selection.py) 的 restore_source_tables 补回带 rowspan/colspan 的 HTML 表格。
2. [summary_evidence_units.py](../backend/app/service/summary_evidence_units.py) 的 _native_table 与 split_evidence_units 按管道分隔行识别 Markdown 表格，没有专门的 HTML DOM 表格分支。pack_structured 会逐行装包并重复 prefix/suffix；多级表头歧义或空白格会触发整表保留，超预算抛出异常。
3. [session_evidence_chunks.py](../backend/app/service/session_evidence_chunks.py) 已有 table 类型、table_id、行范围、表头/注释范围等元数据，并在分块后再次检查预算。
4. [session_evidence_rag.py](../backend/app/service/session_evidence_rag.py) 的设置类默认 chunk_tokens=1024，允许 64 至 2048；context_tokens=8192，citation_tokens=2000。这些是代码默认值，不代表每次运行的实际覆盖配置。
5. [web_document_structure.py](../backend/app/service/web_document_structure.py) 在截断点落入表格时延到表尾，但不保证整页后续表格都被保留。表格候选和完整源数据应在正文输出预算裁剪前保存。

## 推荐流水线

获取原始 HTML 或浏览器 DOM → 识别正文与表格候选 → 建立有序内容块 → 正文按段落切分，表格按行组切分 → 保存来源映射 → 分别入库。

HTML 是网页的输入格式，不应直接交给通用字符串切分器。原生表格用 DOM 解析器读取，保留单元格的行列坐标、跨行跨列、原始文字、表头关系。以 DOM 节点分离正文与表格，避免先 get_text 丢失行列关系，再尝试重建。嵌套表格分别建对象并保留父子关系，不能靠简单正则正确覆盖所有嵌套情况。

建议上游直接输出 paragraph/table 等结构化块，供 chunker 消费。若暂时仍需在混合正文字符串中识别 HTML 表，应增加专用结构解析及来源映射，不能把 HTML 盲转 Markdown 后假设合并关系仍完整。本方案未实施任何兼容层。

## 分块大小起点

第一版沿用现有 1024 tokens 预算，以实际送入 embedding/检索内容的序列化文本计数，包含重复表头、标题、单位、必要注释及放入文本的元数据。各模型的 tokenizer 与请求上限可能不同，还需按相应模型的计数口径验证输入长度；项目现有 Qwen 计数器不构成其他模型长度上限的自动保证。

| 情况 | 建议策略 |
| --- | --- |
| 整表及必要上下文不超过 1024 tokens | 整表一个独立 chunk，不强行拆分 |
| 超过 1024 tokens，且行可独立理解 | 按完整行装包，最后一片允许较短 |
| 多行属于同一语义组 | 优先把组作为不可切分单位，再检查是否可携带分组标签拆分 |
| 单行加表头就超过 1024 tokens | 按指标列组切分，重复行主键及对应完整表头 |
| 一个单元格本身超长 | 单元格正文按段落分片，重复行主键、列名、来源 cell_id，并标注部分单元格 |
| 结构无法确定、找不到安全切点 | 保留整表原件和检索入口，显式转交定向读取，不丢表也不假装完整 |

不设置固定“超过 20 行必须切”的规则：20 行金额表可能很小，3 行长文本表也可能很大。阈值没有通用最优值，可在真实问答开发集比较 512、1024、1536；这些仅是候选配置，1536 也须考虑现有 2000 tokens 引用总预算及元数据开销，不能直接把整表放大到 2048 当成通用兜底。

例：假设每片固定标题/表头/注释占 180 tokens，数据行平均 40 tokens，1024 的预算约能放 floor((1024-180)/40)=21 行。这是假设计算，实际必须对拼装后的整片重新计数，token 长度不保证严格可加。

## 结构安全切分

每片应能独立回答“这是什么数据、哪一年、哪个地区、单位是什么”。多级表头可派生为“2025年 / 营收（亿元）”等完整列路径，同时保留原始表头关系；不能给原文没有的表头补写成确定事实。

rowspan 关联的行优先成组。如果一个大分组需要拆分，先明确恢复其行头，再在各片重复分组标签，标记为派生展示而非多条独立原始数据。真实空值不等于跨行，不能盲目前向填充。总计行保存，但不能让模型把分片小计误当全表总计。文字型单元格碎片属于同一个原格，后续聚合须按 source_cell_id 去重。

表格通常无需像普通文本一样设置 20% 数据行重叠。重复表头和必要上下文即可；若使用重叠行辅助跨片比较，必须共享原始 row_id，并在统计时去重。

## 原表和检索片段

父对象保存完整净化 HTML、结构化格子、标题、表头、单位、注释、URL、抓取快照哈希和源节点路径。子 chunk 保存 table_id、chunk_id、row_ids、column_ids、source_cell_ids、行列覆盖、序号、提取完整性及变换说明。

原表不必全部送入 embedding。简单表可派生为带表头的 Markdown，复杂表可派生为明确字段路径的记录，结构原件仍独立保存。程序可生成“某表，包含年份、地区、营收等列”的目录性描述作为表级检索入口；模型生成摘要只能作检索辅助，不能替代原格证据。

事实查询可召回子 chunk；全表合计、排名、最大最小值或跨年度趋势应根据 table_id 加载完整相关行/列后计算，不能把向量检索 top-k 的少数片段当完整数据集。必要的邻近正文通过 parent/neighbor 关系按需补取。

## 待验证失败样例与验收

以下是测试设计，尚未执行：

- HTML 表被补回正文，但没有生成 table 类型 chunk。
- 表格每个 chunk 都有数值，但第二片缺失单位或多级表头。
- rowspan 跨过分片边界导致年份/地区缺失。
- 单行宽表超过预算，导致整页入库失败。
- 正文预算提前裁剪，位于后半页的表格没有进入候选。
- 检索仅命中部分片段，却据此计算全表合计。

验收指标包括表格独立识别率、源单元格覆盖率、表头关联正确率、完整行保留率、超预算比例、遗漏和重复率，以及表格问答准确率。测试须区分字段查询与全表聚合，记录实际 tokenizer、参数与最终片段；未检出或丢失的表格不能从统计分母消失。

## 外部参考与结论

[Unstructured 官方分块文档](https://docs.unstructured.io/api-reference/legacy-api/partition/chunking)体现先识别文档元素、表格独立分块、超长表产生 TableChunk 的设计。该页面也明确某些超长元素使用文本切分，因此不能据此假定它自动保证完整行、跨行结构及脚注关联；本文的按行/行组与来源映射是针对本项目的设计建议。

当前最先应接通 HTML 表格结构化解析与已有 table chunk 元数据。先沿用 1024 tokens，以完整行/行组为边界并重复表头，再依据真实检索和问答结果调节预算。此次仅新增分析文档与证据索引，没有修改业务代码或执行评测。
