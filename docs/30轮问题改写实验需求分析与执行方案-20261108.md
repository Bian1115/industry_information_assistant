# 30轮问题改写实验需求分析与执行方案

日期：2026-11-08，Asia/Singapore。评估对象：第20题“小桥 / Streamable HTTP”连续会话的任务改写准确性及首次偏移位置。

**状态：需求分析、样本与源码静态核查已完成；本次未启动正式实验，未修改业务代码、部署配置或业务数据库，未生成新的模型改写成绩。** 本方案中的阈值、脚本和运行目录如标注“拟”，均为后续执行设计，不是已完成的功能或结果。

## 一、需求解释与实验边界

按用户要求，使用已有单题长会话的前30轮：第1轮建立研究主题并生成起始报告；第2—30轮测量模型能否根据当前用户原话和此前历史形成正确任务。每轮由本聊天助手按照被测系统实际接受的任务代写一篇报告，评测程序把报告保存为该轮助手回答，供下一轮读取。

这是一项**使用代写报告的连续问题改写实验**。它可以测量任务理解、历史指代、有效要求继承，以及错误如何通过报告传入后续历史；它不直接测量搜索质量、完整多智能体研究交付能力或真实研究报告事实质量。报告由本助手代写是用户指定的实验条件，不能据此声称报告由 Qwen3.7 Plus 的 Writer 生成。

本次建议先做1条会话、1次连续运行。30轮之间存在依赖，不是30个独立样本；从第2轮开始有29个待评分轮次。后续如需判断波动，可另做至少3次独立会话复跑，每次保留自己的报告、摘要和首次失败位置；复跑仍不能代表其他主题的总体准确率。

## 三、“每轮精确比例”的具体定义

### 3.1 先固定判分依据，再查看模型答案

执行前由评测侧根据第1至当前轮的用户原话，为每轮建立独立的要求清单。清单记录每项要求由哪轮、哪句话提出，以及何时被后来的要求替代。不得用被测模型的报告作为用户意图的真值，也不得在看到错例后修改清单来提高分数。

清单分成两部分：

1. **改写文字必需表达的要点**：本轮动作、对象、必要指代补全、新增或修改的约束。无需要求每轮逐字重复所有历史约定。
2. **完整执行任务必须保持的要点**：当前仍有效的历史约定、正确报告目标、当前操作与要求变更。历史约定已由正确选中的报告契约继承时，不因它没有重复出现在 `resolved_query` 中就判定整套系统遗忘。

“契约”在这里指程序随报告保存的结构化要求，例如正文上限和研究范围；它是数据，不是另一个裁判。正式运行应保存这些要求及其来源，避免把评测侧的标准答案偷偷写进契约。

评测标准留在独立文件。被测模型只接收当前问题和已经发生的会话信息，不接收标准答案、未来问题、`depends_on`、预期操作标签和评分反馈。

### 3.2 每轮至少记录以下指标

设某轮应该表达的要点有 N 项，模型明确且正确表达了 M 项。把模型实际表达的独立任务要点也逐项核对，重复表述不重复计数。

| 指标 | 计算方式 | 用途 |
| --- | --- | --- |
| 要点完整率 | M / N | 用户该轮要求保留了多少；这是建议作为“每轮百分比”的主列 |
| 要点精确率 | 模型输出中有用户依据且表达正确的任务要点数 / 模型输出的全部任务要点数 | 识别模型新增目标、错误对象和错误约束 |
| 整轮改写正确 | 必需文字要点全部满足，且没有错误或无依据的任务要求 | 每轮为通过/失败，不伪装成概率 |
| 完整任务正确 | 综合问题、目标报告、操作、修改指令、要求变更、正确继承的有效约定判定 | 判断错误是否真正进入后续报告任务 |
| 累计整轮正确率 | 第2至当前轮正确轮数 / 其中已取得可评分输出的轮数 | 展示随会话增长的累计表现；完整运行分母为29 |

**示意而非实测：** 某轮应保留8项要求，模型保留6项并新增1项错误要求，则完整率为6/8=75%，精确率为6/7≈85.7%，整轮判失败。如果模型只保留1项正确要求，精确率可能仍为100%，但完整率只有12.5%；因此不能只报告精确率。

优先用有证据的0/1逐项判定，不靠模型直接给一个印象分。每个失败要点都保存“用户依据、输出原文、差异说明”。语义等价表述允许通过，不能用字符串完全相同作为正确标准。空输出、无效协议、网络失败、服务澄清各有独立状态；无法语义评分时记录不可评分，不能填成正常的0%或100%。同时报告取得可评分结果的轮数/计划29轮，防止忽略提前终止造成的缺失。

### 3.3 首次跑偏应记录三种位置

- **首次模型改写错误轮**：首次响应的问题文字不满足上述完整正确标准的最早轮次。这回答“模型从哪轮第一次改错”。
- **首次最终任务错误轮**：经过现有重判与校验后，程序实际接受的任务仍错误的最早轮次。这回答“错误从哪轮进入后续任务”。
- **首次严重偏移轮**：主题、报告目标、当前动作、实现语言、关键数值约束或新旧约定覆盖关系首次错误的轮次。严重项必须在评分清单中预先标明。

另列遗漏一般要求、错抄上轮、错误指代、旧约定复活、凭空新增要求、程序拒绝执行和技术中断。可报告连续两轮错误的起点作为持续偏移现象，但不把它替代“首次错误”。后续恢复也不能消去首次错误记录。

若第2—30轮全部正确，只能写“本次样本截至第30轮未观察到错误”；若中途停止，写明观察截至哪一轮及剩余未评估轮次。

## 四、报告怎样生成并进入下一轮上下文

### 4.1 每轮顺序

```text
第1轮：
评测程序读取第1轮原话 → 本助手按原话生成起始工程说明
→ 评测程序保存报告正文、章节和本轮要求 → 提交会话消息 → 建立后续历史

第2至30轮：
评测程序读取当前轮原话并保存用户消息
→ 生产会话服务读取此前已提交的消息、摘要及报告候选
→ Qwen3.7 Plus 输出首次任务
→ 程序执行已有的有界重判和校验，并保存所有原始输出
→ 本助手按程序实际接受的任务和选中报告生成该轮报告
→ 评测程序将报告作为本轮助手回答提交到数据库
→ 评测程序保存实际输入、摘要、报告与元数据，随后进入下一轮

评分侧在独立文件中对照冻结要求判分；评分结果不进入以上链路。
```

第1轮在新隔离会话中通常没有历史，因此沿用生产首轮分支，不人为制造一次不存在的改写调用。

### 4.2 代写报告必须遵守的限制

1. 本助手以实际接受的 `resolved_query`、选中报告、模型给出的修改指令及程序真实继承的要求为生成依据。评测程序需导出这一小份输入包；未来问题、标准答案和失败标签不进入生成包。
2. 本助手不得依据自己看过的标准答案补回模型丢失的要求。例如第14轮模型没有把 Python 改成 TypeScript，本助手不能代替模型完成这次语言修正。模型选错旧稿时，也不能偷偷改用最新稿。
3. 如果系统的其他正确字段仍保存了某项要求，本助手可按实际任务保留它；这应归为“问题文字不完整但完整任务可执行”，不能故意删除以制造下游失败。
4. 每轮按实际任务生成一篇完整当前稿，保留正常的章节与信息密度。报告长度服从模型实际任务中的限制，不为促使摘要触发而灌水。第1轮使用原题1800—2400字要求，后续长度遵循运行中的真实约束状态。
5. 正式运行前准备与主题有关的冻结来源材料，供代写报告使用；只允许使用实际有原文支撑的事实和引用。无材料支持的细节标为待核实，不编造搜索结果、URL或运行成功记录。代写报告属于实验材料，不能声称六个补证轮真的执行了联网检索。
6. 代写过程与评分由同一助手参与，存在无意修正的风险。除隔离输入包外，每轮归档生成依据和实际报告，并审查报告是否擅自修复了任务。如果发生这种污染，该轨迹不能当作原始有效运行，应另建运行目录重跑。
7. 每轮报告生成后冻结正文及 SHA-256，不随后的评分结论回头修改早期报告。

### 4.3 存储和实际可见性

报告首先是本助手生成的文本。评测程序应将它同时写入运行目录的 `第N轮/注入报告.md`，并通过会话服务保存为研究类型的助手消息，填入本轮运行标识、完成状态、真实章节目录和按实际任务更新的要求。

这里的完成状态只表示**该实验轮的代写报告已交付**，运行清单和元数据需明确 `report_origin=assistant_fixture`、`research_graph_executed=false`，不能冒充多智能体已经完成了研究。实验使用独立用户/会话，并隔离长期记忆后台任务，避免影响真实会话或读取既有用户偏好。

会话服务执行数据库 `commit()` 成功后，该轮消息才算完成数据库事务提交；缓存刷新不能代替数据库提交。运行目录的关键原始文件采用临时文件写入、刷新与文件同步、原子替换方式保存；数据库状态和文件归档两者都完成后再推进轮次，续跑时核对两边哈希及轮号，不能仅依赖程序内存里的“已完成”标记。

下一轮实际发送给模型的内容可能是完整报告、摘要加近期消息，以及报告目录/节选的组合。评测程序必须保存真实 API 请求来证明模型看到了什么，不能把“数据库中有报告”写成“每次模型都读了全部报告”。

## 五、Qwen3.7 Plus 的统一范围

官方文档列出 `qwen3.7-plus` 和固定版本 `qwen3.7-plus-2026-05-26`，并说明该系列默认开启思考模式：[阿里云深度思考文档](https://www.alibabacloud.com/help/en/model-studio/deep-thinking)。建议固定版本优先；实际地区和账户是否可调用，必须在正式运行前通过最小请求验证。别名和固定版本不可在同一条轨迹中混用。

本次已尝试读取 CLI 模型目录，但本机 CLI 会话返回 `TOKEN_EXPIRED`，所以没有取得账户级可用性结论。官方型号存在不等于本账户可调用；CLI 会话失效也不等于项目 API Key 失效。恢复 CLI 或直接使用项目接口做最小生成预检属于执行前步骤，本轮没有启动登录流程或发送生成请求。

| 模块 | 拟统一方式 |
| --- | --- |
| 会话问题改写/任务判断 | 显式设置 `SESSION_TASK_MODEL` |
| Architect、Scout、DataAnalyst、Wizard、Critic、Writer | 显式设置全部 `LLM_MODEL_*`，并统一主模型与默认模型 |
| 会话滚动摘要 | 设置 `SEMANTIC_CONTEXT_MODEL`；显式配置经核实的窗口，不能沿用旧模型窗口假设 |
| 智能体内部摘要及其语言模型步骤 | 设置 `LLM_MODEL_SUMMARY` 并检查所有实际调用 |
| 引用是否得到证据支持的核验及论断抽取 | 当前 `context_policy.py`、`nli_verifier.py`、`summary_message_verification.py` 和 `report_claim_extraction.py` 存在旧模型名称限制或硬编码；需要一起修改模型配置、请求和记录逻辑 |
| 重试/备用模型 | 不允许静默切到其他型号，实际请求遇到非目标模型立即标记配置违规 |

仅改 `OPENAI_MODEL` 不足以完成要求。后续实现时应以新运行使用统一模型为目标，不为旧断言新增旧模型兼容层。

本次报告由本助手代写，主实验实际需要运行的主要是会话判断模型和按阈值触发的会话摘要模型。研究图内的其他角色仍按要求统一配置，但必须标明“本实验未调用”，不能写成已经验证了全体智能体的运行表现。

文本向量模型与检索排序模型执行不同接口，不属于此处的生成/判断模型，不能简单将其模型名替换成聊天模型。本次改写主链路不需要新增此类检索。若引用核验等生成模型在扩展实验中实际被调用，也必须满足统一型号要求。

为固定实验口径，建议问题改写继续使用现有 `temperature=0`、初判输出上限3000；显式设置 `enable_thinking=false`，让非流式结构化输出的模式可复现。其他模块保留各自合理输出上限和现有采样设置，记录完整参数。思考模式实验如需要另设运行，不在同一次会话中临时切换。温度为0仍不保证多次调用完全相同。

## 七、实现顺序、停止规则与验证

### 7.1 执行步骤

1. 冻结前30轮样本副本、逐轮要求清单、判分说明、现有源码及配置快照。只复制用户问题到被测输入，标签留在评分侧。
2. 为实验建立独立配置，把所有生成/判断模型统一到验证可用的 Qwen3.7 Plus 固定版本；保存有效配置和请求审计规则。本轮方案阶段不修改部署。
3. 新增拟脚本 `backend/eval/scripts/评估30轮问题改写.py`：复用生产任务构建器，逐轮等待本助手提交代写报告，再继续下一轮；不执行完整研究图，不提供伪造的模型改写输出。
4. 增加请求记录，覆盖改写初判、整份重判、章节ID修正和会话摘要。保存实际消息、模型标识、普通输出、解析字段、校验结果、usage及结束原因；默认不保存额外的模型思考过程。
5. 先做针对性的离线验证：当前轮排除正确、报告可成为下一轮候选、标准标签/未来问题不泄露、先错后修不被掩盖、没有错配轮号、所有生成请求用指定模型。只验证这些关键风险，不扩展无关测试。
6. 用独立临时会话做第1—3轮小规模预演，检查请求可调用、报告提交和读取、字段完整性；预演结果单独归档，不拼入正式成绩。
7. 从新的独立会话完整运行前30轮。逐轮冻结报告，运行结束后完成29轮评分与关键失败复核；评分不得反馈给运行中的模型或代写输入。
8. 生成逐轮表格、完整率曲线、首次错误标记和中文结果报告，所有指标链接到原始输入、输出和判定证据。

建议初始技术预算：正式运行最多120次生成请求（含判断重试和会话摘要）、每请求300秒且SDK额外重试关闭、总输入加输出token预算300万，另限制模型调用累计等待6小时。此上限是防止失控的执行参数，不是预计用量或容量结论；预演若证明不适用，应在正式运行开始前修改并冻结配置。等待本助手生成报告的时间单独计，不混作模型API延迟。摘要内部重试及判断器自己的修正调用仍照现有有界逻辑执行并计入预算。

### 7.2 出错后如何处理

- 模型语义改错但程序接受了任务：照实际任务生成报告，继续后续轮次，观察传播与恢复，不修改用户问题或提示词补救。
- 首次输出错误、程序已有重判成功：主轨迹按最终任务生成报告，但首次错误保留在模型层指标中。
- 程序要求澄清或拒绝执行：保存完整过程，主轨迹停止，后续轮次标为未评估。不能替模型偷偷选一个正确任务继续。
- 超时、限流、账户权限、输出截断和配置违规：作为技术失败记录。有限重试只按预先固定规则进行，禁止“重试到答对”。
- 若要绕过生产拒绝继续研究错误传播，必须另建“原始输出诊断”分支，明确这是改变执行规则的实验，不与主轨迹合并计分。

### 7.3 上下文压缩的观察边界

主实验先保留当前压缩策略和阈值，冻结有效配置。每轮记录摘要是否触发、覆盖哪些消息、生成文本及下一请求是否采用，也记录报告字符数、累计历史token和实际请求token。

30轮并不保证触发摘要：该样本多数报告只有900或1200字。不能为触发摘要偷偷放大报告，也不能把未触发摘要的运行解释为压缩效果测试。如果需要判断“错误是否由摘要造成”，再以同一前缀历史对照原始历史与压缩历史，或另做明确标记的小阈值机制实验；主运行本身只能定位错误，不能证明其因果来源。
