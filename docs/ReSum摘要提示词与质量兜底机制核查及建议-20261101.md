```text
你擅长分析对话历史并提取相关信息。请仔细分析对话历史和当前问题，
生成有助于回答问题的全面摘要。

任务要求
1. 信息分析：
   - 仔细分析对话历史，识别真正有用的信息。
   - 聚焦直接有助于回答问题的信息。
   - 不得作出超出对话明确内容的假设、猜测或推断。
   - 如果信息缺失或不清楚，不要将其纳入摘要。

2. 摘要要求：
   - 仅提取对话明确提供且最相关的信息。
   - 必要时综合多轮交流中的信息。
   - 仅保留确定且明确表述的信息。
   - 不要输出或提及不确定、不充分或无法从对话确认的信息。

3. 输出格式：
<summary>
- Essential Information: [整理对话中与回答问题有关且确定的信息。]
</summary>

严格避免编造、推断或夸大对话没有提供的信息。
只输出确定且明确陈述的信息。

问题
{{{question}}}

对话历史
{{{recent_history_messages}}}

请生成全面且有用的摘要。在这个过程中不允许调用工具。
```

增量模板保留类似规则，并额外要求摘要模型以上一次摘要为起点：分析此后进展、识别剩余信息缺口、合并旧信息与新信息，并在新增历史较少时保持连续性。程序传入原问题、`last_summary`和`recent_history_messages`。生成结果是完整的新摘要。

版本细节：论文v3附录C称不显式要求列出信息缺口和行动计划；所核对代码的增量模板仍含“Identify remaining information gaps”。不能将论文说明与这个固定代码提交视为完全一致，也不能说官方模板必须输出“事实、缺口、行动计划”三栏目。

官方模板要求省略不确定内容。对于需要持续保留待核实线索和冲突的研究系统，可以设计带状态的保留规则，但必须明确这是工程修改。历史明确写了“尚未证实X”与历史已经证实X是不同信息；保留前者不意味着确认X。

## 官方代码的错误处理边界

依据：[摘要调用源码](../backend/eval/data/ReSum摘要机制核查-20261101/官方摘要调用源码.txt)、[研究循环源码](../backend/eval/data/ReSum摘要机制核查-20261101/官方研究循环源码.txt)。

- 摘要调用异常时会重试；空响应返回空字符串。研究循环只有收到非空摘要才替换工作历史。
- 摘要函数删除think部分并提取summary标签；标签提取失败时可以把剩余内容包进summary标签。格式包装成功不证明语义正确。
- 在所核对的摘要函数与研究循环中，没有看到独立的逐条证据支持检查或关键遗漏验收。
- 已超上下文预算时，代码会要求研究模型停止调用工具并尝试给出答案。这是任务终止处理，不能作为摘要事实正确的保证。
- 完整执行记录保存在`full_trajectory`内存列表中并随结果返回；该列表本身不等于已经持久化的原文档案，也没有在这两处源码中自动构成模型可用的回读工具。

## 怎样提高摘要质量

### 生成前保护关键内容

控制程序单独保留当前有效用户要求、输出要求、任务状态以及关键证据定位，不让它们完全依赖自由摘要。摘要输入明确区分用户要求、助手观点、工具证据和旧摘要。旧摘要中的内容应继续关联原始来源，避免反复概括后把推测升级为事实。

为原始记录保留来源编号、文本快照及内容指纹；内容指纹用于检测读回内容是否改变，不证明内容所述事实真实。原文留在数据库或归档文件中，当前模型输入可以只携带摘要、近期完整记录和按需读取的原文片段。

压缩触发应给生成、检查和修复预留预算。输入过大时，程序按完整调用或主题分批交给摘要模型，保留来源关联后再合并。压缩幅度由任务信息密度决定，不使用任意固定压缩率作为质量保证。

### 生成后进行两个方向的检查

**摘要到原文：检查有没有写错。** 控制程序把摘要中的可核查陈述及对应原文交给核验器，判断原文支持、矛盾还是证据不足。核验器可以由程序规则与模型共同构成。数字、单位、主体、时间、范围、否定词和条件尤其需要检查。原句确实存在，只能证明引用定位正确，不能单独证明摘要结论成立。

**原文到摘要：检查有没有漏掉。** 控制程序从有效任务要求和原始记录中建立关键内容清单，再检查摘要是否保留对应内容及其状态。清单不能只从候选摘要反向生成，否则摘要已经遗漏的内容不会进入检查。清单也可能遗漏，因此需要人工抽查和后续任务验证。

例如原文“2025年中国区收入10亿元，同比增长5%，海外数据未披露”，摘要“2025年全球收入10亿元”中的数字虽然来自原文，但范围被改错；摘要“收入有所增长”则可能没有明显假话，却丢失了金额、年份和适用范围。

模型审核仍会出错。更换审核模型或使用更强模型可以作为策略候选，但必须在相同轨迹、任务与预算下验证，不能把模型等级或模型自评当成质量保证。

### 单独验证继续执行的效果

后续可以选取有代表性的固定研究轨迹，在相同断点比较完整历史、当前摘要方案和加入验收/回读的方案。后续任务应涉及数字与单位恢复、跨来源关联、负面证据、约束遵守和已完成任务识别。

建议指标包括摘要陈述支持率、关键内容保留率、用户约束保留率、后续任务成功率、重复搜索次数、回读成功率，以及包含生成、检查、重试和回读的总耗时与总token成本。本次没有执行该评测，没有实测阈值或收益数字。

## 内容出错时的兜底设计

建议让控制程序区分候选摘要与当前采用的摘要。候选通过必要检查后，程序才在同一次数据库事务中更新有效摘要版本和覆盖位置。覆盖位置表示后续模型输入中哪些历史将由摘要替代。数据库事务提交成功后，应用才把该版本标记为已保存；断电场景的实际持久性仍取决于数据库部署配置，本次未核查。

| 失败情形 | 发现方式 | 控制程序执行的兜底动作 |
| --- | --- | --- |
| 请求超时、空响应、格式错误 | 调用和解析检查 | 有界重试；保留原有效摘要和覆盖位置，必要时分批或换摘要服务 |
| 单条事实写错 | 摘要陈述与原文冲突 | 把错误项、对应原文和候选摘要交给摘要模型定向修复，再核验；未通过时不切换有效版本 |
| 关键条件或内容遗漏 | 独立关键清单检查 | 补回原文中的条件和事实，必要时扩大摘要预算，再核验 |
| 多次压缩后信息失真 | 与原始快照核对发现差异 | 从原始记录重建相关部分或整份摘要，避免仅在出错旧摘要上继续改写 |
| 后续模型遇到证据不足 | 来源缺失、冲突标记、关键数字校验或任务规则触发 | 程序按来源编号读回原文片段，重新组装请求，让研究模型据原文继续 |
| 已采用的摘要后来被判错 | 延迟核验或下游发现冲突 | 标记摘要无效，切换到先前可信版本并补回其覆盖位置后的记录，或从原文重建；重新检查已经依赖错误摘要生成的产出 |
| 修复后仍超预算 | 重新计算实际请求长度 | 保留受保护要求和当前步骤，分批检索相关原文或减少单次任务范围；仍不可执行则明确暂停或失败 |
| 原文不可读或校验不一致 | 权限、可用性或指纹检查 | 保留失败状态，停止把可疑摘要当已核实证据；不能凭旧摘要补造原文 |

“回到上一份摘要”不能只换摘要文本。程序还要恢复相应覆盖位置，重新纳入此位置之后的历史，并重新检查请求预算。历史有效版本需要实际保存，只有版本号或父版本哈希无法重建旧摘要正文。涉及外部工具副作用时不得盲目重放操作。

不能只等待模型主动发现错误：如果关键条件已经完全丢失，模型可能不知道需要回读。因此控制程序应对关键数字、冲突证据和必要任务条件设置直接检查或强制取证。原文回读后必须重新核验相关结论；读到原文不等于模型已经正确使用原文。

## 当前项目可以复用的能力及边界

1. [agent_history.py](../backend/app/service/agent_history.py)的`read_source`按当前run与context读取数据库记录；[BaseAgent](../backend/app/service/deep_research_v2/agents/base.py)检查内容指纹，按字符范围取原文并加入当前调用记录。具备回读链路不等于后续模型必然发起正确回读。
2. `save_summary`在数据库事务中按预期版本更新摘要正文、版本、覆盖位置和元数据。版本检查防止并发覆盖；它不检查摘要陈述是否真实。现有条件要求覆盖位置向前推进，不能直接把它当成支持任意向后回滚的接口。
3. 启用`summary_lifecycle`分支时，[summary_lifecycle.py](../backend/app/service/summary_lifecycle.py)先调用`on_generated`提交正文，再进行论断与引用审核。[agent_context.py](../backend/app/service/agent_context.py)的`annotate_audit`只更新元数据。该生命周期明确不替换已提交正文、不回退覆盖位置。
4. 因此“先验收再采用”和“核验失败自动回到可信版本”属于待设计行为，不能说项目已经实现。具体运行是否启用该分支，需要检查它冻结的策略；本次未读取运行配置。
5. 现有[摘要正文提示词](../backend/app/prompts/摘要正文生成与合并.txt)明确区分事实、计划、冲突、限制和未完成事项，并把引用与核验放到独立阶段。本次建议可以沿用这种阶段划分，不要求把所有技术字段塞进正文提示词。

## 失败样例与局限性

本次没有运行摘要任务，未产生实测失败案例。以下均为设计压力样例：

- 原文含“中国区”，摘要变成“全球”：实体范围错误，引用存在检查可能通过，语义核验仍应拦截。
- 原文含“尚未核实”，摘要变成“已确认”：证据状态被升级，必须保持不确定性或回读确认。
- 摘要每句话都真实，但漏掉用户“不包含2024年数据”的要求：单向支持检查不足，应独立保护并检查用户约束。
- 连续摘要使某个已排除候选的理由消失：后续研究可能反复搜索，应保留排除依据与来源。
- 已提交摘要后核验超时：若仅记录失败状态，下游仍可能使用该摘要，必须另行设计采用策略。

该核查不是ReSum复现实验，也没有证明一种兜底策略优于另一种。原始材料自身可能包含错误；忠实摘要与现实事实正确性是两层问题。摘要检查也需要处理来源冲突和可信度。

## 结论与下一步

优先保留可回读原文、有效任务要求与摘要版本，建立“摘要是否有依据”和“原文关键内容是否遗漏”两种检查，并明确失败时有效版本是否切换。建议先用固定轨迹验证验收成本和修复效果，再决定采用先验收后提交，或允许带状态的临时使用并增加后续失效处理。任何实际代码改动都应以用户后续实施请求为准。
