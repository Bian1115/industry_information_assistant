## 2. 对话消解在哪个模块

入口 `research_router.py` 调用 `ResearchContextService.build()`，并以 `FOLLOWUP_ROUTER_ENABLED != '1'` 决定是否启用旧消解器。

1. 路由关闭时：有会话历史或记忆才调用 `ResearchContextService._resolve_query()`，输出 resolved_query、assumptions、unresolved_references 等。它不生成完整研究契约。
2. 路由开启且存在可用父研究时：图进入 `FollowupRouter`。路由模型结合当前原话、父研究问题/契约/大纲/事实索引和部分全局对话，同时输出 resolved_query、修改指令和路径选择。此时消解属于路由决策的一部分。
3. 路由开启但没有父研究时：旧消解器已关闭，而图直接进入 plan，没有经过 FollowupRouter。Architect 仍可能结合传入的全局历史自行理解，但不存在单独消解步骤保证。这是需要补齐的条件分支。

建议统一“消解结果”的数据协议与入口调度，保留 original_query、resolved_query、依据和未解决歧义。没有必要为了模块独立强制新增一次模型调用：正常追问仍可由路由一次完成消解和分流；无父研究/关闭路由时由原服务完成。Architect 只消费结果及必要原话，不再隐式承担全局会话消解。

## 3. 自身历史与全局历史目前不是一回事

`ChiefArchitect._render_historical_context()` 当前读取 conversation_context、memory_context，以及消解器的假设/歧义；这首先是全局会话和记忆。继承父材料时还展示部分事实、父约束和有效输出限制。

`BaseAgent` 的调用会记录独立 agent 历史，但 `agent_context.py` 是否加载该历史由 replay_agents 控制。默认只有 DeepScout，因此“记录了 Architect 的输入输出”不等于“下一次调用会回放它们”。历史存储还按 run_id、agent_name、context_key/实验配置隔离。追问新建 run 后，不能只把 ChiefArchitect 加进 replay_agents 就假定会看到父 run 的规划记录。

建议传入三部分：

- architect_context：自己的历史摘要、最近必要交互、上一版已提交大纲/契约、当前规划模式和研究进度；服务端检查父研究归属后显式继承规划快照。
- current_query：本轮原话、已消解问题、最小必要的消解依据，明确标注这是来自全局对话的用户依据。
- research_constraints：已确认旧契约、本轮更新和只读运行配置。

优先传最后已提交规划，避免用全部历史输入输出反复堆叠；不要重复同时加入手工历史和自动回放。历史规划中的模型建议不应升级为用户要求，历史报告也不能替代原文证据。

## 4. 追问会不会生成约束，是否复用提示词

追问路由会输出 constraint_updates，但当前只有 max_body_chars。其他修改主要进入 resolved_query 和 revision_instructions。apply_decision 会继承或清空 active_constraints，再合并非空更新，并给 research_contract 增加 followup_instructions 和 active_constraints。这是部分更新，不是完整、统一的研究约束重建。

| 场景 | 实际链路 | 提示词/约束行为 |
| --- | --- | --- |
| 首次研究 | plan → Architect._initial_planning | PLANNING_PROMPT；随后 build_research_contract |
| 追问整篇重规划 | FollowupRouter → architect_replan → plan | 同一 PLANNING_PROMPT；再次 build_research_contract |
| 追问改篇幅/表达且材料足够 | FollowupRouter → user_revision → Writer | 不经过 Architect；继承契约并局部更新 |
| 追问补充证据 | FollowupRouter → re_research → Scout | 不经过 Architect；继承契约并局部更新 |
| Architect 研究中动态修纲方法 | _check_revision | 有独立 REVISION_PROMPT，但当前主图没有接到该方法；该方法本身也不重建契约 |
| 故障恢复 | 恢复检查点所在节点 | 不等同于每次重新规划 |

所以，“首次和追问重生成大纲”确实复用；不能据此说“所有再次修改/追问都走同一路径”。当前 review 节点是 Critic，revise 是 Writer，不是 Architect 的动态修纲方法。

另外，replan 继承材料时主要继承事实、来源等，不把父 outline 直接设为当前 outline。建议显式传 last_outline，避免模型没有可靠旧大纲可改。

## 5. 对方案的建议与理由

### 5.1 保留一个研究契约，不再维护第二套研究约束状态

同意输出“大纲＋研究约束”，顶层使用 outline 和现有 research_contract。模型输出是候选版本，服务端规范化后才生效。active_constraints 可作为兼容的执行投影，但应由契约生成并校验一致性。

原因：现在 Writer/Scout 追问可继续使用旧 contract.query/required_entities，而 state.query 已经改变。继续增加一个平行 constraints 字典，会扩大状态不一致风险。

### 5.2 追问所有分支都先完成约束更新

路由负责提取本轮修改和选择执行路径；公共函数负责将旧契约与增删改合并、验证用户依据。Writer、Scout、Architect 三个分支及路由失败降级都使用本轮有效契约。首次由 Architect 提取候选约束，再经过同一个归一化/校验逻辑提交。

不要要求每次改字数都额外调用 Architect。“压缩到3000字”且材料够时，更新字数约束并走 Writer 即可；改变研究对象或整体结构才进入重规划。

原因：当前 null 表示“继承”，无法明确表达“取消字数限制”；路由异常降级只是把父契约拼到 query，没有等价恢复结构化 active_constraints。文字里还记得限制，不代表确定性长度检查能读到限制。

### 5.3 用户硬约束与规划建议必须分开

每项硬约束带用户原话/已确认旧约束的出处；模型建议的实体、假设、比较方法留在大纲。当前 build_research_contract 在 required_entities 为空时回退使用 key_entities，会把模型选择误当成硬性清单；新协议必须同步取消这类隐式提升。

首次规划和重新规划共用核心提示词与 schema，用 planning_mode 区分。暂不为尚未接入的动态修纲增加第二套协议；后续要接入时复用同一约束规则，并传入研究进展。

### 5.4 提示词之外必须同步改输入和适配层

实现顺序建议：统一约束更新/版本语义 → 组装 Architect 独立上下文与父规划快照 → 接入新提示词和解析 schema → 将 outline 与 contract 原子提交 → 覆盖各条追问路径。

旧代码仍读取 requirement_responses、research_questions、hypotheses、key_entities，并执行显式要求覆盖检查。新提示词将内容归入两个顶层字段，必须有适配层；不能只改字符串、丢掉原有假设驱动研究能力。build_research_contract 也必须保留新协议中的约束出处、变更和未解决项。

规划模式、提示词版本、输入/输出协议版本与上下文配置一起冻结到每次运行，便于后续消融比较；不应用新配置解释旧轨迹。

## 6. 引用修复的实际边界

当前实现已把 source_ids 当作候选池，允许只返回其中有引句的子集，不再要求每个候选都提供引用。此前机制验证报告也覆盖了候选 A、B 只引用 A、后续批次找到证据和旧缓存回读等情况。

但 parse_citation_result 仍严格检查“模型实际返回的每条引用”：只要某条 quote 不在其指定 source_id 的当前片段中，就报错；它没有自动丢弃该错误引用再保留其他正确引用。因此，当前可确认的是“允许候选子集”，不能扩展描述为“任何错误候选/错误引句都会自动过滤，只有全候选失败才报错”。本次没有再次改写引用代码。

若后续要自动过滤，必须区分未选中候选与模型返回的伪造/错配引用，记录拒绝原因；只有成功定位仍不能说明引句支持论断，语义核验继续独立执行。

## 7. 失败风险与后续验收样例

以下为代码可推断风险和待测案例，不冒充本次线上失败复现：

| 场景 | 当前风险/需要验收的行为 |
| --- | --- |
| 开路由、无父研究、“把它按近五年重写” | 没有独立消解步骤；应保留歧义或使用统一兜底，不猜对象 |
| 新 run 重规划旧大纲 | 同 agent 不等于同 run 历史可见；需验证父规划快照授权和实际入模 |
| “改为3000字”走 Writer | 无需调用 Architect，但完整契约与长度执行投影必须同步 |
| “取消字数限制” | 当前 null 是继承，需显式 remove 并确认最终检查已解除 |
| “只研究B，不研究A”走补搜 | 旧 required_entities 可能残留；应更新完整契约并避免旧材料越界 |
| 路由超时后降级 | 不能仅靠自由文本继承旧硬约束；需要验证结构化约束仍生效 |
| 模型自行选出研究实体 | 不得因此变成用户必须覆盖的对象 |
| 返回一条正确引句和一条错配引句 | 当前解析器会拒绝，区别于未选中候选；需明确期待行为 |

另发现一个直接代码缺陷：architect.py 的 _render_historical_context 在 inherited_evidence_manifest 非空时调用 json.dumps，但该模块没有 import json。按当前文件，此分支会触发 NameError；本次仅静态确认，未触发真实运行。接入/验收重规划之前应修复并覆盖该分支，避免把运行错误误判为提示词失效。

## 8. 结论与局限性

建议采纳“自身上下文＋当前query＋研究约束 → 大纲＋研究约束”，并把约束提交、历史继承和消解职责明确到代码层。首次/重规划共用提示词是合理方向，当前已经部分复用；真正缺口是自身历史输入、所有追问分支的契约一致性及新旧 schema 适配。

已确认：上述函数、schema、图路由和默认配置的静态行为。间接推断：这些缺口可能造成约束遗忘、规划漂移或降级后限制失效。尚未评估：真实运行的环境开关/冻结配置、此次候选修复后的完整轨迹、新提示词模型表现、token/时延和研究质量。后续应按第7节做确定性机制验收，再用固定失败材料回放，最后做在线开发集验证；本报告不声称已完成这些测试。
