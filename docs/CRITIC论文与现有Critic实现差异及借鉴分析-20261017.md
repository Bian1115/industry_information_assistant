# CRITIC论文与现有Critic实现差异及借鉴分析

## 分析信息与结论

- 分析日期：2026年10月17日，Asia/Singapore。
- 对象：当前工作区 DeepResearch 主链路的 CriticMaster、Scout补搜、Writer修订、独立引用核验，与ICLR 2024 CRITIC方法。
- 口径：静态阅读当前代码，复用已有实验与意见复核结果；本次未调用生成模型、未重新运行质量评测、未修改业务代码。
- 当前源码以工作区内容为准，Git HEAD不能代表未提交修改；本次保存相关文件SHA-256及带行号片段。
- 本地核查记录：[代码核查与历史评估引用](../backend/eval/data/CRITIC与现有Critic对照分析-20261017/代码核查与历史评估引用.json)。

结论：项目已有“报告初稿—审核—定向补搜或修订—复审”的外层闭环。主要可借鉴之处是让工具返回的具体依据参与批评判断，并把问题、证据、修改和复查对应起来。可以沿用现有主图、原文库和核验器进行小范围改进。

这不能简化成“项目没有外部工具”：Scout确实搜索和读取正文，Writer使用原文RAG，另有独立引用核验。差异主要在这些结果怎样进入Critic的判断，以及返工是否按问题验收。

## 论文作为比较基准

[论文第3节与算法1](https://arxiv.org/html/2305.11738v4)的核心过程是：模型生成初始输出，在验证阶段与工具交互获得反馈并形成批评，再依据批评修改输出；可以重复验证和修订。模型参数保持冻结，任务工具在实验中预先配置。

[官方问答实现](https://github.com/microsoft/ProphetNet/blob/master/CRITIC/src/qa/critic.py)在一轮检查中允许多次模型与搜索交互：识别模型查询，插入真实搜索结果，再继续生成分析与新版答案。因此，查询可以随证据调整。

下面提出的稳定问题ID、程序检查引用位置、逐问题验收、预算控制等，属于针对本项目的工程建议，并非声称论文已经实现了这些完整协议。论文也不能保证不把正确答案改错。

## 当前流程与已有能力

主图见[graph.py](../backend/app/service/deep_research_v2/graph.py:185)及[节点连接](../backend/app/service/deep_research_v2/graph.py:286)。

```text
初始检索 → 分析节点 → Writer写作及可选引用核验 → Critic
                                                    ├─ 通过 → 完成
                                                    ├─ 补搜 → Scout → 分析 → 写作 → Critic
                                                    └─ 修订 → Writer按章修订 → Critic
```

达到返工上限也会结束，但完成原因保留为 `revision_limit`，与通过审核的 `passed` 区分。代码配置默认允许两轮返工，实际运行可覆盖；搜索初始阶段和补搜共享预算。

项目当前值得保留的能力包括：问题与补搜字段的严格契约、来源网站范围限制、原文读取与编号、按章节定位返工、检查点及过程记录、独立核验状态，以及“未通过但额度耗尽”的明确完成原因。论文针对较短问答或程序，项目还承担整篇长报告的要求覆盖和跨章一致性检查，适用对象不同。

## 逐类差异及代码依据

| 比较点 | 论文方法 | 当前项目 | 实际含义 |
| --- | --- | --- | --- |
| 批评形成 | 工具交互属于验证过程 | Critic先读报告及摘要判断，再安排补搜；独立核验在Writer阶段 | 工具已有，但反馈进入Critic判断的路径较弱 |
| 审核范围 | 事实、程序正确性、文本属性等任务 | 逻辑、要求覆盖、时效三维评分，另查重要论断缺引用 | 当前Critic是报告审核角色，引用支持性由独立模块负责 |
| 证据输入 | 验证上下文包含工具结果 | 主提示传整篇报告、事实摘要、数据点、引用目录，未主动检索原文 | 引用URL和原文证据不能等同 |
| 搜索交互 | 一轮验证可按新证据继续查询 | 一次产出任务列表，Scout执行后进入写作 | 缺少写作前针对待核问题的自适应追查与结论确认 |
| 修改范围 | 修改当前答案或程序 | 按章修订或重开相关章节写作，再重整摘要结论 | 长报告中需要约束无关改动和新增事实 |
| 再检查 | 重复验证修改后的输出 | 已有全文复审，但未显式逐条核销旧问题 | 新一轮未提到旧问题，不能直接证明其已解决 |

### 1. Critic的直接输入仍偏向报告与旧事实摘要

[审核提示词](../backend/app/service/deep_research_v2/agents/critic.py:148)明确要求不做逐条引用核验，只评逻辑、要求覆盖、时效，并定位未附引用的重要论断。

[_review_content](../backend/app/service/deep_research_v2/agents/critic.py:431)传入完整报告；事实最多60条，每条正文截到220字符，数据点最多50条，引用目录最多100条。它没有调用会话原文检索接口，也没有绑定联网搜索、网页阅读或计算工具循环。

BaseAgent支持[历史回读](../backend/app/service/deep_research_v2/agents/base.py:150)，因此不能绝对断言Critic永远接触不到历史材料。但历史回读与明确检索当前论断的原文、验证支持性是不同的能力。

10月16日改造已取消新研究的写作前事实提炼，允许 `facts=[]`，Writer直接检索原文；[分析节点](../backend/app/service/deep_research_v2/agents/data_analyst.py:287)也不再重建事实摘要。Critic主提示仍保留事实摘要输入，却没有像Writer一样接入原文检索。这是当前版本中特别需要注意的证据输入差异。

### 2. 独立核验已经存在，但结果没有成为Critic的逐项判断依据

[Writer](../backend/app/service/deep_research_v2/agents/writer.py:1036)会执行写后引用核验与可选处理。核验记录包含论断、原文定位、支持性判断和报告版本哈希，见[引用核验实现](../backend/app/service/deep_research_v2/citation_verification.py:205)。

服务首次运行的[代码缺省配置](../backend/app/service/deep_research_v2/citation_verification.py:30)是开启正文核验，默认处理方式为 `audit`；实际部署环境、请求参数和已保存运行配置可覆盖。不能仅看模型类字段默认False就断言生产关闭，也不能假定所有已有运行开启。

Critic仅把门禁中的 `enabled/passed/blocking_reasons` 放入主提示，没有显式注入逐条支持性结果，并在结果规范化时剔除模型自行产生的 `fact_check_results/citation_audit`。默认audit模式记录核验结果，不自动要求修稿；[报告基础门禁](../backend/app/service/deep_research_v2/quality_pipeline.py:81)也只检查非空及引用网站范围。

可借鉴的是把已有核验结果作为外部反馈交给Critic安排返工，保留独立核验器负责支持性判定的职责，避免让Critic再凭记忆重复核验。核验的覆盖边界仍是已声明、可绑定的论断；错误、未执行或证据不足必须单独保留，不能当作事实为假。

### 3. 补搜任务可执行，但验收条件不够具体

[_build_research_tasks](../backend/app/service/deep_research_v2/agents/critic.py:417)保留问题ID、目标章节、查询，最多10条；`acceptance`统一写成“新增reader_verified证据并通过对应质量门禁”。

[Scout补搜](../backend/app/service/deep_research_v2/agents/scout.py:612)执行查询、读取正文，并保存 `critic_issue_id` 等关系。这说明已经有问题与来源的绑定起点。该执行路径没有消费 `acceptance`，也未在进入写作前逐问题判断“新材料是否真的回答待证命题”。

`reader_verified`用在来源读取和准入流程，不能直接解释为报告论断获得语义支持。新增一篇同主题网页，与证实某个年份、分母或因果关系，是不同结果。

### 4. 补搜后的章节重写未显式带上全部待修问题

Scout会[重开目标章节](../backend/app/service/deep_research_v2/agents/scout.py:696)，保证新资料有机会进入正文；Writer也已接入[按章原文检索](../backend/app/service/session_evidence_rag.py:467)。

但补搜后沿 `re_research → analyze → write` 进入普通写作，[_write_section构造提示词](../backend/app/service/deep_research_v2/agents/writer.py:680)未显式传入这一章的旧问题、逐项修改要求和验收状态。原文召回查询主要由原问题与章节标题/描述构成。

纯修订分支的[_revise_report](../backend/app/service/deep_research_v2/agents/writer.py:1240)会传问题描述和建议，并提供原文证据；但反馈文本没有显式携带该条 `evidence` 字段及具体待核查命题。两条返工路径的反馈输入不一致。

这不是断言所有反馈都会丢失：它们仍保存在状态与历史中。准确结论是，当前调用没有把这些内容强制组织成逐问题修订输入。

### 5. 复审与“问题已解决”的证据尚未逐项闭合

Critic每轮把旧问题移入 `critic_history`，再创建当前问题集，见[问题保存逻辑](../backend/app/service/deep_research_v2/agents/critic.py:316)。主提示没有显式要求对上轮所有未解决问题逐条返回复查结论，也没有强制稳定ID。

Writer根据模型返回的 `addressed_issues` 标记解决；要求补搜的问题还检查[证据指纹变化](../backend/app/service/deep_research_v2/agents/writer.py:1301)。这是有用的防护，但指纹涵盖全局原文和章节关系，变化本身不能证明某一条问题已解决。

后续可区分“Writer已处理”和“复查确认解决”，要求复查记录对应的新句子、原文或计算结果。问题不再出现、来源数量增加、模型总分提高，都不能替代这条验收。

可用于设计改进的历史失败例：

1. **漏读已有引用。** 56条意见中的14条错误有10条属于此类。35-R2-issue_2要求给德州“三统一”补官方链接，但当轮正文已有同一个URL。应先定位原句及同段链接，再区分“缺引用”和“支持性待核查”；识别到链接不代表已验证支持性。

## 借鉴建议与优先级

### 第一优先：让现有证据进入决定，减少无效返工

在Critic作出修改或补搜决定前，按问题汇总已有核验结果及必要原文，至少保留：报告原句、位置、待核问题、来源定位、检查结果与边界。

- 缺引用：程序先展示原句、段落或表格单元附近的实际链接，降低漏读概率。程序只能确认链接存在，不能凭此宣告语义支持。
- 支持性疑问：复用现有 `citation_verification` 和RAG回读，对高影响问题按需提供原文，不重新核验全部报告。
- 年份、单位、分母、计算：能用程序复算的就复算，并把输入来源与口径一起保存。项目已有 `deterministic_analysis.py`，但依赖结构化输入与显式计算要求；不能声称它已自动覆盖原文直写报告中的所有数字。

查证后再区分“确认存在的问题”“待补证问题”和“检查失败”。纯逻辑、偏见或要求覆盖问题可以依据报告和原题成立，不必为每条意见强行联网。

### 第一优先：统一两条返工路径的逐问题处理

保留目前的“补搜”和“仅修订”分支，但都明确传入相关问题ID、待改句子、批评依据、已有证据及验收要求。检索查询也应加入具体问题，不只依赖章节标题。

Writer返回修改位置、使用的来源和无法处理的原因；复审显式检查所有旧的未解决问题，允许判定旧批评本身错误并保留原句。只有对应证据或推理确认后，才把问题标为解决。

这一部分需要连接Critic、Scout和Writer，不能只修改一段“更严格”的提示词。

### 第二优先：少量问题的工具交互与局部修改

在当前原文库中先查，已有材料不足再安排联网补搜。围绕影响核心结论的问题，允许根据新证据再生成查询；仍复用Scout执行器、来源限制和总预算，不必把搜索实现复制到Critic类里。

修订可优先替换相关句段，并复查受影响的摘要、表格、结论。项目已有 `citation_repair.py` 的局部改写及版本检查，可参考其做法；逻辑和要求覆盖的修改不应直接当成引用修复套用。无需恢复已取消的全量写作前事实提炼。

### 第三优先：按新信息和验收进展控制停止

保留返工上限、完成原因与预算限制，增加“已验证问题数、仍缺什么证据、是否找到新信息”等进展记录。同一问题无新资料时，先考虑限定结论、明确未决原因或交付局限，不因低分自动整章重写或单纯增加轮数。

具体每轮处理几条问题、允许几次追查，应通过当前版本实验确定，本次不预设最优参数。

## 一个建议流程示例

以下是接入设计，不是现有系统已实现能力，也不是本次新实验。

```text
报告生成
  → Critic定位待核问题
  → 回读已有原文 / 读取已有核验结果 / 程序复算
  → 给出有依据的批评，或保留不确定状态
  → 确需新资料时由Scout定向补搜并确认回应了哪个问题
  → Writer针对问题修改，保留修改位置及证据
  → 复审逐条确认旧问题，检查改稿新增风险
  → 通过，或按预算交付明确未决事项
```

可以先用一个小字段集表达核查记录：`issue_id`、`report_quote`、`verification_question`、`evidence_refs`、`verification_status`、`revision_location`、`resolution_reason`。格式是工程选择，收益来自证据与修改的对应关系。

## 局限性与下一步验证

- **已测量：** 上述历史五题质量/成本和56条意见复核；均沿用旧日期、旧配置与既有判断。
- **本次已核查：** 当前工作区的输入构造、路由、原文使用、核验入口和问题保存方式，并保存源码指纹与片段。
- **间接推断：** 证据未充分进入Critic、返工未逐问题验收，可能限制当前收益；尚不能量化各机制的因果贡献。
- **尚未评估：** 10月16日改造后Critic的真实质量、当前意见正确率、加入建议流程后的提升、误改率、漏检率与完整费用。

后续验证建议仍固定同一份首稿和模型配置，比较当前流程与“复用已有证据核查＋逐问题修订复查”，单独记录额外调用与预算；关闭Critic可作为参考组。评价包括意见正确性、原错修复、原对改错、核心需求完成、正文质量及成本，避免用Critic自己的总分代替独立评判。新实验需要重新落盘，不能用本次静态分析替代。
