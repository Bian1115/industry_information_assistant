# 网页正文提取论文与开源方案调研及历史评估分析

分析日期：2026-10-17，Asia/Singapore。对象：本项目网页读取链路、51.56%历史正文可用率，以及相关论文与开源方案。状态：完成历史标签复算、代码静态核查和一手资料调研；没有运行新方案效果评测，没有修改业务代码。

建议优先做现有Crawl4AI的正文过滤和质量失败回退，再以Readability、Magic-HTML做CPU对照；模型路线重点试MinerU-HTML／Dripper；Jina Reader适合作为独立读取后端对照。论文和工具主要覆盖不同环节，不能把抽取F1直接当作本项目URL可用率。

以上是同批历史轨迹的不同口径，不代表10月17日当前线上实测值，也不代表服务效果从51.56%下降至47.40%。10月8日程序抓取成功为189/289，但其中49页被AI初评为abnormal；因此HTTP/工具成功不能替代正文质量。反过来，质量门禁收紧只能减少污染，单独拒绝坏页不会增加取得可用正文的URL数。

历史记录中的抽取器为：Trafilatura 103、Crawl4AI sidecar 120、BeautifulSoup 11、PyPDF2 2、未记录53。该分配来自回退链路，不是随机对照，不能由数量或组内成功率推断谁更强；它说明Crawl4AI已经被实际调用，建议不能停留在“再接一个浏览器”。

## 失败类型与逐题分析

按10月11日去重口径，152个不可用URL的分类为：空正文58、导航42、验证码13、错误/错页11、登录/积分页5、二进制乱码5、元信息4、空页3、目录3、仅附件链接2、预览2、封面1、脚本1、仅图片链接1、仅销售说明1。

| 主要问题 | 数量 | 对应方向与边界 |
| --- | --- | --- |
| 无正文 | 58 | 先按HTTP状态、网络、格式拆因；更换HTML解析器不能修复所有空值 |
| 导航、空页、脚本 | 46 | 验证是否拿到正确页面、渲染时机及主体区域；原页面若真是导航则需找正确入口 |
| 验证码、登录/积分 | 18 | 正文选择模型无法从验证页恢复未提供的正文；标记不可用并寻找公开原文或已授权入口 |
| 错页 | 11 | 校验最终URL和目标内容，必要时重新定位原始出处 |
| 二进制、附件、图片链接 | 8 | MIME/文件特征分流、附件跟随和文档解析；图链不等于取得图表数字 |
| 元信息、目录、封面、预览、销售说明 | 11 | 区分真实摘要和空壳预览，必要时获取源文件；不能用“文本够长”判断成功 |

| 题号 | 去重可用/总数 | 分析 |
| --- | --- | --- |
| 35 | 13/45＝28.89% | 政策附件、标准封面、目录和文档平台空壳问题突出；优先补附件与格式路由 |
| 31 | 34/58＝58.62% | 真实文章与摘要较多，仍有导航、乱码和积分下载页 |
| 46 | 41/70＝58.57% | 新闻政策正文较多，报告目录、登录与错页仍需区分 |
| 16 | 21/45＝46.67% | 学术摘要有用，但验证码/导航不能视为论文正文 |
| 49 | 28/71＝39.44% | 空正文、导航和图片链接限制可用性；图片中的数据尚未被提取 |

可追溯失败样例均来自冻结正文，本次没有重新访问这些URL：

- `35-page-003`：目标是政府`.doc`制度文件，拿到政府首页导航。需校验重定向、文件类型与目标匹配；换正文抽取器不保证能找回文件。
- `35-page-023`：技高网仅返回“正在检测您是否是真人”。这是访问层障碍。
- `35-page-028`：浏览器拿到404提示，历史程序仍记success。应检测软404和状态矛盾。
- `31-page-046`：文档平台返回积分下载与推荐内容，5558字符仍不含目标文章。长文本不足以证明正文可用。
- `35-page-010`：政府通知中只有PDF附件链接，需继续读取附件。
- `35-page-036`：`.doc`文件被当作文本解码，出现Office二进制乱码，需独立文档解析。
- `49-page-007`：人口结构图只有图片URL，尚未得到图中数值。
- `35-page-031`：仅章节目录和页码，不能算已取得报告论述。

## 开源项目如何选择

| 项目 | 主要覆盖环节 | 本项目建议 |
| --- | --- | --- |
| [Mozilla Readability](https://github.com/mozilla/readability) | DOM正文识别；Firefox阅读模式使用，Apache-2.0 | 首批CPU对照。输入静态或渲染DOM，保留输出HTML及元信息；不负责获取被网站阻挡的内容 |
| [Magic-HTML](https://github.com/opendatalab/magic-html) | 主体HTML、文章/论坛/微信版面、公式，Apache-2.0 | 首批CPU对照，适合保留结构后接现有表格渲染；README小样本作者自评不替代本项目实测 |
| [Crawl4AI](https://github.com/unclecode/crawl4ai) | 浏览器抓取和Markdown生成，Apache-2.0 | 已接入；先完善渲染等待、正文过滤和质量失败后的回退条件，而非再重复接入 |
| [MinerU-HTML／Dripper](https://github.com/opendatalab/MinerU-HTML) | 模型选择主体HTML，含REST API及回退，代码和相关权重声明Apache-2.0 | 有GPU或独立推理服务时作为复杂HTML候选；不承担HTTP访问、验证码或扫描PDF识别 |
| [Jina Reader](https://github.com/jina-ai/reader) | 独立URL读取服务、浏览器、PDF/Office与Docker部署，Apache-2.0 | 适合作独立后端A/B；支持等待目标选择器。云端代理、内部模型等能力需与开源部署区分 |
| [Firecrawl](https://github.com/firecrawl/firecrawl) | 抓取、渲染、清洗及API服务，仓库为AGPL-3.0 | 当确实需要完整替换抓取服务时再对照；仓库明确云端有附加能力，不把云端表现当作自托管保证 |

Jina Reader是读取服务，[ReaderLM-v2](https://arxiv.org/abs/2503.01151)是HTML转换模型，二者不应混为同一工具。本次优先建议验证读取服务和保留原HTML的抽取方案，未评测ReaderLM-v2在本项目的效果。

## 当前代码中值得优先验证的环节

静态核查基于10月17日工作区文件，不能把当前代码行为反推为10月初失败的全部原因：

1. [web_reader_service.py](../backend/app/service/web_reader_service.py)的`_extract_html`（567行）在存在`article/main`或任意`table`时优先采用BeautifulSoup渲染结果，只有content为空才调用Trafilatura。若初始结果很长但混入导航，其他抽取器没有机会竞争；“出现table”也不意味着整页body都是正文。建议保留候选结果并按正文质量选择，同时检查表格是否完整。
2. `_read_uncached`（380行）主要在内容短、403/5xx或超时时走浏览器；末尾质量校验拒绝后没有在该函数中继续尝试其他抽取器。建议对确有目标正文迹象的噪声页允许一次有界的替代抽取，不对登录、验证码、404无限重试。
3. `_read_with_crawl4ai`（651行）及[自定义sidecar](../backend/crawl4ai_sidecar.py)取`raw_markdown`。[官方Fit Markdown文档](https://docs.crawl4ai.com/core/fit-markdown/)区分未过滤raw与过滤后fit输出，支持Pruning和BM25。应先保存raw及DOM作为依据，再对照正文过滤结果；BM25按查询筛选会丢掉非查询匹配段落，不应默认充当完整原文归档。官方文档为v0.9.x，项目依赖为`>=0.8.0,<1.0.0`，实施前需固定实际版本。
4. 当前格式分流主要是PDF或HTML，PDF以PyPDF2抽取、空文本时可选OCR；`.doc/.docx`等需独立识别与解析。HTML模型不能修复二进制解码，扫描PDF和图片数据另需OCR／文档解析路径。

## 建议复测方式

第一步冻结一个覆盖上述失败类型、中文/英文、文章/政策/论文/表格/附件的小型开发对照集，并保留正常页以观察误伤。只用失败页可以调试，不能估计总体提升。后续在固定289个URL上做端到端配对，同时保留全新留出域名验证泛化；历史URL可能失效，应把页面变化单独标注。

将评测分两层：同一份HTML或渲染DOM比较正文抽取器；同一URL、接近的时间窗比较整个读取后端。前者剥离网络与反爬差异，后者计入下载失败、软404、附件和解析路由。由于历史运行缺少原始HTML/PDF，不能只靠旧抽取文本重建公平的抽取F1。

建议依次对照：现有基线 → 调整Crawl4AI过滤与质量回退 → Readability/Magic-HTML候选选择 → MinerU-HTML困难页回退；Jina Reader作为独立外部后端对照。固定版本、重试、缓存冷热、并发、超时、来源范围和标签口径。抽取器结果须保留原句映射，避免生成式改写污染引用。

同时报告URL可用率、完整正文与摘要分列、非空文本条件可用率、软404/验证/导航误接纳率、正常页误拒率、单页P50/P95、失败率和资源/调用成本。对有金标的HTML另报字符或适合中文分词口径的正文Precision/Recall/F1及表格关键单元格保真；不能只看字数增多或Markdown更短。优先人工复核方案间不一致和新成功样例。

## 局限性、结论和后续建议

**已测量**：历史标签计数复算、289个去重条目URL及正文指纹匹配、失败类别和抽取器来源分布；原始标签仍是AI辅助估计。**间接推断**：现有候选选择、质量回退、raw Markdown及格式路由存在可优化空间；候选工具与这些问题的匹配程度来自代码和公开资料。**尚未评估**：任何新方案对本项目的真实增益、10月17日线上可用率、人工金标F1、成本与延迟、表格保真。

已有SIGIR 2023、SIGIR 2025和ACL演示论文可直接参考；MinerU-HTML／Dripper是值得跟进的模型路线。当前问题同时涉及访问、正文选择、文档格式和目标定位，实施重点应是按失败类型恢复可用正文，并通过固定样本对照验证。现阶段不能承诺从51.56%提高到某个百分比。
