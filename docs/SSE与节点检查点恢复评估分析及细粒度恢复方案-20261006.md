# SSE与节点检查点恢复评估分析及细粒度恢复方案

评估日期：2026-10-06（Asia/Singapore）。

评估对象：当前工作区 `/research/stream` 的 SSE 事件流、事件账本、LangGraph 节点检查点与技术中断续跑；Scout 和 Writer 内部进一步细分恢复的设计。

数据与配置口径：依据当前源码，包含已有未提交修改。执行的是离线机制验证，使用假 Agent、模拟数据库会话、内存检查点和模拟前端事件流。没有调用真实模型、搜索服务，没有连接 PostgreSQL，也没有中断正在运行的研究。没有修改业务代码。

## 一、结论与证据边界

1. 评估应分别回答“页面能否完整恢复”和“执行能否正确恢复”，再比较故障后的重复工作、时间、token 与存储开销。SSE 负责传递事件，执行恢复取决于持久化状态和下一步位置。
2. 当前主图串行节点的提交边界相当于 Agent 阶段。Scout 的多个章节检索、Writer 的多个章节生成都在一个大节点内部；已发送章节事件不代表章节已成为执行检查点。
3. 本次后端 16 项、前端 14 项离线测试全部通过。其中一个真实主图与服务入口的测试注入写作异常，验证恢复时只重新执行写作，规划、搜索和分析不重跑；失败节点的临时修改不污染已提交状态。
4. 这些结果不能换算为生产恢复成功率。跨进程崩溃、数据库写入窗口、真实 HTTP 断线、事务幂等交付和费用节省均尚未评估。
5. 建议先实测终态检查点与业务交付之间的窗口，再实现 Writer 章节级恢复和 Scout 工具调用级恢复。可以拆分图节点，或在现有节点内部使用可持久化 task；两者都必须保存完整产物并能确定性重建状态。

| 边界 | 本次内容 |
| --- | --- |
| 已测量 | 30 个指定离线用例的通过情况；真实主图内存检查点的写作异常续跑；前端真实解析器和状态投影对模拟流的处理 |
| 间接推断 | 源码中的先落账后发送；大节点内产物未独立提交；终态交付缺少明确补偿入口；细分节点可能降低故障重做量 |
| 尚未评估 | PostgreSQL 跨进程恢复、SIGKILL、代理断连、客户端接收延迟、真实费用与质量、更细粒度实现的效果 |

## 三、当前实现实际保存了什么

| 层次 | 当前位置 | 作用与边界 |
| --- | --- | --- |
| SSE | `backend/app/service/deep_research_v2/service.py::encode_sse`；`frontend/src/pages/chat/research-events.ts::consumeResearchSse` | POST + fetch 流；每个 data 行一个 JSON；缓冲网络字节分片。当前不是原生 EventSource，也不依赖 Last-Event-ID |
| 事件账本 | `backend/app/service/research_events.py::ResearchEventRecorder` | 提交事件后再发送。数据库运行行锁分配 seq；after_seq 用于回放，前端按 run_id/seq 去重和检测缺口 |
| 执行检查点 | `deep_research_v2/checkpointer.py`、`graph.py`、`service.py` | AsyncPostgresSaver；thread_id=run_id；durability=sync；恢复时输入 None，沿用 snapshot.next |
| 节点内部工作历史 | `service/agent_history.py`、`agents/base.py`、`service/tool_runtime.py` | 保存 LLM 与工具输入、输出、usage 等审计数据。目前没有把这些记录直接接成已完成单元的恢复结果缓存 |
| 终态交付 | `deep_research_v2/delivery.py::make_commit_result` | 图终态提交后，在业务事务里写报告、run 状态、完成事件；已有完成事件时复用 |

当前图有 `plan → research → analyze → write → review → finish`，另有编辑、补搜与修订路径。主图 `make_node` 对已提交业务状态做深拷贝，Agent 完成后才返回可序列化状态。

Scout 的 `process` 在 `research` 节点内循环章节，`_research_section` 内再执行多个查询与正文提取。Writer 的 `_write_report` 在 `write` 节点内循环章节；`_write_section` 写入 draft_sections、section_claims 和章节状态后发出 section_content。这个方法没有独立产生图提交边界。

因此，“六章中的第三章已在页面出现，第四章生成时崩溃”应验证第三章是否存在于执行检查点。按当前实现推断，初次写作节点尚未完成时，其新增章节不能依赖该节点的全量状态检查点恢复；旧运行继承的既有章节、独立审计历史和网页缓存可能保留其他信息，不能一概称为全丢失。

`resume_policy.py` 是历史阶段游标代码；当前主图/服务入口未调用其 begin_stage 或 commit_stage。新增恢复设计应围绕当前 LangGraph 状态与 task 机制，避免误把旧游标测试当成主图效果。

LangGraph 官方说明：完整检查点在 super-step 边界保存；sync 在后续步开始前持久化；成功节点的 pending writes 也可用于故障恢复。[官方检查点文档](https://docs.langchain.com/oss/python/langgraph/checkpointers)。上述项目边界来自本地源码。

### 失败样例与保护边界

- 已测量的注入失败：Writer 第一次向临时 state.facts 添加“失败节点的未提交数据”，然后抛出“注入写作失败”。读取检查点时 facts 仍为空，next 为 write。第二次写作成功；Architect、Scout、Analyst、Critic 各调用一次，Writer 调用两次。
- 已测量的模拟账本失败：record 抛出 ResearchEventPersistenceError；测试断言没有 SSE 数据被发出。
- 已测量的业务拒绝：空报告未进入审核；未知审核 phase 抛错；缺少 checkpoint_id 不允许交付。这些是预期失败路径，测试本身通过。
- 尚未评估的真实失败：终态图已提交，commit_result 尚未完成，进程被杀；外部 API 成功但本地产物提交前进程被杀；数据库提交成功但客户端没收到；并发续跑与旧执行器迟到写入。

需要特别区分：`persist_events=False` 的服务入口测试每次构造内存 recorder。该用例验证的是图恢复及单段 SSE 形状，没有证明真实账本跨首跑/续跑的 seq 连续性。交付载荷测试没有执行真实数据库交付事务，也没有证明并发幂等。

## 五、建议怎样正式评估

### 1. 使用两阶段评估

第一阶段用确定性 Agent 和固定工具响应，跑真实 PostgreSQL、真实 HTTP 服务和客户端。让各阶段产物可精确对比，并记录每次调用。专门为故障注入启动隔离的测试进程与测试数据，避免杀掉用户正在使用的服务。

第二阶段选同一批真实研究题验证质量和实际资源收益。冻结模型、参数、提示词、搜索范围、证据快照、上下文压缩与核验开关、返工预算、代码版本。固定随机种子或 temperature=0 仍不能保证在线服务逐字一致；对真实报告应比较约束满足、证据覆盖、引用有效性和已有质量口径。

建议起步使用 10 个固定任务覆盖短任务、多章节、补搜、修订与逐条核验；每个故障类型做 3 次重复。第一次发现严重正确性问题时先修复再扩大样本。这个规模是试验建议，尚未执行；报告须按场景列样本量和失败数。

### 2. 设置可比对照

| 组别 | 故障后的行为 | 比较用途 |
| --- | --- | --- |
| 无故障参考 | 正常完整执行 | 质量与正确性参考 |
| 从头重跑 | 相同故障点中断后重做全部流程 | 故障恢复成本对照 |
| 当前节点级恢复 | 同样的故障计划，用当前检查点续跑 | 测现有收益 |
| 候选细粒度恢复 | 同样故障计划，复用已完成工具或章节单元 | 测新增收益 |

SSE 另做显示对照：同一执行流程使用实时显示，与客户端缓冲至完成后显示比较首次可见进度/内容的等待。这样不改变 Agent 执行来评估 SSE 的展示收益。事件账本恢复评估则比较断线后的完整性。

故障位置用“第几个逻辑单元完成/哪个提交边界”，避免仅用随机等待秒数。相同问题、同一注入种子、相同外部响应才能做配对比较；另补充随机 SIGKILL 作为稳健性测试。缓存设置与是否热缓存必须一致。

### 3. 故障注入矩阵

| 故障位置 | 具体操作 | 核心断言 |
| --- | --- | --- |
| 页面刷新或断开 POST 流 | 客户端确认处理 seq=k 后断连；重新读 state/events 或调用 resume | 已提交事件最终补齐，逻辑事件不重复；当前服务取消会传播到执行，恢复需覆盖节点重跑 |
| 序号重复、缺口与 UTF-8 分片 | 重复交付 k；先送 k+2；中文拆成逐字节或随机块 | 去重；缺口补齐前游标不越过；中文和 JSON 保持正确 |
| 节点内部失败 | 搜索完成部分查询、写完部分章节、核验完成部分论断后异常 | 当前组允许重跑失败节点；细粒度组只重做未提交单元 |
| 检查点提交边界 | 在提交前/提交成功后，以可控屏障杀掉隔离 worker | 已提交状态不丢；未提交结果不能冒充成功；重建进程后继续 |
| 外部调用成功、本地提交未完成 | 工具/模型返回后、任务结果或产物持久化前杀进程 | 识别不确定结果；实际重复调用与重复计费要记录，不能宣称 exactly-once |
| 终态图与业务交付窗口 | finish 检查点提交后、报告事务提交前杀进程；交付提交后、SSE 发出前再测 | 不重新做研究；可补交付/补发；报告、完成事件各一个 |
| 数据库异常 | 提交超时、断连接、回滚与恢复连接 | 不发未持久化成功事件；恢复后游标/产物/账本可对账 |
| 并发续跑与租约过期 | 同一 run 发起两个 resume；使旧 worker 暂停再迟到返回 | 一个有效执行者；旧 fencing token 不得提交新产物或覆盖恢复状态 |
| 重复多次中断与版本变化 | 同 run 连续两次故障；变更配置或升级图版本 | 可反复恢复；不静默沿用不兼容游标；配置保持原运行口径 |

本次未执行上述真实故障矩阵；它是后续实验方案。

### 4. 指标定义

| 指标 | 建议定义 |
| --- | --- |
| 首次进度/内容可见时间 | 客户端发出请求至应用处理第一个有意义的进度事件/正文事件；分别统计 P50/P95 |
| 事件端到端延迟 | 事件提交至客户端应用完成；跨机器校准时钟，或使用可校准的测试端到端计时 |
| 最大静默时间 | 客户端连续两个事件之间的最大等待；长 LLM 请求中单独观察，不能用服务开头的一条 start 代替持续可观测性 |
| 最终事件丢失率 | 完成全部重放后，预期已提交事件中尚未应用到 UI 的数量 / 预期事件数 |
| 逻辑重复率 | 重放收敛后同一 run_id/seq 被 UI 重复应用的次数；网络重传次数另外记录 |
| 恢复成功率 | 所有注入运行中，原 run 最终正确交付且不违反关键状态约束的数量 / 所有注入运行数；失败、超时均进入分母 |
| 恢复耗时 | 从请求恢复到重新出现有效进度；从请求恢复到最终交付；从故障到完成另报，包含检测、重启和租约等待 |
| 重做量 | 已成功执行的逻辑工具调用、LLM 调用或章节单元，在恢复中又实际执行的次数；按已提交/未提交分类 |
| token 与费用收益 | 配对实验中 (从头重跑总成本 - 恢复总成本) / 从头重跑总成本；总成本包括首次失败、中断、恢复与重试 |
| 状态一致性 | 对已提交事实、来源、章节等稳定产物比较 ID/哈希与引用关系；剔除时间戳、attempt 等观测字段 |
| 质量变化 | 同题、同证据下的约束满足、引用/事实与报告质量指标；真实模型使用配对差异而非逐字一致 |
| 正常路径开销 | 细粒度方案相对当前方案的无故障耗时、数据库写入量、检查点/产物字节数和 P95 写延迟增量 |

除中断/恢复正确性外，应记录完成原因：审核通过与返工额度耗尽分别报告，不能都算成质量合格。不可恢复的版本/配置问题要另列类别，也不能删掉失败运行来提高成功率。

每次实际调用至少记录 run_id、logical_unit_id、attempt、故障点、checkpoint_id、输入哈希、产物哈希、模型、usage、开始/结束时间和完成状态。费用单价须带模型版本与价格日期；当前 llm_usage 的 cost_status 为 unpriced，不能将 token 直接宣称为美元节省。模型已计费但 usage 未返回的调用标为未知，并单列已知成本下界。

## 六、更细粒度恢复怎样实现

以下是针对本项目的设计建议，尚未实现或测量。

### 路线 A：把大节点拆成小节点或可恢复子图

保留现有主流程，将 Agent 内的长循环展开成有持久化边界的步骤：

```text
research:
  固定检索任务计划
    → 单次查询/单站搜索
    → 单个 URL 读取
    → 正文质量处理
    → 单个证据批次抽取
    → 核验批次
    → 合并证据
    → 下一任务 / research 完成

write:
  固定章节计划与全文预算
    → 生成下一章
    → 校验该章并提交内容、claims、引用
    → 下一章 / 综合报告
    → 论断核验批次
    → 定向修复
    → write 完成
```

六章中第三章已提交、第四章未完成时，恢复应从第四章开始；第三章内容、claims、引用映射与输入依据都应复用。章内 API 已返回但未提交的部分仍可能重做。

适合希望直接查看“恢复到哪一章/哪一个 URL”的方案。父图保存大流程位置，子图保存内部步骤位置；不要额外维护一个与图调度冲突的权威 next_stage。现有 run state 接口需要展示子图待执行位置，避免只返回 research/write。

当前 GraphState 将 research 整体替换。若引入并行分支，不能让多个分支同时提交整个 research；应返回按单元 ID 标识的不可变结果，使用确定性 reducer 合并，或保持串行单元提交。按固定 ID 更新 map，避免恢复时 list 追加产生重复证据。

当前 RECURSION_LIMIT=20 是按粗粒度主图设定的。增加循环节点后需按任务上限推导步数预算，保留异常循环保护，不能直接沿用导致正常任务被终止。

### 路线 B：保留大节点，内部使用持久化 task

将昂贵、非确定性的工作包装成独立 task，例如一次搜索、一次正文读取、一次 LLM 证据抽取或一章生成。恢复会重入节点/工作流并重放控制代码；已持久化 task 的返回值用于重建状态，未完成 task 才重新执行。[LangGraph Functional API 文档](https://docs.langchain.com/oss/python/langgraph/functional-api)。

本地安装的 langgraph.func.task 文档也明确支持在 StateGraph 内调用。可从 Writer 入手；无需一次重写五个 Agent。

实现时必须：

1. 把 _write_section 等“原地修改 state、返回 None”的方法拆成“构建输入 → 生成结构化产物 → 校验 → 合并产物”。task 返回 content、claims、来源映射等可序列化结果；节点在首次执行与恢复重放时都应用该结果。
2. 固定章节顺序、搜索计划、证据批次和真实模型输入。时间、UUID、动态历史视图等影响控制流或产物 ID 的值也需冻结或纳入 task 返回值。
3. 恢复时保持 task 调用结构与顺序；升级代码不能把旧 task 序列静默当新序列。恢复前验证 graph_version、计划哈希、模型/提示词/上下文与证据版本。
4. 实测 task 结果写入的崩溃窗口。已完成但尚未持久化的外部调用仍可能重复；task 返回值缓存也不等于任意 Python 行或模型生成中间 token 的恢复。

路线 B 改动通常更集中，路线 A 的位置、状态和运维可见性更直接。可先用 task 做章节恢复原型，再按实际运维需求拆图；不应为同一执行位置维护两套互相竞争的恢复游标。

### 单元身份、产物与幂等

一个单元可使用类似以下身份：

```text
logical_unit_id:
  run_id + graph_version + iteration/revision
  + node/section_id/operation
  + effective_input_hash

effective_input_hash:
  规范化后的实际消息与证据引用
  + 上下文视图版本
  + 模型/参数/提示词版本
  + 检索范围与工具配置
```

这个 ID 表示“一次逻辑工作”；attempt/call_id 表示“一次物理尝试”。当前 ToolRuntime.execute 和 BaseAgent.call_llm 每次生成随机 call_id，这适合审计，不能直接承担恢复复用身份。只用 URL 或 query 做键也不够：正文版本、章节证据和提示词变化时需要重新执行。

可增设单元产物/执行记录：unit_id、status、input_hash、output_ref、output_hash、attempt、fencing_token、usage 与 error。大型原始网页、LLM 返回和正文内容保存到不可变产物存储，检查点只放稳定引用、完成单元清单和必要游标，降低每个小步骤复制全量 research 的开销。

若使用自建任务日志：

- 单元产物、完成标记和待发送事件 outbox 在同一业务事务提交，防止标为成功却没有产物。
- 图检查点与外部业务产物库通常是两次提交，不能声称天然原子。节点重放先按 unit_id/input_hash 查可靠产物，再重建图状态；用幂等处理与对账跨越窗口。
- 运行租约和 fencing_token 必须覆盖新产物写入；对图 saver 的迟到写入保护也要做真实竞争实验，不能仅凭事件账本拒绝旧 token 推断所有存储都已受保护。
- 对支持幂等键的外部写操作复用稳定 key；对搜索、网页读取、LLM 等无法确认外部完成的调用，接受并记录至少一次执行的窗口。

事件中可加入 unit_id、result_version 与 attempt。前端同一逻辑产物按单元 ID 更新，历史尝试保留观测记录；现有 run_id/seq 去重继续负责同一事件重传。新 attempt 产生的新 seq 不应被误当成同一条网络重复事件。

### 更细粒度的实际界限

优先做到“工具调用级、证据批次级、章节级”，因为完成的单元有明确结构化产物，可以重复应用并验证一致性。

保存模型返回的部分 token 可以恢复页面显示，通常不能让下一次模型请求从原服务端解码位置无缝继续。应用层可做重新生成、拼接/去重与章节版本管理；这属于新的生成策略，需要单独测一致性与引用质量。除非所用推理服务提供并验证可恢复生成会话或解码状态接口，否则不应承诺 token 级精确执行恢复。

## 七、需优先补充的恢复窗口

源码显示：service 在 graph.astream 完成后读取终态，再调用 commit_result。两者之间存在进程可能退出的窗口。此时图 snapshot.next 已为空，但报告事务/完成事件可能尚未提交。

当前 POST /research/resume/{run_id} 对 pending_nodes 为空直接返回 400；_graph_input 也要求这类运行读取报告或补做幂等交付。本次检索 app 源码未发现另一处调用 make_commit_result 的对账入口。因此，终态未交付能否自动恢复不能从既有幂等 helper 推出。

建议先增加可复用的“读取终态并对账/补交付”服务：验证运行归属及执行权，检查终态 checkpoint、final_checkpoint_id 与 delivered_event_id；缺交付时调用现有幂等提交逻辑，已交付时回放完成事件。它可供恢复请求或后台对账使用。具体入口和竞争行为需通过真实数据库实验验收。

## 八、局限性与下一步建议

本次未启动实际数据库、HTTP 服务或浏览器；没有评估服务器代理缓冲、长期静默断连、事件大量回放内存、进程死亡后的租约接管、实际计费以及细粒度实现性能。前端医学命名用例验证的是兼容事件投影，不是对旧医学管线做端到端评估。所有未来建议指标与样本量都不是本次实测成绩。

建议按以下顺序推进：

1. 对当前实现跑真实 PostgreSQL + 固定假 Agent 的故障矩阵，优先覆盖跨进程恢复、终态补交付和账本跨 resume 序号。
2. 建立每次物理调用与逻辑单元的成本记录，避免中断前未提交的工作从总成本分母消失。
3. 优先试点 Writer 章节级恢复，再细分 Scout 搜索/URL/证据批次；冻结输入和产物身份，并验证已提交单元不重新调用。
4. 用相同故障计划比较从头重跑、节点级恢复、细粒度恢复，给出按场景的失败数、重做量、P50/P95、费用与正常路径开销；真实模型质量另做配对评估。

本次结论：现有离线用例支持节点恢复与前端事件恢复的基础机制；实际可靠性和资源收益仍需故障注入测量。更细粒度恢复的关键是让每个完成单元具备可持久化、可复用、可验证的产物，并使调度位置与产物提交保持一致。
