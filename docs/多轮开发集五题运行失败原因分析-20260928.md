## 问题一：8块上限实际被用于记录片段数

[summary_hierarchy.py](/Users/bxy/projects/industry_information_assistant/backend/app/service/summary_hierarchy.py:6) 的 `fragments_for_records` 遍历每一条原始记录，各自切片。即使一条tool_input只有少量字，也至少生成一个片段；长记录可能生成多个。

[summary_citations.py](/Users/bxy/projects/industry_information_assistant/backend/app/service/summary_citations.py:311) 随即检查 `len(fragments)>summary_max_chunks`，检查发生在事实抽取、摘要生成和分层合并之前。`hierarchical_summary` 内部也先检查片段数，随后才检查整个请求是否放得下。

这意味着“14条很短的记录可以共同放进一次摘要请求”也会先因超过8块被拒绝。它既限制了长正文切块，又限制了历史记录数量；并非只限制实际需要的摘要请求批数。

根据每次摘要的安全覆盖边界重建，14次尝试的片段数下界分别为：

- 原题8：14、38、46。
- 原题25、26、27：每题14、22、38。
- 原题28：30、38。

这些是非空记录数给出的下界，不是声称已重新精确切片；长记录只会增加片段数量。全部下界均超过8，足以解释为何每次在模型调用前失败。原始错误记录与之吻合。

建议首先区分“来源片段”和“模型请求批次”，把能放下的短记录按完整请求预算组批、长记录按预算切片，并保留每个来源和偏移。总调用数、时间和费用仍需有限上限。仅把8改成64可能绕过第一道错误，但会放大事实抽取/摘要调用数，不能当作已验证修复。

## 问题二：历史输入中重复嵌入的资料没有被外置

[agent_context.py](/Users/bxy/projects/industry_information_assistant/backend/app/service/agent_context.py:22) 将旧llm_input和llm_output纳入回放；`shorten` 只缩短tool类型的记录。与此同时，Scout将网页正文片段、搜索结果、研究问题及分析模板拼成当前llm_input，该长输入随后又成为下一次调用的历史。

因此，工具正文即使已经缩成预览，复制进旧llm_input的内容仍保留。对本次轨迹逐字核对，16条Scout输入包含此前网页工具返回正文的前1000字符片段，说明存在真实内容重复，不仅是静态代码推测。工具原始返回与标准化返回虽然都落盘，但REPLAY_KINDS不包含tool_raw_result，不能将两份工具日志都保存本身误说成两份都被回放。

“当前系统/任务输入”包括固定契约及回读协议；旧输入文本token独立计数，不含全部JSON/聊天封装，分项不能直接相加等同于完整请求。最后一列是本地反事实诊断，没有请求模型，没有改原轨迹。

五题当前任务本身均未超预算，且排除旧输入后均能落入窗口，支持“历史组装是关键膨胀来源”的归因。但这不证明删除所有旧输入是安全修复：旧输入可能包含仍需保留的任务要求。应把用户约束、证据正文和重复模板拆开，保留原始审计日志，并为模型视图建立可追溯的去重/外置规则。

摘要始终失败使覆盖游标不推进，进一步加重这一问题。原题8某次仅靠外置曾从68,995降至22,044 token，说明外置确实工作；只是不能永久代替可用的摘要和合理的历史视图。

## 问题三：规划schema校验与要求类型不匹配，造成重复调用

五题Architect都调用3次，共15次。日志中的反复失败原因主要为“缺少无权威定义时的透明替代方案”，最终走程序补齐后进入Scout；这不是最终致命错误，但增加了10次规划重试。

实际样例来自原题25：模型将“重点考察2020年以来研究”标为time_range，将“区分动物实验与人体证据”标为dimensions，已写planned_response，但fallback_if_unverified为空。代码对所有requirement无条件要求该字段非空，因此这些用户指定的范围要求也触发了“无权威定义”重试。

建议按要求类型/是否需要外部权威核实做条件校验；明确“不适用”的schema口径。不能把所有要求都强制套进权威定义检索场景，也不能直接取消真正需要权威出处的检查。本次没有重新评测调整后的效果。

3. 首轮失败后停止该题后续轮次是预定执行规则，不是追问按钮或SSE失败。当前只能诊断单次研究内部的压缩，尚未测试跨用户轮的要求继承、反证保留及第六轮3000字要求。
4. 当前运行器跨轮传递问答、不延续Scout内部工作历史的设计仍在；本次没有进入第二轮，不能从这些轨迹推断其实际跨轮效果。
5. NLI未运行，不能计算引用支持准确率、置信度分布、复核命中率；没有生成并采用的摘要，不能计算成功摘要质量。事实标注仍待完成。

## 修复与复跑建议

1. 优先修摘要片段计数/组批。用已冻结的首次失败快照验证，要求实际进入摘要生成或得到准确的新阻断原因；不要先重跑全部联网任务。
2. 同时梳理历史llm_input中的重复证据和模板，分离原始审计存储与模型可见视图，保留用户约束和来源关联。使用本次最终失败快照验证预算与信息保留。
3. 调整Architect的条件schema校验，先用本次已生成的规划JSON做确定性回归，减少无意义的三次整段生成。
4. 摘要能够生成后再验证最终引用补齐、字段/覆盖检查、NLI及定向修复；届时才有依据校准判别阈值。
5. 先跑通1题完整6轮，检查各阶段记录、首次摘要采用及第六轮约束传递，再重新采集5题。新运行必须使用新目录、冻结新的代码与配置，旧失败轨迹保持不变。
