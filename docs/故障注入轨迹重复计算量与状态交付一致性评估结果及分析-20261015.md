## 一、重复计算量的定义

本次按用户补充的口径，**把未提交节点内部已经完成、因恢复而再次执行的工作计入重复计算**，并与已提交节点的异常重放分开。

1. 已提交成果重复执行：持久化节点或成功待合并结果已经可复用，却在技术恢复重放阶段重新计算。对于实际进入节点执行的样本，本次未发现此类初始前缀重放。
2. 未提交节点内部重做：同一业务轮次、同一逻辑子任务在崩溃前已经完成，恢复后再次执行。搜索按工具名和完全相同参数配对；章节按故障 marker 的稳定 section_id、大纲标题及首次恢复 write 尝试配对。
3. 正常后续工作：崩溃前尚未生成的第四章、首尾合稿，以及审核后的新一轮补搜/分析/写作不算技术恢复重复计算。
4. 完整请求文本和生成正文不要求逐字一致。三章目标相同，但上下文受前面重新生成内容等影响，本次只第一章的逻辑输入内容哈希相同；第二、三章哈希不同，仍是同一轮、同一章节的重写。
5. 上下文摘要用请求 system 提示词识别。重写前三章期间的摘要调用作为关联开销单列，不能全部声称为完全相同输入的重复摘要。
6. 被恢复入口拒绝、没有真正执行 Agent 的请求，其内部重做指标记为不可评价；不能因为新增调用为 0 就判断恢复效率好。

### 原题 8：重复搜索的证据

工具名为 `v2_web_search`，参数完全相同：

```json
{"count": 10, "query": "machine learning materials composition optimization review"}
```

故障前调用 ID 为 `b6d080ba-89c3-4f3c-8a00-dc28a9f14ba5`，恢复后为 `d87ce19c-0375-4946-8d18-49af62584ad0`。两次均有派发、原始结果和成功工具输出记录，属于两次不同物理调用。该子任务的已完成未提交结果被重新获取，观测重复率为 1/1。

本指标统计搜索工具调用，不据此推断供应商是否命中缓存或实际重复收费；搜索没有 LLM usage，不能把它换算成模型 token。故障发生时 research 尚无已完成模型请求，因此该断点未确认重复的 research 模型生成。

### 原题 25：三章重复生成的 token

故障 marker 确认 sec_1～sec_3 已完成，节点内有三章正文；持久化断点的 draft_sections 中没有这三章。恢复进入 write，随后首次 review 前重新生成三章。

| 章节 | 故障前生成 token | 恢复重写 input token | 恢复重写 output token | 恢复重写合计 token |
| --- | ---: | ---: | ---: | ---: |
| sec_1 | 6,368 | 13,554 | 1,758 | 15,312 |
| sec_2 | 13,843 | 6,503 | 1,582 | 8,085 |
| sec_3 | 8,849 | 14,940 | 1,539 | 16,479 |
| 合计 | **29,060** | **34,997** | **4,879** | **39,876** |

因此这三章已完成未提交的生成工作全部重做（3/3）。39,876 是恢复后再次生成这三章实际返回的 usage，29,060 是故障前这三章原生成的 usage；两者对应不同物理调用，不能用同一列混称。

三次重写模型调用的归档 duration_ms 合计 **62.779 秒**。这是调用耗时之和，不能直接当成关闭重复计算后的端到端省时。

重写前三章期间还触发了两次上下文摘要，消耗 **28,151 token**（输入 26,261，输出 1,890），调用耗时合计 **22.184 秒**。与三章重写相关的这五次调用合计 **68,027 token**；其中后两次仅列为关联开销，不并入严格章节重复生成计数。

首轮全部恢复阶段共记录 64 次带 usage 模型调用、889,396 token。已确认的重复章节生成占恢复模型 token 的 **4.48%**；这是仅涵盖严格确认章节重写的下界，未涵盖搜索工具和其他无法严格配对的计算。若列出前三章重写及其关联摘要，合计占 **7.65%**，该数应称“重写及关联摘要 token 占比”，不称完整重复计算率。

## 三、状态一致性结果

状态一致性分别检查持久化断点、恢复入口读取、最终保留情况；后续合法新增和修订不要求最终整个状态仍与断点逐字相同。

| 检查项 | 首轮结果 | 解释 |
| --- | --- | --- |
| 完整检查点＋pending writes 与断点业务状态 | **5/5**一致 | 26 题成功 pending research 写入必须合并考虑，不能只读旧完整检查点 |
| 断点业务状态与恢复请求读取的 research | **5/5**完整相等 | 比较整个 research JSON 的规范化哈希，并列出变化键；五题均无变化键 |
| 断点已持久化事实在最终状态的保留 | **145/145**条 | ID 和整条事实记录均相等，不只检查数量 |
| 指定固定业务输入/配置字段 | **44/44**个适用检查相等 | 九字段逐题检查；8 题断点尚无 search_backend，该项缺失单列，未当作通过 |
| 最终检查点正文与最终读取正文 | **5/5**一致 | 两个未交付样本的正文也仍可从持久化状态读取 |

事实逐题为：8 题 0→45，25 题 13→16，26 题 51→51，27 题 32→32，28 题 49→49。四题断点已有的 13＋51＋32＋49＝145 条记录全部保持；新增事实属于后续工作。8 题断点没有已提交事实，不能以 0/0 声称其未提交搜索成果已保存。

九项指定字段为 query、original_query、resolved_query、research_contract、context_policy、session_inheritance_config_hash、allowed_domains、hypothesis_enabled、search_backend。这里只验证已归档字段，不能推广为全部部署模型、工具、提示词及依赖冻结。

25 题未提交的三章没有在图断点中保留，是当前节点级粒度允许的工作回退，本次已计入重复计算；它不同于已经承诺持久化的数据被丢失。事实保留也不证明事实本身正确或所有引用原文都能从外部重新读取。

正确交付要求：图已终止且有报告、业务 run completed、报告和完成事件各一份，终态检查点/状态读取/正式报告/完成事件正文 SHA-256 相等。没有正文或没有交付不能按“空值相等”算通过。

| 原题 | 正式报告数／完成事件数 | 正文哈希检查 | 首轮正确交付 |
| --- | --- | --- | --- |
| 8 | 1／1 | 四处正文一致 | 通过 |
| 25 | 1／1 | 四处正文一致 | 通过 |
| 26 | 0／0 | 正文仍在待合并持久化结果中，未交付 | 失败 |

首轮正确交付为 **3/5（60%）**；已交付的三题正文一致为 **3/3**。多余报告和多余完成事件均为 **0**，但有 **2 个未交付样本**，所以不能用“没有重复交付”代表完整交付成功。

### 修复复评单列

- 原题 26 的 pending writes 恢复入口修复后，同一断点从 review 继续，原初稿没有再次生成；后续两次 write 属于审核后的新一轮业务返工。最终报告和完成事件各一条，正文与终态检查点一致。
- 原题 28 的第一次重试仍被拒绝，保留失败；随后终态交付补偿复评成功，没有新增模型或节点调用，报告和完成事件各一条，正文与原终态检查点一致。
- 原题 28 的另一次重复交付请求实测数据库不变，仅回放已有完成事件 seq=176，没有新增报告或完成事件。
- 因此五类原断点分别都有成功交付记录，但这些记录跨修复版本。不得写成“本次重新注入故障五题成功率 100%”。

## 五、失败样例及分析过程记录

1. **26 题：状态可读，调度入口失败。** 旧入口看到 next 为空，就误判已执行结束；实际 Writer pending writes 已存在。此例没有状态读取丢失，但没有进入后继审核，也未交付。它说明仅验证 checkpoint 可读取不足以证明恢复可用。
2. **28 题：图终态正确，业务交付缺失。** 报告在终态检查点中，助手报告和完成事件为 0，业务 run 仍 running。它说明图完成与业务交付是不同提交边界。
3. **25 题：未提交节点内存成果回退。** 三章重写是节点粒度导致的重做，不是原已提交规划、检索、分析节点被重复执行。
4. **本次首轮解析准备失败。** 脚本假设拒绝样本也有节点日志，读取 28 题失败复评时发生 FileNotFoundError，尚未写结果。修正为显式记录日志缺失，并以准入错误、无新增调用和交付状态交叉核对；没有补造节点日志或把拒绝样本当成功。错误与修正保存在本次结果的 preparation_issue 中。

## 已测量、间接推断和尚未评估

**已测量（历史实测，本次重算）：** 同参数搜索工具再次调用 1 次；稳定章节重写 3 次及对应 usage/调用耗时；重写阶段关联摘要 2 次；持久化边界与恢复入口 JSON、事实记录和指定字段的一致性；归档终态正文和正式交付哈希、事件和报告数量；两类失败与后续修复复评。

**间接推断：** 未提交节点粒度导致内部成果无法自动复用；摘要调用与重写阶段相关，但没有严格配对反事实实验，不能把其所有费用都认定为可避免成本。不同修复版本的最终场景覆盖不代表生产总体可靠性。

**尚未评估：** 实际账单、工具缓存、独立报告质量、逐 token 内容完全相同的计算、所有 CPU/数据库开销、任意崩溃的稳定重复率、真实网络/浏览器交付、生产并发及全部外置原文的跨进程恢复。首轮状态读取 5/5 包含两个入口失败，仅代表存档读回一致，不代表五题都成功执行恢复。

## 结论和下一步建议

此前“重复计算为 0”的窄口径只能描述已保存节点/初稿未被恢复重算。本次把未提交节点内部已经完成的工作纳入口径后，得到明确的非零结果：**1 次重复搜索、3 章重复生成、39,876 个直接重写 token**，另有 28,151 个重写关联摘要 token。

状态持久化检查项通过，但首轮交付存在两类真实失败，后续修复复评分别成功。下一步若评估降低重做成本，可在同题、同故障位置、同配置下配对比较纯节点与更细粒度结果复用，并保留本次“已提交/未提交内部/业务返工”分类；交付继续同时统计重复和遗漏，避免只报告零重复。
