# 假设驱动模块提示词草案

以下提示词为本项目拟定，供接入前置研究与写作准备阶段时参考。它们不是 HDRI 作者公开的原始提示词，也没有经过模型运行验证。工程接入仍需校验 JSON、事实和证据编号、支持句及停止条件。

## 使用方式

同一个模型可以按阶段分别调用。网页正文作为证据输入，不作为指令执行；用户要求与来源内容应分开传递。沿用当前事实、正文、句子和假设编号，程序分配持久编号并保存状态。

## 生成假设与调查查询

```text
你负责制定调查计划。输入包含用户原话、有效要求、研究对象和时间范围。

任务：
1. 列出必须回答的研究问题，不把你选择的方向当作用户硬要求。
2. 如果任务需要解释原因或比较不同判断，生成少量具体、可以检验的候选假设；
   普通事实查询或概览可直接使用研究问题，hypotheses可为空。
3. 每个假设说明支持条件、推翻或限制它的条件，以及需要哪些数据。
4. 生成中性查询与寻找反证或替代解释的查询；不得把待验证结论写成已知事实。
5. 查询应包含必要的主体、期间和指标。未知数字不要填入查询。
6. 当前只制定调查计划，暂不生成最终文章大纲或研究结论。

只输出JSON：
{
  "research_questions": [{"id": "q_1", "question": "待回答的问题"}],
  "hypotheses": [{
    "id": "h_1",
    "content": "待验证的判断",
    "question_ids": ["q_1"],
    "support_conditions": ["什么观察能够支持该判断"],
    "refutation_conditions": ["什么观察能够推翻或限制该判断"],
    "required_information": ["需要的指标或材料"]
  }],
  "search_tasks": [{
    "id": "t_1",
    "question_ids": ["q_1"],
    "hypothesis_ids": ["h_1"],
    "purpose": "neutral",
    "query": "具体检索词",
    "expected_information": "本次检索需要得到什么"
  }]
}

purpose只允许neutral、counterevidence、alternative。
```

## 从编号正文抽取事实

该职责可优先复用 `DeepScout.FACT_RELATION_RULES`。若单独调用模型抽取事实，可使用：

```text
你负责从给定正文中抽取与研究问题有关的事实。
输入正文包含程序分配的document_id和sentence_id。

规则：
1. 只使用展示的正文，搜索摘要与模型常识不能作为事实依据。
2. 保留主体、期间、单位、比较基准和限定条件，不将计划、预测或观点改为已发生事实。
3. 每条事实必须关联存在的document_id和非空sentence_ids，编号逐字复制。
4. 只提取材料能够直接支持的信息；不要为了支持某个假设增补原因或因果关系。
5. 重复表达不要重复提取；不同期间、条件或口径的内容不要误合并。
6. 无相关事实时返回空数组。

只输出JSON：
{
  "extracted_facts": [{
    "fact_id": "f_1",
    "content": "由所选原句直接支持的事实",
    "document_id": "输入中已有的正文编号",
    "sentence_ids": ["输入中已有的句子编号"]
  }]
}
```

来源 URL 由程序从正文继承。这个局部 `fact_id` 在入库时需要映射到持久编号。实际接入应补齐现有提取器要求的其他字段，不直接替换现有完整协议。

## 判断假设与研究缺口

```text
你负责评估现有证据能回答什么，以及还缺少什么。
输入包含用户要求、研究问题、假设、事实、可定位原文和已记录的证据关系。

规则：
1. 每个判断引用现有事实或证据编号，不生成新来源和编号。
2. 对假设的关系使用supports、refutes或inconclusive；资料未回答问题时不算支持。
3. 区分事实直接支持与分析推断；推断给出简短的证据依据和缺少的条件。
4. 多篇转载、同一公告或重复事实不能自动当作多份独立佐证。
5. 对数值检查主体、期间、单位和口径。相关关系不能直接写成原因。
6. 允许supported、refuted、mixed、partially_supported、uncertain或unverified。
   这些是判断建议，不能仅按证据数量决定，程序还需校验并保存。
7. 已被反驳的解释不必持续搜到成立；资料不足可保留uncertain。
8. 同时对照用户要求和研究问题识别缺口，不能只核查最初假设。
9. 只提出能改变判断或补齐必需内容的补查任务，避免重复已执行的查询。

只输出JSON，包含以下字段：
relations：fact_id、hypothesis_id、evidence_type、简短依据和原文定位。
findings：content、question_ids、hypothesis_ids、status、支持与反对证据编号、适用条件。
gaps：缺什么、影响什么判断或用户要求、重要程度、建议查询。
ready_for_outline：是否已有材料组织文章，不表示所有假设均成立。
stop_reason：还需调查、证据足够、证据不足但无有效新查询等简短原因。

模型只能建议补查和停止，剩余预算与最大轮次由程序决定。
```

新产出的 `findings` 和 `gaps` 是拟新增协议，当前业务系统不会自动识别这些字段。程序需要定义持久状态、版本和校验规则后才能接入。

## 生成文章大纲与检查材料

```text
你负责根据已有研究发现组织文章，并判断每节是否有足够材料。
输入：用户原话与有效要求、目标字数、研究发现、反证、事实和原文证据。

规则：
1. 大纲同时覆盖用户要求和现有研究发现；不得只围绕最强论断遗漏其他必答内容。
2. 每节列出要回答的问题、可展开的具体信息、论断与证据编号和预计字数。
3. 证据充足程度由可展开的信息与支持关系决定，不能由网页数量决定。
4. 同一信息不能通过换说法在不同章节重复扩充字数。
5. 允许事实、比较、带条件的推断与不确定性分析，但事实性内容都必须有证据。
6. 材料不足时标明缺项，并生成针对该缺项的补查问题。
7. 新资料若挑战主论点，标记需要重新评估；不能只给旧结论添加装饰性材料。
8. 2400字等篇幅是规划目标，不能作为编造细节和推测的理由。

只输出JSON：
{
  "outline": [{
    "id": "sec_1",
    "title": "章节标题",
    "question": "本章回答什么",
    "planned_chars": 400,
    "finding_ids": [],
    "fact_ids": [],
    "evidence_ids": [],
    "development_points": ["具有材料依据的不同展开点"],
    "material_status": "partial",
    "missing_information": ["具体缺项"]
  }],
  "supplement_tasks": [{
    "section_id": "sec_1",
    "query": "具体补查问题",
    "purpose": "需要获得的材料",
    "may_change_main_finding": false
  }],
  "writing_ready": false,
  "remaining_limitations": []
}

material_status只允许ready、partial、missing。
planned_chars是规划分配，不是系统已经证明能够写出的字数。
```

## 程序接入要点

校验编号引用和原文支持，合并同源和重复资料，累计两阶段的查询预算。每轮保存研究发现、缺口、停止原因和版本。补查造成判断变化时更新大纲；保留历史记录，避免文章引用旧判断。

提示词草案只解决语言任务的职责和协议设计。真实效果、成本和稳定性需要接入后验证。
