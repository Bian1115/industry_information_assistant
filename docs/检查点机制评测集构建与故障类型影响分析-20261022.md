# 检查点机制评测集构建与故障类型影响分析

评估／分析日期：2026-10-22（Asia/Singapore）。

评估对象：本项目 DeepResearch 检查点恢复的评测集设计、故障分类、恢复契约与已有证据边界。

数据／配置口径：读取现有方案、2026-10-21 原始回归结果及当前关键源码；当前图版本为 `single-main-v6-atomic-events`。本次没有运行新测试、调用模型、注入故障或修改业务代码。下文样本数量、故障场景和验收目标均为建议，不能当作已完成的评测结果。

## 一、基本单位：任务、故障、提交窗口和预期行为

评测集不能只有研究问题。每条样本应由以下部分组成：

**业务任务 × 故障类型 × 精确发生窗口 × 恢复条件与预期行为。**

最关键的问题是：故障时哪些成果已可靠提交，哪些工作仅在内存中，外部请求是否已经发生，以及保存的依赖是否仍可读取。故障类型决定需要处理哪一层，提交窗口决定能复用多少工作。

例如三章报告：前两章 task 结果及对应事件已经提交，第三章生成中崩溃。期望恢复后复用前两章，允许第三章重新调用；不能要求接着原模型的某个 token 生成。若第三章结果也已保存，只差整个 Writer 的完整图检查点，就应验证已保存 task／pending writes 的复用，不能仅凭完整检查点尚未推进判定必须重写全部章节。

当前 saver 将节点完成事件与完整检查点同事务保存，将章节完成事件与章节 task 结果同事务保存，并在提交后唤醒发送器。正式报告交付仍有自己的幂等与补偿边界，不能视为和全部检查点同一个事务。

事务原子性用于避免事务内半提交状态；数据库提交成功和客户端收到确认仍须作为两个故障窗口处理。参见 [PostgreSQL 事务文档](https://www.postgresql.org/docs/18/tutorial-transactions.html)。

## 二、如何构建两层评测集

### 1. 确定性机制集：验证恢复是否正确

固定模型、搜索、网页读取返回值，给事实、来源、章节、调用和事件稳定身份；使用真实隔离 PostgreSQL。进程崩溃用独立控制进程终止专用 worker，再通过新进程和实际恢复入口续跑，不能用同进程 catch 后继续替代硬崩溃。

覆盖第三节全部适用故障族，重点配对每个提交边界的前后窗口。先用屏障精确命中边界，再增加有种子的随机时间中断。不能只 sleep 若干秒后杀进程，却不证明杀在了哪里。仅使用内存保存器不足以验证跨进程恢复；[LangGraph 持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)也区分图检查点与外置 store。

每个场景写明：必须保留什么、允许重做什么、禁止出现什么、何时算结束，以及期望是成功恢复、可重试暂停还是受控拒绝。错误版本、权限失败、损坏存档应验证正确拒绝，不与可恢复中断混成一个成功率。

### 2. 真实任务效果集：验证实际收益与质量

优先从现有业务题和轨迹中挑任务，保留真实工具和写作结构。覆盖：多轮检索、多来源证据、长证据／外置内容、多章写作、审核返工、追问继承。冻结来源快照、工具数据、提示词、模型与预算配置；实时联网作为单独实验。

低成本首批建议：4 道开发题，每题覆盖搜索执行中、节点结果待合并、章节保存后、终态交付前四个窗口，每个窗口重复 2 次，共 32 个故障情景。题目必须实际到达所选窗口；否则记录未覆盖，而非补造结果。这不是 32 个独立任务，也不包含对照组和存储／并发专项。

后续可按既有方案扩展为 12 题、6 个主窗口、2 次重复，最多 144 个故障情景。按业务任务分开发与留出测试；同题多窗口、重复实验及同父会话不能跨组。设计量仅用于起步，正式样本量应结合失败率与不确定性需要确定。

## 三、不同故障如何影响检查点

| 故障族 | 对检查点／工作成果的影响 | 应注入的典型场景 | 预期行为与验收 |
| --- | --- | --- | --- |
| 模型／工具临时失败 | 已提交检查点通常仍有效，当前调用可能无结果 | 明确失败的429／5xx、连接前失败，之后恢复服务 | 保留已完成工作，按策略重试未完成工作；单列故障持续时长和重试消耗 |
| 外部请求结果不明 | 图存档可能完好，但供应商已执行或计费，结果未入库 | 供应商接受请求后丢响应、返回后本地保存前崩溃 | 保留未知请求与预算预留；有幂等键／查询能力时对账；不承诺外部调用绝不重复 |
| 进程退出／OOM／SIGKILL | 内存内未提交进度丢失，已提交成果可供恢复 | 节点执行中、pending writes后、完整快照后 | 新进程从可靠边界继续；未保存工作允许重做，已保存逻辑成果应复用 |
| 数据库事务失败 | 当前检查点可能没有提交 | 写blob后失败、章节事件INSERT失败、提交前断连接 | 对同事务内容全部回滚，保留上一可靠状态；不得出现没有产物的完成事件 |
| COMMIT确认丢失 | 客户端无法确认事务是否已提交 | 数据库已提交、返回确认前切断连接 | 查询权威状态，重试保持相同逻辑身份，避免新事件／报告重复；不能把超时等同回滚 |
| SSE／浏览器断线 | 首先影响传输与展示，不等于检查点损坏 | 事件已保存但未收到、收到但未应用、缺口超过一页、刷新 | 验证事件补发、成功应用后推进游标、快照边界与去重；若服务端也取消执行，另测续跑 |
| 租约过期／并发接管 | 存档可能可读，但旧进程已失去写权限 | 双恢复、旧执行器迟到提交、事务内租约到期 | 新执行器可推进，旧token不能写检查点、pending writes和交付；覆盖不同调度顺序 |
| 外置证据缺失／损坏 | 检查点存在但依赖不完整，不能认为可正确恢复 | 原文暂不可读、对象缺失、哈希不符 | 区分暂时不可用和永久缺失；按已声明规则重建或受控失败，禁止静默用空证据继续 |
| 终态交付中断 | 图计算结束与用户正式收到报告可能不同步 | 终态检查点后交付前、交付事务后响应前 | 前者仅补交付，后者返回已有交付；不再调用模型／工具，不新增正式报告 |
| 状态版本／配置／权限不符 | 检查点不一定损坏，但不适用于当前恢复请求 | 旧图版本、配置篡改、他人run、任务快照哈希错误 | 明确拒绝且无越权或额外业务副作用；当前版本拒绝不支持旧图，不新增兼容层 |
| 业务语义错误 | 错误内容也可能被正常保存，存档完好不代表答案正确 | 已保存事实错误、引用不支持、计划走偏 | 由质量检查和业务返工处理，不能指望恢复自动纠正；修订后新输入的重写不是技术重复计算 |

主动暂停另作控制场景：停在允许边界且等待用户恢复；不能把用户明确暂停自动当作瞬时故障去重启。反复故障与组合故障在单故障场景可解释后追加，例如断线引发执行取消后又遇到租约接管。

本项目当前 `service.py` 的 `asyncio.CancelledError` 路径会请求取消执行，所以“浏览器断线只是展示问题，后端一直运行”不适用于这里。该判断来自当前源码，本次未做真实socket断线实验。

## 四、按提交窗口确定可接受结果

| 时间位置 | 恢复预期 |
| --- | --- |
| 模型／工具调用前 | 从该未完成工作开始；此前提交成果保留 |
| 调用成功但结果未保存 | 可能要重做；已有供应商费用不能因图回退消失 |
| task／pending writes已提交、完整图检查点未提交 | 复用可恢复的已存结果，验证合并，不用仅看next或整节点重跑次数判断 |
| 完整检查点已提交 | 从后继工作继续，避免重复计算已存成果 |
| 终态检查点已提交但正式交付未提交 | 补做幂等交付，不重做研究 |
| 正式交付已提交但客户端未确认 | 返回同一报告／完成事件身份，补发不等于再写一条 |

因此同一种TimeoutError至少需要区分请求未发出、供应商已执行、数据库提交未知、浏览器未收到四类实际阶段。异常类名不足以决定恢复预期。

## 五、核心指标、对照和失败判定

1. **按故障族／窗口统计恢复成功率**：在预定期限内满足状态契约并完成技术交付的次数／有效注入的可恢复情景数。注入未命中单列；正确拒绝单列；失败和超时不能隐藏。
2. **已保存成果保留率**：以故障前已确认提交的ID、正文哈希、来源关系为分母，恢复后、业务修订前核验。仅看最终有正文不够。
3. **重复计算**：对相同逻辑工作单元及输入版本、已经保存结果的再次模型／工具调用数及token。单列未保存工作重做、框架函数重放和业务返工。
4. **一致性**：事实、章节、claims、预算、事件、报告身份是否满足不变量；独立统计额外报告数、额外事件数和旧token成功写入数。
5. **恢复耗时**：区分故障持续、进程重启、租约等待、状态加载、剩余计算、补交付；终态补交付不混入中途研究均值。
6. **质量与收益**：事实／引用／必答点和独立盲评，另报技术完成且质量合格比例；费用同时记录已知实际消耗、保守预留及未知请求数量。

至少三组配对：B无故障且启用检查点，C同位置故障后从头重跑，D同位置故障后检查点恢复。B/D比较质量，C/D比较重复工作、耗时和费用。C/D尽量具有相同故障前缀，隔离可变存储；故障后增量节省率为 `1-D/C`，同时报告包含故障前成本的全程收益。失败未交付不能用低消耗冒充节省。

若测正常持久化开销，可补A无故障关闭检查点；但必须保证其他工作可比。本项目交付依赖存档，不应为凑A组改变业务路径后声称测到了纯检查点开销。不可比时仅报告组件写入耗时。

机制集硬验收建议：已提交成果丢失0、已存成果重复生成0、额外正式交付0、已知预算漏记0、接管后旧token成功写入0。范围限定在具体版本和故障情景；不要求外部调用不可能证明的exactly-once。小样本给逐条值、中位数和范围，不包装成生产SLA。

## 七、结论与下一步

评测重点是“在确切故障窗口，恢复到正确状态，并只重做允许重做的部分”。任务题目负责提供真实工作负载，故障注入负责制造边界，预先声明的恢复契约负责判分。

建议先整理确定性机制集与历史失败探针，补齐新进程硬崩溃、提交确认不明、外置依赖及并发接管；随后执行4题32情景开发实验及三组配对，最后增加留出任务和真实浏览器验证。本次仅落盘方案与证据分析，不实施兼容层或业务代码改造。
