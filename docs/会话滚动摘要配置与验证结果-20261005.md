# 会话滚动摘要配置与验证结果

评估日期：2026-10-05，Asia/Singapore。评估对象：会话层复现 LangChain 1.4.2 `SummarizationMiddleware` 的配置、消息保留、滚动摘要、持久化和入口接入。此次为机制及集成验证，没有调用真实模型，没有执行开发集 5 题、30 轮对话实验，也没有测量回答正确率。

## 1. 实现结果及启用状态

原会话层的结构化条目抽取改为自然语言滚动摘要。普通聊天和研究请求在消费会话历史前，读取 PostgreSQL 中的“已有摘要＋尚未覆盖的原始消息”，加入本轮 query 后判断阈值；触发时生成一份完整新摘要，替换旧摘要，再交给原来的会话判断、追问改写和研究入口。智能体内部的工作历史机制没有在此次改造中迁移到会话层。

默认配置已写入代码、`backend/.env.example` 及本地 `.env`。本地 `.env` 已有 `CONTEXT_COMPRESSION_ENABLED=0`，此次保留：源码完成并不代表当前服务已启用。没有重启服务、修改主库结构或执行生产会话压缩。运行时读取环境变量，修改 `.env` 后通常需要重新启动进程；现有压缩总开关同时影响智能体内部机制，不能把它当成仅控制会话摘要的开关。

| 配置项 | 默认值 | 含义 |
| --- | --- | --- |
| `SEMANTIC_CONTEXT_ENABLED` | `true` | 启用会话滚动摘要；仍受压缩总开关控制 |
| `SEMANTIC_CONTEXT_MODEL` | `qwen3.8-max` | 生成摘要的模型 |
| `SEMANTIC_CONTEXT_KEEP_MESSAGES` | `10` | 触发后保留的近期消息数，包含当前用户消息 |
| `SEMANTIC_CONTEXT_CONTEXT_WINDOW` | `1000000` | 计算触发阈值的配置窗口，单位 token |
| `SEMANTIC_CONTEXT_TRIGGER_FRACTION` | `0.85` | 达到窗口的 85% 时触发，含等于边界 |
| `SEMANTIC_CONTEXT_TRIM_TOKENS` | `4000` | 沿用 LangChain 的待摘要输入裁剪上限；`none` 关闭裁剪 |
| `SEMANTIC_CONTEXT_MAX_OUTPUT_TOKENS` | `2000` | 摘要输出上限 |
| `SEMANTIC_CONTEXT_REQUEST_ATTEMPTS` | `3` | 生成失败的最多尝试次数 |

默认触发阈值为 `int(1000000 × 0.85) = 850000 token`。Qwen3.8-max 官方说明的完整上下文窗口为 1,000,000 token；模型最大输入和完整上下文窗口是不同字段。更换其他模型且未配置窗口时拒绝初始化，避免静默猜测窗口。[百炼官方模型说明](https://help.aliyun.com/zh/model-studio/qwen3-8-max)

“保留 10 条”按消息计数，不是 10 个问答轮。普通交替的 user/assistant 消息大约对应 5 轮，但本轮用户输入也占一条。此次会话层的消息来自用户与最终助手答复；智能体内部的 Architect/Scout/Writer 对话不计入这个会话窗口。保留数只在触发摘要时参与切分，未触发时不会每次强制截成 10 条。底层切分支持工具消息：切点遇到工具结果时，向前保留对应调用，可能保留超过配置条数。

## 2. 与 LangChain 的对齐及边界

提示词保存于 [`backend/app/prompts/session_summary.py`](../backend/app/prompts/session_summary.py)，原样复用本机 LangChain 1.4.2 的 `DEFAULT_SUMMARY_PROMPT`，没有翻译或添加项目专属摘要指令。它要求输出 `SESSION INTENT`、`SUMMARY`、`ARTIFACTS`、`NEXT STEPS` 四部分，通过 XML 格式传入消息。摘要作为 Human/user 消息回注，前缀原样使用 `Here is a summary of the conversation to date:\n\n`。许可说明另存于 [`许可说明-LangChain.txt`](../backend/app/prompts/许可说明-LangChain.txt)。

已逐字核对的提示词 SHA-256：

```text
3db0629298e760ec31ccb85d9102ef6c7d93f613b1dbc6b74ad18dce14538d0e
```

下一次摘要将旧摘要消息与新增的较早消息一起作为输入候选，生成完整新摘要，而不是继续追加一段摘要。首次遇到旧 schema v1 条目摘要时，从 PostgreSQL 原文重新构建，不沿用旧抽取机制的覆盖游标。主库已有的摘要 JSON、版本、模型及游标字段继续使用，没有新增数据库迁移。回复后的缓存刷新不调用摘要模型；旧 Outbox 摘要任务安全退役，不再覆盖新摘要或推进游标。

实现复现核心策略，并适配本项目 PostgreSQL/Redis 会话接口，没有安装或直接挂载完整 LangChain middleware。与上游及完整业务请求的差异如下：

1. 使用项目的 Qwen token 计数器估计工作消息，而不是 LangChain 默认近似计数器；PG 会话不保留上一次 AI usage，故未复现按上一条 AI 实际 usage 判定的路径。
2. 触发计数包含会话工作消息及本轮 query，不包含随后加入的业务模板、知识库资料、报告候选等。当前业务模型配置仍为 `OPENAI_MODEL=qwen3-max`，此次没有改成摘要模型。**85% 的配置窗口不能保证其他业务模型的完整请求不会超限**；实验时应按实际消费模型及额外输入余量配置窗口。
3. 为复现 LangChain，默认只用待摘要历史末尾约 4000 token，并以 human 消息为起点裁剪。长历史中的旧摘要或较早消息可能在摘要调用前被移除；`trimmed_input_tokens` 明确记录此损失。若实验希望压缩整个旧历史，可配置 `SEMANTIC_CONTEXT_TRIM_TOKENS=none`，此时仍检查摘要提示词和输出预算能否装入配置窗口。
4. 最多 3 次立即重试，SDK 内部重试关闭；没有复现 LangChain 的指数退避及随机延迟。额外拒绝空摘要、输出因长度截断的摘要，防止提交无效覆盖状态。
5. 一次触发只执行一次摘要。近期消息本身过大、没有可压缩前缀，或摘要压缩不足时，不保证压缩后低于 85%。原始聊天消息始终保留，但此次没有实现摘要丢失信息时自动检索原文的能力。

上游参考：[SummarizationMiddleware 源码](https://github.com/langchain-ai/langchain/blob/master/libs/langchain_v1/langchain/agents/middleware/summarization.py)、[官方 API 文档](https://reference.langchain.com/python/langchain/agents/middleware/summarization/SummarizationMiddleware)。本项目固定的是本次核对的 1.4.2 提示词，不会随上游 master 自动变化。

## 3. 持久化、缓存及失败处理

生成成功后，将新摘要、版本、覆盖时间与消息 ID、模型及指标在同一事务中提交。生成失败或提交失败回滚，不删除原文、不推进游标。启用摘要的研究入口准备失败时返回 503，禁止只用原 query 丢掉历史后继续执行。

同会话用数据库行锁串行化摘要，锁后重新读取摘要和消息，避免并发重复覆盖。当前轮最早消息是历史上界，不跨过被排除的当前轮推进游标。较早轮重试发现共享摘要已覆盖未来消息时，从此前原文重建仅供当前请求的临时视图，`persisted=false`，不回退共享游标。

启用新策略后，会话工作历史不再被原有 5000 token/20 条存储窗口或 3000 token/12 条研究窗口二次裁掉。Redis 缓存完整工作视图，配置指纹、排除轮次、最新消息及摘要版本参与缓存身份；缓存命中仍执行阈值检查。Redis 不可用时仍由 PostgreSQL 准备上下文。

摘要事件已记录：模型、提示词版本及哈希、配置指纹、源消息 token、新摘要 token、实际送入摘要的 token、被裁掉的 token、模型 usage（存在时）、尝试次数、耗时、保留条数、覆盖消息 ID、持久化状态以及压缩前后请求 token。

统一计算口径：

```text
compression_ratio = 新摘要消息token（含回注前缀） / 待压缩前缀token（含旧摘要）
savings_ratio = 1 - compression_ratio
tokens_saved = 待压缩前缀token - 新摘要消息token
trimmed_input_tokens = 待压缩前缀token - 实际送入摘要模型的消息token
```

固定替身的基础样例：20 条原始消息共 400 个字符 token，压缩较早 10 条共 200 token，新摘要含包装为 52 token；压缩比例 0.26，节省率 74%，压缩后历史为 252 token。加入本轮 query 后，需保留的 10 条包含该 query，较早 11 条为 220 token，比例为 52/220≈0.2364。**这些数字仅证明指标计算和保留行为正确，不代表真实模型压缩率、延迟或摘要质量。**

## 6. 失败样例与修复

已测量的故障注入：模型请求异常、空输出、长度截断、无效配置、Redis 不可用、错误用户访问、并发摘要及较早轮重试。结果分别验证重试/阻断、原文不变和游标不错误推进。异常用例属于预期测试，不是正常生产请求失败率。

审查发现的机制问题是：若只排除当前轮却继续读取其后的消息，摘要覆盖游标可能跨过尚未处理的消息；较早轮重试也可能读到含未来消息的共享摘要。已加入当前轮历史上界和临时视图，并用新增 PostgreSQL 用例验证。另补上研究入口所有摘要准备异常的 503 处理，避免通用异常降级丢掉会话历史。

两次 LangChain 运行时原包对照因环境依赖失败，详情保留在上述原始文件。没有因此安装依赖或把环境错误当成提示词不一致；最终使用 AST 从原包源码提取常量，逐字与哈希均一致。最终测试中的原包动态对照仍明确标为跳过。

## 7. 局限、结论与下一步

**已测量**：策略默认值与可配置性、逐字提示词一致性、离线裁剪和保留行为、摘要调用协议、指标公式、数据库提交及并发保护、聊天与研究入口接入、失败不裸 query 降级。

**间接推断**：真实模型遵循该提示词后可生成相同四部分结构；不二次裁剪有助于减少会话层在摘要前的被动丢失。尚无真实回答实验支持质量改善结论。

**尚未评估**：真实 qwen3.8-max 可用性、中文摘要质量、递归摘要的信息遗忘、85% 阈值下真实溢出位置、API token 估计误差、生产延迟及费用、真实 Redis 联合路径、开发集 5 题同会话 30 轮的正确回答率。当前 `.env` 总开关为 0，未评估线上实际生效。

结论：会话层所需策略和配置入口已实现，并通过上述机制与集成回归；不能据此宣称长期对话正确率已提高或不会超出业务模型窗口。

下一步建议：先按实际消费模型窗口设置阈值预算并明确是否保留 LangChain 的 4000 token 裁剪，再在新会话执行已约定的 5 题、30 轮实验。逐轮记录输入与实际 usage、是否触发、压缩次数、压缩/裁剪比例、摘要版本、超限轮次、追问改写与路由是否正确、最终回答正确性、事实/约束保留情况、延迟与费用；将每次压缩的摘要和被覆盖消息另存以支持失败追溯。此次没有启动该实验。
