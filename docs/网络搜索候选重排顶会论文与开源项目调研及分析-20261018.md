# 网络搜索候选重排顶会论文与开源项目调研及分析

调研与分析日期：2026-10-18，Asia/Singapore。评估对象：如何让当前项目搜索得到的页面同时满足任务相关性、来源质量和证据覆盖要求，并在展示或阅读顺序中靠前。

最直接的研究参考是 RankGPT 的相关性重排，配合 RRF 的多路融合、MMR 的多样性选择；查询扩展可参考 Query2doc，研究问题覆盖可参考 STORM。工程上优先参考 RankLLM 的重排与评估接口、BGE 的查询与文档相关性模型，以及 Jina DeepResearch 的 URL 阅读优先级。以上方法承担不同职责，不能把相关性分数直接解释为来源可信度。

## 顶会论文及对应问题

### RankGPT 适合搜索候选相关性重排

[Is ChatGPT Good at Search? Investigating Large Language Models as Re-Ranking Agents](https://aclanthology.org/2023.emnlp-main.923/)，EMNLP 2023 主会论文。官方页面给出实验与 [RankGPT 代码](https://github.com/sunnweiwei/RankGPT)入口。

它研究让生成式大模型直接承担候选段落的相关性排序，也研究把排序能力蒸馏到较小模型。对本项目最直接的启发是：搜索供应商先返回候选，再把当前研究子问题与候选内容一起输入重排器。

建议先用标题和摘要做便宜的候选预排，读取后再根据原文判断支持性；这是针对当前系统的工程设计，不是论文已经验证的中文网页方案。论文中的相关性排序结果不能证明发布者身份可靠或内容事实正确。只给网址、让模型凭站点印象打分，也不能等同于论文的文本相关性排序。

### RRF 适合多查询与多后端结果融合

[Reciprocal Rank Fusion outperforms Condorcet and individual Rank Learning Methods](https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf)，SIGIR 2009；[作者所在项目方的出版记录](https://research.google/pubs/reciprocal-rank-fusion-outperforms-condorcet-and-individual-rank-learning-methods/)可核对会议。

它按候选在不同排序列表中的名次求和：对每个包含文档的列表，累加 1 / (k + rank)。原论文使用 k=60，可作为起始参数，仍需针对本地候选规模验证。

当前章节检索会合并多条查询的结果；RRF 可以替代单纯拼接，保留跨列表的名次信息。先按规范 URL 聚合同一页面，每个列表中最多计一次；不同子问题的列表应先明确是否共享排序目标。高度相似的改写查询会产生相关性很高的列表，重复出现不是独立来源佐证。RRF 不读取文章内容，也不会自动判断权威性。

### MMR 适合减少前排内容重复

[The Use of MMR, Diversity-Based Reranking for Reordering Documents and Producing Summaries](https://www.cs.cmu.edu/~jgc/publication/The_Use_MMR_Diversity_Based_LTMIR_1998.pdf)，SIGIR 1998；[正式出版记录](https://doi.org/10.1145/290941.291025)。

MMR 逐步选择既相关、又尽量不同于已选材料的候选。它适合处理“前五页都在转载同一篇通稿”的情况，把有限阅读预算留给不同资料。

内容相似度去重和原始出处归并比单纯按域名去重更能识别跨站转载。“同域最多两篇”只是便宜的工程约束，不等同于 MMR，也可能误伤同一监管网站上的多份不同政策。应在相关性合格的候选内做多样性选择，避免为了不同而引入无关页面。

### Query2doc 适合候选召回不足

[Query2doc: Query Expansion with Large Language Models](https://aclanthology.org/2023.emnlp-main.585/)，EMNLP 2023 主会论文。

方法先生成与查询有关的伪文档，再用它扩展原查询，主要解决短查询歧义和词汇不匹配。适合借鉴其补充术语和消歧思想，生成实体、地区、时间、指标口径更明确的检索式。

原论文涉及可控稀疏和稠密检索器；直接把长伪文档送进商用网页搜索 API，并不保证得到同样收益。对当前项目，建议保留原问题，提取少量可验证关键词形成短查询。生成内容只服务检索，不进入证据库；模型猜出的数值、公司关系或年份不能作为搜索事实前提。

### STORM 适合研究问题与来源覆盖

[Assisting in Writing Wikipedia-like Articles From Scratch with Large Language Models](https://aclanthology.org/2024.naacl-long.347/)，NAACL 2024 主会长论文；[配套项目](https://github.com/stanford-oval/storm)。

STORM 使用多视角提问和检索组织长文写作前的资料准备。对本项目的价值是，把宽泛主题拆成可搜的证据需求，分别找政策原文、统计口径、公司披露、研究资料等，避免所有查询都围绕同一个宽泛主题。

它与排序模块互补：决定“该找哪些资料”，再让重排器决定“这些候选先看谁”。不能因论文使用网络资料或仓库存在来源名单，就推断其默认流程已提供通用、可校准的来源信誉分数。关于名单和默认接线的既有固定版本核查，见[高质量DeepResearch项目信源评级机制调研及分析](高质量DeepResearch项目信源评级机制调研及分析-20261018.md)。

### RankLLM 适合复现与比较不同重排器

[RankLLM: A Python Package for Reranking with LLMs](https://arxiv.org/abs/2505.19284)，SIGIR 2025 资源论文。作者页面标明会议，官方仓库给出接收记录；[作者版论文](https://zijianchen.ca/publications/rankllm_SIGIR2025.pdf)列出正式 DOI 10.1145/3726302.3730331。

其价值是可配置的重排流程、评估和调用分析，适合把外部搜索得到的候选交给不同模型比较。论文与工具提供实验框架，不自动补充来源真实性标签或本项目需要的中文标注。

## 高质量开源项目的接入价值

| 项目 | 可参考部分 | 在本项目中的使用边界 |
| --- | --- | --- |
| [RankLLM](https://github.com/castorini/rank_llm) | pointwise、pairwise、listwise 重排，候选输入与评估接口 | 优先学习数据契约和复现方式；无需为了使用重排器而迁移现有搜索服务 |
| [FlagEmbedding](https://github.com/FlagOpen/FlagEmbedding) 与 [BGE reranker v2 m3](https://huggingface.co/BAAI/bge-reranker-v2-m3) | 查询与文档联合输入，输出相关性分数；官方模型卡标注多语言 | 作为中文业务的专用重排模型候选；需自行测标题摘要与正文输入、截断、延迟及资源开销 |
| [Jina node-DeepResearch](https://github.com/jina-ai/node-DeepResearch) | URL 阅读优先级、域名偏好和阅读预算选择 | 可借鉴候选管理；其中规则分数不能代替内容相关性和来源可靠性评估 |

BGE 模型卡把相关性分数映射到 0—1 的操作只是 sigmoid 变换；它不产生经过校准的“来源可信度概率”。

Jina 的 [rankURLs 固定版本](https://github.com/jina-ai/node-DeepResearch/blob/fd323b521a51264d497bec333bfb997da1bf3210/src/utils/url-tools.ts#L250)综合 hostname 与路径频率、累积出现权重、指定域名加分和已有 rerank 分数。该机制值得参考，但频繁出现可能来自同一内容重复召回；不能将出现次数当成事实可靠程度。项目不是本轮完整运行后的胜出者。

## 当前项目实现与接入位置

核查范围为 DeepScout 的通用网页研究路径；其他搜索路由不据此作全局判断。

1. [candidate_source_score](../backend/app/service/deep_research_v2/quality_pipeline.py#L26)只接收单条候选，没有查询或章节参数。政府与教育域名加 80，标题或站名命中特定词加 50，PDF 后缀加 20，特定低质域名或标签减分。它是候选优先级规则，不能判断页面是否回答当前子问题。
2. [章节检索](../backend/app/service/deep_research_v2/agents/scout.py#L1278)把多条查询结果拼入 all_results；初始展示逐查询发送供应商返回的前五条。这个列表没有先经过阅读阶段的规则排序。
3. [阅读前处理](../backend/app/service/deep_research_v2/agents/scout.py#L914)过滤来源范围，再按 candidate_source_score 排序。章节初搜调用给出 limit=6，部分追溯调用给出 limit=4。
4. [read_many](../backend/app/service/web_reader_service.py#L799)按收到的顺序选前 limit 个不同 URL，再并发读取。因而阅读前的候选顺序会直接影响实际得到哪些正文。
5. [阿里结果适配器](../backend/app/service/aliyun_search_mcp.py#L26)保留 search_provider 与 search_rank。新增跨查询融合时，还应保留查询身份和每路名次；不能仅给合并列表重新编号来冒充原始检索名次。

因此，修改展示顺序和修改阅读优先级是两个接入点。若两处都需要优化，建议消费同一批经过排序的候选，并明确初始临时结果与最终结果的更新关系。

## 失败样例与适用边界

以下为静态机制分析的示意案例，未运行模型或搜索，不能计为真实错排率。

| 情形 | 当前机制风险 | 对应处理 |
| --- | --- | --- |
| 政府网站的旧工作总结与研究主题仅弱相关 | 域名与关键词可获高分，挤掉具体回答问题的研究报告 | 先判任务相关性，再在合格候选内比较来源与时效 |
| 自媒体标题声称“官方年报全文” | 标题自称官方不构成发布者身份确认 | 核对发布域名、文档原始出处与具体原文 |
| 五家媒体转载同一通稿 | URL 不同，仍可能占满阅读预算 | 正文相似度与上游出处归并，再做 MMR 或覆盖选择 |
| 最新转载与较早的原始发布 | 只奖励新日期可能把转载排在原始来源前 | 区分事件时间、首次发布时间、更新和转载时间 |
| 重要官方页面摘要很短或没有关键数字 | 仅凭摘要重排可能误杀原始来源 | 给不确定候选保留少量探索预算，读后再判 |
| 查询扩展生成错误实体或指标口径 | 偏移查询会让高相关候选围绕错误前提聚集 | 保留原查询约束，扩展词与事实证据分开 |
| 页面排得很高但读取失败 | 排名改进未必带来可用证据 | 阅读后按实际可用性更新排序，并计入失败与补读成本 |

## 建议方案与评估设计

建议按下面顺序试验，而不是一开始把多种异质分数随意加权：

研究子问题与约束 → 少量互补查询 → 保留每路名次并规范 URL → RRF 合并 → 查询与候选文本相关性重排 → 对合格候选考虑原始出处、身份、时间和重复内容 → 按预算阅读 → 根据原文支持性与剩余需求补搜。

每个子问题先用约 20—40 条候选、选约 4—6 页阅读，可以作为开发起点；这些是建议预算，不是本轮测出的最优配置。实际数量服从供应商限制及总研究预算。候选只有少量时，应先改善召回覆盖；重排无法找回从未进入候选池的页面。

来源质量至少分别保存发布主体、原始或转载、时间适配、方法或数据透明度、独立上游与未知原因。商业公司是自家财报的一手出处，并不因此成为行业前景判断的无偏来源；政府来源同样需要检查主题、地区、时间和指标口径。

先用固定候选池比较“当前规则排序”和“相关性重排”，隔离排序收益；再在相同搜索、读取与模型预算下比较查询扩展和融合。主要观察：

- P@5 与共享候选池 nDCG@10，明确标签来源、正文核对比例和未知状态。
- Top K 中相关且符合任务来源标准的页面比例；原始来源占比与转载重复率。
- 固定读取预算下的关键需求证据覆盖，以及实际可用正文比例。
- 整任务延迟与成本，同时包括重试、重排、读取失败和补读。

建立共享盲标候选池并固定等级，例如 0=无关、1=背景、2=实质相关、3=直接回答；来源身份和时效另外标注。不要用每个方案自己返回的候选构造不同的理想排序，再据此比较 nDCG；也不要将模型自己的来源评分当作验证该评分的金标。

## 结论与下一步

优先阅读 RankGPT，并参考 RankLLM 建立可替换的相关性重排接口；随后用 RRF 保留多查询的排序信息，用内容与出处去重保护有限阅读预算。BGE 可作为专用模型候选，Jina 可作为候选管理参考。

当前最明确的改进点是让排序看到研究子问题，并让展示列表与阅读列表采用明确一致的排序策略。来源可靠性应保留独立依据，不能用“相关”“官方关键词”“PDF”或模型输出的 0—1 分数替代。本轮只完成资料与机制分析，实际提升需通过固定预算的配对评估确认。
