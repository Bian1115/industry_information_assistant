## 检查点恢复的指标

| 指标 | 定义与计量方法 | 当前是否具备数据 |
| --- | --- | --- |
| 技术恢复成功率 | 原run从断点继续并正确完成交付的运行数／纳入故障评估的运行数。拒绝、失败、超时都计入分母；图completed本身不算成功 | 有，但最新结果跨版本、跨复评 |
| 恢复至完成耗时R | 从发起恢复到报告与完成事件已提交、恢复流收尾的时间。注明是否包含检测、进程重启、租约等待；本轮含状态读取、请求准备、执行与流收尾，不含人工等待及进程导入启动 | 有；按题记录 |
| 时间节约与节约率 | ΔT=B−R；节约率=(B−R)/B，其中B为已有完整运行耗时。失败和B缺失时不算；负值表示本次恢复耗时更长 | 8、25、26题可计算，属于历史基线近似比较 |
| 恢复新增调用、tokens与费用 | 分开统计恢复阶段模型请求、已返回usage、输入／输出tokens、工具调用及费用。ΔC=C完整−C恢复；费用节约率=ΔC/C完整。中断前费用单独列出 | 模型usage与估算费用有；工具计费与实际账单没有 |
| 重做量与持久化成果复用 | 对相同run、节点、业务迭代和输入，统计故障后重复执行的调用／章节。区分已持久化成果重做、尚未持久化单元重做，以及审核触发的新一轮业务返工；三者不能合并 | 有首个恢复节点、节点次数和部分内部边界记录；尚未统一逐工具／逐章节逻辑单元计数 |
| 状态与交付一致性 | 已提交事实、来源及章节能否被正确使用；最终检查点、报告消息、完成事件的正文与checkpoint_id是否一致，业务run是否completed。每run应有一份最终报告、一条完成事件 | 最终正文、交付数量和run状态已核对；全部中间资料未逐字段核对 |
| 正常路径持久化开销（补充） | 无故障时，检查点增加的耗时、写入次数、写延迟、存储字节；比较更细粒度方案时尤其需要 | 尚未单独评估 |

成功条件固定为“可用终态报告＋研究运行completed＋消息和完成事件各一份＋最终正文与检查点一致”，不是收到HTTP 200或看到[DONE]。审核通过率、事实质量和引用质量另外记录；达到返工上限仍可技术交付成功，但不能算质量通过。

本项目当前建议优先汇报：恢复成功数、恢复耗时／省时、恢复新增tokens／费用、持久化成果的重做量、最终交付一致性。五个故障位置各一题，以逐题结果为主；样本不足以可靠估计稳定成功概率或总体P95。

### 成本比较为什么要分口径

用户当前口径是“发生故障之后，继续恢复与从头重跑相比”。故障前已经花费的成本是两种选择共有的沉没成本，因此使用C完整−C恢复、B−R比较断点后的选择；同时披露中断前费用，方便看到实际累计消耗。

若要衡量整个系统容灾总成本，应比较相同故障计划下的“中断前成本＋检测／重启＋恢复或从头重跑”；本次没有配对执行两种完整故障路径。不能把恢复新增费用直接称为整次运行累计费用，也不能把快速拒绝记为省时省钱。

## SSE的指标

| 指标 | 定义与计量方法 | 说明 |
| --- | --- | --- |
| 首次有效进度可见时间 | 请求发出至前端首次应用有意义的进度事件 | 单独一条research_start或心跳不代表任务进度已可见 |
| 首次正文可见时间 | 请求发出至前端首次显示报告正文／章节内容 | 与首次进度分开；当前流按章节提供内容，不能自动当成模型首token时间 |
| 事件显示延迟 | 服务端可靠提交事件至前端应用该事件的时间；样本充分后报告P50／P95 | 需要服务端与客户端时间记录，跨机器要校准时钟；既有事件timestamp不能直接提供浏览器应用时刻 |
| 最大有效进度静默时长 | 从请求开始至终态，最长一段没有新有效进度或内容到达的时间 | 包括首个事件之前、最后有效事件至结束的间隔；心跳仅用于连接保活，不抵消业务进度静默 |
| 最终事件丢失率 | 断线／刷新后完成全部补齐，预期已落账事件中仍未应用的数量／预期事件数 | 比较(run_id,seq)集合；预期事件取该客户端游标之后、测试范围截止前的账本事件 |
| 前端逻辑重复应用率 | 同一(run_id,seq)被重复应用的额外次数／预期唯一事件数 | 网络收到重复帧与UI重复应用分别统计；重放收到重复帧并不等于UI出现重复内容 |
| 断线补齐成功率与耗时 | 游标重放后事件无缺失、无重复应用且页面投影正确的场景数／断线场景数；从重连发起至补齐并恢复正确展示的耗时 | 需要真实断线或刷新与重放测试；同时记录缺口在补齐前是否被错误跳过 |

运行总耗时受模型、搜索和审核返工影响。SSE展示收益用首次有效进度、首次正文和静默时长衡量；SSE可靠性用补齐后的丢失、重复应用、顺序及投影正确性衡量。

网络接收顺序不要求永远没有乱序；应检查客户端发现缺口并补齐后，应用游标是否按正确顺序推进。seq连续只能证明序列层面的证据；需和账本对账才能判断范围内是否漏事件，且不能单凭它证明UI正确。

当前建议优先汇报：首次有效进度／正文可见时间、事件显示延迟、最大有效进度静默、最终丢失率、逻辑重复应用率、断线补齐成功率。

### 当前SSE证据能支持什么

本次重新对账26题恢复流：after_seq=146，账本预期85条事件，进程内收到85条唯一事件，seq=147—231，缺失0、重复接收0，范围内接收完整率100%。原始范围和集合差保存于本次分析JSON。

这个100%表示“真实账本到进程内StreamingResponse消费”的单次范围接收完整率。没有浏览器消费、没有真实断线重连，因此不能称为浏览器事件零丢失、UI重复率0或断线恢复率100%。现有离线前端用例支持中文分片解析、缺口检测和去重机制，但测试通过比例也不能代替用户网络场景成功率。

## 失败样例与局限性

主要失败样例是28题：已有终态正文和流程内pass结论，研究运行仍running、助手报告和完成事件均缺失，技术恢复入口拒绝。这个例子说明“图completed”“报告可从检查点读取”“业务已交付”必须分开。

26题技术恢复成功而流程内审核为needs_revision、completion_reason=revision_limit，是技术成功与质量未通过分离的例子。历史资料、代码、模型输出和返工路径与恢复运行不同，省时及费用收益只是近似估算；不能将全部差值归因于检查点。

已测量：五题已有故障／恢复结果，实际新增模型usage，四题最终交付数量及正文一致性，26题进程内事件范围的账本对账。

间接推断：B−R和历史完整费用减恢复费用的效益估算；节点启动顺序和保存结果支持已完成节点复用的解释，未逐个工具、章节统一计量重做率。

尚未评估：同版本、多次重复故障成功率；正常路径检查点开销；全部资料字段一致性；独立质量评分；真实HTTP／浏览器SSE首显、延迟、静默、断线补齐与UI去重；实际账单和搜索计费。

## 结论与下一步建议

现阶段用逐故障位置的“恢复成功＋恢复耗时和省时＋新增tokens／费用＋重做量＋最终交付一致性”描述检查点效果；将SSE指标作为单独的前端可观测性与重放可靠性评估。

下一步先补齐28题终态交付恢复并复评原断点。SSE可复用现有事件账本，用轻量确定性事件或已有资料回放测真实HTTP和浏览器；补记请求、首次有效进度、首次正文、事件提交及前端应用的时刻，并注入一次断线／刷新，验证after_seq补齐。无需为测SSE再跑五题完整研究模型流程。
