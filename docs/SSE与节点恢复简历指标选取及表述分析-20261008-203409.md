使用开发集原题8、25、26、27、28的首轮问题，结合三类已有证据：真实模型任务的五题 SIGKILL 故障注入；原26、28题检查点的恢复复评；五题的真实浏览器 SSE 链路机制测试。没有增加 DeepResearch Bench 题目。

优先选取故障覆盖、事件去重/补齐和终态补偿开销。这些指标分别对应评测设计、传输可靠性和恢复后避免重做的能力。没有充分证据支持把研究质量、真实用户首显延迟或整体平均时间收益写成优化成果。

## 逐类、逐题分析及失败样例

1. 协议重复注入：六次均拒绝注入的同序号重复帧，最终序号覆盖完整。这个结论不涵盖节点重跑产生的新序号、相同章节内容。
2. 缺口注入：六次均观察到缺口和实际补发请求，最终无缺失序号。它验证指定故障模型下的补齐机制，不能外推为任意网络故障下零丢失。
3. 浏览器断网及刷新：主评测35次中34次完成最终交付，严格口径仅25次通过；严格口径还要求中途无章节重复。原28题断网主测在观察窗口内连续遇到409租约冲突，未完成交付。连接清理复评10次最终交付均成功，但10次都出现过暂时性的章节正文重复，完成事件覆盖后正文正确。不得将这10次称为所有 UI 指标均通过。
4. 开发集8题：部分搜索后恢复成功，耗时23.69分钟，比历史完整执行多约6.42分钟。未提交搜索节点重做及后续审核返工影响耗时，说明不能宣称所有样本省时。
5. 开发集25题：第三章后恢复8.97分钟，复用已提交的规划、初始搜索与分析，未提交写作节点及章节重新生成。属于节点恢复，不是章节恢复。
6. 开发集26题：初测被空 next 恢复准入逻辑拒绝；修复复评后先进入 review，原初稿未重跑。后续两轮写作是审核返工；总计新增23次模型调用，最终质量判断为 needs_revision、以 revision_limit 结束。交付完成不等于独立报告质量通过。
7. 开发集27题：检查点提交后恢复60.06秒，其中租约等待44.38秒，缺少完整成功历史基线，不计算省时。
8. 开发集28题：终态检查点存在但报告和完成事件未交付，旧入口拒绝恢复。后续终态补偿复评3.47秒完成原报告交付，正文10499字符未改变；重复请求仅回放已有完成事件。该3.47秒不包含研究和报告生成，也不是五题平均恢复时间。

## 已测量、间接推断和尚未评估

已测量：五类指定位置故障注入；上述受控浏览器重复帧与缺口测试；连接清理复评的最终交付与正文一致性；原28题真实检查点终态补偿耗时、新增调用数与重复请求行为；26题本次恢复及历史运行分别记录的时间。

间接推断：26题约58.9%的时间差，来自历史完整执行与恢复执行相减；版本、上下文、搜索内容及审核返工路径不一致，不能归因为检查点的严格因果收益。其他终态断点是否同样无需模型调用，尚需重复验证。

尚未评估：同一冻结版本的五题全故障组合与多次真实模型重复运行、并发和生产网络负载、同版本配对的平均/P95恢复时间及费用节约、独立报告质量、真实模型链路的正文首显改善。目前还有新建任务正文在完成事件后才显示、节点重跑造成暂时章节重复的 UI 缺口。

本机回放网络计时的约3毫秒P95接近时钟误差，且报告快速回放不代表真实模型节奏；确定性 Agent 的首显及续跑时间也不代表用户真实研究时延。不得写“生产网络P95低于3毫秒”“研究5秒恢复”或“报告实时流式输出已验证”。
