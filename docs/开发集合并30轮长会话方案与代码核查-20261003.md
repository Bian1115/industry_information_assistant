# 开发集合并30轮长会话方案与代码核查

核查日期：2026-10-03，Asia/Singapore。对象：将开发集原题8、25、26、27、28各6轮串为同一会话30轮，同时启用Writer、Architect工作历史摘要与追问路由。仅检查当前工作区代码和离线机制，不启动真实研究、不调用供应商API、不创建数据库评测身份，不修改业务代码或部署配置。

## 结论

方案适合作为多主题长会话压力测试，但当前代码不能仅靠合并JSONL并打开几个开关就完成目标实验。逐智能体摘要和三路追问已有可复用实现；实验入口、数据结构及跨用户轮会话历史压缩仍需要补齐。30轮全部交付只能证明在冻结模型、预算、输入和质量标准下至少支持30轮，不能确定最大轮数，也不能只凭交付证明没有遗忘。

最关键的边界：Writer/Architect的工作历史摘要压缩同一run中的既往调用，不自动压缩每轮新run首次输入所携带的全会话报告。旧报告被拼进当前提示词后受到保护，这一份原文依然可能超限。

## 逐类问题与代码依据

### 1. 数据结构与入口尚不支持一个30轮会话

[Task.turns](/Users/bxy/projects/industry_information_assistant/backend/eval/multiturn.py:61)限制2至10轮，而且Task只有一个source，不能忠实表示五个来源的合并。需要新增长会话数据结构，保存全局轮号、原题ID、题内轮号、局部依赖和检查项的对应关系，保留原开发集。

[旧多轮入口](/Users/bxy/projects/industry_information_assistant/backend/eval/multiturn.py:149)每个Task创建session，使用`user_id=None`，未提交真实聊天turn，因此不会建立生产追问父成果链。不能以`is_follow_up=True`代替真实父研究定位。

[真实追问采集入口](/Users/bxy/projects/industry_information_assistant/backend/eval/scripts/采集真实追问开发集.py:92)已有隔离用户、UUID会话、真实用户消息和交付后的父检查点定位，可作为新入口基础；但目前仍在每题循环里新建session、清空history、重置预算，且main断言5条任务。现成两个入口均没有单session串30轮模式。

### 2. 同一session不代表工作历史摘要跨用户轮延续

每个用户轮新建run是业务追问的正确执行语义。生产[历史context定位](/Users/bxy/projects/industry_information_assistant/backend/app/service/agent_history.py:107)按`run_id + agent + context_key`隔离，摘要版本与覆盖游标随该context保存。父研究复制的是白名单业务成果，不复制AgentMessage和历史摘要。

因此不能把新轮首个Architect请求描述为“已经继承上一轮Architect摘要”。也不应复用完成态run或用`resume=True`伪装业务追问；resume用于恢复中断运行。

### 3. 全对话历史会落入受保护当前输入，是首要容量风险

[research_context](/Users/bxy/projects/industry_information_assistant/backend/eval/multiturn.py:96)复制全部问答。[Architect历史渲染](/Users/bxy/projects/industry_information_assistant/backend/app/service/deep_research_v2/agents/architect.py:47)把这些报告拼进本轮规划提示词，[规划输入](/Users/bxy/projects/industry_information_assistant/backend/app/service/deep_research_v2/agents/architect.py:327)交给BaseAgent。

[prepare_agent_messages](/Users/bxy/projects/industry_information_assistant/backend/app/service/agent_context.py:289)保留当前system/user消息，只为本run中既往完整调用生成摘要。当前输入即使包含旧会话，也不会被当成这些候选。[最后预算门禁](/Users/bxy/projects/industry_information_assistant/backend/app/service/agent_context.py:540)仍可拒绝输入。后续同run摘要即使成功，也不能删掉下一份当前提示词重新嵌入的全部会话原文。

实际失败轮次必须真实运行或用真实报告离线计数测量，不能现在猜测。全量会话压力模式可用于测这个瓶颈；若目标是验证可持续长会话，需要额外接入会话级摘要、近期原文及可回读旧成果的组装机制。

生产也已有独立的`semantic_context_service.py`会话语义摘要链路及SessionMemory，不能说整个仓库不存在会话摘要；但本次两个评测入口直接传`research_context(history, query)`，绕过它的上下文构建，不会自动消费其摘要。若改用[ResearchContextService.build](/Users/bxy/projects/industry_information_assistant/backend/app/service/research_context_service.py:100)，还会引入默认3000-token/12消息裁剪及可能的长期记忆、异步摘要，必须显式冻结并分别报告，否则会把裁剪或其他记忆模块的作用归因给Writer/Architect。

### 4. 追问路由可用，但可见范围有限

[服务父研究定位](/Users/bxy/projects/industry_information_assistant/backend/app/service/deep_research_v2/service.py:366)要求真实user/run身份，定位同会话最近完成并交付的研究。[路由输入](/Users/bxy/projects/industry_information_assistant/backend/app/service/deep_research_v2/followup_router.py:287)只取最后6条消息，也就是通常最近3个完整问答轮，并在自身token预算下逐项省略资料；不是阅读整个30轮对话。

Writer修订路由可跳过Architect，Scout补搜路由也不必重新规划。应按智能体统计实际请求与摘要采用，不能要求每轮两个Agent都触发摘要。路由超时、格式失败或材料校验失败可以回退重规划，应将回退与正常重规划区分计数。

### 5. 换题隔离与跨题记忆是两件事

第7、13、19、25轮开始新主题。前一题第6轮都设置3000字，跨题还存在研究对象、物种/人群、时间及证据边界。当前代码在`reuse_previous=False`时清空旧成果与约束并移除session_planning_context；换题隔离已有回归。但是否能正确判断换题仍由模型决定，全文conversation_context也不会因此自动删除。

应记录换题的路由、reuse_previous、有效契约以及旧题约束是否误继承。正常清除旧题事实能帮助隔离任务，却意味着不能用最近父研究的成果继承证明系统还记得更早题目。五段任务各自只依赖最近六轮；纯顺序拼接缺少跨题早期召回检查。

### 6. 成功口径、预算和观测还需要补齐

真实采集入口目前每题共享一次有限预算，改为单长会话后需明确整条30轮共享的时间、请求、各模型token上限及分轮上限，涵盖路由、研究、摘要、回读与重试。预算耗尽、网络失败、交付失败、上下文超限与遗忘须分开归因，不能都叫“模型最多支持N轮”。

现有context_view及llm_request能记录输入长度、摘要尝试/采用、覆盖游标；长会话还需加全局轮号、原题/题内轮号、实际会话输入范围、路由回退、主题切换、连续成功前缀和失败时未执行轮次。[compression_points](/Users/bxy/projects/industry_information_assistant/backend/eval/multiturn.py:103)的`summary_used_in_request`只关联本次新采用摘要，已有摘要继续使用但本次无版本更新不能据此记为“没用摘要”；已有的请求计数也不等于供应商响应成功。

## 建议的实验方案

1. 保持原5题开发集不变，新增单session的多主题30轮压力集，顺序按8→25→26→27→28，每轮仍使用独立run。保留五题来源及依赖映射；每次换题显式标注开始新课题和旧课题专属要求不适用于本题，不泄露未来追问或评价答案。
2. 基于真实追问采集入口新增长会话模式，统一隔离身份、session、预算、逐轮结果和失败停止规则。启用ChiefArchitect、LeadWriter摘要，明确保留DeepScout现有机制，显式启用追问路由，冻结逐Agent配置与源码。
3. 区分全量会话输入压力模式和会话级压缩模式。先用前者识别当前受保护输入瓶颈；后者应把已结束旧轮次从当前完整报告区移到会话摘要/成果索引及可回读存储，保护本轮指令与有效契约。现有run级工作历史摘要仍保留其独立职责。
4. 在相同路由、模型、单次窗口、输出上限和搜索范围下做摘要关/开的配对实验。工作历史摘要效果与会话摘要效果分别设置对照；若直接增加会话摘要，只比较全部摘要开/关不能单独证明Writer/Architect的收益。实时研究会产生不同证据，机制归因最好补充冻结材料回放。
5. 先检查第一题6轮及第一次换题，验证真实父成果、题目隔离、输入范围和实际摘要请求，再完整30轮。完成后在新增版本中增加有意义的更早题目召回、引用来源定位、修订早期结论等追问，并继续扩展轮数；不靠重复报告凑长度。
6. 并行报告连续交付轮数、早期约束遵守、历史事实/冲突/限定保留、来源可追溯性、摘要触发/采用、输入token与累计开销。质量检查项留在评测侧，事实答案来自人工核对的冻结原文；不要把模型报告当作真值。若30轮完成，结论为“至少30轮”；如第k轮失败，报告已完整交付k−1轮及具体失败类别。当前只有一条顺序长会话，轮次不是30个独立样本，也不是正式测试成绩。
