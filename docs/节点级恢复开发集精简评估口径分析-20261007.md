# 节点级恢复开发集精简评估口径分析

分析日期：2026-10-07（Asia/Singapore）。

评估对象：既有开发集上的当前 LangGraph 节点级恢复。依据用户本轮要求，将上一版广泛故障矩阵精简为“一次完整基线＋分配到不同运行的五个故障位置”。不纳入更细粒度恢复对照或单独的 SSE 性能评估。

状态：本次核查源码与分析实验口径，没有启动真实模型、搜索、数据库故障注入或新的恢复实验。这里的计划、公式和数字示例均不是实测效果。

## 一、结论

赞成这个设计。每个开发集样本无需在每个故障位置重跑；一次正常完整运行可作为同一题/同一轮各恢复场景的基线参考，再将故障位置分配到不同样本或轮次。

时间节省可以按“正常从头完整运行耗时－故障后节点级恢复耗时”估算，前提是恢复计时从恢复请求开始，比较的是同一题、同一轮、同一完成标准，且不把故障前已花时间算进恢复段。

所得指标应命名为“相对从头重跑的基线估计节省”。因为没有真的在每个故障位置运行从头重跑对照，在线模型、搜索、返工和缓存变化仍可能影响两次执行的差值。

## 二、数据与配置口径

源码中既有开发集是原题 8、25、26、27、28，每题 6 轮，共 30 轮。每轮对应独立 run；是否五题各自会话或合并一个会话，应沿用选择的既有开发集口径，两遍保持一致。

一次完整基线按开发集现有全部轮次执行并记录成本，额外输出逐 run、逐节点和逐次物理调用明细。比较单轮恢复时使用对应轮次的完整基线，不能用 30 轮总耗时减一个 run 的恢复耗时。

如果已有符合当前代码与配置口径、且具有完整时间和成本记录的成功开发集运行，可用作基线；仅有最终报告或累计账本的历史运行不一定足够。

应冻结：数据哈希、轮次顺序、前序会话输入、Agent 历史/摘要视图、模型与参数、提示词、上下文压缩、核验开关、来源范围、返工预算和计费单价口径。缓存命中单独记录；实时搜索无法完全冻结时，在局限性中说明。

## 三、运行安排

建议的简单安排：

1. 开发集正常完整跑一遍，保留逐轮完整耗时与成本。
2. 第二遍按相同会话组织与配置执行，将五个故障位置分配到五个合适的 run；每个选中 run 只中断一次，恢复后继续。
3. 其他轮次正常运行，不做“每题 × 每个故障位置”的笛卡尔积。
4. 每个故障场景记录是否实际触发、恢复成功/失败、节点重跑次数、状态和产物一致性。

若更希望降低总模型成本，第二步也可只重跑五个选中 run 的故障前部分并恢复。但需要把这些轮次的前序会话与 Agent 历史恢复到对应基线轮次开始时的状态。不能直接用已跑完 30 轮的最终会话历史来重测早期轮次。这个路径需要额外做隔离快照与还原；首轮实验采用第二遍开发集更容易控制。

第二遍产生的前序报告可能与基线有差异，影响后续任务输入。若采用这种方式，后续轮次收益属于对应开发集执行的近似配对；冻结同源前序状态可提高可比性。

五个故障位置先在基线轨迹中挑选符合条件的运行，再确定映射，不凭题号猜测是否经过该节点。

| 位置 | 精确定义与触发条件 | 节点级恢复应验证的内容 |
| --- | --- | --- |
| 完成部分搜索后 | research/re_research 内一次搜索成功返回，节点未完成；在下一操作开始前屏障停住 worker | 已提交规划等前序节点不重跑；检索节点允许重新执行，具体复用的历史/缓存另记 |
| 写完第三章后 | 本轮实际新生成第三个唯一章节，并应用正文与 claims；write 未完成；第四章开始前停住 | 已提交检索/分析不重跑；失败 write 内新增章节可能重做；不把章节 SSE 当检查点 |
| 检查点提交前 | 选定节点输出的完整 checkpoint 持久化前停住 | 读取真实 full checkpoint 与 checkpoint_writes，验证调度符合已持久化状态 |
| 检查点提交后 | 同类节点检查点确认持久化成功，下一节点开始前停住 | 已提交节点不能重新执行，后续未完成节点继续 |
| 完成事件发送前 | commit_result 成功提交报告、run 状态与完成事件后，yield 完成事件前停住 | 回放已提交完成事件即可；已完成图不应重新执行 |

“第三章”按本轮生成顺序和唯一 section_id 统计，不能按重复事件数统计。如果某轮不足三章，或编辑路径没有逐章生成，该轮不适用，应预先换成基线中符合条件的 run。不能为了触发故障而改变报告任务。

检查点提交前不必然等于“整个当前节点结果全部丢失”：LangGraph 还可能已持久化成功任务的 pending writes。应记录实际提交状态与恢复后的调用计数，不预设必须重跑哪一个节点。

完成事件发送前的定义选择了业务事务已提交的窗口。如果要测 finish 已提交但 commit_result 尚未提交，那是另一种“终态补交付”场景；当前代码存在待验证的恢复入口问题，不能将两个窗口混成一个样例。上一版报告已记录该问题，本轮不自动扩展场景。

## 四、核心指标与计算

对同一题的同一轮：

- B：正常基线从本轮开始到完成标准的耗时。
- P：故障执行从本轮开始到中断位置的耗时。
- R：发起恢复请求到达到同一完成标准的耗时，不含 P。
- D：故障发生到发起恢复之间的停机、人工等待时间，单独记录。

核心公式：

```text
相对从头重跑的估计时间节省 = B - R
估计时间节省率 = (B - R) / B

故障执行相对正常基线的开销 = P + R - B
用户实际等待总时长 = P + D + R

估计费用节省 = C_B - C_R
故障执行已知费用 = C_P + C_R
```

比较的是故障之后的两种选择：从头再来约需 B，节点级续跑实测需 R。两者共有的故障前已消耗 P 因而抵消。B 不必减去故障发生时的已运行部分；B-P-R 则是在比较本次故障执行与正常不中断的总耗时，应以相反符号报告为故障开销。

教学示例，非实测：基线 B=600 秒，故障前 P=400 秒，恢复 R=250 秒，则相对从头重跑估计节省 350 秒；故障执行总耗时为 650 秒，相比正常运行多 50 秒，不计停机等待。这两个结论可以同时成立。

R 建议包含恢复请求后的租约等待、状态读取与执行；内部纯执行时间也可单独列。用户等待 D 不混进模型执行时间，但保留便于理解真实恢复体验。

成本按实际物理调用分账：主任务、摘要、核验、重试和失败调用都要保留。失败调用未返回 usage 或价格缺失时记为未知，列已知成本下界与未知调用数，不能填零。总 token 的相同差值也可以报告，但不同模型 token 不应直接当成等价费用。

每个场景至少报告：

1. 对应 source_id、turn_id、run_id 和实际命中故障点。
2. 故障前最近 checkpoint_id、pending writes、恢复前后的待执行节点。
3. 恢复是否正确完成、已提交节点是否重跑、报告/完成事件是否重复。
4. B、P、R、D 以及差值；C_B、C_P、C_R、token 与未知用量。
5. 与基线的模型调用、搜索、返工、输入与缓存差异。

五个场景各一个样例足以做首轮机制验收，不能据此宣称稳定总体成功率或有代表性的 P95。不同题和不同故障点不能直接作为严格的场景间性能排名；负收益、失败与未触发都应如实保留。

## 五、源码核查与运行器需补的记录

依据本轮读到的源码：

- 采集真实追问开发集.py 已有 resume=True、原 run/session 恢复和成本账本继承入口，但没有上述五个指定硬中断钩子。
- 当前 TaskBudget 的 requests 是模型预留/usage 账本，duration_seconds 是账本生命周期累计值。它不足以独立给出每个节点的 B、P、R；恢复期间的累计时长也不能直接当恢复段。
- run 级 AgentMessage 含 node、run_id、LLM usage 等，有助于分账；仍需记录跨进程的每次尝试和起止时间。
- 硬退出会跳过 finally 和内存账本导出。每次调用费用/usage 和计时应实时写到持久化记录，避免故障后原始成本消失。
- 调用 cancel 接口属于受控取消；如果要测进程死亡，使用隔离 worker、明确屏障和进程重建。不要把受控取消测试报告成 SIGKILL 恢复。
- service.py 的 commit_result 在完成事件 yield 之前。业务已经完成时应读 state/events 补发完成事件；盲目调用 /resume 会遇到“图已结束”的拒绝，这不等于已提交报告丢失。

首轮只应增加测试运行器与持久化遥测，不为了提高测试成绩先改变恢复粒度。若测到恢复问题，先保存失败轨迹再决定修复与复评。
