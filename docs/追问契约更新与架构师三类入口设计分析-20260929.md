# 追问契约更新与架构师三类入口设计分析

后续范围确认（2026-09-29）：用户决定暂不增加 Critic → Architect 路径。本报告中的该路径仅保留为历史设计讨论，不纳入当前实施范围；当前机制说明见 [追问路由研究契约状态更新机制说明](追问路由研究契约状态更新机制说明-20260929.md)。

分析日期：2026-09-29。评估对象：所有追问分支的研究契约更新，以及首次规划、用户追问重规划、Critic 驱动修纲三类入口。

本次为同日架构分析的补充，新增文档保留历史。前一份报告为 [架构师上下文与追问约束链路分析及改造建议](架构师上下文与追问约束链路分析及改造建议-20260929.md)。本次新增口径：区分“模型提出契约变更”和“程序提交有效契约”，并纳入尚未实现的 Critic → Architect 路径。下述新增字段、函数与路由均是建议，不是已接入功能。

## 2. 谁更新追问契约

建议让当前负责理解追问的模型，在同一次调用中输出：resolved_query、constraint_patch、route_proposal 和 revision_instructions。程序随后合并并校验契约，确认路由仍适用后再进入下游。这样不需要为“更新契约”再增加一个模型调用。

模型负责识别语义，例如“取消之前的字数限制”“只分析2025年”；程序负责约束ID、字段类型、版本、继承、变更出处、执行投影和原子提交。程序能确认引文确实来自用户，却不能仅凭字符串匹配证明所有语义解释正确；歧义需要显式保留，不能把确定性校验描述成语义正确性保证。

建议流程：

```text
本轮原话 + 旧有效契约 + 必要历史/材料索引
    → 消解/路由模型：独立query + 约束变更提案 + 路由建议
    → 程序：校验提案，合并为本轮完整有效契约
    → 程序：按新契约校验材料复用和路由条件
    → 原子保存本轮query、契约、执行约束与选定路由
    → Writer / Scout / Architect
```

“先更新再路由”指在执行路由之前提交有效契约；模型可以一次同时提出路由和更新，无需先后调用两个模型。模型判断材料充分性时必须按本轮修改后的要求判断，不能只按父研究的旧目标判断。

### 2.1 变更提案示例

假设用户明确说“字数上限从5000改成3000，其他不变”，现有字数要求ID为 req_length。模型可提出：

```json
{
  "resolved_query": "原研究主题及其他要求保持不变，正文不超过3000字",
  "constraint_patch": {
    "base_version": 4,
    "operations": [
      {
        "op": "replace",
        "requirement_id": "req_length",
        "value": {"max_body_chars": 3000},
        "provenance": {
          "message_id": "本轮输入中实际存在的消息ID",
          "quote": "字数上限从5000改成3000，其他不变"
        }
      }
    ]
  },
  "route_proposal": "writer_revision"
}
```

省略了完整路由协议中材料充分性、支撑事实等字段；此片段不是可直接传给现有 RouteDecision 的对象。

建议新增 `apply_contract_patch()` 作为统一入口：

1. 校验 base_version，避免把旧提案应用到新契约。重试使用变更ID或消息ID保证幂等。
2. 校验操作类型、目标ID、值域和用户出处；运行配置/来源权限不可由模型扩大。
3. 对已有契约执行 add、replace、remove；未涉及的要求原样继承。取消字数限制使用 remove，不使用表示无修改的 null。
4. 更新完整 query 与要求清单，从规范化要求推导 active_constraints；禁止两套状态分别修改。
5. 校验新要求与材料、章节、路由的关系。修改时间或来源范围后，旧材料不能未经重新判断就当作充分证据。
6. 原子保存契约及相关状态，使用服务端生成的新版本，再执行目标分支。

不是每次追问都必须更改契约内容：例如“换一种表述”可以只更新修订指令；仍需要经过同一有效契约检查。契约未发生语义变更时可以保留版本，不必人为递增。

### 2.2 各入口如何复用

- 智能路由开启：扩展 FollowupRouter 的输出，复用同一次模型调用完成消解、约束变更提取和路由建议。
- 路由关闭：若仍支持追问，应扩展现有消解器输出相同的变更协议，合并后按默认规划路径执行；不必再强制调用智能路由。
- 首次研究：Architect 可从用户原话提取初始契约候选，由同一契约规范化/校验层提交。
- 路由超时或解析失败：不能把失败当作“用户没有修改要求”，也不能先提交半份更新。可复用已有重规划降级路径，让 Architect 明确以“旧契约＋本轮原话”重新提出完整变更，校验成功后才能继续；无法可靠解释时进入澄清或明确失败。
- 新主题：明确旧要求的适用范围。研究对象、时间范围等主题绑定要求不能机械继承；持久的用户偏好是否继承由既定规则决定，不以“换主题”一概清空或全保留。

## 3. Critic 是否能让 Architect 重写大纲

当前不能。Critic 根据是否有补搜任务选择 Scout 或 Writer，图中不存在 review → Architect 的边。已有 _check_revision 方法不等于该能力在主链路可达。

建议增加这条路径，但只用于大纲结构问题，不把“评分低”“major_issues”直接等同于需要重规划。

| 问题 | 建议接收方 | 原因 |
| --- | --- | --- |
| 现有章节漏写已有事实、措辞或跨章节结论矛盾 | Writer | 结构仍然适用，局部修订即可 |
| 现有章节需要更新数据、补来源 | Scout | 缺证据，不必改变大纲 |
| 用户要求多个对象比较，大纲只围绕一个对象，现有章节无法承载比较 | Architect | 需要调整任务分解和结构 |
| 大纲章节严重重复、研究范围分配错误、核心要求无合适承载位置 | Architect | 修正结构后才能合理补搜和写作 |

“缺一项内容”不一定意味着缺一个章节；必须说明现有章节为何无法修复，否则容易导致不必要的重规划。

### 3.1 三种规划模式

统一入口 `Architect.plan()`（建议接口）接收同一核心schema，用 planning_mode 区分：

| 模式 | 核心输入 | 额外输入 | 用户约束是否可改变 |
| --- | --- | --- | --- |
| initial | 自身上下文、当前query、研究约束 | 首次历史可为空 | 从用户原话提取初始候选，经程序确认 |
| user_replan | 自身上下文、原话/消解query、本轮有效契约 | 上一版大纲、本轮修改指令 | 有用户依据才改变；上游已更新的约束不可再次擅改 |
| critic_revision | 自身上下文、当前有效query、有效契约 | critic_feedback、当前大纲、相关报告片段和证据/进度摘要 | 保持用户要求，调整完成要求的方法与章节映射 |

因此用户提出的三条路径合理。第二条需要显式的 Critic 意见，不能只期待 Architect 从自身历史里找到它。Critic 是另一智能体，其最新输出不属于 Architect 过去的历史；以前已经处理的意见也不能替代最新意见。

### 3.2 建议统一的输入结构

```text
planning_mode: initial | user_replan | critic_revision
architect_context:
  own_history_summary / recent_messages
  last_outline / last_contract_version
  progress_summary / outline_limits
current_query:
  original_query / resolved_query / resolution_context
research_constraints:
  effective_contract / runtime_constraints
critic_feedback: null 或结构化审核意见
```

planning_mode 是控制元数据；critic_feedback 为条件字段。前两种模式通常不需要它，critic_revision 必填。用户追问若仍需处理旧审核问题，可以附上与当前版本匹配的未解决问题，但它们不能覆盖新用户要求。

critic_feedback 建议包含 review_id、outline_version、report_version、contract_version、issues、相关报告片段。其中 issue 包含问题ID、关联要求ID/章节ID、具体缺陷、所需结构变更及验收条件。不需要每次完整复制所有历史报告和原始证据。

提示词采用共用核心规则、共用输出schema，再按模式添加任务说明。输出继续保持 outline 与 research_contract 两个顶层字段；Critic 模式下研究对象、日期、篇幅等用户要求保持不变，但契约中的章节覆盖映射和规划派生字段可随新大纲更新。程序可校验用户约束前后相等，避免模型为通过审核降低要求。

## 4. Critic 路由协议和执行闭环

建议给 issue 增加 `requires_outline_revision`、`affected_requirement_ids`、`outline_revision_reason`，并保留 `requires_new_search`。二者不是互斥关系：一个问题可能同时需要改大纲和补证据。严重程度不代替动作标记。

服务端验证相关章节/要求是否存在、重规划理由是否齐全、意见对应的版本是否当前版本。完整性检查不能保证 Critic 语义判断一定正确，仍要通过回放验证误触发率。

建议按以下顺序调度：

1. 审核结果与动作标记必须一致；仍提出结构修订/补搜时不能同时作为 pass 结束。
2. 有有效结构修订请求且预算允许，进入 Architect 的 critic_revision。
3. 无结构修订、但需新证据，进入 Scout。
4. 仅需写作修订，进入 Writer。
5. 通过或返工上限到达，使用明确终态；到达上限不称为通过。

结构问题与证据问题并存时先改大纲，然后把尚未解决的问题及检索任务绑定到新章节。不能直接复用已被删除的章节ID，也不能在重新规划时丢失 Critic 的补搜要求。

重规划后不应默认从零研究。对比新旧大纲，保留适用原文和事实；重新建立章节与材料的关联。需补搜则 Scout → 必要分析 → Writer → Critic；证据已经足够则复用相应分析结果并交 Writer，再审核。大纲/指标变化导致旧分析失效时必须重算。旧草稿按章节失效范围处理，不能直接把不适用段落拼入新报告。

当前 plan 固定进入 research，而且 _initial_planning 会创建新的规划状态。接入 Critic 时需要新增明确的重规划入口或在统一 plan 中按模式分派，并调整出边和派生状态失效规则；不能仅加一条 review → plan 的边。

返工保护建议：Critic 重规划共享现有总返工次数，同时设置独立 `max_critic_replans`（初版可设为1，需实验验证）。重规划不得重置 iteration、搜索消耗或总预算；相同问题和相同大纲反复出现时应停止重复循环、保留未解决问题。用户新一轮追问的预算由新run规则决定，与同一run内 Critic循环分开。

## 5. 验收样例、局限与下一步

本次没有真实失败样本复现；以下为待测的机制风险案例：

| 案例 | 必须验收的结果 |
| --- | --- |
| 上限5000改为3000走Writer | 契约、执行投影与Writer输入一致，其他要求保留 |
| 取消字数限制 | remove真正生效；不是null继承 |
| 更换时间范围走Scout | 新时间要求进入契约，过期材料不算充分证据 |
| 提案版本过期或重试 | 不覆盖新契约，不重复应用同一变更 |
| 路由失败 | 无半份提交，不静默忽略本轮修改 |
| Critic仅指出数据过时 | 走Scout，不无故改大纲 |
| Critic指出结构无法承载比较要求 | 三模式之一critic_revision，收到具体意见及当前版本 |
| Critic建议删除用户明确要求 | 不改变用户要求；暴露未解决冲突 |
| 修纲且补搜，旧章节删除 | 补搜任务重新绑定章节，审核问题不丢失 |
| 连续相同结构问题 | 达到预算后停止，并明确尚未通过 |

已确认：当前Critic主图不能回到Architect，现有追问变更字段和旧消解器协议不足以直接实现本方案。已测量边界：只做静态核对和文档示例JSON语法检查，没有成功率、成本或时延测量。间接推断：公共契约提交可减少路径间约束不一致，受限结构返工可处理Writer/Scout无法修复的问题。尚未评估：模型约束提取准确率、Critic重规划误触发率、版本/缓存适配正确率及端到端质量收益。

下一步建议先实现追问契约公共更新，再实现三模式输入/输出及Critic结构问题协议，最后接图路由和材料/草稿失效规则；用上述机制案例验收后，使用固定开发集比较“无Critic重规划”和“最多一次Critic重规划”，同时报告质量、返工次数、token、时延及预算终止率。生产接入前还需将前一版提示词草案的 initial/replan 扩展为本报告中的三模式，不能把本报告当作已部署行为。
