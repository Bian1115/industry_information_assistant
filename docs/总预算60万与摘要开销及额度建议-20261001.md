## 开销原因及证据

1. **原文外置只缩短主研究请求视图，整体摘要仍读取原始记录。** 冻结的 `agent_context.py` 将原文替换写入 `views`，生成摘要却将原始 `candidates` 传入 `summarize_history`。因此上下文视图缩短不等于摘要模型读取量同步下降。
2. **大段工具结果与提示词副本形成多份材料。** 首次摘要读取的工具输入及输出分别约2.31万、5.77万字符。后续还读取长旧LLM提示词。工具输入也携带搜索摘要，工具输出携带正文，同一资料可以出现在不同记录中。
3. **旧输入引用化没有利用已覆盖的工具来源。** 4次已保存上下文的引用化命中均为空。离线用完整历史匹配，seq17提示词可从15853字符缩至4431，其来源是seq16工具输出；该输出已被第一次整体摘要覆盖。seq55、96、139的来源也在先前游标内。运行代码只在未覆盖历史中查找可匹配的工具输出，遗漏这些来源，正文副本随后作为新输入记录再次进入整体摘要。离线统计为逐字匹配及字符长度，使用字符计数进行长度筛选，不能视为实际供应商token节省。
4. **分块后还需合并，且摘要触发频繁。** 一份整体摘要需要3—5次模型调用；每次添加材料后又接近约24456 token的摘要阈值。不是最终短摘要只付几千token，分块读取原文及合并均计费。

历史覆盖游标依次推进16、54、95、138。这里的重复主要是相同正文被保存为不同历史记录，以及摘要合并继续读取旧摘要；没有据此认定游标失效。此次没有单条旧输入摘要事件、没有Claimify生成调用，不能再把开销归因于已删除的分支或已关闭的核验。

## 预算讨论，尚未实现阶段分配

基于当前单次完整摘要约3.7—8.3万token，建议先采用如下诊断分配，总计60万：

| 用途 | 建议额度 | 说明 |
| --- | ---: | --- |
| 规划、研究、分析 | 22万 | 普通模型调用，不含摘要 |
| 整体摘要 | 30万上限，20万警戒 | 按所有摘要调用的输入与输出累计，约可容纳5次当前平均规模的完整摘要 |
| 写作与审核 | 保留8万 | 覆盖初稿、审核及有限修改，实际需求尚未测量 |

30万是当前结构下的临时诊断上限，不是已验证的最优值。20万警戒时应开始减少补搜、复用已有事实并规划收尾；达到摘要上限后不再启动新摘要，而应复用已提交摘要、紧凑事实及可回读来源，推进报告。若视图仍超限，应明确处理或提前收尾，不能继续重复尝试摘要直至消耗写作额度。

实现独立额度时，应在每个模型请求发出前预留输入与输出预算，回包后按usage结算；未完成调用的预留也需记录，避免只按已完成调用事后检查而超过上限。本次只实施已确定的60万总预算，以上摘要上限、警戒和写作预留为讨论建议，尚未增加执行逻辑。
