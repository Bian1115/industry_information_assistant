# 研究总token预算不足与摘要开销分析

分析日期：2026-10-01，Asia/Singapore。原始复核快照时间：22:09:22。评估对象：固定中文研究评测集35、31、46、16、49的三个运行目录，以及当前研究任务累计token预算机制。本次只读取已有归档并统计，不调用模型、不启动评测、不修改预算或研究逻辑。

## 结论

**对已经观察到的当前流程，单题30万token确实不足：五次预算失败都发生在研究阶段，尚未生成报告。主要瓶颈是摘要开销，而非报告生成本身。** 第二轮三个预算失败样本的摘要消耗约占77%—84%；最新一轮第35题关闭逐句Claimify和单条旧输入摘要后，整体历史摘要仍消耗249655 token，占该题80.24%。因此不能将预算不足全部归因于旧版Claimify，也不能认为关闭单条输入摘要就能解决。

没有完成运行的总消耗数据，尚不能确定合理上限是50万、100万还是更高。若先验证能否跑完，可以把**单题100万**作为临时诊断配置，先试一个固定样本，并同时记录各阶段消耗；该值是工程试验建议，不是已经验证的完成预算。长期应降低摘要输入与触发次数、为写作留出预算，并让研究阶段在额度接近耗尽时收束。

原题保持不变；三轮主模型为qwen-plus/qwen3-max，全网检索。本次只统计在快照时间之前已经存在`运行结果.json`、原始历史和调用埋点的12次归档尝试，未运行的题目不纳入。第三轮只归档35和31；31为用户停止。完整五题第二轮中49也是用户停止，两个停止样本不能作为预算或系统失败。

- 第二轮：`backend/eval/data/通用研究中文5题重跑-20261001-201500/`，Claimify关闭，整体历史摘要保留，单条旧输入摘要配置仍存在。

统计方法：按原始历史`call_id`关联`summary_stage`与`llm_usage`，区分摘要调用和主流程调用。累计供应商已返回的`total_tokens`，分别统计`prompt_tokens`和`completion_tokens`。每题原始历史usage累计值与`LLM调用埋点.json`累计值相等，12题核对均通过。缓存token不从usage总量中扣除；该指标是运行保护口径，不等于实际账单金额。

## 失败样例与消耗解释

### 第二轮35、46、16：关闭Claimify后仍被整体摘要耗尽

35题主流程累计63377 token、摘要237486 token；46题主流程49178、摘要266816；16题主流程71125、摘要241048。摘要调用分别16、17、16次，覆盖分块生成和合并，而主流程成功调用仅5、4、6次。三题整体摘要均有成功提交，不能把这些调用全部解释成超时重试。

35题摘要输入token为223580，占摘要消耗94.14%；46题为253405，占94.97%；16题为225784，占93.67%。消耗主要来自读入材料，单独压低摘要输出上限不能解决大部分开销。

### 第三轮35：移除单条旧输入摘要后仍失败

该题耗时578.5秒，总token311154，其中整体摘要249655，主流程61499。摘要共16次完成调用：12次`summary_chunk`消耗227388，4次`summary_hierarchical_merge`消耗22267。摘要输入234542，占摘要消耗93.95%。最终错误仍为`研究任务超过 300000 token 预算`。

第三轮31题在用户停止前已记录250072 token，其中摘要204426，但尚未预算失败；不能将“若继续运行可能超预算”写成已测量结果。

### 首轮及其他终止类型

首轮35题的284248摘要token包含逐句Claimify；历史分析已记录摘要失败后重处理相同输入。该路径与后两轮成功提交正文的摘要路径不同，不能把首轮重试机制当作所有后续消耗的原因。首轮另外四题主要涉及休眠、连接或租约中断，详细证据在首次失败分析中。

第二轮31题仅记录1753 token就失败；原始日志为PostgreSQL JSONB拒绝含`\u0000`的网页正文，随后报工作历史保存失败，提高预算不会修复该错误。用户停止的两次运行单列，不计入工程失败。

## 源码机制与间接推断

1. **预算按每次研究任务累计。** [stage_runtime.py](../backend/app/service/deep_research_v2/stage_runtime.py)将已完成阶段token与当前Agent新增消耗相加，超过token_limit就取消节点，并抛`StageBudgetExceeded`。[service.py](../backend/app/service/deep_research_v2/service.py)将其映射为`research_budget_exceeded`。30万不是五题共用额度，也不是单次上下文窗口。
2. **摘要与主流程共用计数。** [summary_lifecycle.py](../backend/app/service/summary_lifecycle.py)通过同一个Agent的`_call_llm_impl`生成摘要；[base.py](../backend/app/service/deep_research_v2/agents/base.py)把已返回usage累计到`llm_total_tokens`。更换摘要模型也不会自动给摘要另一份研究预算。
3. **限额是返回后检查。** 阶段保护每0.5秒检查已返回usage；未按下一请求的预估输入加输出做任务总额预留。最后一次调用可使累计量越界，这解释了300863、315994等结果。增加上限不会让阶段提前收束或保证把剩余额度交给Writer。
4. **摘要仍读取原始材料。** [agent_context.py](../backend/app/service/agent_context.py)先缩短回放视图`views`，判断摘要触发后仍将原始`candidates`交给摘要器。[summary_hierarchy.py](../backend/app/service/summary_hierarchy.py)按`source_text(row)`拆分材料，再分块与合并。视图已经缩短不代表摘要输入也相应减少；原始历史里保存的工具和模型输入输出会扩大摘要数据量。

第4项为已核查的代码路径；究竟有多少token来自各类重复材料、能消除多少开销，尚未逐片段量化。因此“应优先减少重复材料和摘要频率”是有证据支持的工程推断；“删除摘要后30万一定足够”没有实测支持。移除摘要后主流程携带的历史也可能变长，不能简单从总量减去摘要token就预测完整成本。

## 下一步建议

1. 如当前优先目标是取得首份完整报告，用新运行目录对一个固定样本临时试`RESEARCH_MAX_LLM_TOKENS=1000000`，保持其他配置一致，并同步检查900秒研究阶段等独立时限。100万仅用于诊断，不直接作为生产默认；本次未修改该配置或运行中的任务。
2. 为摘要和研究阶段设单独份额，并为分析、写作、审稿明确预留余额。在研究预算接近份额时，根据现有证据收束并输出缺口说明；不能只抛异常丢失交付，也不能强行将无证据内容判为研究完成。
3. 优先减少摘要输入：仅处理新增且必要的历史，避免将包含旧上下文的模型输入与同源工具正文再次整体总结；保留原始快照、来源编号和可回读能力。给失败摘要设置冷却与中间产物复用。
4. 在相同原题上另做受控对照，比较当前摘要、优化摘要输入、降低摘要频率等策略，记录完整完成率、各阶段输入输出、证据覆盖与报告质量。完成运行后再用总消耗分布确定默认额度。

## 局限性与尚未评估

- 本次为已有小样本轨迹复核，未运行100万预算、无摘要或优化后的对照。
- 已返回并保存的usage是可追溯统计；未返回usage的取消或网络请求不在总量中，不能用于精确账单核算。
- 三轮源码、摘要配置、网页和模型采样有变化，不构成严格控制变量实验。
- 当前源码机制已静态核查；没有为本次分析重跑运行保护测试，也没有改动生产代码。
- 报告均未生成，报告质量、最终引用准确性和达到完整交付所需token**尚未评估**。不能据此判断研究能力为零，也不能承诺提高预算后一定完成。
