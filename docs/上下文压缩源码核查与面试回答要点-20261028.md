## 一、面试时可以直接使用的回答

这个项目是多智能体研究系统，搜索结果、网页正文、写作草稿和修改记录会反复进入后续模型输入。我们做上下文压缩，首先是为了让长链路研究在单次输入预算内继续执行，同时尽量保留任务要求、研究进展和原文回查入口。

实现分两层。会话层处理用户与助手之间的长期对话：后端在下一次消费历史之前，读取数据库中的旧摘要和未覆盖消息，达到阈值后，用摘要模型更新早期历史的摘要，并保留近期原文。智能体层处理一次研究内部的工作历史：先保护当前请求和有效任务约束，再将已保存的重复资料和工具正文替换成可回读引用；如果处理后仍超过触发阈值，才调用模型生成增量合并摘要。原始记录保留在 PostgreSQL，压缩主要改变发送给模型的消息；模型需要细节时，可以通过来源编号请求后端回读。

效果方面，2026 年 10 月 2 日五题历史轨迹回放中，完整输入减少了 75.7%–96.8%，五题都进入当时的输入预算；四题提交摘要，一题只靠外置就足够，同一输入再次组装没有新增模型请求。但这是单次输入体积的结果，不是费用下降比例，也不是当前版本的端到端成功率。

不足主要是有损摘要、回读与核验开销，以及当前任务资料本身过大。另一批七份自然摘要在模型选出的 112 项检查点中完整保留了 79 项，约 70.5%，仍会遗漏限定条件。我的后续优化重点是按完整请求动态分配预算，显式保护数字的适用条件和证据状态，并用固定轨迹对照实验同时测保真、交付率、延迟和总 token，不能只追求压缩比例。

个人贡献需按实际负责部分表述；代码和提交记录本身不能证明所有模块均由个人完成。

## 二、为什么需要压缩：从项目实际问题回答

这里的“上下文”是本次发送给模型的消息集合；token 是模型计量文本长度的单位，不等同于字符数。一次用户提问可能引发多次搜索、工具调用、章节生成和返工，内部调用历史比用户对话轮数增长得更快。

实际存在三种输入增长：

1. 用户多次追问，历史问题与报告正文不断累积。
2. Agent 重复携带搜索结果、已读网页、旧章节和审核意见。同一正文可能出现在工具输出和后续模型输入中。
3. 当前请求自身携带大量证据。即使历史已经压缩，当前材料仍可能把请求撑满。

历史五题中未压缩的组装视图曾达到 438,986 tokens。它是准备发送的历史视图计数，不表示供应商实际接受过这么大的请求。历史第 24 轮还出现过“历史摘要已经采用，但最终输入仍超限”的真实失败，见第五节。

因此可以说压缩是输入预算和持续执行的需要；不能凭这些实验声称已经测出了注意力改善、准确率提升或净费用下降。

## 三、当前代码如何实现

### 1. 入口与预算

研究 Agent 的统一入口是 [BaseAgent.call_llm](/Users/bxy/projects/industry_information_assistant/backend/app/service/deep_research_v2/agents/base.py:120)。后端先执行当前证据预算适配，再归档输入，并在每次模型请求前调用 [prepare_agent_messages](/Users/bxy/projects/industry_information_assistant/backend/app/service/agent_context.py:418)。模型要求回读历史后，下一次请求也会重新经过这个组装过程。

预算由 [InputBudget.available](/Users/bxy/projects/industry_information_assistant/backend/app/service/context_policy.py:64) 计算：

`可用输入 = min(单次输入上限, 配置窗口 − 本次输出预留 − 安全余量)`

本次加载本地 `.env` 得到五个研究 Agent 的输入预算均为 65,536。Writer 配置窗口 250,000，输出上限 60,000，安全余量 1,024，因此其预算仍为 65,536。这里是项目配置预算，不是本次在线测量的模型原生窗口。

代码使用 [QwenTokenCounter.count_messages](/Users/bxy/projects/industry_information_assistant/backend/app/service/qwen_token_counter.py:76) 和消息模板计算长度，不是简单按字符除以固定比例。

### 3. 智能体内部：先引用化与外置，再摘要

后端按如下顺序处理 Writer 历史：

1. **固定当前要求。** [protected_agent_messages](/Users/bxy/projects/industry_information_assistant/backend/app/service/agent_context.py:103) 把最新有效任务约束加入系统消息，当前输入单独保留，并将历史标记为参考资料。这保护了指令位置，不等于证明模型一定不会遗忘约束。
2. **读取旧摘要和未覆盖记录。** 后端从 PostgreSQL 获取该研究、Agent、子任务的记录，在程序内存中构造本次消息视图。
3. **达到整体阈值后，先处理旧工具参数。** 只处理已完成工具调用，并保护最近 5 条历史消息中的参数；较早的长参数可以变成带来源编号、字符位置的引用。
4. **替换历史材料与成果正文。** [input_history_view.py](/Users/bxy/projects/industry_information_assistant/backend/app/service/input_history_view.py:18) 对已知 JSON 字段或明确栏目生成引用，例如 `source_evidence`、`original_report`、`draft_sections`；工具正文匹配还会核对逐字内容。不是在任意文本位置盲目删除。引用必须比原文短，并通过来源读取权限和哈希校验。历史模型输出中的章节、结论等字段也可以引用化。
5. **工具结果保留预览和回读入口。** 后端在回放视图中用默认 400 字符预览加 `source_id` 替代已完成工具结果正文。当前正文分支只要求替换后更短；不能把旧说明中的“所有正文均以 800 tokens 为门槛”当作当前规则，800 仍用于旧工具参数条件。
6. **处理后仍达到 17,000，才尝试摘要。** 后端选择连续、已结束的调用作为候选；当前调用和仍在执行的调用形成边界，避免只覆盖一半工具交互。原文变成引用后，摘要模型读取的是这些处理后视图，而不是再次接收完整外置正文。[prepare_summary_records](/Users/bxy/projects/industry_information_assistant/backend/app/service/summary_history_view.py:8) 保存派生快照及其与原记录的映射。
7. **按请求预算分批生成与合并。** [summary_hierarchy.py](/Users/bxy/projects/industry_information_assistant/backend/app/service/summary_hierarchy.py:25) 先尝试完整记录；单条放不下时才按连续字符范围拆分，保证范围覆盖。多个分块摘要与旧摘要合并；必要时只允许一次额外分批合并，仍超限则报错，不无限递归。当前摘要模型配置为 `qwen3-max`，输出最多 3,000 tokens。
8. **提交新摘要与覆盖位置。** “覆盖位置”表示哪些历史已经进入摘要，例如覆盖到序号 100，则后续通常发送“摘要＋序号 100 之后的记录”。后端先检查格式和是否缩短，再通过期望版本条件提交；数据库提交成功后，才在本次视图中采用新摘要并推进覆盖位置。
9. **重新计数后发送。** [最终检查](/Users/bxy/projects/industry_information_assistant/backend/app/service/agent_context.py:764) 超出硬预算会抛出 `ContextBudgetExceeded`，不会通过静默截断当前要求强行发送。摘要失败若留下的视图仍合预算，可以继续；若仍超限，则明确失败。

例如，旧 Writer 输入中有一整章正文，后端已经将该输入归档。后端可以只给模型一个含 `source_id`、`start`、`chars` 的标记；模型需要其中的数字时输出 `_history_read` 请求，后端从数据库读取对应原文，校验归属与哈希，将片段放入下一次模型请求。读取由后端执行，模型本身不直接连接数据库。

### 4. 摘要内容与核验关系

当前 [摘要提示词](/Users/bxy/projects/industry_information_assistant/backend/app/prompts/摘要正文生成与合并.txt:1) 规定三个栏目：`SESSION INTENT` 保存用户目标与要求，`SUMMARY` 保存结论、限制、冲突及已有未完成事项，`ARTIFACTS` 保存资源、路径及失败结果。当前不再单列 `NEXT STEPS`；旧资料写四栏目时要标注历史版本。

[summarize_prose_first](/Users/bxy/projects/industry_information_assistant/backend/app/service/summary_lifecycle.py:23) 先生成并提交正文，标记为未核验，再按开关执行 Claimify 等审计。Claimify 指将自然语言整理为可单独检查的小论断；语义核验则判断提供的证据是否支持这些论断。

当前本地 Claimify 关闭，Writer 摘要语义核验也关闭。即使启用审计，这条生命周期的审计主要更新已提交摘要的核验状态，不自动用审核结果替换正文或回退覆盖位置。不能说“只有所有事实核验通过后才保存摘要”，也不能仅凭策略名称 `claimify-v1` 就说 Claimify 已启用。

### 5. 会话层：在下一次调用前滚动更新早期对话摘要

会话服务经 [SessionMemoryService](/Users/bxy/projects/industry_information_assistant/backend/app/service/session_memory_service.py:323) 调用 [prepare_semantic_context](/Users/bxy/projects/industry_information_assistant/backend/app/service/semantic_context_service.py:261)。后端从 PostgreSQL 读取旧摘要与全部未覆盖原文，把本轮 query 加入阈值判断。

当前触发点为 `int(65,536 × 0.85)=55,705` tokens。触发后按 [SessionSummarizer.partition](/Users/bxy/projects/industry_information_assistant/backend/app/service/session_summarization.py:145) 保留最近 10 条消息（包含本轮 query；不是 10 轮），用 `qwen3.5-plus` 将更早前缀连同旧摘要生成完整新摘要，最多输出 2,000 tokens。摘要模型请求窗口配置为 1,000,000，与消费摘要的研究 Agent 预算分开。

会话摘要是调用前执行，不是回答后异步后台更新。当前代码不再在摘要前裁掉早期前缀；它会检查完整摘要请求及输出预留是否放得下。失败时回滚数据库事务并阻止本次准备，原文和旧覆盖位置保持不变。Redis 只缓存派生结果，命中缓存也不能跳过本轮阈值检查。

### 6. 数据在哪里，什么时候真正保存

| 内容 | 实际位置与职责 | 提交边界 |
|---|---|---|
| 已归档工具、模型调用记录 | PostgreSQL；`PostgresAgentHistory` 是操作这些记录的对象，不是存储介质 | `session_factory.begin()` 正常退出时提交事务；`flush()` 只把变更发到事务内，不能独立当作提交 |
| Agent 新摘要、版本与覆盖序号 | PostgreSQL 的 AgentContext | [save_summary](/Users/bxy/projects/industry_information_assistant/backend/app/service/agent_history.py:307) 在同一事务中条件更新并提交 |
| 本次准备发送的引用化消息 | Python 程序内存中的 `views`、`messages` | 构造这些对象不代表已经持久化；组装完成后传给模型客户端 |
| 本次回读循环临时摘要 | `AgentCallContext` 的内存状态；相关事件另行归档 | 不推进全局历史摘要游标 |
| 会话摘要及覆盖消息位置 | PostgreSQL 的 ChatSession | `db.flush()` 后仍需 `db.commit()`；异常走 `db.rollback()` |
| 会话派生缓存 | Redis | 不承担本链路原始历史的最终依据 |

数据库事务成功提交是应用判断持久化成功的边界。代码没有直接操作操作系统文件缓存或调用文件 `fsync`；具体断电耐久性取决于 PostgreSQL 的 WAL/同步提交和部署存储配置，本次未审计这些配置，因此不把一次 `flush()` 或内存赋值说成数据已经可靠落盘。

## 六、面试追问速答

**“压缩是不是删数据库里的历史？”** 这条机制主要修改本次发送视图；原始事件仍在 PostgreSQL。摘要提交只推进“后续哪些记录由摘要替代”的覆盖位置，不删除那些事件。其他数据过期机制不属于这里的压缩证明。

**“为什么不一开始就用模型摘要？”** 代码先引用化重复正文和已保存成果；若体积已经够小，就不用额外模型调用。第49题35,234降到8,560，确实没有生成摘要。但不能把这个例子当成所有任务均无需摘要。

**“怎么防止摘要重复覆盖或者漏掉正在执行的工具？”** 后端按完整调用边界选取摘要候选；提交时要求数据库里的版本仍等于生成时读取的版本，并且覆盖位置只能前进。条件更新失败就不采用该结果。

**“摘要是不是全部核验过？”** 当前默认没有。代码将正文生成与核验分离，当前Writer核验关闭，正文带未核验状态；即使开启审计，也不能把审计状态更新说成原始事实都被证明正确。

**“最多能聊多少轮？”** 当前没有依据承诺固定轮数。旧记录经修复续跑累计交付23轮，第24轮因证据输入超限；这不是当前版本无修复连续通过23轮，也不代表23轮均正确。10月19日的200步算术模拟不能说成200轮真实对话验收。

**“你最重要的设计取舍是什么？”** 把任务要求、可回查原文与有损摘要分开管理；优先去掉重复输入，再做语义压缩；最终同时看预算、信息保留和端到端净收益。
