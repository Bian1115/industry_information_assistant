## 原问题与故障样例

原入口只检查 `snapshot.next`：为空便抛出“图已执行结束，应读取报告或补做幂等交付”。

项目当前LangGraph读取最新状态时，会应用已持久化的节点写入，并从 `next` 中排除已有结果的节点；同时通过 `snapshot.tasks[].result` 暴露这些结果。若节点结果已保存，但下一步完整检查点尚未提交，可能出现 `next=()`、存在任务结果、业务状态仍为 `running` 的组合。这时不能仅凭空 `next` 推断业务完成。

本次修改的背景是第21轮原记录中的组合：分析节点已有结果，待合并写入包含 `research` 和 `branch:to:write`，没有交付。原始观察来自[先前只读核查](../backend/eval/data/第20题32轮章节ID修复后续跑-20261007-205504/第21轮检查点可恢复性核查.json)，此次没有重新访问或执行该生产断点。实验运行中租约失效的终止原因与恢复入口误判是两个问题，本次只修复后者。

## 修复方案及实际实现

修改位置：`backend/app/service/deep_research_v2/service.py` 的 `_graph_input`。

| 状态组合 | 恢复入口处理 |
| --- | --- |
| `next` 非空 | 使用既有恢复路径，返回 `None` |
| `next` 为空，研究 `status=completed` | 提示读取结果或补做幂等交付，不重新执行研究 |
| `next` 为空，研究未完成，任务结果不为 `None` 且任务无错误、无中断 | 返回 `None`，交由LangGraph合并已保存结果并推进后继节点 |
| `next` 为空，研究未完成，无上述恢复依据 | 抛 `ResearchStatePausedError`，明确提示断点待核查，不宣布完成 |

结果判定使用 `task.result is not None`，与任务结果值是否为空容器区分。错误或待人工输入的任务结果不会单独被当成已成功保存的恢复依据。

仍由服务以原 `run_id` 构造图配置，用 `graph.astream(None, config=原配置)` 执行。此次没有手工改 `next`、`phase`、任务结果或数据库检查点，也不重建初始query。原有图版本、旧路由、会话任务哈希和冻结配置校验在上述恢复判断之前执行；已有租约与交付保护继续负责实际执行和最终交付。新增日志只记录恢复的run和节点名称。
