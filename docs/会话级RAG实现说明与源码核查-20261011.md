## 1. 实现的整体含义

本项目的会话级 RAG 是一套会话临时证据库：研究过程中读取的来源正文进入 PostgreSQL，正文被拆成可定位的段落、原句、表格和字段记录，其向量进入专用 Milvus 集合。规划与写作按问题检索较大的上下文单元，报告论断按自身文本检索较细的证据单元。

核心对象是 [`SessionEvidenceRAG`](../backend/app/service/session_evidence_rag.py)。在 DeepResearch 运行入口，只有 `persist_events` 为真、有 `user_id` 且 `SESSION_EVIDENCE_ENABLED` 开启时，才实例化并传入图执行（[service.py](../backend/app/service/deep_research_v2/service.py)）。默认开启表示配置默认值，不能证明某个运行实例已经启用。

这套组件处理的是 `state.raw_sources` 中具有正文版本、内容哈希和句子编号的来源材料。会话聊天历史另由 `RedisSessionMemoryService`、PostgreSQL 消息及语义摘要构建上下文（[session_memory_service.py](../backend/app/service/session_memory_service.py)）。普通聊天的知识库检索有自己的入口，不能把这些路径都理解为本组件自动索引的内容。

## 2. 按调用链逐类说明

### 2.1 创建作用域与跨轮复用

`attach()` 创建或读取会话证据空间，选择 `topic_id`：优先继承父研究或当前状态已有主题；本轮任务关系为 `continue` 时可以沿用空间中的 `active_topic_id`；否则以父运行、本次运行编号或会话与查询的哈希生成主题。

因此证据的逻辑作用域包括 `user_id + session_id + topic_id`。Milvus 检索还带 `generation` 过滤。相同会话可以包含多个主题，继续主题和返回旧报告时能复用相应材料；切换到新主题时，正常入口会使用新的主题作用域。

回到旧报告的入口还会校验成果所属用户与会话、报告哈希，读取父研究检查点，再恢复其证据正文（[service.py](../backend/app/service/deep_research_v2/service.py)、[followup_context.py](../backend/app/service/deep_research_v2/followup_context.py)）。

### 2.2 正文准入、不可变版本与切块

Scout 将网页阅读结果加入 `raw_sources`（[scout.py](../backend/app/service/deep_research_v2/agents/scout.py)）。正文版本的 `document_id` 由 URL 与正文哈希派生；`sentence_index` 保存稳定句号及字符起止偏移。入库时校验哈希、编号和索引一致性，同一正文编号不允许被不同内容覆盖（[web_document.py](../backend/app/service/web_document.py)、[session_evidence_store.py](../backend/app/service/session_evidence_store.py)）。

切块由 [session_evidence_chunks.py](../backend/app/service/session_evidence_chunks.py) 实现，默认单块预算为 1024 token：

- 普通正文产生 `sentence` 子块，再按章节和段落组织成 `paragraph` 父块，子块登记 `parent_chunk_id`。
- 表格与字段记录先结构化识别。短表整表保留，长表按完整数据行拆分，每片保留表头和注释；字段记录保留记录标识。无法在预算内保留的普通单句、表格行或固定表头会显式报错，不静默截断。
- 每块携带正文哈希、来源 URL、标题路径、原句编号、`source_spans`、父块与相邻块编号。表格块由两层共用，各自保存相邻关系。

检索过滤器支持 `section` 类型，但当前切块器实际产生的主类型是 `sentence`、`paragraph`、`table`、`record`，不能据此声称实现了独立章节块生成。

未通过正文准入或切块失败的材料可以保存原始正文及 `rag_chunk_error`，但不生成可召回块（[summary_evidence_units.py](../backend/app/service/summary_evidence_units.py)、[session_evidence_store.py](../backend/app/service/session_evidence_store.py)）。

### 2.3 PostgreSQL 与 Milvus 分工

PostgreSQL 的四张表分别保存空间、文档、块及独立清理任务：`session_evidence_spaces`、`session_evidence_documents`、`session_evidence_chunks`、`session_evidence_purges`（[session_evidence.py](../backend/app/models/session_evidence.py)）。正文和定位以此为权威来源。

`ingest()` 先提交正文及待索引块，然后生成 embedding、写入 Milvus，最后校验会话及 `generation` 并标记已索引。已有文档去重，未完成的索引块可在后续阶段重试。

Milvus 集合按 embedding 模型和维度命名，为不同会话共享的专用临时证据集合；会话隔离靠过滤字段实现。它存块 ID、作用域字段、类型、generation 和向量，返回块 ID后从 PostgreSQL 对照当前可用块。索引使用 `FLAT`，相似度使用 `COSINE`，查询采用 `Strong` 一致性（[session_evidence_vectors.py](../backend/app/service/session_evidence_vectors.py)）。

### 2.4 两层检索与粗精排

| 层 | 用途 | 主检索粒度 | 查询内容 | 精排种子数量 | 返回视图预算 |
|---|---|---|---|---:|---:|
| `context` | 规划与写报告 | 段落、表格、字段记录 | 本轮完整问题；写章节时再加章节标题、描述 | 8 | 8192 token |
| `citation` | 论断证据检索 | 原句、表格、字段记录 | 每条 `claim` 的文本 | 5 | 2000 token |

这些是代码默认值。TopK 指精排种子；默认向前和向后各扩展一个同文档邻居，再按 token 预算筛选，所以最终块数可能大于 TopK，也可能因预算不足而减少。

两层都调用 `retrieve()`，采用相同流程：

1. 从 PostgreSQL 加载当前会话、主题、单元类型下的块，应用允许域名及可选文档过滤；默认加载上限为 20000 块，超出会报错。
2. 词法路在本次加载的块上计算 BM25 风格得分。中文使用单字和相邻双字，英文及数字按词分词；这一路由 Python 在内存计算。
3. 向量路将 query 编码后查询 Milvus，默认 128 条一页，最多 3 页。
4. 两路按 `1 / (60 + rank)` 进行 RRF 融合，融合后取最多 384 个粗排候选；两路原始并集可以大于 384。
5. 用 `qwen3-rerank` 精排。上下文层指令关注问题、章节要求及适用范围；引用层指令关注论断主体、时间、数字、单位，并要求保留支持和反驳证据。
6. 扩展邻居、按包含文本与定位元数据的 JSON token 预算选完整单元，最后再次从 PostgreSQL 鉴权回读有效块。

Embedding 默认为 `text-embedding-v4`、1024 维。两层指的是两种粒度与用途；每层内部各有词法、向量两路召回和精排。

精排在候选过多时按请求预算组批，各批选 TopK，然后继续缩减，直至能够在一次最终精排请求中比较剩余候选；不直接拼接不同请求的相关性分数。这是分批淘汰机制，不等同于把所有原始候选放入一次请求后的排名保证（[session_evidence_ranking.py](../backend/app/service/session_evidence_ranking.py)）。

### 2.5 注入模型与论断回读

`context` 层在初始化阶段生成 `research_material_context`，供 Architect 规划使用；Writer 写章节时以“本轮任务 + 章节标题 + 描述”调用 `evidence_prompt()`，得到 `<session_evidence_view>` 中的证据文本和定位编号（[architect.py](../backend/app/service/deep_research_v2/agents/architect.py)、[writer.py](../backend/app/service/deep_research_v2/agents/writer.py)）。

模型可输出 `document_id + evidence_unit_ids`。后端通过 `resolve_units()` 和 `references()` 校验这些编号是否属于当前会话、主题和文档，再按 `source_spans` 从保存的正文组装 quote，并确认它与块文本完全一致。

`claim_inputs()` 先精确回读论断原有引用，再针对论断在整个当前主题的引用层重新检索，补充候选；它没有将范围限制在上下文层选中的段落或原引用文档。返回的额外材料标记为 `retrieval_candidate`。

报告的引用检索独立于 NLI 开关：关闭 NLI 时仍保存可回读的候选定位，但不会将其标为语义支持。开启 NLI 时才根据核验结果产生 `verified_citation_bindings`（[citation_verification.py](../backend/app/service/deep_research_v2/citation_verification.py)）。

### 补充核查：直接使用证据写作与原文回读

补充核查日期：2026-10-11。补充口径：针对“是否可以直接读取证据写作”核对 Writer、`evidence_prompt()`、`references()`、`hydrate()` 和引用核验入口；没有修改实现，没有进行对照实验。补充来源哈希记录在原始核查 JSON 的“补充核查”字段。

可以直接用召回的原文证据块写作，当前 Writer 已经采用这个方式：`evidence_prompt()` 将块的 `content` 作为 `evidence_units[].text` 提供给模型，附带正文和块编号。写作模型拿到的既有文本又有定位，无须先通过编号另行取全文才能开始写作。

目前代码中有三种不同的读取行为：

1. `retrieve()` 从权威存储取得证据块，并在返回前再次确认当前会话仍可读取所选块。这是证据获取及生命周期校验。
2. `references()` 在解析报告引用时，根据 `source_spans` 从保存的来源正文重建 quote，比较它与证据块 `content` 是否一致。这是后端来源一致性校验；读取的是本地数据库正文，不会因此重新访问来源网页。
3. `hydrate()` 在节点或章节任务恢复时将被外置的正文引用恢复到后端状态。这是当前运行状态和旧引用处理的依赖，不代表模型必须阅读所有恢复的全文。

如果“证据”指当前不可变的原文证据块，设计上也可以让引用核验直接使用权威证据块文本，而将全文回读延后到审计或需要更多上下文时。前提是验证块所属用户、会话、主题及有效期，块的不可变性和来源定位在入库时得到校验，保留原始正文用于追溯，并处理旧的 `sentence_ids` 引用。这样的优化需分别改造 `references()`、相关恢复及旧引用路径，不能仅删除现有 `hydrate()`。

如果“证据”指 Scout 抽取的事实或摘要，模型也能据此生成草稿，但生成内容已经经过提炼，无法保证保留原文全部限定条件、数字口径或反证。要保持当前原句和表格证据能力，应优先使用携带定位的原文块。

设计推断：采用证据块直接核验可能减少重复正文读取；本次没有测量数据库读取次数、延迟或质量变化，也没有证实省略原文一致性校验后的效果与当前实现等价。写作模型无需再次阅读全文，是本次从当前提示构造代码确认的事实。

### 2.6 检查点与生命周期

图节点前调用 `prepare_stage()`：恢复正文、入库或补建索引，初始化阶段检索上下文。节点执行期间通过 `ContextVar` 绑定当前服务。节点后调用 `commit_stage()`：保存新材料，再用 `externalize()` 把 `raw_sources` 中的正文和句子索引替换为引用标记，避免检查点重复持有全文。后续节点由 `hydrate()` 回读（[graph.py](../backend/app/service/deep_research_v2/graph.py)）。

Writer 的证据提示还经过模型输入预算检查，默认给历史保留 4096 token。超预算时移除末尾完整证据单元，不截断单元文字；如果去掉所有证据仍超出总输入预算则报错。这个专门处理依赖 `<session_evidence_view>` 标记；Architect 的规划视图由检索返回预算及其通用输入处理约束。

临时证据默认 TTL 为 86400 秒，模式为 `idle`。它同步已经提交的新消息所延长的会话期限，检索和摘要自身不续期；也支持 `absolute` 模式。读取时验证会话归属、状态与期限，过期正文不会被假造恢复。

显式关闭、删除或超时清理会关闭证据空间、提升 generation，并使未结束运行失效，随后通过可重试任务删除向量、正文块、研究检查点、相关 Agent 历史和会话网页缓存（[session_evidence_lifecycle.py](../backend/app/service/session_evidence_lifecycle.py)、[session_router.py](../backend/app/router/session_router.py)、[scheduler_service.py](../backend/app/service/scheduler_service.py)）。`SessionEvidenceRAG.close()` 仅关闭 API 客户端；单次研究结束不等于关闭整个会话证据空间。

## 3. 配置与可观察字段

所有会话证据参数可通过 `SESSION_EVIDENCE_*` 环境变量覆盖。Embedding 与 rerank 请求复用 [summary_temporary_retrieval.py](../backend/app/service/summary_temporary_retrieval.py) 的 `RetrievalAPI`，API key、模型端点沿用其 `SUMMARY_RETRIEVAL_*` 与 `DASHSCOPE_*` 配置。

状态中的 `evidence_rag_metrics` 记录入库文档和块数、索引状态、查询、两路候选数、粗排页、精排请求、选中 ID、token 数和耗时等。精排预算中的 token 计数标记为 `local_estimate`；API 返回 usage 时另行记录。上述是观测字段定义，本次没有测得这些字段的实际运行值。

## 4. 失败分支示例与局限性

以下为源码中可确认的失败处理，均未在本次运行复现：

| 场景 | 代码行为 | 实际效果边界 |
|---|---|---|
| Embedding 或 Milvus 建索引失败 | 正文保留，记录 `lexical_only:*`，待索引块仍可重试 | 不能据此保证词法召回质量 |
| 向量查询失败 | 使用词法结果；已有向量页时保留部分结果 | 候选完整性可能下降 |
| 精排 API 或预算失败 | 记录失败并回退到 RRF 先后顺序 | 当前请求没有完成有效模型精排 |
| 单句、表格行或固定结构超块预算 | 正文保存，登记切块错误，不静默截断 | 对应文档可能没有可检索块 |
| 虚构引用编号或原文回读不一致 | 拒绝定位，记录引用绑定错误或抛出异常 | 定位成功也不能代替语义核验 |
| 会话已关闭、过期或正文引用丢失 | 拒绝读写和恢复，旧索引提交不能复活空间 | 过期后的原句证据不再可用 |

## 5. 结论与下一步建议

当前源码构成“会话与主题隔离 → 不可变正文及父子块 → 两路粗排融合 → 按层精排与预算视图 → 原文编号回读 → 可选语义核验 → 生命周期清理”的完整实现。它支持研究材料跨轮复用，并将正文存储、模型输入和引用核验分开管理。

若后续要确认实际效果，应以当前部署配置运行独立评测，覆盖多轮追问、新主题切换、反证召回、表格定位、基础设施降级和关闭并发场景，并分别报告检索质量、语义核验质量、延迟及成本。本次仅解释和核查实现，不把静态代码结论计为效果评测结果。
