# 网页正文抽取算法比较论文通俗总结与实现及评估分析

分析日期：2026-10-17，Asia/Singapore。

对象：Janek Bevendorff、Sanket Gupta、Johannes Kiesel、Benno Stein，*An Empirical Comparison of Web Content Extraction Algorithms*，SIGIR 2023，2594–2603，DOI：10.1145/3539618.3591920。

本次完成论文原文、作者公开复现说明和项目代码的静态核查，解释研究结论并提出实现方案。没有运行抽取器效果实验，没有恢复此前中止的289网址评测，没有修改业务代码、安装依赖或训练模型。下文数值均明确区分论文报告与本项目结果。

## 一、用一个例子理解研究问题

打开新闻网页，能看见标题和文章，也能看见菜单、广告、推荐阅读、版权说明。正文抽取要做的事，就是留下文章，去掉旁边和底下的杂物。它和“总结文章”不同：抽取主要决定保留原文哪些部分，不应该自行改写事实。

例如，原页面是“网站导航 → 文章标题 → 三段正文 → 相关推荐 → 页脚”，理想输出是标题与三段正文。直接把HTML标签删掉，仍可能把导航和推荐一起留下；规则太严，又可能把真正的正文删掉。

这篇论文主要贡献是建立更统一的比较条件，弄清现成工具各自的长处和短处，并测试组合投票能否减少失败。它没有提出一个负责下载、浏览器渲染、PDF解析和正文识别的完整网络读取系统。

## 二、数据与配置口径

作者合并、清洗8套人工标注数据，最终得到3,985个HTML页面及对应的正文纯文本；比较14个专门的正文抽取器、5个HTML转文本基线，并构造3种组合。原始金标格式不统一，因而统一为纯文本比较。

| 数据集 | 清洗后页面数 |
| --- | ---: |
| CETD | 700 |
| CleanEval | 738 |
| CleanPortalEval | 71 |
| Dragnet | 1,379 |
| Google-Trends-2017 | 180 |
| L3S-GN1 | 621 |
| Readability | 115 |
| Scrapinghub | 181 |
| 合计 | 3,985 |

主要评价指标为最终文本的ROUGE-LSum Precision、Recall和F1，基于句子及最长公共子序列进行对齐，不是简单判断“有无返回文本”。通俗理解：Precision关心抽到的文字里有多少是正文；Recall关心该保留的正文找回多少；F1平衡两者。论文同时报告均值、中位数及分布，并按页面抽取复杂度分组。

论文的复杂度大体表示“页面文本中非正文占多大比例”，计算依赖金标。它不是HTML字节数或DOM深度，也不能在生产环境直接用未知金标计算。作者另用HTML统计特征训练简单分类器，展示估计复杂度的可能性；这种估计与完整的生产路由策略仍有区别。

数据主要面向英文，作者明确未纳入CleanEval中文集；多数页面年代较早。论文的分词、匹配和评分不能原样视为中文效果保证。

## 四、逐类分析与失败样例

| 类型 | 论文观察或工程含义 | 处理方向 |
| --- | --- | --- |
| 简单页面，杂物少 | 多数方法表现不错，直接转文本也可能占优 | 保留简单基线，检查是否过度删除正文 |
| 导航、侧栏和推荐较多 | 直接转文本的Precision明显受影响 | 需要主体识别或质量选择 |
| 非典型版式 | 各工具表现差异大，单工具存在异常失败 | 保存多个候选，分析不一致来源 |
| 抽取结果为空或过短 | 一些工具存在明显的Recall异常值 | 将空结果、严重漏抽单列报告 |
| 中文政策、表格或附件 | 本文不能直接回答其端到端表现 | 单独建立中文与结构化内容评测 |

下面是帮助理解的机制示例，**不是本次实测页面，也不是声称论文逐页公开分析过这些例子**：

1. 一页含1,000字正文和1,000字菜单，全部转成文本，正文虽未遗漏，但污染很多。
2. 一篇没有标准`article`标签的文章，过于保守的规则只留下标题，甚至输出为空。
3. 原页面只显示“请完成验证”，几个抽取器都留下这句话。多工具一致不代表拿到了目标文章。
4. 表格正文被转成一串数字，文本重合度可能仍不低，但列名、单位和数值对应关系已经丢失。

## 五、怎样实现论文中的组合方法

可以想象让多个编辑对同一份网页划重点，然后按大家的意见决定原文哪些词留下。

1. 给各个抽取器同一份HTML，分别保存它们的输出。抓取快照必须相同，否则混入网站内容变化和网络因素。
2. 从原HTML提取文本节点，排除`script/style/noscript`，得到按原页面顺序排列的词序列。
3. 为抽取输出建立连续5词片段的索引。对原文中每个词，检查“以它结束的5词片段”或“以它开始的5词片段”是否出现在某个抽取器输出中；出现就给该词一票。两端用4个哨兵补齐。
4. 获得约三分之二票数的词被保留，按原文顺序输出。这样利用上下文判断位置，优于只问某个单词有没有出现。
5. Best only选用Readability、Trafilatura、Go DOM Distiller、Goose3、Web2Text、Resiliparse、BTE、jusText、Boilerpipe这9个工具。
6. Best weighted仍用这9个工具，其中Readability、Trafilatura、Goose3的权重为2，其余为1。总权重12，达到8票即保留。

以下是按论文描述写的教学实现，返回原文词位置的保留掩码；它不是作者源码，也未执行本地验证：

```python
def vote_token_mask(source_tokens, output_tokens, weights):
    """调用前对原文与各输出采用相同的规范化和分词规则。"""
    n = 5
    sentinel = object()

    def padded(tokens):
        return [sentinel] * (n - 1) + list(tokens) + [sentinel] * (n - 1)

    def grams(tokens):
        values = padded(tokens)
        return {tuple(values[i:i+n]) for i in range(len(values) - n + 1)}

    if len(output_tokens) != len(weights) or not weights or min(weights) <= 0:
        raise ValueError("抽取输出与正权重必须一一对应")
    indexes = [grams(tokens) for tokens in output_tokens]
    values = padded(source_tokens)
    mask = []
    for i in range(len(source_tokens)):
        j = i + n - 1
        left = tuple(values[j-n+1:j+1])
        right = tuple(values[j:j+n])
        votes = sum(
            weight for index, weight in zip(indexes, weights)
            if left in index or right in index
        )
        mask.append(votes >= sum(weights) * 2 / 3)
    return mask
```

这个函数刻意只展示投票核心。部署时还要处理编码、Unicode、实体、空白、重复片段、分词偏移和输出映射，并区分正常空抽取与执行异常。不能悄悄把空输出工具从分母去掉，否则变成另一种投票策略。完整复现应固定作者代码版本及其规范化、模型、失败处理和评分实现。

纯文本5词匹配仍可能把重复文字的不同出现位置混淆，也不负责恢复表格结构。中文若按空格切词，一整句可能只算一个词；可另做字符或固定中文分词适配，但这已经改变实验口径，必须重新测量。工程版更适合保留DOM节点或字符偏移，再映射回段落、表格等结构；按块投票同样属于新的实现变体。

## 六、在当前项目里怎样落地

这是基于代码的实施建议，尚未测量效果。

当前入口是[web_reader_service.py](../backend/app/service/web_reader_service.py)的`_extract_html`（核查时第567行）。代码会先用BeautifulSoup清理，并在发现`article/main`或任意表格时直接渲染；只有`content`为空才调用Trafilatura，再以更宽的直接抽取回退。因此，存在“已有非空内容便跳过另一种候选”的路径。模块顶部概述不能代替真实分支判断。

`_read_uncached`在静态内容低于最小字数时尝试浏览器，在HTTP错误或超时分支也有回退；最终通过`_validate_body`做质量检查。它已有`assess_body`识别验证码、错误页、推荐、预览等能力，但质量检查失败后没有统一回到替代HTML候选的闭环。上述是静态分支核查，不是性能提升的实验证据。

建议先做一个能清楚对照的版本：

1. **保留输入快照。** 保存未被前置规则修改的原HTML；每个抽取器使用独立副本。避免先把有用的`header`、`aside`或正文段落删除后，所有工具一起失去信息。
2. **生成多个候选。** 先比较现有结构化抽取、Trafilatura和Python `readability-lxml`，可加入Resiliparse。Readability通过`Document(html).summary()`得到主体HTML；接已有渲染器保留结构。Trafilatura的当前文档支持正文抽取及表格选项，但必须固定部署版本；当前项目配置偏向Precision，可另设均衡配置作为对照。
3. **按质量选择。** 每份候选调用`assess_body`，再看标题与主体匹配、导航/链接占比、重复和明显缺段等信号。先去除明确的错误或验证页候选，再按经过开发集验证的规则选取；`passed`也不是完整正文金标，不能只选最长候选。
4. **困难页再增加成本。** 没有可接受候选且有动态内容信号时获取浏览器DOM，再运行抽取。当前Crawl4AI路径主要返回Markdown；若要同DOM比较，需要增加渲染HTML的返回，而非把已清理Markdown当原HTML输入。
5. **保护引用与表格。** 主体区域确定后复用[web_document_structure.py](../backend/app/service/web_document_structure.py)的`render_html_body`；规范化完成后，再由[web_document.py](../backend/app/service/web_document.py)的`index_document`生成编号及哈希。保存原DOM位置、表头、单位、脚注，不能投票后随意拼句并沿用旧编号。
6. **测出必要性再做组合。** 如果候选选择仍有明显漏抽和异常页，再增加三工具简化投票或论文九工具加权组合。简化方案和质量选择都属于工程变体，不能直接引用论文组合F1为其效果。

建议链路为：下载与格式识别 → 同一HTML的多个正文候选 → 质量选择／经验证的组合 → 必要时浏览器DOM重试 → 结构保留与最终质量检查 → 文本定版与引用编号。PDF、Office、扫描图像仍需各自解析；抽取器无法从只提供验证码或登录提示的响应中还原未收到的文章。

## 七、如何评估实现是否有效

先冻结少量包含正常页和失败页的开发快照，再保留独立域名测试集。标注真正应保留的正文，含表格的页面额外标注关键单元格、单位和脚注。中文分词及空白规范化在金标、预测与对齐中保持一致。

将实验分开：同一HTML/DOM比较正文选择，按相同URL与明确时间窗比较包含下载、渲染和附件路由的整个读取系统。历史轨迹若只有抽取文本、没有原HTML，不能据此重建公平的抽取器F1对照。

至少报告：

- 正文Precision、Recall、F1的均值、中位数及逐页分布；中文与英文、新闻与政策等类别分列。
- 空输出率、严重漏抽比例，以及验证码/导航/错误页误接纳和正常页误拒。
- 表格关键字段的对应关系是否保存，完整正文、部分正文和摘要分别计数。
- 下载成功率、端到端URL正文可用率、P50/P95耗时和成本。

建议对照为：现有实现 → 仅Trafilatura → 仅Readability → 候选质量选择 → 简化投票。权重、阈值和选择规则只在开发集调整，冻结后在测试集比较，避免在同一批页面上反复调优再宣称泛化。

## 八、局限性、结论与下一步

**已测量：** 本次没有新增本项目效果测量。已核对论文公开表格和算法说明、作者README的复现入口，以及当前项目相关代码；论文数值是作者测量结果，不是本地复现。

**间接推断：** 当前“非空即跳过后续候选”的分支值得改成质量驱动的候选比较；复用现有表格渲染和质量检查有明确接入点。是否改善、改善多少、是否增加误伤，目前无法从静态代码确定。

**尚未评估：** 新方案中文F1、URL可用率、表格保真、时延与资源开销；本次没有实际失败页面回放，也没有用本地数据训练或选定组合权重。

论文自身还存在数据老化、以英文为主、部分金标缺陷及模型训练数据与测试集合存在重叠等局限。其神经模型结果不能外推到2026年的全部模型；纯文本指标也不足以证明RAG引用正确率提升。

下一步优先实现可追溯的同快照候选抽取与质量比较，用中文正常页和典型失败页验证，再决定是否引入投票。具体业务改造与评测仍以之后明确的实施任务为准，本次交付是总结和实现说明。
