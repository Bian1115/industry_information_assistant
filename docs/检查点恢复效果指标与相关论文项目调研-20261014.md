# 检查点恢复效果指标与相关论文项目调研

分析日期：2026-10-14，Asia/Singapore。

评估对象：本项目 DeepResearch 的节点检查点续跑、Writer 章节结果复用、终态交付补偿，以及适用于这些机制的评估指标和文献依据。本报告讨论应用工作流恢复，不评价模型训练权重检查点或 GPU 推理现场恢复。

本次执行文献检索与历史结果核对，没有新运行模型、搜索业务、故障注入、数据库实验或浏览器评测。下面的指标方案是根据本项目和所列资料提出的评测设计，不是一篇论文定义的统一 Agent 恢复排行榜。

## 核心指标及具体定义

建议先做正确性验收，再比较性能和成本。RTO、RPO 可以借用运维概念，但需要明确本项目的时间点和工作单位，不能直接套用数据库指标名称。

| 指标 | 建议口径 | 怎样判断效果 |
| --- | --- | --- |
| 技术恢复成功率 | 在固定期限内沿原运行身份续跑，并满足终态、正式报告、完成事件一致性的样本数 / 实际触发目标故障的样本数 | 越高越好；失败、错误拒绝、超时都入分母，不能只统计恢复入口返回成功 |
| 恢复就绪时延 | 恢复请求进入服务端至首次新的节点执行或待合并结果推进；另记录首次新的持久化进展 | 越低越好；历史事件回放和 HTTP 200 不算新的执行进展 |
| 恢复后交付时延 | 恢复请求至正式报告与完成事件成功提交 | 越低越好；包含租约等待和业务返工，和就绪时延分别报告 |
| 已保存工作丢失量 | 故障前确认已持久化、恢复后无法取得或错误改变的节点/章节/证据数量 | 目标为 0；另统计已执行但未持久化的工作，其丢失属于恢复粒度成本 |
| 恢复重复计算 | 因恢复而重新执行的已持久化逻辑任务数量、模型调用数、搜索次数和 token | 越低越好；同一任务恢复重复执行与新一轮业务修订分开统计 |
| 时间与费用节省 | 配对比较故障后续跑与故障后从头重跑；节省率分别为 `1 - T续跑/T重跑`、`1 - C续跑/C重跑` | 越高越好，也允许负收益；须满足共同质量门槛并单列失败率 |
| 状态与交付一致性 | 检查大纲、已保存正文/claims、事实与引用 ID、配置、预算、执行位置及外置证据；终态正文哈希与正式报告和完成事件一致 | 报告通过数量、检查项和失败例，不能用“能反序列化”代替状态完整 |
| 重复副作用与并发安全 | 每个逻辑交付多出的报告、完成事件或其他外部写入；租约接管后过期执行器的成功提交数 | 目标为 0；图状态恢复不会自动提供所有外部工具的幂等保证 |
| 恢复后的任务质量 | 使用独立于执行过程的要求满足率、引用支持率、事实正确性与总体评分；与无故障配对基线比较 `ΔQ=Q恢复-Q无故障` | 质量不能明显退化；流程内 Critic 的 pass 只作辅助观测 |
| 正常运行持久化开销 | 无故障时 `T启用检查点/T关闭检查点-1`；另记录保存 P50/P95、每次/每任务写入字节、存储和资源占用 | 越低越好；细粒度检查点应同时减少故障重做成本，比较两者的权衡 |
| 预算记账准确性 | 独立调用账本/供应商可用账单的累计消耗与持久化预算之差，涵盖失败尝试和重启 | 越接近 0 越好；不能只拿可能漏记的检查点累计值计算省 token |

时延样本足够后报告 P50/P95 和范围，并给出成功率分母；当前四题只适合展示逐题值和均值，不能据此宣称生产 P95 达标。完整故障恢复 RTO 若从故障时刻开始计时，还要包括发现故障、触发恢复、启动新进程和恢复环境的时间。

“重复计算”应按稳定逻辑任务身份识别，例如运行、节点、业务修订轮次、章节 ID 和输入哈希的组合。已有初稿被复用后，审核要求新版本重写属于新工作，不是恢复重复生成。事件网络回放次数也不等于数据库里多写了完成事件。

最终报告不要求与另一条无故障 LLM 轨迹逐字一致；应要求恢复前已保存产物正确复用、终态交付正文一致，以及恢复后的质量满足同一评价标准。

## 已有结果与逐题分析

| 样本 | 恢复后交付秒数（含租约等待） | 首个恢复节点 | 交付一致、报告与完成事件各一条 | 流程内质量 |
| --- | ---: | --- | --- | --- |
| 8 | 662.531 | review | 是 | needs_revision；达到返工上限 |
| 25 | 419.047 | review | 是 | needs_revision；达到返工上限 |
| 27 | 56.904 | review | 是 | pass |
| 28 | 327.852 | review | 是 | pass |

指定故障窗口的四题均恢复交付（4/4），平均 366.583585 秒，即 6.11 分钟。排除租约等待后平均 323.613542 秒，即 5.39 分钟。四题均复用原 Writer 初稿，从 review 继续；8、28 后续写作属于审核后的业务返工。

逐题含义：8 有补搜、分析、再写作和修订，交付最慢；25 有两次 revise；27 只审核一次，交付最快；28 经过补搜与再写作后通过。平均 6.11 分钟衡量的是恢复后交付，不能描述为“检查点加载耗时”。

四题中两题流程内 needs_revision，说明技术恢复成功与内容质量达标必须分开统计。这里的 2/4 pass 也不是独立质量评测通过率。

另一终态单例补交付为 3.465310 秒（3.47 秒），新增模型请求及节点执行均为 0，一次重复恢复请求后数据库未变化。该样本只评价已经完成图的交付补偿。

另一真实 PostgreSQL、SIGKILL、双进程章节实验使用假模型：已保存的前两章恢复后重复生成调用为 0。能证明受控场景下的章节复用机制，不能量化真实模型费用和延迟收益。

## 失败样例与统计边界

- 历史题目 26 的 Writer 成功输出已成为 pending writes，入口曾因 next 为空误判为不可恢复。应归为恢复准入/调度错误；后续修复成功不能删除原失败。
- 历史题目 28 已有终态图正文，但正式报告和完成事件缺失，恢复入口曾拒绝。应归为交付恢复失败，不能因图 completed 就记成功。后续终态补偿属于修复版本结果。
- 题目 28 的旧复评受电脑休眠影响：墙钟与单调计时差异显著。正常性能分析采用再次复评，异常结果保留并单列。
- 一次环境复评在正文提取阶段失败，尚未触发目标 Writer 故障。不能算成该窗口的恢复失败或 0 秒恢复成功；但应作为实验准备/执行失败保留，并报告故障注入完成率。
- 版本不同、故障窗口不同、真实模型与假模型不同的样本不能合并为“总体恢复成功率 100%”。当前工作区还有后续变化，此处历史成功数不构成当前版本全场景验收。

## 相关顶会论文与开源项目

### 1. Beldi：有状态工作流故障恢复与事务语义

[Fault-tolerant and transactional stateful serverless workflows](https://www.usenix.org/conference/osdi20/presentation/zhang-haoran)，**OSDI 2020**；[论文 PDF](https://www.usenix.org/system/files/osdi20-zhang_haoran.pdf)。

论文研究有状态 serverless 函数组成的工作流，在失败和并发环境下提供恢复与事务语义；日志和重新执行是其关键机制。第 7 节比较延迟、吞吐及日志管理等开销。

对本项目的启发是：既评估失败后的正确执行和提交，也评估为可靠性支付的正常运行开销。它与多阶段 Agent 流程有结构相似性，但不是 LLM 报告质量基准，其语义保证也不能直接移植到未受其协议保护的外部工具。

### 2. Flink 2.0：检查点与恢复性能的直接参考

[Disaggregated State Management in Apache Flink 2.0](https://www.vldb.org/pvldb/vol18/p4846-mei.pdf)，**PVLDB 18(12)，2025（VLDB 体系）**。

论文直接研究状态存储、检查点和恢复。第 6.1 节展示检查点耗时分布，并在配对配置下比较恢复与扩缩容时长；另外评价资源和成本。适合借鉴“保存耗时、恢复耗时、写入量、资源开销”的评测方法。

论文工作负载是大状态流处理，和本项目远程 LLM/检索工作负载不同。本项目可以借鉴实验设计，不能引用它的加速倍数作为自己的效果。

### 3. LangGraph：本项目最直接的实现参照

[开源仓库](https://github.com/langchain-ai/langgraph)与[官方 Checkpointers 文档](https://docs.langchain.com/oss/python/langgraph/checkpointers)。

官方资料区分 super-step 完整检查点与任务级 pending writes，并说明恢复时可以复用成功节点的持久化结果。这与本项目 Writer 输出已保存但后继检查点尚未推进的实验窗口直接相关。

建议针对所用版本验证实际数据库写入和真实进程崩溃，避免仅凭文档推断项目的全部保障。

### 4. Temporal：持久工作流与事件重放

[官方 Workflow Execution 文档](https://docs.temporal.io/workflow-execution)与[开源架构文档](https://github.com/temporalio/temporal/blob/main/docs/architecture/README.md)。

Temporal 以事件历史和确定性重放恢复工作流。适合参考恢复、重试、长任务与版本兼容的职责边界。官方架构明确区分工作流代码与活动代码，活动需要幂等或禁用重试等执行约束；不要把工作流可重放等同于任意外部 API 只执行一次。

### 5. 更贴近 Agent 的补充论文：需明确预印本身份

[Resume Means Resume: A Machine-Checked Conformance Contract for Checkpoint, Interrupt, and Resume Semantics in Workflow Persistence Layers](https://arxiv.org/abs/2608.03836)，2026 年 arXiv 预印本；[v3 全文](https://arxiv.org/html/2608.03836v3)。

它提出持久化前缀续跑、外部效果恰好一次、分叉确定性、检查点合法性、恢复输入只消费一次和恢复确定性等恢复契约，并提供故障与并发测试思路。与“怎样证明 resume 的语义正确”最贴近。

本次查到的原始来源不足以确认顶会录用，因此不将它列为已发表顶会论文；也没有复现其框架比较结果，不能据此宣称本项目或当前依赖版本存在同样缺陷。

## 建议的下一轮评估

冻结应用源码、图版本、依赖、模型参数、提示词、工具、数据源、预算和评价标准；保留供应商与独立调用日志，防止恢复预算漏记影响成本结论。先做确定性假模型机制测试，再以真实模型确认性能与任务质量。

至少设四组：A 无故障且不保存检查点；B 无故障且保存检查点；C 指定故障后从头重跑；D 同题同故障窗口从检查点恢复。A/B 评价正常开销，C/D 评价恢复收益，B/D 评价故障恢复后的质量变化。比较完整总成本时应包含故障前消耗、检查点开销、所有失败与重试；比较故障后增量成本时则明确共同前缀不在分母。

| 故障类别 | 至少覆盖的位置 | 重点检查 |
| --- | --- | --- |
| 进程终止 | 节点执行中、节点返回值保存后/完整检查点前、完整检查点后 | 恢复前缀、丢失量、重复调用 |
| Writer 章节 | 章节生成中、章节 task 提交后、合稿中 | 已保存章节复用、claims、usage 和调用身份 |
| 工具或模型异常 | 请求超时、服务端完成但客户端未收到结果 | 重试与重复费用；外部效果是否可确认 |
| 终态交付 | 终态检查点后/业务事务前、事务提交后/响应前 | 正式报告和完成事件恰好一份 |
| 并发接管 | 同时恢复、租约过期、新执行器接管后的旧写入 | 执行权唯一、过期提交拒绝 |
| 存储与长期恢复 | 检查点库暂不可用、外置证据缺失、版本/配置不兼容 | 正确恢复或明确拒绝，避免静默丢状态 |

范围内故障全部计入对应成功率。故意不兼容的版本、非法用户、损坏存档另测正确拒绝率，不因拒绝速度快就计恢复成功。每个窗口建议重复运行，并在确定性窗口测试后增加随机时间 SIGKILL；按故障类别、位置和任务分别报告，覆盖矩阵比一个总均值更有解释力。真实业务总观察窗口固定，超时/失败不能从成本和成功率报告里消失。

## 已测量、间接推断和尚未评估

- **已测量（历史实测，本次重新核对）**：四题指定 Writer 提交窗口恢复交付、逐题耗时和交付一致性；终态单例补交付及一次重复请求；假模型真实数据库跨进程章节复用。
- **间接推断**：复用已保存结果能减少已完成工作的重做；Beldi、Flink、Temporal 的设计和评测方法可以启发本项目。不是已测量的本项目总体成本收益。
- **尚未评估**：本次没有新增运行；当前版本全故障矩阵成功率、真实章节恢复费用、配对省时率、恢复就绪 P95、正常持久化开销、独立恢复质量差、生产并发与长期恢复。

## 结论与下一步建议

项目效果优先报告“技术恢复成功率、已保存工作重复调用、交付一致性、恢复后交付耗时”；补齐配对基线后再报告时间与费用节省。将任务质量、正常开销和并发提交作为独立评价维度。

当前可用的历史表述是“指定 Writer 提交窗口四题 4/4 恢复交付，平均恢复后交付 6.11 分钟，均复用原初稿并从审核继续”。尚不能表述为任意中断 100% 恢复、总体平均省时或成本降低。阅读顺序建议先看 LangGraph 官方边界，再看 Beldi 的语义与正常开销、Flink 的性能评测，以及 Temporal 的重放与幂等约束。
