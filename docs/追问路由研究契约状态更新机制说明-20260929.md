# 追问路由研究契约状态更新机制说明

分析日期：2026-09-29。对象：Architect 首次规划与 FollowupRouter 追问节点如何将研究契约写入共享研究状态。

范围确认：按用户最新决定，暂不增加 Critic → Architect 路径。前一份三入口设计中的该部分仅保留为历史讨论，不属于当前实施范围。本次说明机制并给出接入建议，不修改生产代码。

## 当前实际机制

这里的“全局变量”准确来说是一次研究运行的共享状态 `ResearchState`，其中包含 `state['research_contract']`。它不是所有用户共用的 Python 全局变量。追问可以从父研究继承契约，在本轮运行的状态中写入新版本，不需要修改父研究历史。

模型只返回文本/JSON，不会直接改动 Python 状态；由调用模型的节点代码解析、校验并赋值。

- 首次规划：Architect 调用模型后，程序执行 `state['research_contract'] = build_research_contract(result, processed_outline, state['query'])`，再补充原话和有效执行约束。
- 追问：FollowupRouter 解析为 RouteDecision，随后调用 `apply_decision()`。这个函数已经会修改研究状态，最后 `return state`。
- 状态提交：`graph.make_node()` 从当前图状态复制 work，运行节点，成功后经 `pack_state(result)` 返回外层 `{'research': ...}`；图使用配置的 checkpointer 保存节点更新。后续节点从更新后的 research 状态读取契约。

所以追问路由有与 Architect 相同的写状态能力，不必重新调用 Architect 才能“落实”约束，也不需要另一套全局存储。

## 目前已有与缺失的部分

`apply_decision()` 已执行：

```python
state['research_contract']['followup_instructions'] = decision.revision_instructions
state['research_contract']['active_constraints'] = state['active_constraints']
```

同时，它继承/清空 active_constraints，再合并 constraint_updates 中非空的 max_body_chars。Writer/Scout 路径会继承旧契约，随后添加上述更新；这已实现有限的状态写入。

不足在于：自由文本的 revision_instructions 不会自动转换成契约中的研究对象、时间范围、显式要求或指标范围。把“只比较A和B”添加为一句修改指令，不等于删除 required_entities 中旧的 C。当前 contract.query 等字段也没有在这些分支中被完整同步更新。

## 建议的具体接入位置

扩展已有 RouteDecision，让模型在 revision_instructions 之外返回结构化 constraint_patch；补丁包含操作、目标要求、值和用户依据。新增公共函数 `apply_contract_patch()` 合并旧契约并做校验，接在 `apply_decision()` 内。以下仅为伪代码，函数与字段尚需实现：

```python
def apply_decision(state, decision, settings):
    parent = state['followup_parent']
    # 根据主题/约束适用范围决定基线，不能只靠任意JSON覆盖。
    base_contract = select_applicable_contract(parent, decision)
    new_contract = apply_contract_patch(
        base_contract,
        decision.constraint_patch,
        original_query=state['original_query'],
        resolved_query=decision.resolved_query,
    )
    validate_contract_and_route(new_contract, decision, parent)

    # 先继承适用材料；现有继承函数可能复制旧research_contract。
    inherit_applicable_artifacts(state, parent, decision)

    # 最后安装新契约，避免被旧契约覆盖。
    state['research_contract'] = new_contract
    state['active_constraints'] = derive_active_constraints(new_contract)
    state['query'] = state['resolved_query'] = decision.resolved_query
    state['revision_instructions'] = decision.revision_instructions
    state['followup_route'] = decision.route
    return state
```

上例省略现有事实/材料复用检查、检索任务设置、父研究追溯信息等，接入时须保留；建议将 query、原话、修改指令分字段传递，并同步调整当前依赖拼接query的下游提示词。不得仅复制伪代码替换整个已有函数。

公共函数完成：校验结构/允许字段/要求ID和版本、核对用户出处、按 add/replace/remove 合并、保留未修改要求、同步派生执行约束。程序能验证出处和结构，但不保证模型的自然语言解释一定正确，歧义仍要暴露。

例如已有 `max_body_chars=5000`，本轮明确改为“不超过3000字”：模型输出替换字数上限的补丁，程序将契约改为3000，并同步 `state['active_constraints']`。当前长度门禁读取后者；只改契约却不更新该投影，会造成写作要求和最终检查不一致。正文能否真正满足要求，仍需 Writer 执行和交付前检查，写入状态本身不是完成任务。

## 三个现有追问分支

- Writer：读取更新后的契约，按新要求修订正文。
- Scout：按更新后的对象/时间/来源范围补搜；旧材料需重新判断是否适用。
- Architect：读取更新后的用户约束，生成新大纲，并更新契约中的章节覆盖等规划字段。接入时必须调整其当前无条件重建契约的逻辑，避免覆盖掉路由刚提交的有效用户要求。

Writer/Scout 不应从自然语言指令各自再构造另一份有效契约。Architect 也不应因重新生成大纲就自行删除已确认的用户约束。三条路径都使用同一契约字段与公共校验规则。

## 原始记录、指标、风险和结论

原始机器可读核对记录：`backend/eval/data/追问契约状态更新静态核对-20260929/核对结果.json`，包含源码路径及 SHA-256。

本次静态确认的核心结果：首次契约写入位置1处；追问已有 followup_instructions 与 active_constraints 两类直接契约字段写入；现有追问路由为3类；未新增任何路由。未执行线上模型或开发集，成功率、成本和时延均未测量。

待验收的失败风险案例：继承材料把新契约覆盖为旧契约；只修改契约却未同步 active_constraints；Architect 重规划清空追问约束；自由文本修改未反映到对象/时间字段；补丁校验失败仍进入下游。以上为静态机制风险，不是本次真实失败轨迹。

已确认边界：代码存在上述节点状态写入与图状态返回链路。间接推断：扩展现有 apply_decision 和公共契约合并函数可实现所有现有追问分支的一致更新。尚未评估：新增补丁协议的模型遵守率、字段合并测试、真实检查点持久化与恢复、端到端追问执行效果。

结论：追问契约落实到共享状态的执行位置已经存在，缺的是更完整的结构化变更协议和公共合并/校验逻辑。下一步应先实现并测试这两部分，再验证三个现有分支与检查点恢复；不扩展 Critic 路由。
