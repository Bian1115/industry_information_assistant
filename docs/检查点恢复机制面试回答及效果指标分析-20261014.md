## 失败样例与局限性

- 历史初测曾把空 next 的待合并节点结果误判为不可恢复，题目 26 原断点被拒绝；修复后从 review 继续。真正终态已保存而业务交付缺失的题目 28 曾被恢复入口拒绝，增加幂等补交付后成功。保留旧失败，不能将不同版本分阶段成功记录合成总体恢复成功率 100%。
- 原题目 28 有休眠导致的计时异常，墙钟 1829.456 秒、单调计时 524.984 秒；原异常保留，四题正常平均采用再次复评。第一次环境复评在正文提取阶段失败，尚未触发目标 Writer 故障，不能记为恢复失败或 0 秒恢复。
- 原报告保留两次模型调用前的评测器准备失败：字节码哈希校验和布尔开关格式问题。本次没有把它们纳入有效故障样本，也没有删除原记录。
- 四题中两题以 needs_revision 交付。技术恢复与交付成功不等于独立报告事实质量达标。
- 历史实验未覆盖当前 v5 外置证据依赖组合的全量恢复矩阵；未测任意崩溃、真实双执行器接管、数据库故障和生产并发。事件、历史和业务交付的 fencing 校验不能被概括为所有底层 checkpoint 写入都具备数据库强制 fencing。
- 部分业务配置有快照和一致性校验，但全部角色模型、提示词、工具、预算、代码与依赖尚无统一完整冻结快照。面试中使用“检查配置兼容性”，不承诺所有配置自动恢复为原值。
- 未建立同版本配对完整执行基线，不使用平均省时或整体成本降低指标。历史单例约 58.9% 的时间差不纳入主回答。

## 可直接使用的面试回答

“我在这个项目里实现的是节点级检查点恢复，并在写作阶段进一步支持章节级结果复用。主要解决长时间研究任务中断后，需要从头检索、分析和生成报告的问题。

第一，保存业务状态和执行位置。我把规划、检索、分析、写作、审核组织成 LangGraph 状态图，通过 AsyncPostgresSaver 把检查点持久化到 PostgreSQL。业务状态包括研究大纲、事实、分析结果、报告草稿和配置快照；框架同时保存节点调度信息。入库前，我会剥离事件回调等运行对象，并检查状态是否可序列化。

第二，沿用原运行身份续跑。每次研究的 run_id 对应 LangGraph 的 thread_id。恢复时先验证运行归属、检查点和配置兼容性，再沿用原编号，调用 graph.astream(None, config=原运行配置, durability="sync")。None 表示继续已保存的执行，sync 保证下一步开始前，当前步的检查点已经保存。例如分析节点已经提交、写作中途失败，恢复后进入写作，不会重新执行前面的规划和检索。

第三，缩小写作阶段的重做范围。我把每章生成封装成独立的 LangGraph task，保存章节正文和论断。恢复时写作节点会重新进入，但已持久化的章节结果可以复用。应用层再校验章节 ID、输入和写作配置的哈希，并按章节 ID 覆盖写回，避免重复追加。

第四，处理并发恢复和界面恢复。后端通过数据库租约获取执行权，定期续租，并在事件、历史和最终交付写入时检查 fencing_token，拒绝过期执行器提交。界面进度通过独立事件账本恢复：事件先入库再通过 SSE 发送，客户端用 after_seq 补拉遗漏事件，并按 (run_id, seq) 去重。

第五，处理图完成但报告尚未交付的情况。图的终态检查点和业务交付是两个提交边界。报告、运行完成状态和完成事件在同一个业务事务里提交，并做幂等控制。如果图已经完成、交付尚未提交，恢复时只补交付，不再调用 Agent。

效果方面，此前纯节点恢复专项在四个开发集任务的同一写作提交窗口注入 SIGKILL，四个样本都恢复交付，平均恢复 6.11 分钟，包含租约等待和后续审核返工。四题均复用原初稿，从审核继续，最终报告与检查点正文一致。终态补交付另有单例实测 3.47 秒，新增模型调用为 0，重复恢复请求没有产生第二份报告或完成事件。章节复用另外通过真实 PostgreSQL 跨进程机制实验，模拟模型下已保存的前两章重复生成调用为 0。

这套机制的恢复边界是已持久化的节点或章节成果。尚未保存成功的模型调用仍可能重做；这些结果证明的是指定场景下的技术恢复和交付能力，不代表任意位置无损恢复或报告质量全部达标。”

## 结论和下一步建议

采用“实现方式＋提交边界＋实测样本＋适用范围”的面试表达。主效果选取四题 4/4、平均 6.11 分钟，以及终态单例 3.47 秒、零新增模型调用、一次重复请求无重复交付。章节实验单独标明模拟模型；不混用四题数据证明章节级资源收益。

若后续需要回答平均节省多少时间或费用，应在当前冻结版本上补同题同预算配对完整执行基线与重复故障实验；章节收益另做真实模型评测。当前回答所需的指标已核对，不因面试文案任务额外调用模型或执行长时评测。
