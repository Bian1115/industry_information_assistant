- 评估日期：2026-10-16（Asia/Singapore）。

## 1. 结论

当前已经具备正文分块、来源章节 metadata、BM25 词法召回与向量召回、RRF 融合和模型精排。与目标的主要差距是：

1. **读取后保存的是受长度限制的正文，并未保留全文。** 普通 HTML 默认在约 30,000 字符处截断，再对截断后的正文编号、入库和切分。PDF 还有最多前 100 页的限制。
2. **章节关联有写入 metadata，但没有用于 Writer 正文证据的检索前过滤。** 当前将研究问题、章节标题、章节描述拼成 query，在当前主题证据库检索。章节文本影响相关性，不能代替 `section_id in related_sections` 的过滤条件。
3. **候选量默认是 RRF 前 3 页 × 128＝最多 384 条，目标是前 2 页 × 128＝最多 256 条。** 每页 128 条已经一致。
4. **写作层精排默认 Top8，目标是 Top10。** 精排后还会加入相邻 chunk，并受输入预算删减，因此当前最终交给 Writer 的单元数量并不固定。
5. **已入库文档后续增加章节关联不会同步到存储中的文档和 chunk。** 因此不能只加章节过滤，还必须补齐关联更新，否则可能漏掉新增关联章节的证据。

其中页数与精排 TopK 已有环境配置；全文保留、章节过滤、关联更新以及最终 Top10 的返回口径需要改代码。

## 2. 用户目标与术语口径

目标链路按以下顺序理解：

`提取并保留正文全文 → 全文切 chunk → metadata 标记关联报告章节 → Writer 按章节先过滤 → BM25 与向量双路检索 → RRF 排序 → 前2页，每页128条 → 精排 → 返回 Top10 作为本章节证据`

- 此处“页”是 RRF 候选列表的逻辑分页，不是网页数量，也不是 PDF 页数。
- 两页合计最多 256 个去重 chunk 候选；Top10 指精排后的证据单元，不等于 10 篇来源文档。
- 若本章节合格证据不足 10 个，应返回实际数量并注明不足，不能为凑数跨章补证。
- “前2页进入精排”不必等于固定调用两次精排 API；API 组批还需要满足真实输入预算，最终排名需在统一口径下产生。

### 3.3 边界

- **已测量**：当前函数对合成输入的实际处理、章节 metadata 继承、跨章节召回、关联未同步、候选分页与精排入参数量、邻居和预算对返回数量的影响。

## 4. 逐环节实现与差异

### 4.1 网页读取：先截断，再编号和切分

主要位置：

- `backend/app/service/web_reader_service.py:130`：默认 `max_chars=30000`、`max_bytes=10MiB`。
- `backend/app/service/web_reader_service.py:567`：`_extract_html()` 提取正文，返回时调用 `limit_body_preserving_tables(content, self.max_chars)`。
- `backend/app/service/web_reader_service.py:425`：读取主流程又对正文应用同一限制。
- `backend/app/service/web_document_structure.py:83`：普通正文按字符前缀截断；若边界落在表格内，可延长至完整表尾，因此30,000不是所有场景下严格不超过的上限。
- `backend/app/service/web_reader_service.py:612`：PDF 只循环前100页，字符数达到上限后停止，返回时再次切片。
- OCR、本地 Crawl4AI 也有字符裁剪；Crawl4AI sidecar 经常规主流程返回时也受到最终裁剪。
- `backend/app/service/deep_research_v2/agents/scout.py:1006`：成功读取的 `read_result.content` 被写入 `full_content` 和 `raw_sources`，但此时正文已经受到读取器长度限制。

因此，`full_content` 这个名称和“全文读取”注释不能证明内容完整。当前不是“完整正文入库后，仅缩小模型输入”，而是正文源数据在入库前就已经丢掉后缀。

补充区分：Scout 常规搜索分析目前通过 `evidence_batches.py:52` 按预算覆盖全部**已经读取且准入通过的**编号正文，不再固定只展示每页前12,000字符。`scout.py:2038` 的 `deep_read_url()` 辅助方法仍有 `[:12000]`，但本次仓库调用搜索仅发现它的定义，不能把该辅助方法当作当前常规链路的裁剪原因。

### 4.2 chunk：已具备结构化切分，但章节关联是来源级继承

主要位置：`backend/app/service/session_evidence_chunks.py:16`。

- 普通正文保留句子子单元，并按段落组装父 chunk。
- 表格、记录使用结构化单元，长表按行拆分并保留表头、注释、来源偏移。
- 单元 metadata 包含 `document_id`、`source_url`、`source_title`、`content_sha256`、`source_spans`、`sentence_ids`、`heading_path`、`related_sections`、父子及邻居关系。
- `related_sections` 直接复制来源的章节列表。同一网页若关联A、B两章，它的所有 chunk 都继承A、B，不会逐块判断哪一段只属于A或只属于B。
- `heading_path` / `source_section_id` 表示来源网页内部标题和章节位置；`related_sections` 才是报告章节关联，两者不能混用。
- 单句或结构化单元无法在预算内切分时抛出错误，Store 保留正文并记录 `rag_chunk_error`；不应把“正文已保存”等同于“每篇正文都成功产生可检索 chunk”。此边界来自源码，未在本次另外测量发生率。

写作 `context` 层检索段落、表格、记录等上下文单元；引用 `citation` 层检索句子、表格、记录。这是现有双层证据视图，不是用户所说的两路召回；每一层内部才执行 BM25+向量双路召回。

### 4.3 关联更新：后续章节关系可能仅存在于内存

- `scout.py:1023`：同一 URL 后续用于另一个报告章节，会向内存来源的 `related_sections` 追加章节 ID。
- `session_evidence_store.py:80`：同一文档已存在且内容哈希不变时直接 `continue`，未合并新的 `related_sections`，也未更新已有 chunk 的 locator。
- `session_evidence_vectors.py:21`：Milvus 集合字段中没有 `related_sections`，也没有章节关联更新路径。

此问题的前提是文档已经入库，随后才增加章节关联；同一轮首次入库前已合并完整章节列表的来源不受这个特定问题影响。正文内容不可变与章节关系可增补需要分别处理。

### 4.4 Writer 检索：事实列表有章节筛选，正文 chunk 检索没有

主要调用：`writer.py:705 → session_evidence_rag.py:467 → :393 → :238`。

1. `writer.py:620` 先按 `related_sections` 选择**结构化事实列表**，没有本章事实时退回全局前10条；这是事实输入的章节选择，不是 RAG chunk 的章节过滤。
2. Writer 调用 `evidence_prompt()`，传入“问题+章节标题+章节描述”以及相关事实 ID。
3. RAG 启用时，`session_evidence_rag.py:467` 的包装函数不使用 `fact_ids`，直接按 query 调用证据检索。
4. `retrieve()` 仅按用户、会话、主题、单元类型、来源域名等约束取候选。接口支持可选 `document_ids`，但 Writer 没传；接口没有 `section_id` 参数，也未检查 metadata 的 `related_sections`。
5. 向量 `search()` 同样没有章节过滤参数或表达式，只过滤用户、会话、主题、generation 和单元类型。
6. 单章修订入口虽然收到 `section_id`，在 RAG 分支也只是从章节信息构造 query，没有将章节 ID 用作过滤条件。

结果是“在整个当前主题中按章节文本检索”，与“先限定到本章证据，再双路检索”不同。仅在 query 写章节标题无法保证不会返回其他章节专属证据。

若后续只在向量结果返回后删除其他章节，也不等价于检索前过滤：有限的向量候选页可能已被其他章节占据，使本章相关证据进不了候选。应让两路召回采用一致的章节范围。

此外 Writer 还接收事实、数据点、洞察等输入，并不是只接收 RAG 选中的证据单元。若“Top10作为本章证据”还意味着所有外部事实均须限定于这10条，则这些额外输入和回退策略也需要统一；用户目前的要求可以先落实为本章正文证据候选 Top10。

### 4.5 双路检索与 RRF：已实现

主要位置：`session_evidence_rag.py:266` 至 `:315`。

- 词法路：采用 BM25 公式，分词使用中文单字、相邻双字及英文词/数字。
- 向量路：查询 Embedding + Milvus COSINE 检索。
- 两路结果按 chunk ID 对齐，RRF 得分是各路 `1 / (rrf_k + rank)` 之和，默认 `rrf_k=60`。
- 先融合排序，再切取候选分页，符合目标中的整体顺序。
- 当前每路最多召回3页×128，融合后最多取3页×128个去重候选；不会将两路直接拼成768条全部精排。候选不足时不补齐。

### 4.6 精排与 Writer 实际输入：默认384候选、Top8种子，再扩展与裁剪

主要位置：`session_evidence_rag.py:316`、`:330`、`:347`、`:485` 与 `session_evidence_ranking.py:23`。

- 默认融合候选最多384条，一起传入 `rerank_candidates()`。
- 精排 API 的请求批次由输入 token 预算和最大文档数决定，不按 RRF 每页128条固定调用一次。
- 能放入同一请求时整体精排；否则各批选出候选，继续统一精排，避免直接拼接跨请求相对分数。
- 写作层默认精排种子 Top8，引用核验层默认 Top5。
- `neighbors=True` 会给种子添加前后相邻单元，默认半径1；邻居没有再次统一精排，也没有最终重新截成Top8/Top10。
- 随后按整个 JSON 证据视图的 token 预算保留能放下的完整单元，较大的高排位单元可能被跳过。
- 在真正调用 Writer 模型前，`fit_evidence_prompt()` 还可能为了整体输入窗口逐个移除末尾单元。
- 向量故障可以降级为词法召回；精排故障会记录失败并退回RRF顺序。因此也不能把所有返回证据都称为成功精排的 TopK。

因此，只把 `context_top_k` 改成10只能得到“最多10个精排种子”，不保证 Writer 最终收到恰好10个单元，也不保证整个提示词中的其他事实来源都属于这些种子。

### 4.7 生效条件

`deep_research_v2/service.py:214` 在启用持久化、具备用户身份且 `SESSION_EVIDENCE_ENABLED` 开启时创建会话证据服务，Graph 在阶段前入库并绑定该服务。未绑定时，`evidence_prompt()` 回退为按事实绑定取原句的旧证据视图，不走上述双路RRF链路。

因此，直接调用 Writer、关闭持久化的实验或某些单元测试不能代表临时RAG已启用；验收应覆盖正常服务入口。

## 6. 相对用户目标的失败样例

这些是当前实现相对目标的失败样例；既有回归均通过，两者口径不同。

1. **长文尾部证据丢失**：构造1800个叙述段落并在最后加入“全文末尾唯一证据标记”，直接调用生产 `_extract_html()`，输出恰为30,000字符且没有该标记。后续切chunk无法恢复这个标记。
2. **章节过滤缺失**：分别写入只关联A章、只关联B章的来源，再用包含“章节A、只写章节A”的query经过 Writer 使用的 `evidence_prompt()` 入口检索，仍返回B章专属单元；传入无效 `fact_ids` 也未限制RAG结果。
3. **新增关联无法检索**：文档首次以A章关联入库，之后在内存追加B章并再次 `ingest()`，已保存文档和chunk仍只有A章。若直接加 `B in related_sections` 过滤，B章会漏掉这份来源。
4. **TopK不是最终条数**：将种子数设为1且保留邻居，实际返回3个单元；缩小视图预算时，4个种子又可能一个都放不下。真实返回多少需结合正式tokenizer和Writer整份输入验证。

## 7. 建议的改动范围与验收

1. **保留完整正文**：移除HTML、浏览器、OCR等成功提取路径的字符前缀裁剪；若PDF纳入同一要求，移除固定100页/字符截断。保留明确的资源限制，并在无法完整提取时记录失败或不完整状态。不能将 `WEB_READER_MAX_CHARS=0` 当成无限制，当前函数按切片处理0。
2. **处理旧缓存和正文版本**：读取缓存键目前仅由URL生成（`web_reader_service.py:217`）；旧截断正文不会因为改TopK或分页自动补齐。需区分新提取策略、重新抓取并为完整正文建立新版本与索引，保留既有引用版本的可追溯性。
3. **稳定传递章节ID**：Writer初写、单章修订均向RAG显式传入报告 `section_id`；按 `related_sections` 先限定词法和向量两路的候选范围。若页内还需要更细粒度的归属，应另行定义chunk级章节映射，不能将来源级继承描述成逐chunk语义归属。
4. **同步章节关联**：正文仍可保持不可变，但新增章节关系需要同步文档、chunk和向量过滤所需的派生元数据。对已入库数据补全关联，防止上线过滤后漏证。

7. **保持核验层独立**：本章写作按章节过滤；写后逐论断核验目前主动检索整个当前主题以寻找反证，不应仅为实现Writer章节Top10就把核验范围同时缩小。
