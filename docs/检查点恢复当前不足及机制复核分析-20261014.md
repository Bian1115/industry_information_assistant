## 当前不足及影响

### 1. 失败尝试与已复用章节的运行预算会漏记

当前[节点包装器](../backend/app/service/deep_research_v2/graph.py#L124)在已提交状态的深拷贝上执行；[阶段保护](../backend/app/service/deep_research_v2/stage_runtime.py#L178)在 `finally` 中把时间、调用与 token 写进该工作副本。节点抛错后不会正常返回 `pack_state`，这些新增预算无法成为成功的节点状态。

本次故意让搜索节点消耗 100 个模拟 token 后失败。工作副本正确记录 100，但故障检查点仍为 0；新 Agent 续跑消耗 40，最终累计只有 40。失败消耗的约 0.021 秒也未进入后续累计；该短时数字仅说明机制，不用于性能评价。节点尝试次数同样回退，事件中的 attempt 不能据此唯一识别物理重试。

Writer 的[章节 task 返回值](../backend/app/service/deep_research_v2/agents/writer.py#L570)只有版本、章节 ID、输入哈希、正文、claims、核验标记，没有 usage。前两章成功入库、第三章失败后，恢复正确复用了前两章，但重建 Writer 的计数器从 0 开始；最终图预算未包含前两章原生成消耗。本次模拟累计 400，图预算只记 200。

这不表示独立 Agent 历史或埋点必然丢失所有 usage；[模型调用](../backend/app/service/deep_research_v2/agents/base.py#L391)可另写 `llm_usage`。问题是 `consumed_tokens` 只读图内 `runtime_budget`，恢复没有从独立历史重建预算。默认 token 上限为 0，不限制；启用正上限时该漏记影响约束效果，默认总时长限制也受失败尝试漏记影响。

建议优先建立独立、幂等的调用预算账本，分别保存已预留、已返回 usage、结果未知和已对账状态；章节产物关联调用 ID。恢复时核对真实累计消耗，保留独立物理 attempt ID，不依赖成功节点提交才保存消耗。

### 2. 执行租约未原子约束检查点写入

当前有 60 秒租约、续租、事件写入 fencing 校验、终态交付 fencing 校验和历史写入 token 校验，已有保护应保留。薄弱处是[阶段执行](../backend/app/service/deep_research_v2/stage_runtime.py#L173)取回 action 结果后直接返回，没有完成后的租约复查；服务的 `lease_valid` 也只检查续租任务设置的本地失效标记。

本次可控实验让 action 在返回前把租约检查函数的状态设为失效。前置及循环检查均已执行，结束后未再检查，结果依然进入内存 saver。这验证了检查位置的缺口。

进一步查看[原生 AsyncPostgresSaver 注入](../backend/app/service/deep_research_v2/checkpointer.py#L59)和[图配置](../backend/app/service/deep_research_v2/graph.py#L306)：检查点只按 thread/run 定位，未接入业务 run 的 owner/fencing 条件。因此“执行器 A 长时间停顿、B 租约接管、A 返回迟到结果”的图提交隔离还不能由事件与报告的校验推出。本次没有实测两进程向真实 PostgreSQL 竞争，也没有观测生产检查点污染。

建议先补完成前检查缩小窗口，再在 saver 写入或运行提交协议中实现与租约接管一致的原子 fencing。只增加一次 Python 检查仍存在检查之后至提交之前的竞态；验收需覆盖 A 停顿、B 接管、A 迟到的真实双进程实验。

### 3. 细粒度恢复只覆盖部分写作产物

普通初稿章节已经通过 `writer_section_draft_v1` 保存，不能再将“初稿前几章一律重写”列为当前普遍不足。仍未覆盖：

- Scout 的每次搜索、每个 URL 阅读、正文提取和事实核验产物。
- Writer 首尾合稿、统一引用核验/修复，以及[逐章定向修订](../backend/app/service/deep_research_v2/agents/writer.py#L1201)和用户编辑路径。
- 分析、审核节点内部的多次模型调用。

Scout 的[搜索缓存](../backend/app/service/deep_research_v2/agents/scout.py#L332)属于 Agent 实例内存，服务恢复重新构造 Agent；网页文件缓存、外置证据和历史记录可能提供部分复用，但不等于每个工具调用都有可靠的执行结果检查点。

节点未提交且缺少独立 task 产物时，需要重新进入节点，可能重复搜索、提取、修订或核验。即使有章节 task，外部 API 已完成而返回值尚未入库的窗口仍可能重复请求；当前不能承诺外部调用恰好执行一次，也不能恢复模型生成到某个 token 的调用栈。

建议优先为 Scout 的高成本逻辑单元、修订章节和逐条核验建立可重放产物。用输入哈希、稳定逻辑单元 ID、完整结果与调用账本区分恢复重做和 Critic 新一轮业务返工；不要只缓存“已完成”标记。

### 4. 检查点依赖多套存储，恢复没有统一对账

图状态、Agent 历史、会话证据、向量索引、事件账本各自提交。[证据提交](../backend/app/service/deep_research_v2/graph.py#L170)发生在节点返回 saver 之前，[会话证据入库与索引](../backend/app/service/session_evidence_rag.py#L142)又包含不同存储步骤。某处成功、后一处失败后，可能留下“历史/证据已保存、图节点未提交”或“事件显示了进度、执行产物尚未提交”的组合。

终态已采用[单个业务事务](../backend/app/service/deep_research_v2/delivery.py#L207)写报告、run 状态与完成事件，恢复入口也支持补偿。因此“终态未交付完全无法恢复”属于已修复的历史问题。当前不足主要在中间产物和依赖的统一状态清单、故障对账、失败诊断；不能因终态幂等成立就推断所有组件原子一致。

建议让检查点引用明确的产物清单和版本，在恢复前验证缺失、过期及已完成逻辑单元；分别处理可重建索引、可重放产物和不可恢复的正文缺失。继续保留“进度观察”和“已提交成果”的语义区别。

### 5. 长期恢复受会话与证据保留期限制

当前检查点可只保存[外置正文引用](../backend/app/service/session_evidence_rag.py#L188)，恢复需 hydrate；缺失正文时[明确拒绝](../backend/app/service/session_evidence_rag.py#L122)。默认证据 TTL 为 86400 秒，会话按 24 小时无新消息过期；检索、摘要和继续执行本身不会按当前时间延长保留期。

清理会话证据时会[删除对应检查点线程](../backend/app/service/session_evidence_lifecycle.py#L80)，因此当前恢复是有保留期的会话能力。若需求包含隔天、隔周继续研究，或暂停任务长期保留，需要单独定义运行和产物的保留策略。该限制来自明确的生命周期设计，不应当称为正文恢复 bug，也不应通过绕过过期校验来修复。

建议在状态接口和页面显示恢复期限、依赖过期原因；按产品需求决定是否对运行中/暂停中的任务提供专门保留策略或显式归档。

### 6. 配置冻结和版本兼容不覆盖完整执行环境

当前已冻结并校验上下文策略、核验/假设/Critic 开关、会话决策哈希、来源范围及搜索后端，Writer 章节还有输入和写作配置哈希。这些保护已经生效，本次章节更换模型拒绝回归通过。

但[恢复创建 Agent](../backend/app/service/deep_research_v2/service.py#L211)仍读取当前部署配置，[运行预算](../backend/app/service/deep_research_v2/stage_runtime.py#L63)也重新读取环境中的总时长和 token 上限。没有覆盖全部角色模型、全部提示词/工具行为、代码和依赖版本的统一运行配置快照。即使 graph_version 相同，部署变化也可能让后续节点使用不同配置；部分 Writer 产物不匹配则会拒绝复用。

图版本准入目前依赖[人工列出的旧版本集合](../backend/app/service/deep_research_v2/service.py#L494)，旧路由、未知版本或不支持的策略要求重新发起，缺少完整的迁移及恢复能力诊断。Writer task 上下文判断还使用内部 `__pregel_call` 协议键，依赖升级需专项回归。

建议记录完整有效执行配置、提示词与产物协议版本，明确哪些变化可兼容、需迁移或必须新建运行。API 在展示可恢复状态时就返回版本/配置/依赖检查结果，避免开始恢复后才发现不兼容。

### 7. 服务端自动恢复与补交付调度仍不足

客户端已有自动重连/恢复逻辑，路由支持续跑和终态补交付；此处不应概括为“只能手动恢复”。当前[后台调度任务](../backend/app/service/scheduler_service.py#L29)主要处理清理和长期记忆，没有研究运行的租约过期扫描、终态未交付对账或持久化恢复队列。`make_commit_result` 的实际业务调用集中在研究服务入口。

所以没有客户端继续触发恢复时，中断运行和未交付终态缺少主动完成的服务端路径。硬崩溃后的新执行器还要等待原租约到期；历史四题中实际等待 37.55～50.35 秒。这个等待承担防止双执行的作用，不能通过直接抢占活跃租约消除。

建议先为终态缺交付增加幂等后台对账，再明确哪些技术中断可自动续跑、哪些取消必须等待用户。恢复队列保存退避、次数、原因和预算，结合租约与独立物理 attempt ID。

### 8. 开销与稳健性证据仍不完整

GraphState 使用整份 `research` 字典替换；节点执行深拷贝，Writer 每章也复制和哈希当前业务快照。原文外置已经减少一部分正文体积，但累计章节正文、claims、事实、分析、父报告等仍可能较大。本次没有测检查点写入字节、库增长或持久化 P95，不能直接声称已经存在显著性能瓶颈。

历史真实节点恢复新四题在指定 Writer 提交窗口 4/4 成功，含租约等待均值 366.58 秒（6.11 分钟）；另外引用旧 26 题后是分阶段五题汇总，不能描述为当前 v5 的同版本五题稳定成功率。该组关闭章节 task，也不能用于证明章节级真实模型收益。四题中 8、25 题以 `revision_limit/needs_revision` 交付，27、28 题流程内 pass；技术交付成功和报告质量合格需分别评估。

历史 Writer 跨进程实验为一次真实 PostgreSQL + SIGKILL + 新进程，使用假模型/核验；历史原 28 题终态补偿实测成功且重复请求不改数据库，但没有真实双进程、数据库异常和浏览器端到端矩阵。当前 v5 新增外置证据后，这些旧实验不能自动证明新依赖组合可靠。

建议补充同版本、固定故障点与随机崩溃的重复实验；覆盖搜索中途、修订中途、核验中途、检查点/证据/事件提交前后、租约接管和证据过期。分别统计交付一致性、重做量、累计消耗、恢复时长和独立报告质量；随后再测正常路径开销。

## 失败样例与复评记录

1. **已复现的功能边界**：搜索节点消耗 100 个模拟 token 后抛错，预算只留在失败工作副本；成功续跑后最终累计漏记该 100。章节 task 实验中首跑正文已保存且正确复用，仍漏记对应的 200 个模拟 token。
2. **已复现的机制窗口**：action 完成前失效的模拟租约没有阻止节点提交至内存 saver；真实 PostgreSQL 租约接管与旧执行器迟到写入尚未测量。
3. **预期拒绝与注入失败**：章节模型改变、无可恢复结果、缺少终态字段、未归属、租约冲突及交付失败的既有回归均按预期通过。日志中的注入交付错误不代表这次真实业务数据库失败。

## 结论与下一步建议

优先处理累计预算的独立持久化和图提交的租约隔离，这两项影响正确性。随后扩展 Scout、修订和核验的产物恢复，加入跨存储检查与终态后台对账。配置冻结、恢复期限和拒绝原因应形成清晰的恢复契约。

在扩大性能收益表述之前，先用当前版本完成真实 PostgreSQL 双进程接管及外置证据恢复实验。已有节点、章节和交付机制均有成功证据；样本与故障覆盖仍不足以承诺任意位置无损恢复、外部请求恰好一次、长期恢复或总体时间/费用收益。
