# 数据库检查点缓冲与200毫秒批量提交设计分析

评估日期：2026-11-03（Asia/Singapore）。

评估对象：应用使用 PostgreSQL 保存恢复数据时，是否需要程序内存缓冲，以及首条消息入队后等待 200ms 批量提交的可行性。

数据与配置口径：阅读当前工作区的历史存储、检查点存储及调用入口；工作区已有未提交修改。未连接数据库，未修改运行时代码，未执行性能或故障测试。这里的消息指应用准备保存的历史或事件记录，不假设每个流式文本片段都是完整检查点。

原始核查记录：[源码核查记录.json](../backend/eval/data/数据库检查点缓冲设计分析-20261103/源码核查记录.json)。记录包含所读源码的 SHA-256、仓库提交、静态发现与未测项目。

## 结论

数据库恢复不要求应用额外建立消息缓冲区。应用可以直接开启短事务、保存恢复数据、等待数据库提交。缓冲区是减少小事务数量的可选性能策略。

用户提出的方式可以实现：当待写队列从空变为非空时，应用启动一次 200ms 计时；后续消息只加入同一待写队列，不重置截止时间。计时到期后，后台写入任务取出当时队列中的消息，在一个数据库事务中批量插入并提交。

关键检查点、模型/工具执行前必须保存的记录，应能提前触发提交；调用方必须等待提交成功后再执行依赖它们的动作。不能把现有“保存返回即已提交”偷偷改成“保存返回仅代表已排队”。

## 存储位置与执行者

| 对象或位置 | 职责 | 是否已经持久保存 |
|---|---|---|
| 应用创建的消息对象 | 在 Python 内存中表示一条历史或事件 | 否 |
| 应用待写队列、正在提交的批次 | 保存尚未确认提交的消息，供后台写入任务读取 | 否；进程退出后无法依靠这份内存恢复 |
| 数据库连接、SQLAlchemy Session | 应用用于发送 SQL、管理事务的操作对象 | 它们不是数据的持久存储位置 |
| 数据库内存、操作系统缓存 | 数据库和操作系统用于处理及暂存写入的数据 | 不能仅凭数据到达缓存判断抗崩溃持久性 |
| 数据库 WAL 和表文件 | 数据库在持久存储上保存恢复日志与表数据 | 取决于提交和持久化配置 |

数据库通常仍使用磁盘或 SSD；改变的是由数据库负责管理持久存储，应用不再自己追加 JSONL 文件。WAL 是数据库先保存的修改日志，数据库重启后可以用它恢复已提交修改。正确启用持久同步提交时，数据库在确认相关日志已持久保存后返回提交成功，无须等待每个表数据页都立即落盘。实际保证依赖 fsync、synchronous_commit 与存储设备，本次未核查运行配置。依据：[PostgreSQL 提交说明](https://www.postgresql.org/docs/current/wal-async-commit.html)。

数据库自己的 checkpoint 是整理数据页与恢复日志的内部机制，不等于 Agent 的执行位置检查点，也不应通过把数据库 checkpoint 参数改成 200ms 来实现消息批处理。依据：[PostgreSQL WAL 配置说明](https://www.postgresql.org/docs/current/wal-configuration.html)。

## 200ms 批处理的完整过程

以下时刻均为说明用的相对时间，不是实测数据：

1. 0ms：Agent 生成消息 A，应用将 A 放入空队列，设置截止时刻为 200ms。
2. 60ms：Agent 生成 B，应用将 B 放入队列，截止时刻仍为 200ms。
3. 160ms：Agent 生成 C，应用将 C 放入队列，截止时刻仍为 200ms。
4. 约 200ms：后台任务把 A、B、C 从待写队列移交到一个独立的“正在提交批次”，随后获取数据库连接、开启事务、执行批量写入并提交。不能在整个收集窗口内占用数据库事务和行锁。
5. 数据库确认提交成功后，后台任务标记该批次已保存，并通知等待 A、B、C 的调用方。
6. 写入期间到达的 D 进入下一批；D 使新的待写队列从空变为非空时，应用为新批次设置自己的截止时刻。同一有序数据流内的下一批提交仍须排在前一批之后。

200ms 是目标收集等待时间。实际保存延迟还包含任务调度、前批排队、连接获取、SQL 执行和提交耗时，因此不能承诺消息在 200ms 内持久化。若每次新消息都重置计时器，连续输入可能长期无法提交，与用户要求不同。

## 必须明确的接口语义

- 入队接口只承诺接纳消息，可返回标识或等待凭据，不能宣称持久化完成。应用应复制或冻结消息内容，避免调用方随后修改队列中的记录。
- 强制保存接口应提交并等待调用时已接纳的目标消息及其前序依赖；不得仅启动后台任务就返回。可按“数据流身份＋目标序号”确定等待范围，不必等待未来不断到来的消息。
- 强制提交与计时提交应共用同一有序写入器，避免旧计时器提交错误批次、重复提交或后批越过前批。
- 一次批量事务成功后，才能推进已提交位置。关联的检查点、产物和完成事件必须继续满足当前原子提交要求，不能分别排队后独立宣布成功。
- 队列要有消息数或字节上限；达到阈值可提前提交。数据库持续失败时，应限制接收速度或返回失败，防止内存无限增长。
- 提交失败时保留正在提交批次，传播错误；连接中断可能意味着提交结果未知，应沿用稳定事件 ID 查询核对或安全重试。本地避免重复记录不自动保证外部工具不会重复执行。
- 正常停机时先停止接纳新消息，再等待已有消息提交；强杀进程不会可靠执行停机清理。

这里的“强制保存”是拟议的应用接口。当前 SQLAlchemy Session 的 `db.flush()` 只把待处理修改发送为当前事务内的 SQL，不等于事务提交；`session_factory.begin()` 的上下文正常退出后才完成提交。

## 失败样例与局限性

以下均是机制推演，没有执行故障注入：

| 场景 | 后果及所需处理 |
|---|---|
| A 在 0ms 入队，应用在 120ms 被强杀 | A 尚无数据库副本；恢复器无法从这个内存队列找回 A |
| A、B、C 提交期间应用退出 | 数据库可能提交或回滚；恢复器读取已提交记录，并按稳定 ID 核对，不以客户端异常断言未提交 |
| 数据库在 200ms 时仍不可用 | 未保存数据持续积累；200ms 不构成最大丢失时间保证 |
| 工具意图只入队就执行工具 | 工具可能产生外部效果，但应用崩溃后数据库没有对应意图；必须先等待意图提交 |
| 每条消息到达都重新等待 200ms | 连续消息可能使提交无限推迟；应保留首条消息的截止时刻 |
| 后台写入时直接清空共享列表 | 可能清掉写入期间新到达的消息；应在短锁保护下移交固定批次，新消息进入下一批 |

本次只提供机制说明和当前源码静态核查，未实现缓冲器，未证明批处理提升性能或保证不丢不重。下一步若决定实现，应先定义入队与已提交两种返回语义，复用现有事务及执行权校验，再验证首条计时、强制保存、并发入队、提交失败、确认丢失、队列上限和强杀恢复。
