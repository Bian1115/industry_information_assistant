## 原因一：系统反复休眠，连接、计时与租约受到不同影响

**已测量。** 电源日志记录00:06:07进入休眠，00:22:28进入DarkWake；随后多次重复，单次休眠通常约13—18分钟。模型重试警告集中在唤醒后，例如：

| 题号 | 系统唤醒 | 应用日志 |
| --- | --- | --- |
| 31 | 00:22:28 / 00:54:32 / 01:13:08 | 00:22:39 / 00:54:39 / 01:13:16连接错误重试 |
| 46 | 01:47:22 / 02:01:02 | 01:47:31 / 02:01:09连接错误重试 |
| 16 | 02:27:57 / 02:44:14 | 02:28:10 / 02:44:27连接错误重试 |
| 49 | 03:04:49 | 03:04:56连接错误重试 |

第31题运行区间累计4856秒处于日志标记的系统休眠。第49题只完成规划，首次研究模型调用进入连接失败与重试，尚未触发摘要，因此摘要开销不能解释全部五题失败。

**源码证据。** 阶段预算使用 [stage_runtime.py](/Users/bxy/projects/industry_information_assistant/backend/app/service/deep_research_v2/stage_runtime.py:119) 的 `time.monotonic()`；采集器 `asyncio.wait_for` 与最初的 `subprocess.wait(timeout=...)` 也基于该时钟。本机Python 3.13实测其实现为 `mach_absolute_time()`。macOS上的Python单调时钟使用该API，而它在系统休眠时停止增长。[Python时钟文档](https://docs.python.org/3.13/library/time.html#time.monotonic)、[Apple时钟文档](https://developer.apple.com/documentation/driverkit/mach_absolute_time)。

数据库租约采用真实UTC时间，默认60秒；续租任务每20秒运行一次，见 [service.py](/Users/bxy/projects/industry_information_assistant/backend/app/service/deep_research_v2/service.py:145)。事件保存要求 `lease_until > datetime.utcnow()`，见 [research_events.py](/Users/bxy/projects/industry_information_assistant/backend/app/service/research_events.py:293)。系统休眠期间UTC时间继续推进，执行器不能正常续租。

**间接推断，证据较强。** 系统休眠是四题长时间停滞与连接中断的主要共同诱因；计时基准差异解释了“30分钟超时，实际过了更久”的现象。第31题在01:31:03唤醒，同秒发生租约失效，符合“恢复后事件写入先于有效续租”的路径。续租线程实际调度顺序没有埋点，不能断言具体竞态已被直接捕获。也没有供应商独立可用性记录，不能断言所有连接错误都只由本机休眠造成。

休眠占比通过 `finished_at - duration_s` 重建墙钟区间，与Sleep至下一次Wake/DarkWake求交得到。第46题结束记录包含中断后归档时间。扣除休眠的剩余时间不是CPU时间，也不保证期间网络或进程始终可用。外部墙钟看门狗在系统睡眠期间同样无法执行，最多在恢复后立即检查截止时间。

## 原因二：摘要开销过大，失败后重新处理相同材料

**已测量：第35题。** 301162 token中，284248用于摘要和分句抽取，主流程仅16914 token；43个返回usage的摘要相关调用，对应规划1次、研究事实抽取1次主流程成功调用。

第一次摘要从23:59:15到00:01:14，耗时119.77秒，已花142883 token后出现 `summary_error`，没有采用摘要。该错误只记录空字符串，结合 [summary_citations.py](/Users/bxy/projects/industry_information_assistant/backend/app/service/summary_citations.py:503) 的120秒超时，强烈指向摘要超时；原事件没有异常类型，不能仅凭错误字段确认。

随后继续研究，第二次摘要又花141365 token。前三个 `summary_chunk` 的输入哈希与第一次完全相同，直接证明旧材料被重复处理。最终在第二次Claimify处理期间触发研究token预算，下一条请求被取消。此题结束前没有系统休眠记录，不能用休眠解释其预算耗尽。

**源码与轨迹吻合的机制。**

1. 回放同时包含工具输入、工具输出、旧模型输入和输出。第35题全文读取工具的输入带30条搜索候选及其摘要，约28582字符；这些搜索摘要此前也出现在搜索工具输出中，增加重复材料。
2. [agent_context.py](/Users/bxy/projects/industry_information_assistant/backend/app/service/agent_context.py:336) 判断需要摘要后，将原始 `candidates` 送入摘要器，而不是已缩短的 `views`。因此模型回放视图的外置、去重并未等比例降低摘要器输入。
3. [claimify.py](/Users/bxy/projects/industry_information_assistant/backend/app/service/claimify.py:178) 对摘要逐句串行执行筛选、消歧、拆解；之后还计划补齐引用。一份摘要会扩展为多次模型请求。第35题实际尚未到引用补齐阶段，已经耗尽预算。
4. 超时后保留旧摘要及覆盖游标是正确的保全行为，但本次缺少失败冷却与中间阶段复用；下一轮再次从未覆盖的旧原文开始。第46题也观察到摘要失败后重新处理旧材料。

第35题第一次待组装历史为62030 token；旧工具外置后仍为45671，触发整体摘要。摘要失败后继续外置近期工具，实际主模型请求视图降至11368 token。说明现有外置机制能使请求落入预算，但昂贵摘要发生在进一步外置之前。

关闭语义核验、NLI或最终报告引用核验，并不会自动关闭 `claimify-v1` 的分句抽取和引用结构维护。这些是独立配置。此次关掉的核验状态符合配置；高开销发生在仍然启用的摘要准备链路。没有证据表明失败来自引用核验判定不通过。

## 次要问题与尚未评估的边界

- 错误记录不足：`summary_error` 仅保存 `str(exc)`，超时得到空字符串；缺少异常类型、摘要尝试编号和累计费用。第31题续租没有逐次心跳埋点。
- [stage_runtime.py](/Users/bxy/projects/industry_information_assistant/backend/app/service/deep_research_v2/stage_runtime.py:146) 和模型取消收尾存在无独立时限的 `await gather(...)`。这是需要检查的可靠性风险；现有证据不足以认定它是本轮长时停滞的主因。
- 研究Agent已经显式设置SDK `max_retries=0`，应用层默认最多3次尝试。不能把本轮连接重试归因于SDK隐藏重试叠加。
- 部分网页正文丢弃、候选越界过滤、事实关联警告不是五题的终止异常。前端不是本轮运行路径，采集直接调用后端服务。
- 所有题目均停在研究节点：报告质量、事实正确性、裁判一致性、Writer/Critic表现、修复后的成功率均尚未评估。没有进行付费裁判或网络模型连通性试跑。

## 建议的修复与复跑顺序

1. **先保证执行环境持续运行。** 使用不会休眠的执行环境；本机运行时为采集进程保持系统唤醒。增加启动前检查与电源状态记录，不能只观察进程仍存在。
2. **优先减少在线摘要成本。** 保留全量原始轨迹，模型侧使用紧凑工具结果、状态和可回读来源。先执行必要的外置与去重，再判断是否仍需摘要；避免把已外置的正文重新全量送入摘要器。为摘要设置独立token与调用上限，为研究、写作保留预算；评估将逐句Claimify审计移到离线流程的方案。
3. **阻止失败摘要重复消耗。** 为相同来源区间、配置与输入哈希设置失败冷却，复用合法的中间结果；保持只有完整成功摘要才能提交覆盖游标。不要把失败摘要当作已覆盖历史。
4. **统一截止时间与恢复规则。** 采集记录墙钟和单调耗时；唤醒后先检查墙钟截止时间与租约，再发起模型请求或写入事件。失效时停止或通过现有带fencing的恢复机制重新获得执行权，不能移除租约检查。取消收尾另设有限等待。
5. **补齐诊断埋点后验证。** 记录异常类型、压缩是否采用、重试原因、预算与租约心跳。先用开发集完成一题链路验证，冻结修复版本，再对固定的这5道原题建立新的尝试目录复跑，保留首次失败记录。不要以单纯调高300000 token预算作为首个修复。

本次已测量的是首次运行的失败机制与消耗。上述修改尚未实施，也尚未证明修复后能生成合格报告。
