# 阿里搜索 MCP 接入与对比评估说明

适用项目：`industry_information_assistant` 的 `deep_research_v2` 主链路。
接入日期：2026-10-05。默认仍选择 `bocha`，通过配置启用 `aliyun_mcp`。

## 接入位置

```text
Architect 规划查询
    → DeepScout._execute_search（网站范围与报告级预算）
    → ToolRuntime.execute（参数、结果契约、超时、取消、记录）
    → 搜索后端配置
        bocha      → 现有 Bocha REST 调用
        aliyun_mcp → MCP Python SDK → 阿里 EnhancedSearch → search_pro
    → 统一 url/title/summary/snippet/site_name/date
    → 原有 WebReader 正文读取、证据抽取、分析、报告生成
```

本项目由程序控制查询和工具调用，LLM 负责规划、抽取和写作。因此在现有工具执行入口调用
MCP 客户端即可，不必把主链路改成一个新的 `create_agent`。
把 MCP 加进 Codex 的全局配置，仅使 Codex 能使用它；自研 Python 项目需要自己的客户端代码。
“SDK”就是这里安装的 Python 开发包 `mcp`，它处理协议初始化、工具发现、调用和连接生命周期。

## 已核实的服务契约

阿里地址：`https://dashscope.aliyuncs.com/api/v1/mcps/EnhancedSearch/mcp`。
传输：Streamable HTTP。鉴权：`Authorization: Bearer <百炼 API Key>`。
这是[阿里官方接入说明](https://help.aliyun.com/zh/model-studio/token-plan-harness-tool)中的配置。

2026-10-05 使用项目本地已配置的百炼 Key 实际执行 `tools/list`，结果为：

```json
{
  "name": "search_pro",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": {"type": "string", "minLength": 2, "maxLength": 500}
    },
    "required": ["query"],
    "additionalProperties": false
  }
}
```

注意：工具的描述文本和 schema 对最小长度有差异，代码以服务端 schema 为准。
工具目前没有 `count/top_k` 参数。适配器只发送 `query`，按原始排序保留前 K 个有效、不重复 URL。
工具实测返回 `content[].text`，文本中的 JSON 使用 `pages` 数组；同时支持相同形状的 `structuredContent`。
无法识别的格式、服务端 `isError=true` 和缺失凭据会明确报错，不伪装成正常空结果。

## 配置和启用

在实际启动后端的 Python 虚拟环境安装依赖。本次验证环境为 Python 3.11，MCP SDK 2.3.0。
实现使用 SDK v2；与 v1 的 `ClientSession/streamablehttp_client` 示例不要混用。
[官方 SDK 的认证传输示例](https://github.com/modelcontextprotocol/python-sdk/blob/main/docs_src/client_transports/tutorial003.py)
使用 `Client` 和带认证头的 `httpx2.AsyncClient`。

从项目根目录运行：

```bash
backend/.venv-eval-py311/bin/python -m pip install 'mcp>=2.3.0,<3'
```

在后端 `.env` 中设置：

```dotenv
RESEARCH_SEARCH_PROVIDER=aliyun_mcp
ALIYUN_SEARCH_MCP_URL=https://dashscope.aliyuncs.com/api/v1/mcps/EnhancedSearch/mcp
ALIYUN_SEARCH_MCP_TOOL_NAME=search_pro
```

`ALIYUN_SEARCH_MCP_API_KEY` 留空或未配置时复用已有 `DASHSCOPE_API_KEY`。
如需单独统计或不同权限，可以仅在本地 `.env` 设置 `ALIYUN_SEARCH_MCP_API_KEY`。
使用截图控制台要求的百炼按量付费 API Key；Token Plan 的 `sk-sp-` Key 与该服务 Key 不同。
不要把密钥写入源码、评估报告或前端配置。

修改 `.env` 后重启后端，创建新的研究运行即可使用 MCP。
改回 `RESEARCH_SEARCH_PROVIDER=bocha` 并重启后端，即使用原有搜索模块。
两个后端都沿用 `v2_web_search` 工具契约、报告级请求预算和网站过滤。
第一次搜索冻结后端、MCP 地址和工具名称；续跑时配置不一致会报错，防止一篇报告混用两种后端。
已经搜索过但没有后端字段的旧检查点按 Bocha 处理。

MCP 每次搜索在同一协程中打开和关闭会话，以避免异步 transport 跨节点清理。
当前未做持久连接优化。MCP 调用不自动重试，也不静默回退 Bocha，便于归因调用失败。
阿里实测协商的协议版本是 `2024-11-05`，SDK 使用 `mode="legacy"` 的初始化握手；
初版 `auto` 模式的现代协议探测曾收到 HTTP 500 后正常回退，当前直接跳过该探测。
Bocha 保留现有重试和熔断策略，评估文件记录真实尝试次数。

## 先发现工具，再比较相同查询

以下命令均从项目根目录运行。对比脚本不调用 LLM，直接经过真实 DeepScout 搜索入口，
显式创建两个后端并关闭搜索缓存，不需要来回改 `.env`。

```bash
# 只查看服务端工具及 schema，不执行搜索工具
LANGFUSE_ENABLED=false backend/.venv-eval-py311/bin/python \
  backend/eval/scripts/比较博查与阿里MCP搜索.py --discover

# 单题配对：相同查询，最多保留 5 个结果
LANGFUSE_ENABLED=false backend/.venv-eval-py311/bin/python \
  backend/eval/scripts/比较博查与阿里MCP搜索.py \
  --query '大语言模型 医学研究 综述' --count 5

# 示例查询集：每条查询分别调用两种搜索服务，涉及各自的搜索费用
LANGFUSE_ENABLED=false backend/.venv-eval-py311/bin/python \
  backend/eval/scripts/比较博查与阿里MCP搜索.py \
  --queries backend/eval/data/医学搜索后端对比示例查询.json --count 10 --repeat 1
```

需要限定网站时，两组共同使用 `--allowed-domain pubmed.ncbi.nlm.nih.gov`；可重复指定。
每个网站产生一个 `site:` 子查询，程序也会复核返回 URL 的域名。
没有指定网站时，两组都是全网检索。

每次运行创建新的中文结果目录和 `docs/` 报告。原始 JSONL 包含查询、后端、轮次、耗时、
合格结果、预算、每个子查询的原始返回和错误类型。报告会区分调用错误与成功但无结果。
失败或中断也会保存已经得到的结果；搜索错误时进程返回非零退出码。
报告里的“合格 URL”只表示通过当前结构和网站过滤，不能代表内容正确或权威。

## 如何判断哪个后端更适合你的项目

先做查询级评估：固定 20–50 个有代表性的医学研究查询、K 和网站范围。
人工为前 K 条结果标注相关性（无关/部分相关/高度相关）和来源等级，计算 Precision@K 或 nDCG，
同时看错误率、空结果率、P50/P95 延迟和账单费用。
现有脚本自动计算技术指标、保留候选结果供标注；不会把 URL 数量包装成质量评分。

再做整条 Deep Research 链路的对照：同一批研究题分别运行 Bocha 和 MCP，固定模型、提示词、
报告结构、网站范围、阅读策略、搜索预算和审核轮数，使用独立运行 ID。
检查可用正文比例、事实来源可追溯性、引用正确性、问题覆盖度、报告耗时与总费用。
报告生成有随机性，固定设置并做重复运行；记录阅读缓存策略，避免先运行的一组占据缓存优势。
若查询级比较要排除规划差异，可回放同一份 Architect 查询词和顺序。

这实际比较的是“现有搜索服务及适配模块”与“阿里搜索服务及 MCP 适配模块”。
MCP 是调用协议，搜索质量取决于服务端引擎；要测协议自身的影响，需要同一引擎的 REST 和 MCP 两种入口。

## 代码入口

- `backend/app/service/aliyun_search_mcp.py`：SDK 会话、工具发现、schema 校验、结果适配和原始诊断。
- `backend/app/service/deep_research_v2/agents/scout.py`：后端分派、缓存身份、运行冻结和 MCP 埋点。
- `backend/app/config/llm_config.py`、`backend/app/service/deep_research_v2/graph.py`：环境变量配置和注入。
- `backend/test/test_aliyun_search_mcp.py`：协议适配、错误、超时/取消、缓存、过滤和预算测试。
- `backend/eval/scripts/比较博查与阿里MCP搜索.py`：查询级对比入口。
