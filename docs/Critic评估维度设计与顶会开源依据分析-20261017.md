# Critic评估维度设计与顶会开源依据分析

- 分析日期：2026-10-17，Asia/Singapore。
- 评估对象：当前工作区 `CriticMaster` 的评分维度、报告返工职责，以及适用于 DeepResearch 的评价维度与细则设计方法。
- 工作口径：代码静态核查、历史评估结果引用、论文及官方开源代码调研。没有运行新的模型评测，没有修改业务代码，没有证明建议方案优于现有方案。

## 二、当前 Critic 的维度究竟是什么

实现见 [critic.py](../backend/app/service/deep_research_v2/agents/critic.py:30)。评分口径标识为 `report_review_3d_v2`，三项均要求1至10的整数分。

| 当前评分项 | 权重 | 实际检查内容 |
| --- | ---: | --- |
| `logical_coherence`，整体逻辑 | 4/9 | 跨章节矛盾、比较口径、汇总结论、相关与因果、冲突证据；观点平衡与局限性也并入本项 |
| `requirement_coverage`，要求覆盖 | 3/9 | 用户要求的研究对象、范围、指标、分析任务、输出交付是否完成 |
| `freshness`，整体时效 | 2/9 | 是否覆盖用户要求的时间窗口；不要求历史题使用今天的数据 |

总分先按4:3:2归一化、四舍五入；随后还有严重度与 verdict 的分数约束、确定性门禁、开放问题和补搜任务的通过限制。`quality_score >= 7` 是 `pass` 的必要条件，不能只凭三项加权均分判断最终通过。

当前提示词明确把以下内容交给独立引用核验：遗漏引用、引文能否支持论断、计划/预测是否被改成事实、对象/数字/年份/限定词是否忠实于来源。Critic不应重复输出 `missing_source`、`citation_error`、`prediction_as_fact`，也不因“未发现核验失败”加分。因此，当前三维分数只是报告层面审核分，不能称为整篇报告的事实准确率或完整 DeepResearch 质量分。

现有维度已能表达多类研究问题，但有两个设计风险：一是“没有逻辑矛盾”与“有深入分析”混在一起；二是观点平衡、推断边界、可读性缺少独立、稳定的验收口径。本次只发现这些表达风险，尚未测出它们造成了多少误判。

## 三、最值得参考的论文与开源项目

### 1. DeepResearch Bench：适合确定整体评价框架

[ICLR 2026论文](https://openreview.net/forum?id=hQ0K2Hhq7H)，[官方仓库](https://github.com/Ayanami0730/deep_research_bench)，[原始论文全文](https://arxiv.org/html/2506.11763v1)。

其 RACE 在全面性、洞察/深度、指令遵循、可读性四个顶层维度下，为任务生成专属细则及权重，再与参考报告进行相对评价。FACT 另外抽取“论断—URL”并检查支持关系，统计引用准确率和有效引用数量。

对本项目最直接的启发是：报告质量和引用支持分别评估；深度应显式出现；细则与任务相关。参考报告相对分不能直接转换成本项目在线 Critic 的1至10通过阈值。FACT 的引文支持也不等于对现实世界真假的独立验证；其数量指标不能替代对未引用关键论断的覆盖检查。

### 2. ResearchRubrics：最适合学习如何编写细则

[ICLR 2026论文](https://openreview.net/forum?id=ErnvfmSX0P)，[官方仓库](https://github.com/scaleapi/researchrubrics)，[论文初版全文](https://arxiv.org/html/2511.07685v1)。

论文第3.3节把细则组织为显式要求、隐式要求、信息综合、参考资料使用、沟通质量、指令遵循六类；区分必要与可选项，设置正向细则和惩罚常见错误的负向细则。论文初版有101个任务、2,593条专家编写细则。任务复杂度另按概念广度、逻辑嵌套和探索程度标注，这三项是任务难度标签，不是报告质量分。

官方实现提供二元满足判定、理由、权重及汇总流程。值得迁移的是“具体任务对应具体可验收行为”，以及把关键错误与锦上添花分开。论文比较了不同打分口径，不能据此认定二元评分对所有中文任务都最优。六类轴来自作者设计，也不是对本项目最优维度的实证证明。

### 3. DeepResearch Bench II：适合把抽象深度拆成可核查的研究产物

[论文](https://arxiv.org/abs/2601.08536)，[官方仓库](https://github.com/imlrz/DeepResearch-Bench-II)。本次确认公开预印本与代码，未确认正式顶会录用，故单列为开源基准。

其132个任务共有9,430条细粒度细则，按信息召回、分析、呈现组织，从专家报告中提取并经过人工修订与专家审查。原子性、包含具体内容、数值要求明确，是它对细则工程最有用的约束。

需要区分论文对二元细则的概括和当前仓库实现：代码还有因引用被屏蔽参考资料而记 `-1` 的特殊惩罚。这不是通用的“不确定”分数，也不应照搬到本项目状态字段。来自一篇专家报告的内容、数字和结构仍可能有口径与参考偏好；迁移时必须复核，允许有证据支持的合理替代分析，不能把复述参考报告当成研究质量。

### 4. ALCE：适合设计独立引用核验指标

[EMNLP 2023论文](https://aclanthology.org/2023.emnlp-main.398/)，[官方仓库](https://github.com/princeton-nlp/ALCE)。

其评估区分流畅度、正确性和引用质量，代码显式计算 `citation_rec` 与 `citation_prec`。可借鉴“需要支持的内容是否获得支持”与“所给引文是否有效”的区别。项目若改成原子论断分母，必须说明这属于本地口径，不直接冒充 ALCE 原始句子级指标。来源支持一个说法，不足以保证来源本身准确、独立或代表主流结论。

### 5. STORM：适合补充研究覆盖、多视角与组织质量

[NAACL 2024论文](https://aclanthology.org/2024.naacl-long.347/)，[官方仓库](https://github.com/stanford-oval/storm)。

该工作从多视角提问、资料收集和大纲构建组织研究写作，评估也关注大纲与覆盖、组织方面。对本项目的启发是将“有没有覆盖关键研究方面”和“文章写得是否顺畅”分别验收。多视角应服务于题目，不以立场数量或机械正反各半作为质量标准。

### 6. CRITIC：适合学习有依据的批评与修订闭环

[ICLR 2024论文](https://arxiv.org/abs/2305.11738)，[官方代码](https://github.com/microsoft/ProphetNet/tree/master/CRITIC)。

核心是用工具反馈检查并修订初始输出，原任务包括问答、程序与文本去毒。它支持“批评需要外部可观察依据”的流程设计，不提供一套可以直接套用的 DeepResearch 报告维度。项目中叫 Critic 的模块，也不等于已经复现该论文。

建议阅读顺序：ResearchRubrics第3.3节和提示词 → DeepResearch Bench的RACE/FACT → Bench II的细则与逐条证据输出 → ALCE。STORM和CRITIC分别补充研究组织和修订流程。

## 四、建议本项目采用的六个顶层维度

以下是根据论文与现有职责边界提出的工程建议，尚未实施或验证；不是任何单篇论文的原样六维定义。

| 维度 | 要回答的问题 | 典型失败 | 返工方向 |
| --- | --- | --- | --- |
| 用户要求满足 | 对象、范围、时间和明确交付物是否完成？ | 要求三种方案比较，只写一种；要求比较表却未交付 | 补齐交付或纠正范围 |
| 关键研究覆盖 | 回答这个问题必要的背景、机制、证据视角是否覆盖？ | 方案只讨论建设，漏掉长期运维；只看供应商宣传 | 定向补搜关键内容 |
| 分析与综合深度 | 是否把多来源信息变成比较、解释、权衡和结论？ | 罗列十篇资料，没有说明差异原因或选择条件 | 重构比较与推导，必要时补证据 |
| 逻辑与可比性 | 跨章节结论、比较基线、统计分母和推理是否一致？ | 用不同数据集准确率直接排名；因果结论无论证 | 统一口径、重算或降低结论强度 |
| 不确定性与观点平衡 | 是否交代重要反证、适用条件及未知边界？ | 单案例外推全国；只呈现支持结论的研究 | 补充有实质影响的反证或限定 |
| 表达与交付可用性 | 读者能否快速理解并使用研究结果？ | 表格缺单位、全文重复、建议无法定位到前文依据 | 改写结构、表格与摘要 |

这些维度并不天然完全独立，需要通过细则归属消除重复。例如“2024—2026覆盖”归用户要求；“在同期数据上作比较”归逻辑；“引文年份是否被写错”归引用核验。同一个缺陷只设置一个主要评分归属，可保留多个诊断标签。

“要求满足”只管明确要求，“关键研究覆盖”管专家事先认可的必要背景与隐含要求。隐含要求必须与任务有明确关系，并区分必要与可选，不能由 Critic 看完报告后无限增加研究范围。

时效不必对所有题独立固定占2/9。对“最新进展”设为必验条件，对历史研究按指定时间窗口判断；必要的来源新旧问题仍可进入具体细则。可操作性也按任务启用：政策建议、方案选型需检验实施步骤、约束、成本或取舍；纯历史解释题不应被要求给落地路线图。临床等领域可由领域专家增加适用人群、证据等级等附加细则，本次没有提供医疗建议或验证这些附加项。

独立引用核验继续报告论断覆盖、引用支持、来源读取失败和矛盾状态。对支持率、真实准确性、来源权威性和来源独立性分别命名；转载同一篇稿件不算独立交叉验证。

## 五、怎样把维度变成真正能执行的 Critic

### 1. 先定义本题研究契约，再冻结验收细则

从用户问题及已确认的澄清中提取对象、时间、地域、必答问题、输出产物。再从任务模板、专家建议与可得资料补充必要的隐含要求。细则生成后保存版本，在比较不同报告或修订轮次时保持相同标准；新增要求必须有变更理由，不能悄悄改变分母。

离线可以从参考报告提取带具体答案的细则，需检查参考资料偏差与替代正确答案。在线往往没有金标，应先用问题、任务类型模板与专家规则定义可观察交付，不能用待评报告本身来决定它应该回答什么，也不能把离线保留的答案材料泄露给生成器。

### 2. 每条细则只验一个可观察行为

以既有污水治理题为例，“全面、深入、有操作性”过于抽象。可以拆为：列出建设/运维/改造/应急成本类别；解释至少一个雨污协同减少重复投入的机制；比较至少两种可行治理安排；针对优先方案分别说明启动条件、责任分工、执行动作。后者仍要继续拆成原子条目。条目数量只是本题设计选择，不能成为所有研究题的固定模板。

如果缺真实成本收益数据，可以给出清楚标注的假设、变量与测算方法；不能为过关要求 Writer 编造节约百分比。若用户明确要求实际量化结果，诚实说明不足仍意味着该交付未完成，应与编造事实区分记录。

每条细则保存 `criterion_id`、维度、来源/必要性说明、可观察要求、必要/可选、适用条件、失败定义、证据需要、验收条件与修复方向。已有问题协议中的 `report_quote`、`requirement`、`acceptance_criteria`、稳定 `issue_id` 和逐条复查可以承载这套设计，不必首先更换研究框架。

### 3. 先给逐条结论与依据，再汇总

建议以满足/不满足为基础，另设不可判断和事先声明的不适用状态。后两项是本项目拟议的工程扩展，不是 Bench II 的 `-1`。不可判断要明确缺的是正文、原文、时间锚点还是专业判定，不凭模型记忆补事实。缺少本应交付的内容通常是“不满足”，不能全部转为“不可判断”。

必须展示待审正文的定位与理由；缺失项记录已检查的范围和对应契约，不能伪造不存在的原句。证据段落存在、证据编号合法，只能证明定位机械有效，不能代替语义判断。

存在不可判断项时，单列可评覆盖率与未知比例，必要项未知不能直接通过。若展示满足率，应同时给分子、全部适用项分母和未知数，或给出未知项按全失败/全满足计算的上下界，避免删除难题后虚高。必要项与可选项先分别汇总，再考虑经校准的总分；可读性或引用数量不能抵消核心任务失败。

当前“永远不满意”的类说明不应成为验收目标。可以输出空问题、维持正确原文、撤销错误批评；只有可定位且有依据的问题才能触发相应修订。缺新证据时明确问题未决。

## 六、如何确定它对本项目最适合

没有现成论文能证明某组六维和权重就是本项目最优。建议将下列方案作为待评候选：现有三维、RACE四维加独立核验、六维加每题细则。比较时冻结同一首稿、完整证据、模型版本、提示词、温度、工具与预算。

先选不同任务类型的小型开发集，覆盖调研综述、技术选型、方案建议与历史分析；由人工独立标出真实问题，评审分歧再裁决。仅汇总Critic已经提出的意见只能算意见正确率，无法估计漏检率。若条件允许由两位人工独立标注，或分轮独立审阅；这些是后续实验建议，本次未运行。

| 待测指标 | 分子/分母或计算口径 | 用途 |
| --- | --- | --- |
| 意见精确率 | 主要指控正确的反馈 / 全部反馈；部分正确单列 | 控制误报和无效返工 |
| 真实问题召回率 | 被发现的人工已确认问题 / 全部人工已确认问题 | 防止只挑容易问题得高精确率 |
| 核心需求判定正确率 | 与人工一致的必要项判定 / 全部必要项判定，未知另列 | 验证是否审到了用户真正关心的交付 |
| 问题修复率 | 经独立复核已修复的问题 / 实际尝试修复的真实问题 | 检验反馈能否指导Writer |
| 误改率 | 修订前正确、修订后错误的内容单元 / 被修改的原正确内容单元；补充每报告是否出现误改 | 识别负收益 |
| 修订净收益 | 固定细则下终稿与首稿的质量差，同时列修好与改坏数量 | 评价整个闭环 |
| 人工一致性 | 逐项一致率、适当的kappa或配对偏好一致率，并报告人工自身分歧 | 校准自动裁判 |
| 成本与耗时 | 每报告新增模型/工具开销、时延、返工轮数 | 判断部署价值 |

同题多轮记录相关，统计与置信区间应按任务聚合或按任务重采样，不能把同题反复出现的意见当独立样本扩大样本量。有限开发集选择维度与阈值后，再在保留任务上验证；本次没有确定样本量、最优权重或显著性结论。

还可做轻量机制检查：删除关键子问题、制造跨章矛盾、改变统计分母、去掉反证、只增加冗余字数、调整正反报告顺序。期待相应细则响应，而无关项稳定。这些检验用于发现维度重叠、长度偏好或顺序偏差，不能替代真实任务上的人工评估。

## 七、历史核心指标与失败样例如何影响设计

以下为2026-10-11报告的既有测量，本次仅复用汇总和分析，没有重新逐条判定，也不代表2026-10-17当前三维版本的效果。

- 五题、14次审核、56条当轮意见；正确27条、部分正确15条、错误14条。严格正确率27/56＝48.2%；至少部分有效42/56＝75.0%，不能把后者写成完全正确率。
- 14条错误中10条是漏读当轮已经存在的引用。这支持继续区分引用位置、来源支持与报告逻辑三种问题，但不能证明当前分工已经提高精确率。
- 第35题的旧反馈曾要求补一个当轮已经提供的官方链接：对应的改进是先定位当前正文，再提出缺失指控，而不是增加“引用数量”维度。
- 第16题反馈涉及不同准确率、基线与提升范围：需要分别验收可比性与原文支持，不能凭一个“事实可靠性”总分包办。
- 第35题真正有效的意见指出应急方案缺少启动条件、责任与动作：对应题目专属操作性细则，说明链接齐全仍可能研究未完成。
- 第49题曾仅因资料发布日期较近就推断属于预测，并标critical：需要按审核基准日和来源内容判断，不能把时间新旧自动等同于真假或严重度。

这些历史样本含重复意见，且原口径没有完整人工真实问题清单，不能由48.2%推出漏检率，也不能归因为仅由维度设计造成。当前逐问题复审虽已有机制回归，真实模型的复查准确率和误改率仍未评估。
