## 主要结论

项目已经有完整的“规划—研究—写作—审核—补搜／修订”流程。章节写作、原文证据 RAG、逐问题返工、Critic 显式复审、最终报告独立引用核验均已接入。继续增加相似角色，未必能填补当前缺口。

当前更值得处理的是三个断点：

1. **篇幅分配与整篇目标矛盾。**默认整篇目标 7500 字，章节目标却被 500 字限制；五章的内容组成目标合计仅约 3100 字，不含标题。它压缩了比较、解释和限定条件的展开空间。
2. **研究结果不能及时反过来改变研究计划。**Architect 有改纲方法，但当前主图研究后直接进入分析、写作，没有调用改纲；旧方法还依赖已停用生成的 facts。
3. **检索到相关材料，不代表关键问题都得到证据。**Writer 已用混合召回、精排和邻接原文，但每章主要用一个合成查询召回；没有逐问题的证据满足判断，也没有写作前的缺口补搜循环。

独立引用修复也不是“没有”：已有 audit／delete／rewrite_once 三种策略，代码缺省为 audit。下一步应验证并使用已有能力的适用范围。

## 实际主链路与边界

[主图](../backend/app/service/deep_research_v2/graph.py#L286)的新任务路径为：

规划 → 搜索／读取原文 → 数据节点与确定性计算 → 逐章写作／首尾合稿／独立引用核验 → Critic → 完成，或补搜／修订后再次审核。

同一主图还支持会话任务编译后的 edit／augment 入口。[会话任务编译](../backend/app/service/deep_research_v2/session_task_execution.py#L10)会提交约束；已提交契约由[契约保留逻辑](../backend/app/service/deep_research_v2/contract_updates.py#L124)保留。因此，不能因为初始规划提示只输出少量格式字段，就断言项目完全没有用户要求管理。

历史医疗接口现为只读查询，不是第二条新研究主链路，见[接口说明](../backend/app/router/medical_research_router.py#L4)。

本文中的“有”表示进入了当前代码路径；不表示该模块已经达到足够的语义准确性。“缺”也区分完全缺失、只有提示／字段、方法未接入与默认策略未启用。

## 具体发现与代码依据

### 1. 默认 7500 字目标没有传导到章节写作预算

[配置](../backend/app/config/llm_config.py#L135)设定 target_report_chars=7500、min_section_chars=300、max_section_chars=500。

[预算函数](../backend/app/service/deep_research_v2/agents/writer.py#L333)先从整篇目标扣除结构与首尾，再按章节均分，但随后取 min(max_section_chars, per_section)，使有充足篇幅的任务仍以每章 500 字为目标。[写作提示](../backend/app/service/deep_research_v2/agents/writer.py#L121)同时要求表格、定义、来源和“结论→数据→归因→影响”展开。

纯函数探针结果：

| 场景 | 章节目标合计 | 加首尾的内容目标合计，不含标题 |
| --- | ---: | ---: |
| 默认 4 章 | 2000 | 2600 |
| 默认 5 章 | 2500 | 3100 |
| 默认 6 章 | 3000 | 3600 |
| 5 章，用户限制正文 1500 字 | 935 | 1335 |

这是**已测量的预算返回值**。500 是传入提示的章节预算，并非证明模型会严格遵守，也不是报告的真实字数上限。用户明确上限仍有单独检查。

建议：用整篇可用预算分配章节目标，允许复杂比较章获得更多篇幅。可采用“章节预算＝可用正文预算×章节权重／权重总和”；用户明确上限优先。先做预算一致性修正，再观察是否带来有效分析，而非仅增加字数。

### 2. 改纲方法有两个断点，单纯加一条图边不足以修复

[Architect 分发](../backend/app/service/deep_research_v2/agents/architect.py#L285)仅在 init 初始规划，或 reviewing 时调用改纲。[主图](../backend/app/service/deep_research_v2/graph.py#L287)只有 plan 调用 Architect，研究后没有重新进入该角色。

[改纲方法](../backend/app/service/deep_research_v2/agents/architect.py#L500)又只取 facts 最近十条作为新发现；为空就退出。[Scout 原文入库](../backend/app/service/deep_research_v2/agents/scout.py#L1069)当前明确不生成事实、数据点或假设证据摘要。因此，即使增加调用，旧方法也可能没有输入。

静态扫描发现 _execute_deep_search、_analyze_search_results、_analyze_supplementary_results、_ingest_search_analysis 均没有 backend/app 内的调用点；假设更新仅被 _ingest_search_analysis 调用。扫描不构成全程序可达性形式证明，但与主图及 process 分发相互印证。

建议：设计一个基于当前原文检索结果的写作前检查，输出“哪些问题仍未解决、需要什么证据、章节如何调整”，直接消费证据单元和任务要求。保持原文直达写作的设计，不恢复通用事实二次摘要。新增章节必须具备稳定 ID、状态及检索任务，并按实际路径重新核算图步数上限。

### 3. 证据 RAG 已较完整，主要缺口是多问题覆盖

[Writer](../backend/app/service/deep_research_v2/agents/writer.py#L699)把当前问题、章标题、描述和待处理问题拼成一个查询，召回证据后确认非空。[RAG 默认](../backend/app/service/session_evidence_rag.py#L23)使用 context_top_k=8、context_tokens=8192；已有词法与向量召回、RRF、精排、邻接补全及预算审计。

这套实现已经具备材料回读能力，不能归为“只把摘要传给 Writer”。但[选择过程](../backend/app/service/session_evidence_rag.py#L292)主要按相关性保留材料，没有逐问题、对照对象、支持／反驳或共同上游的覆盖分配。缺口属于选择策略，不是缺少向量库。

合成风险例：同一章要比较三种方案及局限，前八个高相关片段可能主要介绍其中最常见的方案。非空检查通过，仍可能漏掉另外两种方案。这是机制推断，本轮未测得真实漏召回率。

建议：把章节中的独立问题分别用于召回，合并去重后在同一总上下文预算内选择材料；记录哪些问题已有证据、哪些尚无证据。为限制条件和不同观点保留检索机会。不要以“至少若干来源”代替实际支持判断。

### 4. 逐问题返工已接通，优先验证判断质量

[Critic 输出协议](../backend/app/service/deep_research_v2/agents/critic.py#L228)有问题 ID、位置、原句、原始要求、证据、修改建议、验收条件及明确的补搜标记。

[Writer 修改记录](../backend/app/service/deep_research_v2/issue_workflow.py#L126)校验实际正文定位和本次展示过的证据编号；[复审逻辑](../backend/app/service/deep_research_v2/issue_workflow.py#L219)不因问题本轮消失、分数提高或 Writer 自报 addressed 而自动关闭。补搜后[重开相关章节](../backend/app/service/deep_research_v2/agents/scout.py#L706)，使新证据能够进入重写。

两组协议探针分别确认：缺少 Critic 显式复审时问题仍为 unresolved；显式返回关闭状态与非空摘录／理由时可关闭。它们不证明理由语义正确，也不证明修改真正解决了问题。

建议保留这条链路，后续测量“Critic 意见是否正确、误报多少、修改后是否修复、是否引入新错”。这些比继续增加返工次数更能判断该机制的实际收益。

### 5. 假设机制不能按保留字段认定为已运行

规划可生成 hypotheses，Writer 有[正反证据共同消费提示](../backend/app/service/deep_research_v2/agents/writer.py#L128)。然而新研究主路径不再调用事实提炼及假设证据入账方法；DataAnalyst 也不再生成新的语义材料，见[当前数据节点](../backend/app/service/deep_research_v2/agents/data_analyst.py#L287)。

因此，新任务即使启用了假设开关，也不能据字段存在声称已系统搜索反证、更新 supported／refuted／mixed 状态。历史继承材料或其他直接调用路径另当别论；Writer、Critic 仍可能在自然语言层面讨论反对意见。

建议由研究缺口与原文召回提供正反材料，明示“未检验”的状态。研究问题和待检验假设可以指导搜索，但其证据状态必须来自实际原文，不能从阅读成功或来源数量推导。

### 6. 独立引用核验存在；修复与交付策略需要单独判断

[首跑配置解析](../backend/app/service/deep_research_v2/citation_verification.py#L30)在请求未指定时，环境变量的代码缺省为开启 report_claims；显式配置对象按对象字段默认值解析，因此传空对象并不等于省略配置。本轮未读取部署环境，不断言每个真实运行都开启。

[Writer 合稿后](../backend/app/service/deep_research_v2/agents/writer.py#L1042)执行独立核验；[抽取入口](../backend/app/service/deep_research_v2/citation_verification.py#L234)从 final_report 提取论断，清除旧结果，不直接依赖 Writer 自报列表。缺失引用、来源支持与预测写成事实已有对应审计。

[失败处理](../backend/app/service/deep_research_v2/citation_repair.py#L156)有 audit、delete、rewrite_once，默认 audit。已有 rewrite_once 受原有证据编号和原有 URL 限制，适合收窄过强表述；不能解决尚未搜到资料的缺口，也不能随意补一个新链接。核验执行失败不应当作内容错误自动删除。

[基础发布检查](../backend/app/service/deep_research_v2/quality_pipeline.py#L81)仅检查非空与来源范围。Critic 与引用核验职责分开，且引用失败默认不会阻断交付。达到返工上限也可交付，完成原因记录为 revision_limit；[交付载荷](../backend/app/service/deep_research_v2/delivery.py#L84)已区分执行完成、审核判定与引用核验。这不是完全没有状态区分。

建议优先用已有 audit 与 rewrite_once 做配对验证，观察净修复和误删／新错，确认后再选择默认策略；真实材料缺口进入补搜，文本范围错误进入局部改写。当前不需要重写一套引用核验器。

### 7. 来源可靠性与分析深度仍有补强空间

[候选优先级](../backend/app/service/deep_research_v2/quality_pipeline.py#L26)按域名、标题及文档形式排序，原文还做正文准入和跨 URL 重复提示。这不等于发布主体经过背景核验；所查主路径没有共同上游归并和独立证据组。

建议先补可回查的发布者身份、文档性质、原始出处、共同上游及未知原因，再考虑综合可信度分数。不要把相关性排序或“官方”标题词展示为事实正确概率。

[Critic](../backend/app/service/deep_research_v2/agents/critic.py#L163)已检查跨章矛盾、因果越界、冲突隐去与观点平衡，但评分只有逻辑、要求覆盖、时效。缺少对“是否给出有用解释、可比比较、条件和权衡”的明确正向锚点。可先细化逻辑维度下的深度标准；如新增独立维度，应更改评分口径标识，单独比较新旧口径。

合稿[只生成首尾](../backend/app/service/deep_research_v2/agents/writer.py#L178)，正文程序拼接；跨章修改主要靠 Critic 发现后逐章返工。不能说没有全局检查，也不能把首尾合稿称为完成了整篇正文的编辑。

定量任务还需注意：DataAnalyst 当前不从原文提取新 data_points，因此图里的确定性计算不保证对每次新研究都具备必要输入。用户明确要求计算时，可按需从原文抽取数值、单位、时间和定位，交给已有计算函数，保留可复算依据。

## 优先改进顺序

| 顺序 | 改动 | 原因与成本 | 验证重点 |
| --- | --- | --- | --- |
| P0-1 | 修正整篇目标到章节预算的分配 | 已有确定配置矛盾；改动集中 | 不突破用户上限；正文增加的是比较、解释和边界 |
| P0-2 | 明确分析深度与意见质量标准 | 主要改评分锚点和提示，复用当前返工协议 | 正确问题比例、实际修复、新错；不能只看 Critic 分数上涨 |
| P1-1 | 接入写作前问题缺口检查与有界改纲 | 解决研究材料不能反馈计划的断点；中等改动 | 新发现能否进入计划，用户要求是否保留，是否避免无效补搜 |
| P1-2 | 按独立问题选择证据与定向补搜 | 复用现有 RAG、来源库和工具；中等改动 | 多对象覆盖、限制条件、相反材料是否进入写作 |
| P1-3 | 验证已有引用修复策略 | 新业务代码需求较少，准确性验证必要 | 引用净修复、误删、缺失引用、残留失败和耗时 |
| P2 | 发布者／共同上游证据、按需计算、全局定向编辑 | 需结合任务类型与剩余错误决定范围 | 证据独立性、数字可复算、跨章修改是否有效 |

搜索预算现由初搜、换源和补搜共享，代码默认最多 20 次，见[预算逻辑](../backend/app/service/deep_research_v2/agents/scout.py#L1648)。加入前置检查时应在既定预算内预留补搜额度，避免前期用完预算。这个数不是质量保证；也不建议为每个章节强制增加固定搜索次数。

第一批实施范围建议控制在“章节预算分配＋深度评分锚点”，第二批接入“基于原文的研究检查＋按问题选择证据”。专用模型训练和新增相似角色可以在这些改动完成配对验证后再决定。

## 失败样例与证据边界

| 样例 | 性质 | 已知边界 |
| --- | --- | --- |
| 五章默认预算内容目标约 3100，与整篇 7500 目标不一致 | 已测量的纯函数结果 | 未测模型实际字数或质量损失 |
| 主图 research → analyze → write，没有研究后改纲节点 | 已核验源码结构 | 没有做线上轨迹覆盖测试 |
| 改纲依赖 facts，新主路径不再生成事实摘要 | 源码直接核验与路径推断 | 历史继承或其他直接调用可有 facts |
| Writer 自报完成、Critic 漏复查 | 已测量的合成状态探针：问题保留 | 未测试语义修复正确率 |
| 高相关片段集中于一个对象，遗漏其他对象 | 合成机制风险 | 未测真实发生频率 |
| audit 记录引用失败但正文仍交付 | 已核验策略设计 | 不能据此统计实际错误率 |
| 多 URL 是同一新闻稿转载 | 合成机制风险 | 当前未建立并运行来源独立性金标准 |

## 局限性、结论与下一步验证

**已测量：**4 组篇幅预算纯函数结果、2 组问题状态协议。**直接核验：**代码默认值、主图接线、方法调用点、原文 RAG 与核验入口。**间接推断：**对质量的影响和改动优先级。**尚未评估：**真实报告质量增益、误报率、净修复率、线上配置、中文任务泛化、模型开销及端到端耗时。

探针提取当前函数执行，替换了业务包导入并注入同一源码中的字符计数函数；不覆盖数据库、API 或完整 Agent 集成。静态扫描无法排除反射等动态调用；工作区文件后续也可能变化，复查时应对照保存的哈希。本次没有重新分析历史评估，不将旧成绩当作今日代码的表现。

当前返工和引用核验框架已经具备，优先改动应集中在写作预算、研究结果对计划的反馈，以及关键问题的证据覆盖。随后在固定任务、模型、检索后端和资源限制下，每次只切换一项机制，做同题配对；覆盖、分析深度、引用与开销分开统计，并人工复核部分意见及修改。实际收益验证前，本文优先级属于有代码依据的工程判断。
