# Scout 每章两个初始查询调整及回归结果

日期：2026-10-02。对象：将 Scout 每章初始查询上限从 3 改为 2。

## 修改及配置口径

修改 `backend/app/service/deep_research_v2/agents/scout.py` 的构造默认值及实际展开限制，每章最多执行两条初始查询。旧环境配置或对象属性仍为 3 时也不会执行第三条；配置为 1 或仅有一条有效规划查询时不凭空增加查询。同步修改 `ResearchConfig.max_searches_per_section=2` 和 `.env.example`。

换源查询、来源追溯和审核补搜沿用各自已有规则，因此 2 是初始查询上限，而非该章节所有阶段合计的搜索上限。没有增加证据充分性提前停止机制。

## 原始结果与指标

结果：[Scout 每章两个初始查询回归结果](../backend/eval/data/Scout每章两个初始查询回归结果-20261002.json)。测试使用本地模型与搜索桩，不执行真实付费搜索。

已测量：`test_quality_pipeline` 16 项全部通过。核心用例提供四条规划查询，故意将对象旧属性保留为 3，实际只调用查询一和查询二；原有每章一条、深度一的来源追溯及报告总搜索预算检查通过。

较广检查 `test_quality_pipeline test_Scout埋点` 共 32 项，30 项通过、2 项失败。失败是埋点用例的新增事实期望 1、实际 0。其旧测试桩不提供事实对应的正文及原句编号，日志显示事实未通过编号绑定；正文测试材料还触发了质量检查与额外换源。

## 失败样例与修改前复查

失败用例为 `ScoutObservationTests.test_process_exports_only_retained_facts_and_evidence_with_budget_delta` 和 `ScoutObservationTests.test_supplementary_process_exports_new_state_and_existing_budget`。

仅在独立 Python 测试进程中把查询展开表达式恢复为修改前形式，对上述两项重跑，仍然产生相同失败。其测试桩明确配置每章一条初始查询，降低三条上限到两条不改变该桩的执行查询数。这个对照已经测量；更完整的埋点测试数据更新尚未完成，不据此声称所有回归通过。本次没有为查询数量调整修改这些埋点用例或降低编号准入要求。

## 局限性、结论与下一步

已测量的是初始查询数上限及相关预算机制。间接推断：降低初始查询数可能减少候选材料及后续处理输入，但换源和追溯仍会消耗查询，不能据此给出整体成本节省比例。

尚未评估真实任务的证据覆盖率、成本和报告质量。结论：每章最多两条初始查询已实现，查询相关 16 项回归通过；较广检查有两项修改前同样失败的埋点用例。后续真实评测可记录查询分类、证据缺口和成本，以判断两条查询是否足够。
