## 失败证据与定位

### 35、31：章节成功后，Writer 当前整合输入超过预算

35 已生成四章，共 7,319 字符；31 已生成四章，共 7,631 字符。两题的最后一条写作动作均为“正在整合各章节，生成完整研究报告”，随即分别以 28454 和 27852 tokens 超过 25744 输入预算被拦截。没有产生最终报告，也未进入 Critic 审核。章节正文保存在 section_content 事件与 LLM 输出中，不应当说完全没有内容产出；没有单独的最终报告文件。

两题失败调用的 context_view 均为 history_replay=false、summary_attempted=false、summary_adopted=false，压缩前后 token 数相同。冻结实现中，非 replay_agents 的智能体直接检查当前指令和任务契约，不调用历史摘要。因此当前失败指向 Writer 整合提示的输入容量；不属于摘要生成或引用核验失败。

输出预算从旧轮 3000 提高到 6000，会把同一 32768 窗口的可用输入从 28744 降到 25744；本轮两题输入分别超出 2710 和 2108 token。两份当前输入在旧输出预算下数值上会落入输入上限，但这仅是预算算术，不能据此保证使用旧配置就会生成合格报告。需要为整合阶段独立控制输入和输出容量，并减少重复证据/正文载荷。

### 46、49：Scout 采用摘要与外置后仍超过输入预算

46 在 research 阶段，压缩前 124148 token，外置后 57296，摘要等步骤之后仍为 32776，高于预算 25744，超出 7032。49 的对应数值是 113858 → 42944 → 30624，超出 4880。两题 history_replay=true、summary_attempted=true、summary_adopted=true，摘要版本均已更新，没有 summary_error。

历史压缩确实发生，但剩余总输入仍未达标。仅从这些总数还不能断定全部超额来自某一字段；当前指令受保护，后续应按任务契约、当前正文材料、摘要与未覆盖历史分别统计体积，定位并按问题选择原句。继续增加摘要调用或简单重复同一输入，不能保证解决此问题。

### 16：规划器输出类型不匹配，门禁展开成字符组合

原始 ChiefArchitect JSON 的 required_metrics 中，entity_scope 为字符串“非接触式感知算法”，years 为字符串“2019–2024”。冻结 quality_pipeline.py 对这两项直接遍历，生成 entity_scope=["非","接","触","式","感","知","算","法"] 和 years=["2","0","1","9","–","2","0","2","4"]。指标覆盖检查又将实体与年份交叉展开，出现“非/准确率/1”“接/准确率/–”等错误缺失项。

这同时涉及规划输出的 schema 约束和程序缺少类型校验。该时间范围也由规划器自行给出，原用户问题没有明确要求 2019–2024。门禁确实拦截了写作，但不能据此断言真实 Accuracy/F1 指标全部缺失；修正类型并重新做覆盖检查之前，真实来源充分性仍未评估完毕。此轮有 31 条事实、各章节均有全文来源，章节覆盖与指标覆盖并非同一指标。

上述定位依据是本轮原始模型输出、context_view、llm_error、section_content 和检查点，未修改研究逻辑或对失败题自动重试。预算不足、检索无效网页等可能仍有其他影响，不把这轮全部失败归因于摘要。
