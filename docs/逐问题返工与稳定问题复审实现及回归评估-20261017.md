## 实现说明

### 1. 两条路径共享按章问题输入

新增[issue_workflow.py](../backend/app/service/deep_research_v2/issue_workflow.py)集中管理问题身份、按章上下文、修改记录、记录重放与复查合并。

每个待处理问题明确提供：

- 稳定的`issue_id`、位置、原报告句子或对应用户要求；
- 问题描述、判断依据、具体修改建议；
- 本问题的补搜结果及来源定位，或尚无可用新证据的明确状态；
- 问题专属`acceptance_criteria`，旧记录缺失时使用其修改建议并明确复查要求。

现有资料是否支持某命题，仍须结合实际提供原文判断。补搜读取成功只记录为`sources_collected`，无可用结果记录为`no_usable_evidence`，不会被程序伪装成语义支持。Writer必须在输出中说明具体支持范围和剩余缺口。

补搜后普通章节写作、直接按章修订都使用相同的`revision_context`和`ISSUE_RESPONSE_INSTRUCTIONS`。检索查询加入所指原句、要求、问题描述和补搜词，帮助召回对应材料。补搜重开章节前保存旧章节，供Writer保留正确内容和定位修改。

一次返工同时包含“甲章需补搜”和“乙章仅修订文字”时，Scout会重开两个待修章节，避免只处理补搜任务所在章。摘要、结论、展望的全局问题也进入合稿；用户编辑后的Critic返工专用入口同样记录逐问题回应。

### 2. Writer记录处理结果，不关闭问题

Writer新增`issue_responses`，每个问题包含：

```json
{
  "issue_id": "稳定问题ID",
  "status": "addressed/unable_to_address/disputed",
  "revised_quote": "本次正文中可逐字定位的句段或表格行",
  "change_description": "改动或维持原文的理由",
  "evidence": [{"document_id": "提供过的正文编号", "sentence_ids": ["提供过的原句编号"]}],
  "evidence_summary": "原文具体支持什么",
  "remaining_gaps": "仍缺什么或明确无剩余缺口",
  "acceptance_check": "对验收条件的逐项回应"
}
```

RAG材料使用`evidence_unit_ids`；首尾合稿可使用本次章节索引中的`source_claim_ids`，程序保留其章节依据和继承证据，不能把章节声明冒充来源原文。

程序检查修改引句是否出现在实际输出中、证据编号是否来自本次提供的材料，并保存程序解析的证据文本/定位、章节、轮次及内容哈希。遗漏回应、重复回应、伪造定位、无效证据编号都会留下`not_reported`和诊断信息。旧`addressed_issues`自报不能替代逐项记录，也不能关闭问题。

记录保存于`writer_revision_records`；`writer_status`与`review_status`分开。全局问题只在部分章节返回处理记录时显示`partial`，不会因为最后一章声称处理就掩盖其他章节未处理的情况。

### 3. Critic显式逐条复查旧问题

Critic输入增加全部未关闭旧问题、验收条件、本轮Writer修改记录、程序解析的证据及修改引句能否定位于当前报告的标记。

模型返回`issue_reviews`，对每个旧ID分别选择：

- `resolved`：确认修复；
- `unresolved`：问题仍存在、证据不足或尚未完成；
- `dismissed`：确认旧批评本身有误，可以维持原答案。

关闭问题必须有当前报告中可逐字定位的`report_quote`和具体`reason`。无有效定位或依据时保留为未解决；复查与待修问题列表冲突也不关闭。缺少某条复查时继续保留该问题，并阻止通过审核。未知、重复或已关闭的复查ID会报契约错误，不允许误关其他问题。

新一轮旧问题沿用原ID；相同问题被模型重新编号时，根据现有问题内容关联回旧ID。新问题不能复用已关闭ID。问题账本持续保存，历史轮次另存深拷贝，计数和补搜仅使用仍开放的问题。重复新问题ID被拒绝，避免覆盖不同问题。

`resolved`布尔字段保留给旧消费者，表示问题已结束待办；`review_status`区分“修复”与“撤销误报”。旧检查点中只有Writer自报的`resolved=true`、没有明确复审状态时，会重新纳入待复查，不追认已验证。

来源增加、证据指纹变化、总分提高、Writer声称已处理或新一轮不再列出旧问题，都不会单独关闭问题。

### 4. 恢复与追溯

章节task产物同时保存修改记录；首次生成和恢复重放使用同一幂等写入逻辑，按轮次、章节和问题ID替换，不重复追加。

运行状态接口的draft、完成事件和审核事件透传问题账本与修改记录，便于恢复后回看。没有新增前端交互流程。

主要修改位置：

- [Writer](../backend/app/service/deep_research_v2/agents/writer.py)：两条返工路径、专用编辑、合稿及章节产物。
- [Critic](../backend/app/service/deep_research_v2/agents/critic.py)：逐项复查提示、合并、状态与路由。
- [Scout](../backend/app/service/deep_research_v2/agents/scout.py)：按问题补搜结果、混合问题章节重开。
- [状态定义](../backend/app/service/deep_research_v2/state.py)：新增账本字段与旧章节保留。
- [原文检索](../backend/app/service/session_evidence_rag.py)：修订查询包含具体问题。
- [定向测试](../backend/eval/tests/test_逐问题返工与复审.py)。

## 首轮失败与修复分析

首轮4项失败均保留了日志，没有跳过或隐藏：

1. 补搜任务旧测试仍期待固定“新增reader_verified证据”验收文本。本次改为断言该问题的明确验收条件被原样传递。
2. 确定性门禁测试把“无事实列表”当作应阻塞条件，但当前门禁只检查非空及网站范围。本次改为真实的范围外引用夹具来验证门禁问题和查询生成。
3. Writer零材料测试仍断言旧“无可追溯事实”报错。本次按当前原文直写机制，验证无可用原文时停止生成。
4. 搜索预算测试仍期待事实提炼产生的自动追搜。该流程已于10月16日退出主链路，本次验证初始查询数量不扩张，且不执行旧事实分析/自动追搜。

没有为通过旧测试恢复已取消的事实提炼或自动追搜。另将旧“Writer改写后即可resolved”的断言改成“保留未关闭；缺少新修改记录时明确not_reported”，这是本次需求的预期行为变化。

## 局限性、结论与下一步

- **已测量：** 本次离线逐测试状态、构造输入下的两条Agent图级闭环、修改记录校验及章节恢复。
- **间接推断：** 统一问题输入和逐条复查有助于减少意见丢失及误关；本次没有测量真实报告上的改善幅度。
- **尚未评估：** 真实模型的修改记录遵从率、复查准确率、误改率、漏检率、质量/费用收益，以及41项跳过的外部存储集成测试。

程序只能校验定位与证据编号等机械条件，复查理由是否正确仍依赖Critic及独立核验。缺少Writer新格式输出时保留可观测的未处理状态，不能保证模型每次都遵守提示。章节合稿或引用修复改变引句后，当前报告定位会显示失效，复审必须对照最终正文。

所请求的两类机制已实现并通过本轮离线验证。下一步可在固定首稿、小规模真实模型样本上检查新协议遵从率与误关率，再评估报告质量和额外成本；本次未额外启动该实验。
