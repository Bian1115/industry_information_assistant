## 二、当前“照抄旧问题”检查具体怎样执行

依据：`backend/app/service/research_context_service.py:32` 的 `_historical_query_source`，以及同文件第353行附近的重判循环。

程序执行以下步骤：

1. 从模型返回的数据中取出 `resolved_query`，即模型改写后的问题。
2. 程序使用 `''.join(text.split())` 删除比较文本中的空白，包括空格、换行等。
3. 如果模型输出的问题等于本轮原话，程序允许通过。用户主动重复旧问题也属于这种情况。
4. 否则，程序将改写文本与当前上下文中的历史用户问题逐条比较，并与可用报告候选中的旧 `query` 字段比较。
5. 去掉空白后完全相等才命中。程序不计算语义相似度，不检查两句话含义是否一致；标点、大小写等差异并没有被统一处理。
6. 命中后，程序把错误输出和一条纠正提示再发给模型，让模型重新生成整份任务，最多重判一次。若仍命中，或已命中过而后续处理异常，程序进入澄清状态，不继续执行该任务。

例如，上轮原话为“把正文压缩到900字”，本轮原话为“将实现语言改成TypeScript”。模型输出仍为“把正文压缩到900字”，程序就会命中；但输出“请缩短文章至九百字”可能同样处理错了任务，却不会被这条精确匹配规则发现。

### 删除建议

对于本次观察原始改写错误和压缩后信息保留的实验，建议取消这条规则触发的**在线重答及其专属拦截**。每轮以首次成功返回的原始模型输出评分；保留离线的“是否照抄历史问题”统计，用于说明错误类型，不反馈给被测模型。

理由是：该规则只针对一种表面形式的错误，额外纠正会改变模型第一次表现，也可能中断观察后续错误传播。它不能证明全部改写语义正确。

这项简化不要求删除响应格式校验、字段类型校验、报告归属检查等职责。如果同时简化任务协议，应按新协议保留必要校验。网络重试与语义纠错要区分：技术重试可按预定上限执行，不能依据语义得分重试到答对。

用户本轮询问是否可以删除，尚未实施删除。若以后比较删除前后的系统表现，必须单独记录版本，不能把改写重答规则变化与压缩变化一起当作唯一变量。

## 三、目标报告、修改指令和要求变更在什么时候产生

它们来自会话入口的一次任务判断调用，在研究规划和搜索开始之前，并非报告写完后的另一个评审模块。

当前数据流：

```text
用户发送本轮问题
→ research_router 保存本轮用户消息
→ ResearchContextService.build 读取旧对话、摘要和报告候选
→ _resolve_query 调用模型，同时得到改写问题与结构化任务字段
→ session_task_service 校验模型输出并确定执行路线
→ DeepResearch 服务读取所选旧报告及其研究成果
→ prepare_task 更新要求、准备执行输入
→ 研究图进入编辑、补充搜索或重新规划分支
```

“结构化任务字段”指让程序能直接读取的分项数据，例如 `max_body_chars=900`，而不只有一段自然语言说明。

| 字段 | 谁提供，谁使用 | 具体例子 |
| --- | --- | --- |
| 目标报告 `target_artifact_ref` | 程序先提供合法候选，模型选中其中一份；服务验证归属后读取旧报告 | 用户说“把当前稿缩短”，模型选最近交付稿 |
| 修改指令 `revision_instructions` | 模型解释用户想怎样修改，程序交给后续写作流程 | “删除重复介绍，保留引用与版本信息” |
| 要求变更 `requirement_changes` | 模型提取本轮明确变更，程序更新旧报告保存的要求数据 | 把正文上限由1200替换为900 |
| 操作 `operations` | 模型判断动作，程序据此安排分支 | 纯编辑、定向补证、新增结构、新研究 |

源码位置：`research_router.py:190`、`research_context_service.py:265`、`session_task_service.py:283`、`session_task_service.py:335`、`deep_research_v2/session_task_execution.py:10`、`deep_research_v2/graph.py:322`。

这些字段主要服务于“沿用已有研究成果继续编辑或补充”的产品行为。按用户现在指定的“每轮完整重新研究”，建议将本次实验所需的会话模块简化为：**根据会话历史，把追问补成一份可独立执行的完整研究请求。**

例如，用户在第17轮说正文缩到900字，改写模型应在完整请求中保留当前的TypeScript实现、资料截止日、来源要求等必要约束，并写明新的900字上限。研究程序从这份请求开始新一轮研究；不要再依赖旧报告要求表补齐改写遗漏。这样“问题改写是否完整”才能对应新一轮研究真正收到的输入。

因此，旧报告选择、旧要求增量更新、编辑/补证路线不再作为本次实验的执行支柱。不是简单删除字段而不改下游程序：当前服务和研究图仍会读取这些字段，需同步调整入口、状态构建和执行路线。若后续项目仍要保留旧报告增量编辑产品能力，应另行明确需求，不默认新增兼容路径。

## 四、每轮重新搜索需要哪些实际修改

静态核查显示，智能体内部历史已经包含当前研究运行标识，读取记录时也限制 `AgentMessage.run_id == scope.run_id`，见 `agent_history.py:116`、`:247`。真正需要重点处理的是显式的旧研究成果继承与会话证据复用。

- `deep_research_v2/followup_context.py` 的成果列表包括旧事实、网页来源、草稿、引用和证据空间。
- `deep_research_v2/service.py` 会根据模型选中的报告读取父研究结果。当前关闭 `SESSION_RESEARCH_INHERITANCE_ENABLED` 后，选中过去报告的请求会进入澄清，不会自动转为新研究，见第456行附近。
- `session_task_execution.py` 即使选择重新规划，也可能设置 `session_parent`，并非所有旧资料都因此退出链路。
- `session_evidence_rag.py:106` 在话题延续时可以沿用会话活动主题的证据空间。仅取消父报告参数，仍不一定阻止跨轮检索旧证据。

修订后的实现应为每轮建立独立的研究输入与证据范围，取消上一轮研究成果的自动装入。程序仍保留会话消息给改写模块，但研究事实来自本轮真实搜索和读取。重新研究所需的完整要求由改写结果传入，不由旧研究契约暗中补齐。

本助手代写报告这一原要求继续有效。新的执行顺序应是：项目模型完成问题改写、规划与本轮新搜索，本助手按实际改写结果及本轮证据生成报告，再由程序保存报告供下一轮使用。报告不再仅依赖原方案建议的固定来源包。若仅做改写模块的离线对照，应明确那是冻结轨迹回放，不声称回放时又执行了一轮搜索。

## 五、怎样体现压缩机制的效果

### 5.1 原来的单条连续运行只能观察表现

一条会话可以显示“第几轮第一次改错”，但无法仅凭这个时间点说明错误来自压缩。模型自身判断、改写提示、此前错误报告和输入长度都可能影响结果。错误发生在压缩后，也不自动证明是压缩造成的。

需要明确压缩对象：本次改写模型读取的是用户提问与助手报告组成的会话历史，所以这个实验直接评估的是**会话历史摘要对改写任务的影响**。它不能直接证明 Scout、Writer 等智能体在单轮研究内部压缩工具记录的效果；后者需要另外选择其实际内部轨迹及任务评分。

### 5.2 在连续运行之外增加同历史配对对照

保留用户要求的30轮连续主轨迹，主轨迹每轮使用新的搜索结果和实际报告。每次准备改写前，评测程序冻结截至上一轮的完整会话历史，并在独立评测侧建立两个输入：

| 对照组 | 改写模型实际读取的历史 |
| --- | --- |
| A：完整历史 | 冻结的此前用户提问与助手报告原文 |
| B：压缩历史 | 当前摘要机制根据同一份历史生成/维护的摘要，加尚未被摘要覆盖的近期原文 |

两组使用相同的本轮问题、Qwen3.7 Plus版本、任务提示、生成参数、输出预算和评分标准，取消语义纠错重答。B组保留自己的摘要状态和覆盖游标，避免每轮重新摘要全文而改变现有滚动摘要算法。对照输出不写回主会话，只有主轨迹实际选用的输出决定下一轮报告。

这样每轮比较的是“同一段已经发生的历史，以原文或摘要呈现时，改写有什么差别”。如果两组各自生成后续报告，两条历史很快会不同，测到的将是两套系统运行结果的综合差异，而不是这一轮压缩的单独影响。

必须控制额外信息来源：若程序另行注入未经压缩的旧报告要求表或长期记忆，模型可能从那里找回摘要遗漏的信息。简化后的主要对照应让历史约束只从被测会话历史进入；如保留其他生产输入，则两组保持一致并记录具体内容，结论只能写“带这些额外信息时的整体效果”。评测标准绝不能充当额外输入。

### 5.3 指标与归因证据

继续采用每轮要点完整率、要点精确率、整轮正确率、首次错误轮次，新增：

- A/B逐轮得分差、关键要求丢失或反转的项目数。
- 两组实际请求输入token，B组摘要生成的额外请求与token；同时记录处理时间，区分等待本助手写报告的时间。
- 每次摘要触发位置、覆盖范围、摘要文本和后续请求实际采用情况。
- 关键要求的来源链：用户原话在哪一轮提出、何时被替代、是否进入摘要、错误输出具体遗漏或混淆了什么。

例如第14轮明确从Python改为TypeScript；某次摘要之后第19轮A组仍使用TypeScript，B组却恢复Python，并且B组摘要确实漏掉或写反了语言切换。这是该样本中压缩影响任务理解的直接对照证据。它仍不是该机制在所有任务上都会如此的统计结论。

如果B组压缩明显减少模型输入，而关键要求和改写得分与A组相当，可报告“该样本中压缩节省输入且保持了被测任务所需信息”。如果A组完整历史超过相同输入预算，需记录其不可执行状态；B组仍可正确回答反映容量收益，不能为A组编造质量分。必要时另加“同输入预算下直接截断历史”的第三组，比较摘要与简单丢弃旧消息。

### 5.4 必须真实触发并使用摘要

上一轮安全读取的磁盘配置为触发窗口65,536 token、比例0.85，即55,705 token；保留最近10条消息。这是配置核查，不是本轮动态测量。前30轮报告通常有900或1200字限制，不能保证达到触发阈值。

若主运行没有触发并采用摘要，应明确“尚未评估压缩效果”。可以另做预先固定较低阈值的机制实验，以同一数据实际触发摘要；该实验要单独命名并标注修改阈值，不能当作默认配置在30轮内的表现。不得擅自加长报告来制造触发。
