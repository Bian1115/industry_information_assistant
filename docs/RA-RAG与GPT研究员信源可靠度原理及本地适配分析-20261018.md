## 一、先用好懂的话说明两者差异

**RA-RAG 像给多个来源做同一套题：先看哪些回答互相一致，再反复调整每个来源的投票分量。GPT Researcher 像请一位编辑读材料：根据任务挑选值得使用的来源。**

前者有明确的一致率和权重更新过程；后者的所查模块没有独立数值评分公式。两者的输出都不能未经验证直接展示成“这家网站说真话的概率”。

| 比较点 | RA-RAG | GPT Researcher |
| --- | --- | --- |
| 判断材料 | 多来源对相同核查问题的回答 | 研究问题与已收集研究材料／上下文 |
| 核心动作 | 聚合答案、更新来源一致率、反复迭代 | LLM 按提示筛选材料 |
| 输出 | 估计一致率与投票权重 | 保留的来源列表 |
| 对后续影响 | 优先选择可靠且能回答问题的来源；加权聚合 | 替换写作上下文 |
| 特别适合 | 来源集合相对稳定、核查问题可跨源比较的问答 | 开放网页研究中的材料审阅 |
| 对本地建议 | 借鉴关键事实跨源比较，完整离线估计后置 | 先借鉴独立评审接口、依据记录与材料选择 |

## 二、RA-RAG 的可靠度怎样得到

### 1. 先确定“给谁评级”

论文里的 source 是一组有共同来源身份的文档，粒度可由任务定义，例如一家媒体、某个账号。每个来源有自己的文档集合；同一个问题分别只在每个来源内部检索和作答。[论文第3.2节](https://arxiv.org/html/2410.22954v4#S3.SS2)

因此，某个来源的分数不是天然等于一个 URL 的分数，更不能默认覆盖一个大型平台上的所有作者。来源可靠性、这篇文章质量、某个句子是否有证据，是三个不同对象。

### 2. 准备一套可核验的小问题

论文从文档内容构造事实核查问题，再让多个来源分别回答。理解时可用一个无实际公司的例子：“甲公司成立于哪一年？”A、B 的原文支持 2010 年，C 支持 2011 年，D 没有相关材料。

它不要求预先给每道题标注标准答案。接下来产生的“暂定答案”来自来源之间的共识，因此有摆脱人工逐题标注的优势，也会继承共识错误的风险。[方法第4.2节](https://arxiv.org/html/2410.22954v4#S4.SS2)

### 3. 每个来源独立作答，先排除模型自己补的答案

例如只向模型提供 A 的相关正文，让它根据 A 回答；再分别处理 B、C。为了防止模型明明没有从正文找到答案，却凭已有知识回答，RA-RAG 检查“回答是否得到给定正文支持”，支持不足则改成 `i don't know`。

论文采用 AlignScore。代码还用 QAConvertor 将问答整理成陈述，方便与正文比较。这个环节判断的是忠实于材料：错误网页被忠实转述仍可能通过，因此它不直接证明现实真实性。[过滤实现](https://github.com/ml-postech/RA-RAG/blob/7479bb04cdee4ee48be643987749166a517302b5/src/reliability_utils.py#L225)

### 4. 把意思相同的答案放到一起

“2010”“2010年”“成立于2010年”应视为同一答案。论文使用自然语言推理模型比较语义，形成答案组，再比较每组支持票数。[论文第4.1节](https://arxiv.org/html/2410.22954v4#S4.SS1)

公开实现默认等价规则比“严格双向蕴含”更宽：两向都不矛盾且不同时为中立也可归组；只有开启 `strict_entailment` 才要求两向均蕴含。不能把默认代码写成严格双向蕴含。[聚类实现](https://github.com/ml-postech/RA-RAG/blob/7479bb04cdee4ee48be643987749166a517302b5/src/reliability_utils.py#L310)

### 5. 第一轮先让大家拥有相同的投票权

每个来源初始权重为 1。一道题中，累计权重最高的答案成为暂定答案。得到整套题的暂定答案后，再看每个来源与这些答案有多一致。

可靠度估计的关键计算可以直接写成中文：

```text
来源一致率 = 与本轮暂定答案一致的题数 ÷ 该来源实际给出有效答案的题数
```

例如 A 对 10 道题给出有效答案，其中 8 道与暂定答案一致，一致率为 0.8。B 只回答了 5 道，其中 4 道一致，也得到 0.8。没有材料、拒绝作答或被过滤的题不进入分母，避免把覆盖面少直接当成错误多；但 4/5 与 80/100 的证据量并不相同。

代码 `update_reliability()` 就是统计这个比例，未在此函数中使用人工金标准。[一致率更新](https://github.com/ml-postech/RA-RAG/blob/7479bb04cdee4ee48be643987749166a517302b5/src/reliability_utils.py#L90)

### 6. 把一致率换成投票权重，重新投票

代码更新式是 `v = num_src * updated_reliabilities - 1`。三个来源时，一致率 0.8 对应权重 1.4，一致率 0.2 对应权重 -0.4。权重可以为负，也可大于 1，因此不能把 `v` 当成百分比。迭代时先用当前权重重新选暂定答案，再算新一致率，直到变化足够小或达到迭代上限。[迭代函数](https://github.com/ml-postech/RA-RAG/blob/7479bb04cdee4ee48be643987749166a517302b5/src/reliability_utils.py#L109)

实现还做了一项首轮处理：默认优先用“有唯一最高票答案”的问题初始化。这里不是严格要求超过半数；只有一个来源作答也会被该辅助函数视为有唯一答案。没有这样的题时退回全题计算。票数相同的答案在所查代码中由字典插入顺序决定，不应照注释写成已经执行随机裁决。

### 7. 这些分数怎样影响真实问答

估计通常在正式问答前完成。新问题到来后，系统按来源权重由高到低尝试检索作答；没有相关证据的来源跳过，收集到目标数量的有效来源后，再按权重聚合答案。分数因此同时影响“找谁的材料”和“采用哪组回答”。这比仅把一个信誉标签摆在页面上更深入。

默认 Python 参数与示例脚本存在口径差异：主程序的估计题数默认 100，示例脚本设 200；过滤阈值主程序默认 0.5，示例脚本传 0.1；主程序迭代上限 100、收敛阈值 `1e-20`。本轮探针使用 10 轮和 `1e-10`，没有冒充论文完整复现。[主程序参数](https://github.com/ml-postech/RA-RAG/blob/7479bb04cdee4ee48be643987749166a517302b5/main.py#L58)

实验代码中的 Beta 抽样，以及 0.1／0.9 的 adversary-hammer 设置，是为了构造不同质量的实验来源；它们不是系统看到一个网站后直接给出的评级。

### 8. 论文思路与当前公开代码要分开看

本轮发现估计入口先生成 `unified_multi_src_outputs`，随后调用迭代函数时，却仍传入 `filtered_multi_src_outputs`。也就是已经计算的语义归并结果，没有在这个估计调用中使用。[估计入口153–157行](https://github.com/ml-postech/RA-RAG/blob/7479bb04cdee4ee48be643987749166a517302b5/ra_rag_utils.py#L153)

纯函数探针里，“2010”与“2010年”未归并时，第二个来源一致率为 0；按人工指定的等价簇归并后变为 1。这证明调用数据的差异会影响估计。探针没有运行语义模型，也没有执行完整估计流水线，不能由此报告真实数据集受到多少影响。

此外，从未有效作答的来源在一致率计算中出现零除与 NaN；同票问题受来源顺序影响。这些工程边界需要在复用前修正或明确定义。

## 三、GPT Researcher 是怎样“评来源”的

### 1. 没有独立可靠度公式

`SourceCurator` 接收研究问题和材料，调用配置中的 `smart_llm_model`。temperature 为 0.2，输出 token 上限为 8000，默认提示最多保留 10 个来源。模型根据自然语言标准选择内容，不执行 RA-RAG 那样的跨题统计与权重更新。[SourceCurator实现](https://github.com/assafelovic/gpt-researcher/blob/3582a6841fe7dc801e2a34e34ee408641aea9bce/gpt_researcher/skills/curator.py#L38)

### 2. 提示给模型的五项考虑

| 维度 | 好懂的解释 | 当前提示的倾向 |
| --- | --- | --- |
| 相关性 | 对当前问题有用吗 | 部分相关也尽量保留 |
| 可信度 | 材料看起来是否来自可信主体 | 偏好权威来源，除非明显不可信，不轻易删除 |
| 时效性 | 时间是否合适 | 优先较新材料，有历史价值的可保留 |
| 客观性 | 是否有立场或倾向 | 有偏向但补充不同视角的仍可保留 |
| 定量信息价值 | 是否包含数字、统计和可核对材料 | 特别优先有具体数据的内容 |

它还要求尽量保留原文，不重写或压缩；允许材料重叠，以覆盖面和多样性为目标。没有各维度数值尺度、加权总分或基于标注数据的分数校准。[筛选提示](https://github.com/assafelovic/gpt-researcher/blob/3582a6841fe7dc801e2a34e34ee408641aea9bce/gpt_researcher/prompts.py#L319)

### 3. 输出和入口决定了它的实际边界

输出要求沿用来源 JSON 列表格式，代码只检查解析结果为 list，然后返回。没有强制逐源输出评分、理由、评级证据网址或 unknown 状态；也没有在该模块专门调查网站背景、认证发布者或追溯转载关系。

正常网络研究路径先取得上下文，再决定是否筛选：`_process_sub_query()` 先调用内容相关性过滤，`_get_context_by_web_search()` 最后拼成字符串返回，随后将 `research_data` 传入 curator。因此，提示虽然说是对已抓取来源列表评审，实际入口可能是已经过滤、格式化的研究上下文字符串；必须按具体路径确认输入，不能保证完整网页原文都在场。[上下文链路](https://github.com/assafelovic/gpt-researcher/blob/3582a6841fe7dc801e2a34e34ee408641aea9bce/gpt_researcher/skills/researcher.py#L392)

默认 `CURATE_SOURCES=False`，只有开启时才参与。异常和非列表结果回退到原输入。故它不是每次运行都必有的信誉审核门禁。[配置](https://github.com/assafelovic/gpt-researcher/blob/3582a6841fe7dc801e2a34e34ee408641aea9bce/gpt_researcher/config/variables/default.py#L18)

替身探针让模型返回 13 条、且 URL 均不在原输入集合中的来源，函数全部返回，即没有硬性执行提示上限和成员校验。另两项异常探针均返回原输入。这里没有测试真实模型会不会遵守提示，也没有测试第三方 JSON 修复库。

## 四、能否放进当前 DeepResearch

### 1. 当前可以复用哪些基础

本轮重新检查当前工作区：

- `candidate_source_score()` 用域名、标题中的官方等词、PDF 等规则决定先读谁：[quality_pipeline.py](../backend/app/service/deep_research_v2/quality_pipeline.py)。
- Scout 读取正文、检查可用性并直接保存原文；`_store_collected_sources()` 在章节检索、补搜和显式深搜有三个直接调用：[scout.py](../backend/app/service/deep_research_v2/agents/scout.py)。
- Writer 调用 `evidence_prompt()` 检索原文证据写作：[writer.py](../backend/app/service/deep_research_v2/agents/writer.py)。
- RAG 有 `document_id`、正文哈希、来源 URL、原句和证据块定位；`retrieve()` 的 `document_ids` 参数可将检索限制在给定文档集合：[session_evidence_rag.py](../backend/app/service/session_evidence_rag.py)。
- 当前片段精排输入主要是问题与正文，处理相关性；尚不是来源背景评级：[session_evidence_ranking.py](../backend/app/service/session_evidence_ranking.py)。
- AST 扫描生产目录 161 个 Python 文件，解析错误 0；旧的三个 `_analyze_*` 方法及 `_ingest_search_analysis()` 直接调用数仍为 0。

所以两种思路都能接入当前原文路线，无需恢复写作前的全面事实提炼。这里是设计可行性判断，尚未实施。

### 2. GPT Researcher 的方式：优先做一个独立材料评审环节

建议放在“正文读取和保存完成”之后，分开输出两类结果：一类是发布主体、原始／转载性质等相对稳定的背景；另一类是“对本次任务是否有用、时间是否合适、值得优先读哪些段落”的任务判断。

最低可交付的评审记录建议包含：来源身份及验证状态、文档类型与原始出处、时间、任务用途、推荐或降级理由、支持理由的原文／背景证据链接、仍然未知的问题。可以先给“优先使用／可作补充／仅作线索／证据不足”等可解释标签，无需先编一个百分比。

例如同一篇企业官网页面，可被认定为该企业自己发布产品参数的一手材料；对页面中“全行业领先”的评价则需要独立证据。应记录它适合支持哪些问题，不把一手身份扩张成所有结论可信。

接入时需要补上三处约束：模型只能引用实际输入的 `document_id`；理由中的引文要能回查；筛选失败记录为未完成或未知。原始材料留存，允许在写作中用低优先级来源解释争议，不能将失败伪装为评级通过。

还有一个本地存储细节：已有证据文档的 payload 更新字段是白名单，证据块的 metadata 也单独构造。仅向 `raw_sources` 加 `credibility_score`，不能保证该字段被更新进持久文档并出现在 Writer 的检索结果里。建议独立保存可版本化的评审记录，再在检索／提示构建时按 `document_id` 和正文哈希关联；或者显式贯通文档更新和检索元数据路径。两者是待实施的设计选择，不能把随手增加字段视作完成。[存储入口](../backend/app/service/session_evidence_store.py)、[证据块构造](../backend/app/service/session_evidence_chunks.py)。

### 3. RA-RAG 的方式：先用来核对关键事实，完整信誉库后置

你的项目研究任务开放、来源不断变化，同一个网站未必会回答同一套题。长篇报告还包含解释、条件、推断和多种成立的观点，无法把整篇报告压成一个答案投票。因此，建议先借鉴跨来源核对和证据权重的思想：

1. 只为关键结论或冲突数字创建核查问题，不重新提炼全部网页事实。
2. 固定实体、时间、单位、范围和统计口径，再按发布主体／原始上游分组。
3. 使用现有原文检索取得每组证据，分别生成有原文绑定的回答；没有证据就不作答。
4. 合并同义答案，记录支持、反驳和无法判断，独立上游分别计数。
5. 让 Writer 看到分歧和依据；共识弱、样本少或口径不同则继续核查，不能用最高票直接判真。

这一步可先产出“本次关键结论的跨源核验记录”，不必立即计算网站终身可靠度。以后若建立了经常复用的稳定来源池，再考虑用多道校准问题离线估计来源在特定领域和时期内的可靠性，并保存样本量、覆盖率、不确定性和更新时间。

针对题数较少，平滑、最低样本门槛、置信区间或层级先验等都可以作为改造方案；它们不是本轮核验的原代码已具备功能。处理共同转载、外部锚定事实和反证通道，比单纯增加迭代轮数更应优先验证。

### 4. 两者怎样共同影响材料使用

建议先保证问题相关性，再用有证据的来源评审决定阅读预算、同一原始上游的配额和写作提示；对关键冲突使用跨源核查。暂不把未经校准的信誉分数直接乘以相关性分数，因为两种分数的对象与尺度不同，也可能把重要反证挤出候选。

来源评级仍需与现有引用支持性核验分别存储。引用核验回答“这句话能否由这段原文支持”；来源评审回答“这段原文来自什么主体、具有什么局限”；跨源核查回答“其他独立证据如何支持或反驳”。三者组合才有完整解释。

## 五、机制测试结果和失败样例

本轮不以通过率衡量这八项探针；其中多项是刻意构造的失败情境，目的在于观察算法边界。
