### 实现要点

后台流模式将 Agent 执行放到独立 asyncio task，SSE 客户端只消费事件，断开订阅不自动结束生产者。重新连接使用 `last_event_index`。

`_resume_stream_generator()`区分三条路径：运行仍活跃则补历史后 tail；运行已结束则回放剩余事件；事件缓冲不存在时尝试从数据库运行记录的 events 回放。没有存储 events 时不能凭空补出逐事件历史，代码会返回回放元信息。

Redis 实现使用 `XADD`写入每个 run 的流，`XRANGE`读历史，再从最后看到的 Redis stream ID 用 `XREAD`追新事件。这样覆盖历史读取与实时等待之间新到达的事件；客户端业务游标仍是 event_index，不是 Redis 内部 ID。SSE 空闲时发心跳，tail 出错显式发错误帧。

检查点是另一条路径：`checkpoint="tool-batch"`在工具批次完成后持久化运行状态、消息与工具结果。`/continue`可从已持久化执行状态继续；`/resume`侧重重新连接输出流。SIGKILL 示例等待真实检查点落盘再杀子进程，这比用协程 cancel 模拟进程崩溃更有参考价值。

### 如何借鉴到本项目

优先借鉴接口职责：纯 `subscribe(run_id, after_seq)`只读账本并等待新事件；`resume_execution(run_id)`单独获取租约并恢复图。已完成运行只读事件和结果，不再次抢执行租约。当前 PostgreSQL 事件账本可以直接作为权威来源，不要求先引入 Redis。

若后续多进程、多副本需要 Redis，可参考其 tail 交接；但本项目应保持数据库同事务事件为权威，通知层仅唤醒。跨进程订阅必须有共享通知或数据库轮询兜底，不能沿用只有当前进程知道的回调。

### 不能直接照搬

Agno 的接口明确允许 event_index 单调但不连续：分配编号后、事件发布前崩溃可留下缺口。本项目当前用连续 seq 发现漏事件，不能将其 Redis 编号机制原样接进来，也不应为适配而直接关闭 gap 检测。

默认内存事件流不具备跨进程恢复能力；独立 asyncio task 只解决客户端断开，不解决进程死亡。Redis 是带 TTL 的传输层，回放留存仍依赖数据库及配置。工具批次检查点也不保证外部副作用恰好一次。

## 候选二：LangGraph，继续作为现有检查点基础

重点源码：[PostgreSQL aio.py](https://github.com/langchain-ai/langgraph/blob/3cd57c038ad827d05f80c6488adea9994156c58c/libs/checkpoint-postgres/langgraph/checkpoint/postgres/aio.py)、[Pregel 执行循环](https://github.com/langchain-ai/langgraph/blob/3cd57c038ad827d05f80c6488adea9994156c58c/libs/langgraph/langgraph/pregel/_loop.py)、[任务运行器](https://github.com/langchain-ai/langgraph/blob/3cd57c038ad827d05f80c6488adea9994156c58c/libs/langgraph/langgraph/pregel/_runner.py)。

`aget_tuple()`按 thread_id、checkpoint_ns 和可选 checkpoint_id 读取状态；`aput()`保存完整检查点；`aput_writes()`按 task_id 保存关联检查点的中间写入。pending writes 的价值是恢复已记录的任务结果，避免已成功提交的任务无谓重算。

本项目已经走这条路线，并针对自身业务扩展原子提交和 fencing。下一步应研究昂贵节点内是否还需更细的持久化 task 边界，以及升级时对 `_cursor`等内部扩展点的影响；不应仅为了“支持恢复”替换现有 saver。

LangGraph 核心检查点不自动解决浏览器 SSE 游标、重连退避、分页补齐和 UI 去重。也不能将 LangGraph 开源库与整个托管部署服务的许可/能力混为一谈。本次没有核查 LangGraph 托管服务器内部实现。

## 候选三：Mastra，参考历史/实时交接及恢复所有权

所查核心文件处于 Apache-2.0 范围，语言为 TypeScript。

- [caching-pubsub.ts](https://github.com/mastra-ai/mastra/blob/fbd27197d78660de21919db34b9f91a4f9916551/packages/core/src/events/caching-pubsub.ts#L393)：`subscribeFromOffset()`。
- [stream-adapter.ts](https://github.com/mastra-ai/mastra/blob/fbd27197d78660de21919db34b9f91a4f9916551/packages/core/src/agent/durable/stream-adapter.ts)：订阅与输出流适配。
- [durable-agent.ts](https://github.com/mastra-ai/mastra/blob/fbd27197d78660de21919db34b9f91a4f9916551/packages/core/src/agent/durable/durable-agent.ts)、[运行恢复说明](https://github.com/mastra-ai/mastra/blob/fbd27197d78660de21919db34b9f91a4f9916551/packages/core/src/agent/durable/run-recovery.md)。

其历史到实时交接采用：先订阅实时并缓冲 → 顺序回放历史 → 排除已回放的重复缓冲事件 → 切到实时。索引与稳定事件 ID 用于交接去重。该思路适合未来引入独立事件总线时参考，能够避免“先查完历史、后订阅实时”之间丢事件。

`observe(runId, offset)`侧重旁观运行输出，`recover()`处理孤儿运行。恢复流程取得执行所有权后重新读取快照，避免接管期间原运行已完成而仍依据旧快照续跑。其文档还描述稳定消息/part ID 的 upsert，可启发本项目按章节 ID 和报告版本更新正文。

限制：回放适配器不是浏览器 UI 成功应用后的事务提交实现，不能直接把其中 lastDelivered 当成本项目 applied_seq 的安全模板。默认/配置不同会影响 running 快照留存和跨进程支持；恢复说明明确快照后的工具和模型调用可重做，并列出 evented engine 的已知崩溃恢复缺口。本项目适合借鉴局部设计，不适合为此迁移成 TypeScript 后端。

## 候选四：Vercel AI SDK + resumable-stream，参考前端续接语义

它们属于 Agent 应用工具包与流基础设施，后者不是完整 Agent 执行引擎。

重点入口：[HTTP 聊天传输](https://github.com/vercel/ai/blob/963d75ba42382fea235f69de68f89d7f75f67ebe/packages/ai/src/ui/http-chat-transport.ts#L232)、[聊天状态机](https://github.com/vercel/ai/blob/963d75ba42382fea235f69de68f89d7f75f67ebe/packages/ai/src/ui/chat.ts)、[恢复流文档](https://github.com/vercel/ai/blob/963d75ba42382fea235f69de68f89d7f75f67ebe/content/docs/04-ai-sdk-ui/03-chatbot-resume-streams.mdx)、[resumable-stream 运行时](https://github.com/vercel/resumable-stream/blob/770cdeb4b6e4b3838b294b0565591f3d75930897/src/runtime.ts#L127)。

AI SDK 使用 activeStreamId 找回活动输出，客户端通过 reconnectToStream 请求续接，无活动流时可返回 204。文档区分完整回放与增量后缀：完整回放应重建被中断消息，增量续接应保留已有消息。这直接对应本项目“已保存正文快照 + 从 seq=0 再追加”产生重复的风险。

取消也有两种语义：关闭客户端连接与停止后台执行必须分开；停止按钮需要服务端控制操作，不能只依赖浏览器 AbortController。

关键源码边界：此版本 resumable-stream 的 `createNewResumableStream()`将片段放在本进程 `chunks: string[]`，Redis/pubsub 负责协调续接请求、转发及状态标记。续接按 `skipCharacters`切字符串，不是业务事件 seq。因此它能参考浏览器断线续接模式，但不能替代 PostgreSQL 事件账本，也不能据此承诺生产者进程死亡后仍可重放全部内容。

本项目采用自定义研究事件和 axios/fetch 流，不建议为了这几个能力整体替换成 useChat。将相关状态语义应用到现有 React 控制器即可。

## 适配方案与实施顺序

### 第一阶段：修复现有前端协议，成本最低

1. 首跑与恢复共用事件处理器：校验 → 计算新投影 → 在应用状态容器中一起提交投影和 applied_seq。失败不前移游标。这里的“应用成功”指状态逻辑提交，不等于浏览器像素已绘制。
2. gap 按 has_more 分页补齐至目标位置，保留触发帧并重试处理；EOF 后读取运行状态与账本，不能把 HTTP 关闭当完成。
3. 章节按稳定业务键，例如 `(run_id, report_revision, section_id)`更新；同 seq 去重和同章节更新解决不同问题。
4. 明确投影恢复模式：要么从空状态完整回放；要么载入与 `snapshot_seq`一致的 UI 快照，只消费后缀。不能把任意图检查点 cursor 当 UI 已应用水位。
5. 首跑/恢复统一重连控制，区分网络故障、主动暂停、权限错误、租约冲突和终态；使用有上限退避与抖动，避免多标签页同时重试。

第一阶段不要求改变当前断线后暂停执行的产品语义；可以先实现自动恢复暂停任务。第二阶段再实现断线后后台继续运行。

### 第二阶段：分离执行与订阅，参考 Agno

以下是建议接口职责，不是已实现路径：

```text
创建/继续任务 → 执行器持有租约 → LangGraph → PostgreSQL 检查点与事件
浏览器订阅   → 按 after_seq 读已提交事件 → 等待通知或轮询 → SSE
浏览器断开   → 仅关闭订阅
用户暂停     → 独立控制请求 → 执行器有序暂停并释放租约
执行器崩溃   → 租约过期 → 新执行器接管 → 读取检查点继续
```

第一版可在现有数据库上实现轮询/通知，保留同事务事件提交。后台任务需要明确进程生命周期、启动恢复扫描和取消入口，单独 create_task 不等于持久化任务队列。

### 第三阶段：按规模引入共享事件通知

在多副本压力确有需要时再考虑 Redis Streams。优先让 PostgreSQL 账本保留权威 seq，通知总线仅提供唤醒或可重建缓存；Redis 丢通知、TTL 到期都能回到数据库补齐。若双写缓存，以已提交账本/outbox 驱动转发，不能先发布未提交完成事件。

纯订阅器不应抢执行租约。用户隔离继续沿用当前 user_id/run_id 校验。已有旧机制兼容约定保持有效，本报告未引入任何旧接口兼容层。

## 失败样例、局限性及验收建议

历史已测失败（2026-10-21，本次未重跑）：

| 样例 | 历史结果 | 借鉴方向 |
| --- | --- | --- |
| 页面投影抛错后重发同一事件 | 游标已前移，事件被当重复跳过 | 投影与应用水位共同提交；不能直接照抄传输层 watermark |
| seq=1 后收到 seq=2002 的完成帧 | 只补一页到 2001，完成帧未应用 | 分页补齐、保留触发帧、终态对账 |
| 正文快照再叠加同章节历史 | 出现重复正文 | AI SDK 全量回放/增量续接区分；业务键 upsert |

静态发现的候选边界（不是本次运行失败）：Agno 序号可有缺口；resumable-stream 输出缓存在生产者内存；Mastra 需实际启用运行快照且工具可能重做；LangGraph 检查点不提供完整浏览器投影协议。

下一次实施后的独立评测应至少覆盖：投影失败后重投、超过两页补齐、历史与实时交界并发事件、重复章节修订、首次发起断网、刷新后恢复、两个订阅者、显式暂停、真实 SIGKILL 后接管、旧执行者被 fencing 拒写、缓存失效后数据库回放。SIGKILL 应以数据库检查点提交为触发条件，不依赖固定 sleep。

指标分别记录事件漏应用/重复应用数、最终 UI 与账本重建结果一致性、恢复耗时分位数、已提交 task 重跑次数、未提交 task 重试次数、旧持有者写入拒绝数。网络恢复、执行恢复、业务副作用幂等必须分别验收，不能合成一个模糊的“恢复成功率”。

推荐先读 Agno 的 `_resume_stream_generator()`与 Redis `tail()`，再读 AI SDK 的回放模式和 Mastra `subscribeFromOffset()`；执行检查点继续围绕当前 LangGraph 实现加深。上述建议尚未实施，本次只完成选型核查与证据归档。
