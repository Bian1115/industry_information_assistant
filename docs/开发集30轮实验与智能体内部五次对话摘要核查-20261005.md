# 开发集30轮实验与智能体内部五次对话摘要核查

核查日期：2026-10-05，Asia/Singapore。评估对象：固定五题开发集的单会话30轮入口、当前逐智能体历史摘要、最近五次内部对话保留边界、超限与质量观测能力。

本轮完成源码核查、五个模拟机制探测和32项现有回归。没有调用真实模型，没有创建在线评测身份，没有执行真实30轮研究，也没有修改部署配置或摘要算法。用户随后明确“最近5轮”指智能体内部对话，本报告按这个层级修正实验设计；不把它改成最近五次用户提问。

## 结论及内部对话口径

现有代码可以把五题串为同一session的30轮，并按用户轮创建独立run；同一智能体的工作历史和旧摘要已经可以跨run接续。但当前代码不能直接满足“每个智能体保留最近五次内部完整对话，再压缩此前消息与旧摘要”的要求，尚无这个保留边界。

此处拟采用的内部对话单位是同一智能体、同一context_key的一次`BaseAgent.call_llm`：一份任务输入和该调用的最终输出，使用同一个call_id。供应商重试及该调用中的历史回读不另计轮数。工具输入、工具输出有自己的call_id，需要作为完整关联记录处理，不能把工具调用数直接当成智能体对话数。失败终态、在途调用及工具关联的具体保留边界应在实现时显式规定。

例如Writer已有12次成功对话，准备第13次请求时，保留第8至12次的输入、输出原文；将第1至7次尚未摘要的历史与旧累计摘要一起压缩；本次第13次任务输入另外保护。Architect维护自己的五次对话，与Writer的次数分别计算。这里的五次是五组内部输入和输出，不是五条消息，也不是开发集的五次用户提问。

Architect值得纳入候选方案的独立摘要配置，因为它也会跨用户轮累积规划历史。但开启其摘要并不能保证整个当前输入永不超限：旧会话全文会重新进入本轮规划提示词，属于当前受保护输入，不能只靠旧工作历史摘要缩小这份新输入。

## 当前代码可复用的部分及需要修改的位置

### 单会话入口与基线配置

[采集真实追问开发集.py](../backend/eval/scripts/采集真实追问开发集.py)已有`--single-session-development`，可以共享一个session、一份总预算，记录全局轮号、原题ID、题内轮号和独立run，失败后停止后续轮次。它同时导出逐run原始记录、累计会话工作历史、摘要版本与游标。

基线实验应先冻结当前仅Writer摘要的实际配置。入口当前会无条件替单会话模式开启Architect，直接执行不能代表原配置。需要将这个覆盖改成显式实验选项，并在报告记录实际生效配置。追问路由也要显式标明；若作为这次实验固定条件，基线与候选均使用同一设置，避免将路由变化归因于摘要。

### 最近五次内部对话的保留边界

[context_policy.py](../backend/app/service/context_policy.py)需要新增可冻结的内部对话保留参数，并兼容没有该字段的旧快照及其哈希。明确是每个智能体、每个context_key的五次已完成内部对话，当前请求另行保护。

[agent_context.py](../backend/app/service/agent_context.py)需要基于call_id识别完整调用，找到最近五组的最早安全边界；摘要候选只能取此边界之前、旧游标之后的连续完整历史。与现有在途屏障、交错调用span检查合并，不能推进游标穿过受保护调用。

当前`prepare_input_views`和输出、工具外置在摘要之前已经会改变历史视图。若“保留”要求最近五次原文，相关引用替换与外置也必须避开受保护记录；只调整摘要候选仍不足以保留原文。工具事件不可按单条消息切断；重试和同call_id回读不额外占五次名额。

旧摘要与新增候选共同压缩的链路已存在：`previous_summary`进入`summarize_history`，通过组批/合并策略生成替换摘要，成功采用后推进summary_version及covered_seq。因此优先修正候选边界和观测，不必再另造一套摘要器。

还需固定触发条件：可选“到token阈值才压缩五次以前的历史”，或“第六次历史出现后立即滚动压缩”。前者会暂时保留超过五次原文，不能描述为严格滚动五次；后者成本更高，但与固定窗口口径一致。本轮仅确认保留层级，未替用户决定这一触发规则。

### 本轮受保护输入的容量问题

[multiturn.py](../backend/eval/multiturn.py)的`research_context`传入完整历史问答；[architect.py](../backend/app/service/deep_research_v2/agents/architect.py)把它重新渲染到当前任务提示词。每轮当前输入仍可能增长，单独启用内部五次摘要不能消除这个来源。

实验首先测清超限发生在哪个字段/阶段。如确实由整段旧报告重新注入引起，再改会话历史组装、成果索引及原文回读。该问题需要单独控制变量，不把用户要求的“内部五次对话”改成外层最近五次用户问答。

### 观测及回答质量

[agent_context.py](../backend/app/service/agent_context.py)及[BaseAgent](../backend/app/service/deep_research_v2/agents/base.py)应补充明确的摘要存在/注入状态、受保护call_id、内部调用数、超限来源及异常的budget/actual字段。区分调用最终失败与某次供应商重试失败。

[compression_points](../backend/eval/multiturn.py)当前只凭本次`summary_adopted`计摘要使用，应改为读取“发送视图包含摘要”的明确标记，并另行统计本次新摘要是否提交。历史事件没有字段时保持unknown。

采集入口的错误事件需要保存error_code、失败阶段、Agent及输入预算。逐轮保存预算增量与API usage，末尾生成完整报告，而不只追加“运行结束”。完成交付只代表有正文，不代表正确回答。质量标注和评分必须在评测侧独立完成，不能泄露到生成提示词。

## 逐题质量检查及现有真值边界

| 原题／全局轮次 | 重点检查 |
|---|---|
| 8／1—6 | 计算预测、实验验证和产业化分开；数据集、测试划分及指标条件保留；失败与外推边界保留 |
| 25／7—12 | 动物/人体、不同时间窗、观察/机制预测区分；阶段和亚群的相反结果保留 |
| 26／13—18 | 肿瘤与HIV分别处理；相关性不变成因果；m6A/乳酸化缺证及参数不可辨识性不被补成既定事实 |
| 27／19—24 | 心理支持、筛查、治疗区分；人群、对照、随访条件保留；危机识别及转介要求不丢失 |
| 28／25—30 | 分子、细胞、组织、人体证据分层；基准预测、实验和临床效用区分，避免跨层外推 |

每题现有四类probes：早期范围、早期证据、反证保留、篇幅更新。共20项；其中10项用户约束已有检查口径，另10项证据及反证仍标记`pending_source_annotation`。这些待标项不能直接计算事实正确率。

每题第六轮均要求正文非空白Unicode字符不超过3000，参考文献段不计；应按原约定自动计数，并保存正文/参考文献分割依据。前期材料与最终答案的证据对应、单位/数值/时间条件、冲突处理需冻结原始来源后标注和复核。没有独立真值时只报告初评，不能把模型报告本身当答案。

换题发生在全局第7、13、19、25轮，应记录路由、reuse_previous、父run和有效约束，检查上一题3000字及其他专属约束是否污染新题。不要往模型输入添加未来问题、probes或标准答案。

| 指标组 | 必须保留的字段或分母 |
|---|---|
| 运行身份 | session_id、run_id、全局用户轮号、原题/题内轮号、Agent、context_key、call_id、模型、配置和源码哈希 |

| 执行完成 | 尝试轮数、完成交付轮数、连续成功前缀、失败轮及未执行轮；本地拦截、API拒绝、超时、预算耗尽、搜索失败及交付失败分别归因 |
| 内部五次保留 | 每Agent内部完成调用数、受保护call_id及seq范围、摘要候选call_id、在途屏障、摘要版本和covered_seq前后值、最近五次原文是否仍在实际发送视图 |
| 摘要活动 | 触发/生成成功/提交成功/本次注入/请求成功分别计数；旧摘要复用次数、失败或非缩小拒绝次数、Claimify是否启用及耗时 |
| 输入容量 | 原始会话、当前指令/契约、旧摘要、保留历史、工具/证据各自tokens；外置前、外置后、摘要后最终发送tokens；剩余预算和占用比例 |
| 摘要压缩 | D＝旧摘要正文tokens＋本次新增摘要候选视图tokens，S＝新摘要正文tokens；保留率S/D、缩小倍数D/S、节省率1−S/D；记录是否按处理后视图或原始记录计数，零分母记null |

| 内容保真 | 关键约束、数字/单位/时间窗/对象、否定及冲突保留；完整/部分/缺失/矛盾标签；引用来源与历史回读成功率，分母只含有标注的检查项 |
| 回答质量 | 本轮要求满足率、问题覆盖、事实支持与引用准确、早期约束及修订遵守、主题污染；交付成功和质量通过分开；无法核验及未执行单列 |
| 开销 | 分Agent/研究/路由/摘要/回读/重试的请求数与输入输出usage、逐轮及累计时延；只有冻结单价和真实usage齐全才计算API费用，未知不可补零 |

Qwen本地tokenizer统计用于机制和预算分析，供应商usage用于实际调用开销；两者分别保存。完整摘要请求还包括提示词和任务契约，应单独计费，不混入上述摘要正文压缩分母。

## 失败样例、局限性与下一步

机制探测没有测试框架失败，但复现了三个不满足目标的现象：最近五次也被摘要覆盖；没有旧候选时当前输入超限且摘要调用为零；已有摘要注入被导出为未使用。这些均有原始记录，不能当作真实开发集第N轮失败样例。

**已测量**：固定数据与当前配置、32项模拟回归、五个模拟分支。**间接推断**：Architect累积工作历史适合独立压缩；当前输入中完整旧报告是另一个增长来源；五次保留边界和遥测修正可使实验口径一致。**尚未评估**：真实30轮交付、实际首次超限轮、模型摘要保真与回答质量、当前数据库迁移和供应商/检索状态、候选方案成本收益。

建议按用户指定的先后顺序：先修正基线配置覆盖及记录能力，冻结当前摘要策略跑一条30轮基线；再实现并验证内部五次保留边界，开启Architect候选摘要，以相同数据、路由和单次输入预算复跑。有限总预算不足导致的中断不能解释为上下文窗口极限。若同时改变Architect开关及五次保留策略，只能评估整套候选收益；需独立配置或同源回放才能分别归因。

五题各自只有六次用户请求，缺少跨题很早内容的专门召回问题；30轮来自一条顺序会话，不是30个独立样本。实时搜索和生成材料可能不同，摘要效果比较宜补同源轨迹回放。完整30轮通过只能说明这份数据及冻结配置下至少支持30轮，不能声称最大支持轮数或长期记忆准确率。
