# 会话任务改写与研究证据输入边界核查

核查日期：2026年10月11日，Asia/Singapore。评估对象：会话任务判断器与研究证据召回的输入边界。口径：当前源码静态核查，没有修改业务代码、调用模型、运行新评测或续跑32轮实验。

## 核心结论

追问改写、话题连续性判断和路由通常不需要额外传入网页原文、段落/句子证据chunk。它们需要当前用户要求、会话摘要/近期消息及目标报告索引，来补全指代、继承要求、选择要修改的成果。

当前代码没有把RAG召回chunk直接传入会话任务判断器。ResearchContextService._resolve_query使用本轮query、会话历史/摘要/记忆背景、候选历史成果；成果包含报告ID、标题、章节目录以及最多240字符的节选。历史回答与报告节选可能含事实和引用信息，它们用于识别任务，并被提示词明确标记为不能当作本轮事实证据。

RAG召回发生在完整任务形成之后：research_router构建会话任务，再进入研究服务与研究图；graph调用SessionEvidenceRAG.prepare_stage，init阶段使用resolved_query召回材料供Architect，Writer按当前任务或章节要求再次召回。原子论断形成后，以claim召回原句/表格用于引用。

“会话临时证据库”表示证据由用户/会话/主题隔离，并由TTL管理生命周期，不能由此推断会话判断模型需要读取所有证据。此前把第一层称为“会话层召回”容易混淆，更准确的称呼是“会话范围内、任务改写之后的研究材料召回”。

## 示例及建议

用户说“把上一份报告缩短到3000字”：会话层识别目标报告和新的字数要求；Writer读取报告正文进行编辑。这个任务的会话判断无需再提供研究证据chunk。

用户说“补充中国市场2025年的证据”：会话层补全主题、地区、时间和目标章节；完整检索任务交给研究阶段，RAG/Scout提供证据，再由Writer写入报告。证据原句不会用于擅自增加用户没有提出的目标。

维持链路：当前追问＋摘要/近期消息＋成果索引→主题判断/改写/路由→完整任务→研究材料召回→Architect/Scout/Writer→论断证据召回与引用核验。只做格式/篇幅编辑时，是否可以进一步减少研究阶段的证据召回是独立优化，本次没有修改或评测该路径。

## 指标、失败样例与局限性

已核查7份源码；本次模型请求0、新评测运行0。这里的结果是静态代码事实，不是动态端到端测量。没有新增运行失败样例；命名与层次混淆属于说明口径问题，已在上文澄清。间接推断：会话判断不注入额外证据可减少输入负担。尚未评估：每次实际模型输入、节省token数及回答质量变化。

结论：会话判断层管理“用户想做什么”，研究证据用于后续研究执行；当前RAG注入位置符合这个边界。下一步如要精简会话层，应优先检查历史报告节选/摘要是否包含不必要的长材料，保留报告和章节定位信息，而不是删除研究阶段的证据输入。
