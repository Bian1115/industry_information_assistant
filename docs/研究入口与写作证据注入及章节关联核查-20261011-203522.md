# 研究入口与写作证据注入及章节关联核查

核查日期：2026年10月11日，Asia/Singapore。评估对象：研究入口的证据接收Agent、Writer证据输入、来源chunk与报告章节的关系。数据/配置口径：当前源码和默认配置，静态核查；没有修改业务代码、新运行评测、调用模型或续跑32轮实验。

## 核心结论

研究入口召回的材料给Architect规划使用；Writer逐章写作或修订时重新按章节问题召回，并将正文和定位metadata作为JSON证据单元插入提示词。chunk metadata关联的是来源文章的小节及段落，未绑定报告目标章节。写作完成后的章节论断和引用编号提供实际使用的间接关联。

## 研究入口传给哪个Agent

graph的plan节点调用Architect.process，phase为init。节点执行前prepare_stage(init)使用当前完整任务召回context层材料，写入state.research_material_context；Architect把该字段序列化到historical_context的“本轮按问题召回的来源材料（待核验）”，再组装规划提示词，帮助识别已有材料及补搜缺口。

这里只涉及经过plan的replan入口。edit直接到Writer，augment直接到Scout补搜，均不会先给Architect。首次新研究可能尚无已入库来源，入口材料可以为空。该一次召回不是面向所有Agent的广播：commit_stage会外置来源并去掉research_material_context。Scout负责后续检索、读取来源；Writer使用自己的证据召回入口。

## 写作阶段如何传入

逐章写作以“完整任务＋当前章节title＋description”查询context层；修订单章同样带章节标题及description。context层执行每页128、前3页最多384候选粗排后精排Top8，补邻居并按8192默认JSON预算装包。

evidence_prompt将结果构造成session_evidence_view中的evidence_units，每项包含id、text及document_id、来源URL/标题、source_spans、来源小节/段落/句子编号和邻居等metadata，并附引用格式说明。Writer将它放入SECTION_WRITING_PROMPT或SECTION_REVISION_PROMPT的claim_evidence字段；模型以document_id＋evidence_unit_ids声明引用。

整篇用户编辑通过当前完整任务调用evidence_prompt，证据插入“可用证据”。首尾整合使用章节正文、当前问题、研究要求/输出格式及章节论断索引，没有重新注入RAG来源chunk。原子论断生成后，引用链路按每条claim查询citation层原句/表格，精排默认Top5，再按编号回读冻结原文。

## metadata是否绑定章节

| 当前信息 | 含义 |
|---|---|
| source_section_id、heading_path | chunk属于来源文章哪个小节/标题路径 |
| paragraph_ids、sentence_ids | 对应来源正文的段落和原句 |
| parent_chunk_id | 原句的父段落chunk |
| adjacent_chunk_ids | context/citation两种视图的前后chunk |
| target_section_id | 当前没有这个报告目标章节绑定字段 |

源文章的小节可能叫“市场概况”，研究报告的sec_2可能叫“中国市场变化”，两者不是同一套目录。source_section_id不能拿来当报告section_id。

目前逐章召回通过查询文本实现语义相关性，没有按报告章节ID硬过滤chunk。旧facts有related_sections，Writer仍按它选相关事实；但启用RAG时传入evidence_prompt的fact_ids不会限制chunk检索，不能认为旧事实映射已经让所有chunk绑定到章节。

实际使用关联保存在section_claims[报告章节ID]中：该章节的claim.evidence引用document_id/evidence_unit_ids；collect_report_claims再由程序添加section_id。由此可以追溯“某章哪个论断使用哪个chunk”，但目前未转成chunk metadata中的预分配关系，也不是检索时的目标章节过滤器。

如需稳定复用“某次研究某章已召回/已使用的材料”，建议独立记录run_id或报告版本＋target_section_id＋chunk_id的多对多关系，区分召回候选与实际引用，并随会话证据生命周期清理。同一来源chunk可以供多个章节、多个研究版本使用，单个共享metadata.target_section_id无法准确表达这些关系。此建议尚未实现。

## 指标、失败样例、局限性及下一步

已核查6份源码；新评测运行0、模型请求0。本次没有新增失败运行样例；“来源小节”与“报告章节”名称相似，属于需要澄清的设计边界。

已核查：入口消费者、Writer查询和提示词注入、来源metadata以及写作后引用关联。间接推断：版本化多对多关系可改善章节材料复用。尚未评估：动态模型输入逐请求实测、章节相关性、是否需要强制目标章节过滤及其召回损失。

结论：当前入口给Architect，逐章材料给Writer；metadata已有来源小节定位，未实现报告章节的预绑定。下一步如果用户要求新增目标章节关联，应保留不可变来源chunk，新增独立的候选/使用关系，避免大纲调整或同一来源跨章节使用时破坏现有引用。
