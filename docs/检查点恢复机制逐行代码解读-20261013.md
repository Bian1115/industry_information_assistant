解读日期：2026-10-13。对应当前本地工作区的 DeepResearch 主图；图版本为 `single-main-v5-session-evidence`。本地虚拟环境安装的 LangGraph 为 1.2.11，PostgreSQL saver 为 3.1.2。

可以把研究过程想成写一份长报告：每完成一个大步骤，就把当前成果和流程进度存进数据库。进程中断后，新进程取出存档，继续未完成的工作。当前 Writer 还把逐章生成封装成 LangGraph task，因此写作节点重新进入时，可以复用已持久化的章节正文。

恢复保存的是业务数据和执行调度信息。Python 函数的调用栈、局部变量、网络连接和模型正在生成到第几个 token，并不会原样保存。下文逐行解释恢复链路的关键代码；跨多行的同一条语句合并解释，空行、版权信息和仅闭合括号的行不重复说明。

**1 三种编号分别记住什么**

| 名称 | 本项目中的意思 | 例子 |
| --- | --- | --- |
| `session_id` | 一段用户会话，可含多轮研究 | 用户连续追问同一主题 |
| `run_id` 与 `thread_id` | 一次研究运行的身份；本项目把二者设为相同值 | 本轮完整研究及其技术中断续跑 |
| `checkpoint_id` | 这次运行的一份具体存档 | 分析完成后的存档 |
| `seq` 与 `after_seq` | 界面事件的顺序和客户端已接收的位置 | 界面已应用到第 35 条事件 |

一次会话可以有多个 run。恢复同一个 run 要沿用原编号；用一个新的 run_id，就会去寻找另一份运行的存档。事件序号用于补发界面进度，不能用它决定研究从哪个节点继续。

```python
@asynccontextmanager
async def checkpointer_lifespan(app: Any, database_url: Optional[str] = None):
    """把 saver 和连接池挂在应用上；应与现有 lifespan 合并而不是替换它。"""
    pool = build_pool(database_url)
    await pool.open()
    try:
        await pool.wait()
        app.state.research_checkpointer = AsyncPostgresSaver(pool)
        app.state.research_checkpointer_pool = pool
        logger.info("LangGraph PostgreSQL 检查点连接池已就绪")
        yield app.state.research_checkpointer
    finally:
        app.state.research_checkpointer = None
        app.state.research_checkpointer_pool = None
        await pool.close()
        logger.info("LangGraph PostgreSQL 检查点连接池已关闭")
```

```python
def pack_state(work: Dict[str, Any]) -> GraphState:
    """剥离显式登记的运行字段，拒绝将其他对象静默写入检查点。"""
    saved = {key: value for key, value in work.items() if key not in RUNTIME_ONLY_KEYS}
    leaked = [key for key in saved if key.startswith("_")]
    if leaked:
        raise RuntimeError(f"未登记的运行期字段进入了图状态: {sorted(leaked)}")
    saved["messages"] = []
    # 不使用 default=str：把函数等对象转成字符串会掩盖状态契约错误。
    json.dumps(saved, ensure_ascii=False, allow_nan=False)
    return {"research": saved}
```

```python
def _snapshot_resume_state(snapshot: Any) -> Dict[str, Any]:
    """区分图续跑与终态交付；空 next 可能仍有待合并的成功结果。"""
    research = (snapshot.values or {}).get("research") or {}
    pending_nodes = list(snapshot.next or ())
    saved_result_nodes = [
        task.name for task in getattr(snapshot, "tasks", ())
        if getattr(task, "result", None) is not None
        and getattr(task, "error", None) is None
        and not getattr(task, "interrupts", ())
    ]
    checkpoint_id = ((getattr(snapshot, "config", None) or {}).get("configurable") or {}).get("checkpoint_id")
    return {
        "pending_nodes": pending_nodes,
        "saved_result_nodes": saved_result_nodes,
        "resumable": bool(snapshot.values)
        and research.get("status") != "completed"
        and bool(pending_nodes or saved_result_nodes),
        # 只交付已提交的终态，不把尚待合并的 finish 输出当作终态检查点。
        "delivery_ready": bool(snapshot.values)
        and research.get("status") == "completed"
        and not pending_nodes
        and not getattr(snapshot, "tasks", ())
        and bool(checkpoint_id)
        and bool(str(research.get("final_report") or "").strip()),
    }
```

节点结果和完整后继检查点分两步保存。比如 Writer 已经跑完，输出保存成 pending writes，而完整下一步检查点还没提交。读取最新快照时，LangGraph 可能把 Writer 的输出应用到读取视图，并把已有结果的 Writer 从 next 排除；此时 next 可能为空，tasks 里仍有 Writer 的结果，后继 review 还未推进。当前代码因此同时检查 next 和成功 tasks。

pending writes 的意思是“已经写进数据库、等待图调度器合并推进的节点结果”，不等于只留在内存。完整存档和 task writes 是两个相关但不同的保存层次。[LangGraph 官方检查点说明](https://docs.langchain.com/oss/python/langgraph/checkpointers#super-steps) 对这两个层次作了区分。

**23 用一次断电场景串起整个过程**

以下是按代码路径说明的示例，各种中断结果都以实际持久化成功的内容为准。

| 中断位置 | 数据库可能已有的成果 | 恢复路径 |
| --- | --- | --- |
| 分析完成并提交检查点，Writer 尚未执行 | 规划、资料、分析结果，待执行 write | 用原 thread_id 和 None 进入 write |

| Writer 后继完整检查点已提交，审核前退出 | 正式草稿，待执行 review | 继续 review；审核要求返工时仍可能再次调用 Writer |

**24 阅读代码时容易混淆的地方**

`phase` 用于描述业务阶段；真正的恢复调度由图快照及任务写入决定。旧文件 [resume_policy.py](/Users/bxy/projects/industry_information_assistant/backend/app/service/deep_research_v2/resume_policy.py:39) 定义了 next_stage 游标，但当前主图和 service 恢复调用链没有导入或调用它，讲当前机制应以 graph.py、service.py 和 saver 为准。

“章节已显示”“Agent 历史已保存”“预算已记账”“节点函数已返回”和“图检查点已提交”是不同时间点。确定能复用什么，要看对应结果是否真正持久化。一个节点重新进入，也不代表它里面所有模型调用都会重做；Writer 的章节 task 就是更细的复用单位。
