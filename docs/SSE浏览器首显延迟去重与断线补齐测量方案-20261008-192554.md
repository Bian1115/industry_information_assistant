## 一、埋点位置与时间线

每条记录带`evaluation_id`、`run_id`、`seq`、`event_id`、`event_type`、发送尝试ID、页面实例ID和来源（live/replay）。埋点在评测模式启用，使用内存缓冲并在运行结束导出，避免每条事件同步写磁盘或上传导致测量扰动。

| 时间点 | 项目插入位置／含义 |
| --- | --- |
| t_request | 前端调用研究请求或`resumeResearch`之前，记录客户端单调时钟 |
| t_commit | `ResearchEventRecorder.record`实际`db.commit()`返回后；完成事件在`delivery.py`的事务提交之后；只用于首发持久化延迟 |
| t_send | SSE响应块交给HTTP发送边界前／后记录，注明实际采用哪一边；首发和每次重放分别记录，不能复用历史发送时刻 |
| t_receive | `consumeResearchSse`解析一条完整JSON后、调用业务onEvent之前；这是完整事件到达JS处理边界，不等于第一字节到达网卡 |
| t_apply | `advanceResearchProtocol`接受后，业务投影实际更新时；拒绝的duplicate/gap/run_mismatch另记，不算apply |
| t_dom | 对应事件造成的内容已提交到DOM且位于测试视口可见位置；记录渲染版本、章节标记或卡片ID |
| t_visible_est | DOM更新之后安排绘制机会得到的首显近似；关键首显用浏览器Performance截图／绘制帧核对 |
| t_reconnect | 恢复联网并开始重连，或刷新操作开始；刷新跨页面需使用统一计时基准 |
| t_caught_up | 本次固定测试范围内的预期事件全部补齐、投影正确且对应DOM更新完成 |

### DOM更新与像素显示分开

调用setState、进入onEvent或协议接受，只能证明执行到了相应JS边界。React的`useLayoutEffect`发生在DOM提交后、浏览器绘制前，[React官方说明](https://react.dev/reference/react/useLayoutEffect)；requestAnimationFrame回调同样在下一次绘制之前，[MDN说明](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)。它们不能直接标记“像素已经显示”。

起步时把`t_dom`作为可复现的DOM首显指标，确认进度／正文元素有目标文字、可见且在视口内，再用一次绘制机会给出`t_visible_est`近似；需要更准确的展示时间时，开启[Chrome Performance截图](https://developer.chrome.com/docs/devtools/performance/reference)，找到内容第一次出现的帧。标注截图采样与帧粒度误差，不称像素级精确。

只为首次有效进度和首次正文做较重的帧／截图核对；各事件的主要延迟用receive/apply/DOM边界，避免每次渲染都同步测量布局。页面保持前台，固定视口、报告面板展开状态及滚动位置；已有历史正文不能被当作本次请求的首显。

React可能将多次状态更新合并到同一次DOM提交。为渲染批次记录projection版本、所覆盖事件ID及lastAppliedSeq；DOM延迟仅对能关联的界面变化事件／批次计算，不要求每条事件独立绘制。协议accepted日志与业务实际apply日志分开，不能只看到lastSeq增长就认定正文或卡片已正确更新。

## 二、四类指标具体怎么测

### 1. 浏览器首显

记录`t_request`，页面首次显示当前run的有效阶段／进度时记录`t_progress_dom`，第一段章节或报告正文显示时记录`t_report_dom`。

```text
有效进度DOM首显 = t_progress_dom - t_request
正文DOM首显     = t_report_dom - t_request
```

research_start、research_resumed、加载动画和心跳可单列为“连接／开始提示首显”，不代替有效研究进度。关键样本另外给出绘制帧首显时间，避免把onEvent接收时刻当成用户可见时刻。

客户端单页面耗时用[performance.now()](https://developer.mozilla.org/en-US/docs/Web/API/Performance/now)；刷新后timeOrigin改变，不能直接减两个页面的裸performance.now值。跨页面可保存`performance.timeOrigin + performance.now()`，或由浏览器控制器用同一单调时钟记录刷新开始至新页面验证完成。

### 2. 传递与渲染延迟

```text
发送至完整事件接收 = t_receive - 本次t_send（校准为同一时间基准）
接收至状态应用     = t_apply - t_receive
接收至DOM更新      = t_dom - t_receive
首发提交至DOM更新  = t_dom - t_commit（同一时间基准）
```

发送至接收包含代理／HTTP缓冲、排队、网络传递和浏览器调度，不能叫纯网络RTT。若要单独看网络往返时间，用不执行研究的轻量请求测RTT，另外报告。

服务端和浏览器跨机器时，需同步或估算时钟偏差；用多次轻量时钟请求估算偏差，记录往返时间和误差范围。不要直接从后端UTC时间减前端performance.now。若暂不校准，先可靠报告同一客户端时钟上的接收→应用／DOM耗时，发送→接收标为尚未测量。

既有事件timestamp在事务提交前构造，不是精确提交完成时刻。回放旧事件时，其历史timestamp表示历史发生时间，计算网络传递延迟必须用本次t_send；不能把历史等待时间误算成网络卡顿。

网络条件至少正常和弱网，固定相同事件内容、发送节奏和页面状态，记录节流配置、缓存、浏览器版本、前后台状态及是否经过代理。Chrome可在Network面板设置节流，[官方说明](https://developer.chrome.com/docs/devtools/network/reference)。分别汇总实时首发与回放补齐，不混用两者的时间语义。

### 3. UI去重与缺口

选择会追加正文的section_content或report_chunk，并发送同一`run_id/seq`两次。发送的数据及身份保持一致，测试流中允许重复帧，但账本仍只有一条逻辑事件。

预期结果：receive计数2、apply计数1；当前页面该章节或增量正文仅出现一次，助手消息／卡片没有重复。还要检查完成事件之前的中间页面，因为research_complete覆盖正文可能掩盖此前的重复追加。

再做缺口：已应用到k，先送k+2，后由GET事件接口补回k+1及后续。断言发现gap时游标不越过k；补齐后按序应用，k+2最终只应用一次。错误run事件另作隔离用例，不能污染当前报告。

每次应用记`(evaluation_id, page_instance_id, run_id, seq)`。网络重复接收次数与同页面逻辑重复应用次数分别计算；页面刷新后从头重建投影可重新应用历史事件，不应把跨页面总apply次数大于1自动当作去重失败。刷新场景主要断言最终投影、章节和消息没有重复。

### 4. 真实断线与补齐

在浏览器已接受并应用到seq=k时设屏障，保存已应用游标k；随后让网络离线或终止真实fetch流，确认请求实际中断，记录t_disconnect。只断浏览器连接，避免同时杀后端进程导致混入另一故障类型。可在Chrome Network中选择Offline，[官方说明](https://developer.chrome.com/docs/devtools/network/reference)。

例如离线3秒后恢复网络，记录t_reconnect，按当前产品流程进入已保存记录并点击继续，使用`after_seq=k`。若页面只恢复展示而未自动续跑，应按实际行为报告，不能把“刷新”默认当成“自动重新执行”。

本项目当前显示恢复会读state与events，明确请求继续时再调用resume；服务端消费者断连会影响执行与租约。所以真实续跑组需检查节点是否重新进入、是否等待租约、是否复用了已持久化结果。使用确定性Agent和模拟会话任务，避免新模型调用；记录取消、恢复与租约接管时间。

固定测试范围结束序号S，从事件账本获得应应用集合E={k+1,…,S}；从本页面应用日志获得A。分页拉取直到has_more=false，不能只核对最后一个seq。

```text
最终事件丢失率 = |E - A| / |E|
额外事件       = A - E
重复应用次数   = Σ max(apply_count(seq) - 1, 0)（当前页面及固定恢复窗口）
补齐耗时       = t_caught_up - t_reconnect
```

补齐成功同时要求：E全部应用、无不允许的重复应用、投影与未中断参考一致、页面状态正确、终态报告和消息没有重复。S为空范围时报告“无待补事件”，不以零分母计算比例。

“事件补齐”与“恢复后任务完成”分开：先记录补齐到断线前后已产生事件的耗时，再记录继续执行至最终研究交付的时间。若后端暂停，没有新事件被提交，不能凭看不到新的seq称为SSE丢失；这是执行暂停／续跑问题。已完成run的回放可以验证展示重建，但不能替代运行中断线续跑测试。

## 三、建议起步用例与失败样例

| 用例 | 故障／条件 | 主要断言 |
| --- | --- | --- |
| 正常回放 | 固定节奏发送已知事件 | 进度与正文首显、传递／处理耗时、最终投影 |
| 弱网回放 | 相同事件和节奏，改变网络配置 | 延迟、静默与最终完整性 |
| 重复章节事件 | 同一seq投递两次 | receive=2、apply=1、中间页面无重复正文 |
| 缺口补齐 | k后先到k+2，GET补回 | 游标不越过缺口，后续顺序正确 |
| 流真实断线 | 应用k后Offline约3秒，再按产品路径继续 | 事件补齐和任务续跑分别正确 |
| 页面刷新 | 收到部分章节后刷新页面 | 投影重建、时间基准、消息／章节不重复 |

每种条件先重复5次验证机制并保留逐次结果；之后按需要增加次数再汇总P50／P95。5次的P95只作描述，不能作为稳定尾延迟或生产SLA依据。所有次数是建议，尚未执行。

重点失败样例：接收很快但React状态更新后没有显示；旧timestamp造成异常巨大“网络延迟”；重复章节先追加两次后被最终报告覆盖；缺口未补却将游标推进到k+2；刷新后累计apply被误判为重复；后端执行已暂停却误报SSE丢失；历史报告显示被误记为新报告首显。

## 四、结果落盘字段

每次运行创建新中文结果目录，包含：配置与源码哈希、原始发送／接收／应用／DOM日志、时钟校准样本、测试范围E与A、逐次指标JSON、浏览器Performance trace及关键截图、异常与租约／节点记录。人类分析报告写入docs，链接原始文件。

汇总至少包括：有效进度首显、正文首显、发送→接收延迟、接收→DOM延迟、最大有效进度静默、重复接收与重复应用、最终丢失率、断线补齐成功数／测试数及耗时。缺少埋点或失败样本不得以0补齐；失败／超时保留原始日志并进入场景成功率分母。

## 五、证据边界、结论与下一步

**已测量／核查：** 本次读取并核查了当前前后端事件解析、去重、分页回放、续跑及取消处理源码；当前源码哈希已落盘。此前26题进程内85条事件对账是已有证据，本次未新增实际性能测量。

**间接推断：** 现有接口和协议可作为上述浏览器测试的接入点；实际网络、布局及取消／恢复行为仍需测试验证。回放测出的首显属于固定事件源的链路表现，不能直接外推为真实研究请求的生成等待。

**尚未评估：** 方案中的浏览器首显、跨端传递延迟、实际重复／缺口注入、Offline断线、刷新及恢复成功率。没有新增模型／搜索调用，没有修改生产实现。

结论：采用“真实HTTP与浏览器＋已有事件回放”测传输展示，采用“真实图与恢复入口＋确定性Agent”测运行中断线续接；分别记录收到、接受、DOM更新和绘制近似，固定事件窗口进行集合对账。下一步实现评测模式埋点和隔离回放／确定性服务，先跑上表机制用例，再视需要扩展性能样本。
