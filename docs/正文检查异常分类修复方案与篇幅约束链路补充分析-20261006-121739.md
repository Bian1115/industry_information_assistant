## 正文检查错误分类修复方案

保留`body_quality.status`的passed、partial、rejected、uncertain含义。为模型复核增加独立的执行状态及错误信息，例如`model_review.execution_status=failed`与`error_category`。只有规则或有效模型结论明确证明页面不合格时才使用rejected；输入超限、超时、返回格式异常不能作为页面不合格的证据。

建议错误类型与恢复动作：

| 错误 | 分类 | 恢复动作 |
|---|---|---|
| 明确登录/错误页或有效模型拒绝结论 | 正文不合格 | 排除该页面，保留理由 |
| 模型超时、限流、临时服务错误 | 检查执行失败 | 复用统一入口的有界重试，避免叠加无限重试 |
| 当前输入超预算 | 检查执行失败：输入预算 | 缩小或分批展示正文；固定约束本身超预算时报告任务/配置问题，不删除约束 |
| 无效JSON、状态或正文块编号 | 检查执行失败：输出格式 | 有限次数要求修正；明确拒绝时允许空块列表，声称通过却没有有效正文块则不能算有效通过 |
| 归档基础设施异常、取消 | 系统失败/取消 | 按现有边界上抛，不吞掉并改成页面不合格 |
| 未预期程序异常 | 检查内部错误 | 保存堆栈和关联ID，不通过重试掩盖程序错误 |

抓取成功而模型检查失败时保留`fetch_status=success`及原始正文，质量状态维持uncertain、`reader_verified=false`。但必须同步修改`_enrich_results_with_full_text`：当前代码仅以`read_result.success`决定是否写入full_content并标记reader_verified=true。修复后必须再检查正文质量为passed/partial才可进入已核验证据。未完成检查的正文单独留作恢复资料，不传给Writer作为已核验事实。

## 7500与2400为何同时出现

7500是`LLMConfig.research.target_report_chars`的默认全文目标，传入Writer作为章节分配参数；它不保证输出恰好7500字。2400是该用户首轮明确提出的正文硬上限，在规划阶段已进入`active_constraints.max_body_chars`，并非第二次写作时才提出。

首次生成路径的`_section_target_chars(section_count)`只读取Writer实例上的默认目标及每章600至1200范围，没有读取state里的2400上限；章节提示词同时包含用户原话与默认章节要求。最终`finish`才调用`check_body_length`按2400限制检查交付。已有成果编辑分支也会检查上限并有限重试，但原实验`writing_mode=null`，不走该编辑分支。

因此用户上限在任务信息中一直存在，但首次章节预算未据此生成。这不是设计好的先写7500再自动压成2400流程。修复应让所有写作路径先采用当前任务上限，统一分配摘要、章节、结论和结构余量；合稿计数超限时定向缩写，最后保留交付检查。有任务上限时应允许降低默认每章600字下限，用户没有指定时再使用默认目标。

示例：摘要200、四章各450、结论200，合计2200，余下200用于标题与调整。具体分配可随章节重要性变化，但总和必须受2400约束。
